# مستند پیاده‌سازی پت‌رسان در اپ نوبس

این سند قرارداد فعلی API و رفتار مورد انتظار اپ نوبس را برای سه حالت پت‌رسان مشخص می‌کند:

| حالت | نام محصول در اپ | زمان استفاده | الگوی پرداخت |
| --- | --- | --- | --- |
| سرویس هفتگی | «سرویس پت‌رسان» | تکرارشونده در روزها و ساعت‌های انتخابی | کسر خودکار هر نوبت از کیف پول |
| متصل به نوبت | «پت‌رسان برای نوبت» | رسیدن پت به مرکز، ۶۰ یا ۱۲۰ دقیقه پیش از نوبت | پرداخت خود نوبت و پرداخت سفر دو فرایند جدا هستند |
| فوری | «پت‌رسان فوری» | همین حالا | پس از پذیرش راننده، کیف پول/درگاه |

> دامنه: مسیرهای این سند با `API_BASE_URL/api/EndUser/...` ساخته می‌شوند و همگی، به‌جز مواردی که مشخص شده‌اند، به `Authorization: Bearer <access-token>` نیاز دارند. مختصات همیشه `x = longitude` و `y = latitude` است؛ جای `x` و `y` را عوض نکنید.

## 1. قرارداد عمومی اپ با API

### 1.1 پاسخ‌ها و خطاها

اغلب پاسخ‌ها به شکل زیر هستند:

```json
{
  "isSuccess": true,
  "code": 200,
  "messages": [],
  "data": {}
}
```

- معیار موفقیت، `isSuccess === true` است؛ تنها به HTTP status اکتفا نکنید.
- در خطا، اولین پیام قابل نمایش معمولاً `messages[0].item1` است. اگر خالی بود، یک پیام عمومی و قابل اقدام مثل «دوباره تلاش کنید» نمایش دهید.
- دکمه‌ی ارسال را در حین درخواست غیرفعال کنید، اما برای خطای شبکه راه «تلاش مجدد» را باقی بگذارید.
- بعد از ساخت ناموفق یا نامعلوم شدن نتیجه‌ی درخواست، هیچ شناسه‌ای را حدس نزنید؛ ابتدا از endpoint وضعیت/فهرست همان جریان برای بازیابی state استفاده کنید.

### 1.2 مدل مختصات و زمان

```ts
type Point = { x: number; y: number } // x: longitude, y: latitude
```

- متن آدرس (`fromAddress` و `toAddress`) را همراه نقطه بفرستید تا در رسید و پنل قابل خواندن باشد.
- برای ساعت سرویس هفتگی، مقدار دقیق `HH:mm` بفرستید؛ مانند `"08:30"`.
- تاریخ/ساعت‌های برگشتی API را بدون تبدیلِ بی‌دلیل نمایش دهید و لایه‌ی مشترک اپ را برای یکپارچه‌سازی زمان سرور به کار ببرید.

### 1.3 داده‌های پایه‌ای که پیش از فرم لازم‌اند

| نیاز | API | کاربرد |
| --- | --- | --- |
| پت‌های کاربر | `GET /UserPet` | انتخاب پت و اعتبارسنجی مالکیت در UI |
| روزهای هفته | `GET /WeekDay` | انتخاب زمان سرویس هفتگی؛ شنبه تا جمعه به‌ترتیب شماره‌ی ۱ تا ۷ هستند |
| گزینه‌های سفر | `GET /TripOption` | فقط در جریان فوری، در صورت فعال بودن UI گزینه‌های سفر |
| وضعیت سفر | `GET /Code?codeGroupLabel=Trip_Status` | map وضعیت؛ عدد وضعیت را hard-code نکنید |
| دلایل لغو کاربر | `GET /Code?codeGroupLabel=TripCancelReason_User` | bottom sheet لغو سفر |

`WeekDay` عمومی است؛ سایر موارد را با access token فراخوانی کنید. فهرست‌ها را مطابق envelope و pagination لایه‌ی شبکه‌ی نوبس parse کنید.

## 2. سرویس هفتگی پت‌رسان

### 2.1 تجربه‌ی کاربر

کاربر یک پت، مبدأ، مقصد و یک یا چند زمان هفتگی انتخاب می‌کند. این محصول برای سفر رفت‌وبرگشت تکرارشونده است؛ کاربر در اپ برای هر بار سفر جداگانه پرداخت نمی‌کند. سامانه برای نوبت فردا سفر واقعی می‌سازد و مبلغ همان نوبت را از کیف پول کسر می‌کند.

در صفحه‌ی سرویس این موارد را شفاف نشان دهید:

- انتخاب **دقیقاً یک پت**؛
- مبدأ و مقصد به‌همراه آدرس نوشتاری؛
- یک یا چند زمان (روز هفته + ساعت)؛ یک روز می‌تواند چند ساعت متفاوت داشته باشد؛
- تعداد هفته: اختیاری. خالی یعنی تا زمان لغو ادامه دارد؛ مقدار واردشده باید مثبت باشد؛
- قیمت تقریبی هر نوبت؛ قیمت نهایی در زمان تولید همان نوبت دوباره محاسبه می‌شود؛
- هشدار کیف پول: موجودی کافی باید پیش از هر نوبت وجود داشته باشد.

### 2.2 پیش‌نمایش قیمت

```http
POST /api/EndUser/PetResanService/preview-price
Content-Type: application/json
Authorization: Bearer <token>
```

```json
{
  "userPetId": 41,
  "origin": { "x": 51.3890, "y": 35.6892 },
  "destination": { "x": 51.4231, "y": 35.7324 },
  "fromAddress": "تهران، ...",
  "toAddress": "تهران، ...",
  "totalWeeks": 4,
  "schedules": [
    { "weekDayId": 1, "time": "08:30" },
    { "weekDayId": 3, "time": "08:30" }
  ]
}
```

پاسخ موفق `data` از نوع عدد (قیمت هر نوبت) است. برای جلوگیری از فشار غیرضروری، فقط بعد از کامل شدن مبدأ و مقصد و با debounce فراخوانی کنید؛ هر تغییر معتبر در مسیر باید preview قبلی را نامعتبر کند. در این حالت، رفت‌وبرگشت از سمت سرور اجباری است.

اگر preview ناموفق بود یا `data <= 0` شد:

- قیمت «رایگان» نمایش ندهید؛
- ثبت سرویس را متوقف کنید؛
- پیام خطا و دکمه‌ی تلاش مجدد نشان دهید.

### 2.3 ثبت سرویس و idempotency

```http
POST /api/EndUser/PetResanService
Idempotency-Key: 3d5f3b8d-291a-42fc-a3df-b3e04c1da030
Content-Type: application/json
Authorization: Bearer <token>
```

بدنه همان نمونه‌ی preview است. فیلدهای معتبر:

```ts
type PetResanServiceCreateRequest = {
  userPetId: number
  origin: Point
  destination: Point
  fromAddress: string
  toAddress: string
  totalWeeks?: number | null
  schedules: Array<{ weekDayId: number; time: string }>
}
```

قواعد ضروری در اپ:

1. برای هر تلاشِ منطقیِ ثبت، یک UUID جدید با قالب canonical (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`) بسازید و آن را در `Idempotency-Key` بفرستید.
2. اگر timeout یا قطع شبکه بعد از ارسال رخ داد، **همان کلید و همان payload** را دوباره بفرستید. سرور همان سرویس ساخته‌شده را برمی‌گرداند و duplicate ایجاد نمی‌شود.
3. اگر کاربر فرم را تغییر داد یا عمداً سرویس جدید می‌سازد، کلید جدید بسازید.
4. یک کلید را هرگز با payload متفاوت reuse نکنید؛ سرور آن را خطا می‌داند.
5. پیش از ارسال validate کنید: پت انتخاب شده، هر دو نقطه، حداقل یک schedule، `totalWeeks > 0` در صورت وجود، و نبودن schedule تکراری با همان `(weekDayId, time)`.

### 2.4 پاسخ، فهرست و لغو

```http
GET /api/EndUser/PetResanService
GET /api/EndUser/PetResanService/{serviceId}
PUT /api/EndUser/PetResanService/{serviceId}/cancel
```

مدل نمایشی پاسخ شامل این داده‌هاست:

```ts
type PetResanService = {
  id: number
  userPetId: number
  userPetName: string
  origin: Point
  destination: Point
  fromAddress: string
  toAddress: string
  startDate: string
  totalWeeks?: number | null
  endDate?: string | null
  active: boolean
  pricePerOccurrence: number
  schedules: Array<{
    id: number
    weekDayId: number
    weekDayName: string
    weekDayNumber: number
    time: string
  }>
}
```

در لیست، وضعیت قابل فهم بسازید:

- `active: true` و `endDate` خالی: «فعال تا زمان لغو»؛
- `active: true` و `endDate` موجود: «فعال تا تاریخ ...»؛
- `active: false`: «لغوشده».

لغو فقط اجرای نوبت‌های آینده را متوقف می‌کند. نوبتی که قبلاً به شکل یک سفر واقعی ساخته شده است با لغو سرویس خودکار لغو نمی‌شود؛ برای همین قبل از تأیید، این متن را نمایش دهید: «لغو سرویس، سفرهای ثبت‌شده‌ی قبلی را تغییر نمی‌دهد.»

### 2.5 اتفاقی که در سرور می‌افتد و UI باید بازتاب دهد

- job روزانه برای scheduleهای **فردا** سفر ایجاد می‌کند تا برای هماهنگی زمان وجود داشته باشد.
- هر occurrence فقط یک بار می‌تواند ساخته شود؛ retry یا اجرای هم‌زمان job نباید سفر تکراری بسازد.
- مبلغ occurrence در زمان ساخت همان سفر محاسبه می‌شود؛ `pricePerOccurrence` فقط راهنمایی است، نه تضمین مبلغ نهایی.
- مبلغ به‌صورت خودکار از کیف پول کسر می‌شود. اگر موجودی کافی نباشد، همان occurrence لغو می‌شود و برای کاربر notice ساخته می‌شود؛ خود سرویس فعال باقی می‌ماند.
- در سرویس هفتگی راننده به‌صورت خودکار broadcast نمی‌شود و تخصیص راننده با تیم پاستیل است.

بنابراین در اپ نوبس برای سرویس هفتگی **صفحه‌ی پرداخت درگاه، انتخاب تخفیف یا انتخاب راننده نسازید**. مسیر عملی کاربر پس از خطای کیف پول، شارژ کیف پول برای نوبت‌های بعدی است.

## 3. پت‌رسان متصل به نوبت مرکز

### 3.1 شرط نمایش

این گزینه فقط زمانی در finalization رزرو نمایش داده شود که نوع خدمت مرکز «در مرکز» باشد. در سناریوی آنلاین یا تحویل در آدرس، UI پت‌رسان متصل به نوبت را نمایش ندهد.

کاربر باید این داده‌ها را انتخاب کند:

- مبدأ و مقصد و آدرس‌ها؛
- حداقل یک پت از پت‌های همان نوبت؛
- حرکت راننده ۶۰ یا ۱۲۰ دقیقه پیش از ساعت نوبت؛
- آیا صاحب پت همراه است یا خیر.

در این قرارداد، رفت‌وبرگشت و گزینه‌های جانبی سفر ورودی ندارند؛ آن‌ها را به API این حالت ارسال نکنید.

### 3.2 ترتیب درست ثبت

```text
ثبت CompanionReserve
        ↓
ثبت TripReservation با companionReserveId
        ↓
تنظیم کیف پول/تخفیفِ خود نوبت (در صورت انتخاب کاربر)
        ↓
پرداخت خودِ CompanionReserve
        ↓
نمایش و پیگیری سفر پت‌رسانِ متصل به همان نوبت
```

اگر ساخت سفر شکست خورد، در همان صفحه بمانید و پیام سرور را نمایش دهید. نوبت ممکن است ایجاد شده باشد؛ پس قبل از ارسال دوباره‌ی رزرو، با `GET /TripReservation/{companionReserveId}` بررسی کنید که سفر تکراری ساخته نشده باشد.

پرداخت نوبت با پرداخت Trip یکی نیست: هزینه‌ی خود نوبت از جریان `CompanionReserve` پرداخت می‌شود؛ هزینه‌ی پت‌رسان فقط **بعد از Accepted شدن راننده** از جریان `TripPayment` پرداخت می‌شود. این دو را در یک checkout یا یک فاکتور محلی ادغام نکنید.

### 3.3 ساخت سفر مرتبط با نوبت

```http
POST /api/EndUser/TripReservation
Content-Type: application/json
Authorization: Bearer <token>
```

```json
{
  "companionReserveId": 8521,
  "origin": { "x": 51.3890, "y": 35.6892 },
  "destination": { "x": 51.4231, "y": 35.7324 },
  "fromAddress": "خانه",
  "toAddress": "کلینیک",
  "scheduledLeadMinutes": 60,
  "ownerRidesAlong": true,
  "userPetIds": [41]
}
```

قواعد سرور:

- `scheduledLeadMinutes` فقط `60` یا `120` است.
- زمان حرکت از `doDate` نوبت منهای زمان انتخاب‌شده به دست می‌آید و باید هنوز در آینده باشد.
- نوبت باید متعلق به کاربر جاری باشد.
- برای هر نوبت فقط یک سفر پت‌رسانِ فعال وجود دارد؛ duplicate را به کاربر به شکل «پت‌رسان این نوبت قبلاً ثبت شده است» نمایش دهید.
- قیمت بر اساس ساعت حرکت برنامه‌ریزی‌شده محاسبه می‌شود؛ اگر قیمت برای آن ساعت قابل محاسبه نباشد، سفر ایجاد نمی‌شود.

سفر پس از ایجاد در `Requested` قرار می‌گیرد و از همان زمان برای راننده‌های واجد شرایط broadcast می‌شود. اگر در زمان حرکت هنوز کسی آن را نپذیرفته باشد، سامانه به ادمین یادآوری می‌دهد تا راننده را دستی انتخاب کند. پس در اپ هیچ شمارش معکوس ۵ دقیقه‌ای یا لغو خودکار برای این نوع سفر نمایش ندهید.

### 3.4 بازیابی و نمایش وضعیت

```http
GET /api/EndUser/TripReservation/{companionReserveId}
```

- `isSuccess: false` یا `data: null`: هنوز سفری برای این نوبت وجود ندارد، یا نوبت در دسترس کاربر نیست.
- `data.driverId == null`: درخواست ثبت شده و در انتظار راننده است.
- `data.driverId != null`: راننده انتخاب/پذیرفته شده است؛ اطلاعات راننده و وضعیت را از `data` نمایش دهید.

در صفحه‌ی جزئیات نوبت، تا زمانی که سفر فعال است هر ۳ تا ۵ ثانیه و فقط هنگامی که صفحه visible است این endpoint را poll کنید. برای این جریان، `TripReservation/{companionReserveId}` منبع اصلی state است، نه `TripCurrent`.

## 4. پت‌رسان فوری

### 4.1 فرم و پیش‌نمایش قیمت

در فرم فوری، حداقل مبدأ، مقصد و یک پت را اجباری کنید. گزینه‌های زیر اختیاری‌اند:

- `roundTrip` برای رفت‌وبرگشت؛
- `ownerRidesAlong`؛
- `vehicleTypeId`؛
- `tripOptionIds` از کاتالوگ TripOption؛
- مقصد دوم، مدت توقف، توضیح کاربر و شناسه‌ی سفر قبلی (`previousTripId`) در صورت پشتیبانی UI.

برای نمایش قیمت پیش از ثبت:

```http
POST /api/EndUser/PriceCalculation
Content-Type: application/json
Authorization: Bearer <token>
```

بدنه را با مبدأ، مقصد، `roundTrip` و گزینه‌های مؤثر بر قیمت بفرستید. پاسخ ناموفق یا قیمت صفر به‌معنای قیمت رایگان نیست؛ دکمه‌ی ثبت را غیرفعال نگه دارید تا کاربر مسیر/اطلاعات را اصلاح یا مجدداً تلاش کند.

### 4.2 ثبت درخواست فوری

```http
POST /api/EndUser/TripCurrent
Content-Type: application/json
Authorization: Bearer <token>
```

```json
{
  "origin": { "x": 51.3890, "y": 35.6892 },
  "destination": { "x": 51.4231, "y": 35.7324 },
  "fromAddress": "تهران، ...",
  "toAddress": "تهران، ...",
  "isOnline": true,
  "roundTrip": false,
  "ownerRidesAlong": true,
  "userPetIds": [41],
  "tripOptionIds": [7],
  "userDetail": "لطفاً قبل از رسیدن تماس بگیرید"
}
```

نکات اجرایی:

- `isOnline` باید حتماً `true` باشد؛ این endpoint برای یافتن راننده در لحظه است.
- شناسه‌ی کاربر، قیمت، وضعیت، راننده و مبلغ پرداختی را نفرستید؛ سرور آن‌ها را تعیین می‌کند.
- تا پاسخ نهایی، دکمه‌ی «ثبت درخواست» یک‌بار قابل فشار باشد.
- کاربر نمی‌تواند هم‌زمان دو سفر فوری آنلاینِ فعال داشته باشد. در خطای «سفر آنلاین فعال دارید»، مستقیم صفحه‌ی پیگیری سفر فعال را باز کنید.

پس از ایجاد، سفر `Requested` است و برای راننده‌ها broadcast می‌شود. اگر تا ۵ دقیقه هیچ راننده‌ای قبول نکند، سیستم آن را خودکار `Canceled` می‌کند تا صفحه‌ی انتظار بی‌انتها نشود.

پس از لغو سیستمی دو اقدام ممکن است:

1. ثبت سفر فوری جدید؛ در صورت تکرار مسیر می‌توان `previousTripId` سفر قبلی را فرستاد.
2. درخواست انتخاب راننده توسط ادمین برای همان سفر لغوشده:

```http
PUT /api/EndUser/TripRequestAdminDriverSelection
Content-Type: application/json

{ "id": 9132 }
```

این endpoint فقط برای سفری معتبر است که دقیقاً به‌دلیل نپذیرفتن راننده توسط سیستم لغو شده است. UI آن را با متن «درخواست پیگیری پاستیل» نمایش دهد، نه «ثبت مجدد».

### 4.3 پیگیری، موقعیت و مرحله‌ی سفر

```http
GET /api/EndUser/TripCurrent
GET /api/EndUser/TripLive/{tripId}
POST /api/EndUser/UserCurrentLocation
```

برای location کاربر:

```json
{ "location": { "x": 51.3890, "y": 35.6892 } }
```

قانون polling پیشنهادی:

| وضعیت صفحه | درخواست | فاصله |
| --- | --- | --- |
| در انتظار راننده | `GET /TripCurrent` | ۳ تا ۵ ثانیه، فقط در foreground |
| راننده پذیرفته/نمایش نقشه | `GET /TripLive/{id}` | ۳ تا ۵ ثانیه، فقط در foreground |
| نقشه‌ی فعال با نیاز به موقعیت کاربر | `POST /UserCurrentLocation` | ۳ تا ۵ ثانیه، فقط با مجوز location |
| background یا صفحه بسته | هیچ‌کدام | polling را قطع کنید |

در `TripLive`، `counterpartLocation` ممکن است موقتاً `null` باشد؛ در این حالت نقشه را با متن «در حال دریافت موقعیت راننده» نشان دهید، نه با نقطه‌ی ساختگی. مراحل پیشرفت که UI می‌تواند بر مبنای آن‌ها متن بسازد:

| مرحله | متن پیشنهادی |
| --- | --- |
| 0 | در انتظار شروع سفر |
| 1 | راننده در مسیر مبدأ است |
| 2 | راننده به مبدأ رسیده است |
| 3 | پت تحویل گرفته شد |
| 4 | به مقصد رسیدیم |

در سفر رفت‌وبرگشت، پس از پایان مقصدِ رفت، سرور مبدأ و مقصد را برای مسیر برگشت جابه‌جا می‌کند و `isReturnLeg` را true می‌گذارد. متن و مسیر نقشه را بر اساس مختصات و `isReturnLeg` تازه‌شده refresh کنید.

## 5. وضعیت، لغو و پرداخت سفر

این بخش برای سفر فوری و سفر متصل به نوبت مشترک است. سرویس هفتگی پرداخت و تخصیص خودکارِ جداگانه دارد و وارد این flow نمی‌شود.

### 5.1 map وضعیت

فهرست status را از `Trip_Status` بگیرید و براساس label/نام بازگشتی map کنید، نه عدد ثابت دیتابیس. حالت‌های کلیدی UX عبارت‌اند از:

- `Requested`: در انتظار پذیرش راننده؛
- `Accepted`: راننده پذیرفته و کاربر می‌تواند تنظیم پرداخت را انجام دهد؛
- `Canceled`: پایان یافته/لغوشده؛
- `Compeleted`: پایان موفق سفر (املای label فعلی API را همان‌طور که برمی‌گردد پشتیبانی کنید).

### 5.2 لغو توسط کاربر

```http
PUT /api/EndUser/TripUserCancel
Content-Type: application/json

{
  "id": 9132,
  "cancelReasonCodeId": 204,
  "cancelDetail": "اختیاری"
}
```

`cancelReasonCodeId` باید از گروه `TripCancelReason_User` انتخاب شود. با رسیدن سفر به مرحله‌ی ۳ (تحویل گرفتن پت) یا بعد از آن، لغو مجاز نیست؛ در UI قبل از ارسال دکمه را پنهان/غیرفعال کنید و خطای سرور را نیز handle کنید.

### 5.3 تخفیف، کیف پول و آغاز پرداخت

تنظیم‌های مالی فقط پس از `Accepted` و قبل از آغاز پرداخت معتبر هستند:

```http
PUT /api/EndUser/TripSetRebate
{ "id": 9132, "rebateCode": "PET10" }

PUT /api/EndUser/TripRemoveRebate?id=9132

PUT /api/EndUser/TripSetWallet
{ "id": 9132, "fromWallet": true }
```

پس از اعمال هرکدام، state سفر/فاکتور را تازه کنید تا مبلغ نمایش‌داده‌شده قدیمی نباشد.

```http
POST /api/EndUser/TripPayment
Content-Type: application/json
Authorization: Bearer <token>
```

حداقل ورودی لازم:

```json
{ "tripId": 9132, "merchantId": 3 }
```

- اگر کل مبلغ از کیف پول تأمین شود، `merchantId` لازم نیست.
- اگر پس از کیف پول مبلغی باقی مانده باشد یا کیف پول انتخاب نشده باشد، `merchantId` لازم است.
- مبلغ را از client تعیین نکنید؛ سرور آن را از Trip و تخفیف/کیف پول اعمال‌شده محاسبه می‌کند.
- نتیجه ممکن است URL درگاه در `data.paymentUrl` به‌همراه `data.paymentIsLink` داشته باشد. در این حالت اپ باید به درگاه منتقل شود و بعد از callback، وضعیت واقعی را refresh کند.
- یک کلیکِ پرداخت نباید چند درخواست بسازد. کلید checkout ثابت برای همان تلاش پرداخت نگه دارید و تا برگشت نتیجه، CTA را busy کنید.

## 6. الگوی state در اپ نوبس

برای حفظ UI در rotate، resume و قطع شبکه، دست‌کم این داده‌ها را در state پایدار نگه دارید:

```ts
type PetResanUiState = {
  mode: 'weekly-service' | 'reservation-linked' | 'instant'
  serviceId?: number
  companionReserveId?: number
  tripId?: number
  submitIdempotencyKey?: string // فقط برای ساخت سرویس هفتگی
  phase:
    | 'form'
    | 'price-preview'
    | 'creating'
    | 'requested'
    | 'accepted'
    | 'paying'
    | 'live'
    | 'canceled'
    | 'completed'
}
```

قواعد مهم state:

1. پس از دریافت پاسخ ساخت، شناسه را فوراً ذخیره کنید و برای ادامه‌ی flow به‌جای ارسال دوباره از API وضعیت استفاده کنید.
2. در هر resume اپ، سفرهای فعال را refresh کنید؛ نتیجه‌ی polling قدیمی نباید state جدیدتر را overwrite کند.
3. polling هم‌زمان برای یک سفر ایجاد نکنید؛ یک timer/in-flight request بیشتر از یکی نباشد.
4. اگر token منقضی شد، polling را متوقف کنید، refresh-token flow مرکزی را اجرا کنید و فقط پس از موفقیت ادامه دهید.
5. اعلان push را مکمل polling بدانید، نه جایگزین قطعی آن.

## 7. سناریوهای پذیرش (QA checklist)

### سرویس هفتگی

- [ ] ثبت با یک زمان و با چند زمان متفاوت در یک روز/هفته موفق است.
- [ ] schedule تکراری یا ساعت نامعتبر قبل از ارسال رد می‌شود.
- [ ] retry همان payload با همان `Idempotency-Key` همان `serviceId` را برمی‌گرداند.
- [ ] reuse همان کلید با payload تغییرکرده خطا را نمایش می‌دهد و سرویس جدید نمی‌سازد.
- [ ] cancel، وضعیت را inactive می‌کند و به کاربر توضیح می‌دهد که سفرهای قبلاً ایجادشده باقی می‌مانند.
- [ ] خطای قیمت یا کیف پول صفر/ناکافی، هرگز به عنوان قیمت صفر یا پرداخت موفق نشان داده نمی‌شود.

### نوبت + پت‌رسان

- [ ] فقط برای رزرو حضوری نمایش داده می‌شود.
- [ ] نوبت اول ساخته می‌شود، سپس TripReservation با ID واقعی همان نوبت ثبت می‌شود.
- [ ] فاصله‌ی ۶۰/۱۲۰ دقیقه معتبر و زمان حرکت گذشته نامعتبر است.
- [ ] دوبار tap یا retry پس از قطع شبکه، با GET سفر موجود را بازیابی می‌کند و رزرو/سفر را duplicate نمی‌کند.
- [ ] پرداخت نوبت با پرداخت سفر در دو CTA و دو state جدا نمایش داده می‌شوند.

### فوری

- [ ] بدون مبدأ، مقصد، پت یا `isOnline: true` امکان ثبت وجود ندارد.
- [ ] در انتظار راننده، فقط یک poll فعال است و در background متوقف می‌شود.
- [ ] لغو سیستمی بعد از بی‌پاسخ ماندن، CTA «ثبت مجدد» و CTA «درخواست پیگیری پاستیل» را درست نشان می‌دهد.
- [ ] پس از `Accepted` امکان تخفیف/کیف پول/پرداخت فعال می‌شود، نه قبل از آن.
- [ ] لغو از مرحله‌ی تحویل پت به بعد در UI غیرفعال است.
