# ارائه‌دهنده (Provider) و اشتراک — راهنمای کامل اپ نماینده (اپ فلاتر)

> تاریخ: ۱۴۰۵/۰۷/۲۶ (۲۰۲۶-۱۰-۱۸) · backend: Deploy شده، مایگریشن `AddProviders` اعمال شده.
> برای تیم اپ نماینده (امیرمحسن/آرمان). طراحی کلی: [PROVIDER_AND_SUBSCRIPTION_FA.md](PROVIDER_AND_SUBSCRIPTION_FA.md). نسخه‌ی وب‌اپ: [PROVIDER_WEBAPP_FA.md](PROVIDER_WEBAPP_FA.md).

## ۰. خلاصه

**اپ فعلی بدون هیچ تغییری کار می‌کند.** هیچ endpoint، فیلد یا کد خطایی که اپ استفاده می‌کند حذف یا تغییر نام نداده است. تغییرات سمت سرور: ۱) یک فیلد جدید `providerId`، ۲) منبع `isGold/isSilver` عوض شد (همان فیلدها)، ۳) محدودیت «هر کاربر فقط یک مرکز» برداشته شد، ۴) دو endpoint ادمین‌محور از کار افتادند (به اپ ربطی ندارد). همه‌ی قابلیت‌های جدید (انتخاب نمایندگی، صفحه‌ی ارائه‌دهنده) **هنوز در backend ساخته نشده‌اند**؛ در §۷ قرارداد پیشنهادی هست و تا اعلام نشده چیزی بر پایه‌اش پیاده نکنید.

## ۱. واژه‌ها

- **ارائه‌دهنده (Provider)** = صاحب کسب‌وکار (کاربری که قبلاً «نماینده» می‌گفتیم). در اپ هرجا «نماینده» به شخص اشاره دارد، متن را «ارائه‌دهنده» کنید؛ نام صفحه‌ها/مسیرها/کلاس‌ها را عوض نکنید.
- **نمایندگی** = کلینیک / آرایشگاه / مربی / پانسیون... همان `Companion` در API.
- **پرسنل** = `CompanionUser` (دکتر، اپراتور...) — **بدون تغییر**. «ارائه‌دهنده» فقط صاحب است؛ پرسنل ارائه‌دهنده نیستند و فقط عضو آن نمایندگی‌اند.
- **اشتراک** = نقره‌ای / طلایی / الماس، روی ارائه‌دهنده؛ برای همه‌ی نمایندگی‌های او یکسان.

## ۲. تغییرات قرارداد API (دقیق)

### ۲.۱ فیلد جدید `providerId` (افزودنی)

در هر پاسخی که شیء مرکز (`CompanionVDto`/`CompanionMinVDto`) دارد:

```json
{ "id": 41, "name": "کلینیک مهر", "ownerId": 1203, "providerId": 17, "isGold": true, "isSilver": false,
  "goldAccountDate": "2027-01-01T23:59:59", "silverAccountDate": null }
```

- نوع: `long?` (می‌تواند `null` باشد: مرکزی که ادمین ساخته و هنوز وصل نکرده).
- در مدل Dart فیلد را **nullable و اختیاری** تعریف کنید (`int? providerId`)؛ اگر جایی `fromJson` سخت‌گیرانه دارید (کلید ناشناخته خطا می‌دهد) باید اضافه شود، وگرنه چیزی لازم نیست.
- `ownerId` دست‌نخورده است.

### ۲.۲ `isGold` / `isSilver` / تاریخ‌ها — همان فیلدها، منبع جدید

| اشتراک ارائه‌دهنده | `isGold` | `isSilver` | `goldAccountDate` | `silverAccountDate` |
|---|---|---|---|---|
| ندارد / منقضی | false | false | null | null |
| نقره‌ای | false | true | null | پایان اشتراک |
| طلایی | true | false | پایان اشتراک | null |
| الماس | **true** | false | پایان اشتراک | null |

- الماس فعلاً در اپ مثل طلایی دیده می‌شود. نشان جدا برای الماس نیاز به فیلد `subscriptionLevel` دارد که **هنوز وجود ندارد**.
- زمان پایان اشتراک `23:59:59` روز انتخابی ادمین است؛ منطق `isGold` سمت سرور حساب می‌شود، اپ خودش تاریخ را با «اکنون» مقایسه نکند.
- **تغییر رفتار:** قبلاً فقط یک مرکز در کل سیستم طلایی بود؛ حالا هر تعداد. UI را طوری نگه دارید که چند طلایی در یک لیست مشکلی نداشته باشد.

### ۲.۳ برداشته شدن محدودیت «یک مرکز برای هر کاربر»

| endpoint | قبلاً | حالا |
|---|---|---|
| `POST /api/EndUser/Companion` (ثبت درخواست مرکز) | کاربری که مرکز داشت → خطای `AlreadyIsCompanion` | **ثبت می‌شود**؛ مرکز جدید با `active=false, approved=false` (در انتظار تأیید ادمین) |
| `PUT /api/EndUser/Companion` (ویرایش و ارسال مجدد) | ممکن بود خطای `CompanionAlreadyRegisteredForOwner` بدهد | این خطا دیگر نمی‌آید |
| `GET /api/EndUser/Companion` | حداکثر ۱ مورد (کاربر فقط یک مرکز داشت) | **ممکن است چند مورد** |

اپ نباید: دکمه‌ی «ثبت درخواست مرکز جدید» را فقط چون کاربر قبلاً مرکز دارد مخفی/غیرفعال کند؛ یا فرض کند لیست «مراکز من» حداکثر یک عنصر دارد (`list.first` را به «نمایش همه» تبدیل کنید).

### ۲.۴ ساخت خودکار ارائه‌دهنده

اولین درخواست مرکز (یا فروشگاه) کاربر → سرور خودش `Provider` می‌سازد (فعال، تأییدنشده) و وصل می‌کند. اپ چیزی ارسال نمی‌کند و پاسخی عوض نمی‌شود. تأییدنشده بودن ارائه‌دهنده **هیچ ویژگی‌ای را نمی‌بندد**.

### ۲.۵ از کار افتاده (به اپ مربوط نیست)

`PUT /api/Admin/CompanionUpdateGoldAccount` و `.../CompanionUpdateSilverAccount` اکنون فقط پیام «سطح حساب ویژه از بخش اشتراک ارائه‌دهنده مدیریت می‌شود» برمی‌گردانند. این‌ها فقط پنل ادمین است؛ اپ نماینده هرگز نباید صدایشان بزند.

## ۳. چیزهایی که **تغییر نکرده‌اند** (مطمئن باشید)

- لاگین/ثبت‌نام، توکن، refresh.
- پاسخ کاربر جاری: `companionId` (**اولین مرکز فعال و تأییدشده**)، `storeId` (اولین فروشگاه)، `isCompanionUser`، `canSetExpertise`، `expertise`، `driverId` دقیقاً مثل قبل.
- همه‌ی endpointهای ناحیه‌ی `Companion`: رزرو، خدمات و پکیج‌ها، زمان‌بندی، پانسیون، مدرسه، مشاوره، آنلاین، نسخه، مالی/تسویه، پرسنل (`CompanionUser`)، تخصص‌ها، `CompanionDaySchedule`.
- شناسه‌ها و `CompanionId` در همه‌ی رزروها؛ هیچ ID عوض نشده.
- پوش‌ها و Noticeها.
- تسویه و کیف پول: همچنان **به‌ازای مرکز/ مالک قبلی** حساب می‌شوند (تجمیع در سطح ارائه‌دهنده در این فاز انجام نشد).

## ۴. محدودیت‌های فعلی (مهم برای تست و پشتیبانی)

1. **اپ فقط یک مرکز را مدیریت می‌کند.** سرور برای همه‌ی endpointهای ناحیه‌ی `Companion` مرکزِ کاربر را از `companionId` پاسخ کاربر جاری می‌گیرد = «اولین مرکز فعال و تأییدشده». مثلاً `GET /api/Companion/Companion/{id}` فارغ از `id` همان مرکز را برمی‌گرداند و `PUT /api/Companion/Companion` همان را ویرایش می‌کند. پس ارائه‌دهنده‌ای که دو کلینیک دارد در اپ فقط کلینیک اول را می‌بیند. ترتیب «اول» = پایین‌ترین `Id` بین مراکز فعال و تأییدشده‌ی او.
2. **پرسنل چندنمایندگیه:** کاربری که پرسنل چند مرکز است، برای آن‌ها `FindClinicAsync` (آنلاین) مرکزی را که خودش مالک است ترجیح می‌دهد، وگرنه کمترین `Id`. بدون تغییر نسبت به قبل.
3. اپ هیچ راهی برای **ساخت مرکز دوم از داخل برنامه** جز همان فرم درخواست ندارد و مرکز دوم تا تأیید ادمین غیرفعال است؛ و بعد از تأیید هم اپ آن را نشان نمی‌دهد (مورد ۱).
4. **اشتراک فقط از پنل ادمین** داده می‌شود؛ ارائه‌دهنده در اپ نمی‌تواند اشتراک بخرد یا ببیند چه زمانی تمام می‌شود، مگر از `goldAccountDate/silverAccountDate` خروجی مرکز.

## ۵. کارهای پیشنهادی در اپ (به ترتیب اولویت)

1. **[مهم]** مدل مرکز: `providerId` را اضافه کنید (nullable). جاهایی که `fromJson` سخت‌گیرانه است.
2. **[مهم]** لیست «مراکز من» / «درخواست‌های من»: چند عنصر را پشتیبانی کند، هرکدام با وضعیت (در انتظار / فعال / ردشده بر اساس `active`, `approved`, `activationValue`).
3. **[مهم]** حذف هر چک کلاینتی که «کاربر قبلاً مرکز دارد → ثبت جدید ممنوع».
4. **[اختیاری]** تغییر متن «نماینده» → «ارائه‌دهنده» برای شخص صاحب کسب‌وکار (متن‌ها و عنوان‌های UI؛ نه نام مسیرها).
5. **[اختیاری]** نمایش نشان اشتراک روی کارت مرکز (از `isGold/isSilver`) و تاریخ پایان.
6. **[منتظر backend]** انتخاب نمایندگی (§۷).

## ۶. سناریوهای تست (بعد از Deploy)

| # | سناریو | انتظار |
|---|---|---|
| ۱ | مالک یک مرکز تأییدشده لاگین می‌کند | همه‌چیز مثل قبل؛ `companionId` همان |
| ۲ | پاسخ `GET /api/Companion/Companion/{id}` | شامل `providerId` (عدد یا null)، بقیه‌ی فیلدها مثل قبل |
| ۳ | ادمین برای همان مالک «اشتراک طلایی» ثبت کند (پنل → ارائه‌دهندگان) | `isGold=true` و `goldAccountDate` پر در خروجی مرکز (بدون خروج/ورود مجدد) |
| ۴ | ادمین «پایان فوری» کند | `isGold=false`، `goldAccountDate=null` |
| ۵ | مالک از اپ مرکز دوم ثبت کند | خطا نمی‌گیرد؛ در لیست `EndUser/Companion` دو مورد؛ مرکز دوم غیرفعال/تأییدنشده |
| ۶ | ادمین مرکز دوم را تأیید کند | اپ همچنان **مرکز اول** را مدیریت می‌کند (مورد انتظار) |
| ۷ | اشتراک نقره‌ای ← بعد الماس بدهد | `isSilver` خاموش، `isGold` روشن (الماس) |
| ۸ | مرکزی را به ارائه‌دهنده‌ی دارای اشتراک وصل کند (پنل → نمایندگی‌ها) | همان لحظه badge آن اشتراک را بگیرد |
| ۹ | رزرو، پکیج، مشاوره، مالی | بدون تغییر |

## ۷. قرارداد پیشنهادی فاز بعد (**ساخته نشده — پیاده نکنید**)

برای ارائه‌دهنده‌ی چندنمایندگیه backend این‌ها را اضافه می‌کند؛ این بخش فقط برای هماهنگی طراحی است و ممکن است در پیاده‌سازی تغییر کند:

1. `GET /api/EndUser/Provider/Me`:
```json
{ "isSuccess": true, "data": {
  "id": 17, "active": true, "approved": true,
  "subscription": { "planName": "طلایی", "level": 2, "endDate": "2027-01-01T23:59:59" },
  "roles": [ { "label": "Clinic", "name": "کلینیک", "approved": true } ],
  "companions": [ { "id": 41, "name": "کلینیک مهر", "active": true, "approved": true } ],
  "stores": [ { "id": 9, "name": "پت‌شاپ آرین", "active": true, "approved": true } ] } }
```
2. انتخاب مرکز فعال: هدر `X-Companion-Id: 41` روی همه‌ی endpointهای ناحیه‌ی `Companion`. اگر مرکز متعلق به کاربر (یا پرسنل فعالش) نباشد → `403`. بدون هدر = رفتار فعلی (اولین مرکز).
3. اپ: بعد از لاگین `Provider/Me` را بخواند؛ اگر `companions.length > 1` یک صفحه‌ی «انتخاب مرکز» (و سوییچر در سربرگ) نشان دهد، انتخاب را ذخیره کند و هدر را به همه‌ی درخواست‌ها بزند.
4. فیلد `subscriptionLevel` (۱ نقره‌ای، ۲ طلایی، ۳ الماس) در خروجی مراکز.

## ۸. سؤال‌های باز

- نشان جدا برای «الماس»؟ (نیاز به `subscriptionLevel`)
- انتخاب مرکز (§۷) کِی لازم است؟ اگر فوری نیست، تا آن موقع ارائه‌دهنده‌های چندنمایندگیه را فقط با هماهنگی پشتیبانی بسازیم.
- تسویه‌ی تجمیعی در سطح ارائه‌دهنده (به‌جای هر مرکز) می‌خواهید؟

## تغییر در تسویه‌ها (۱۴۰۵/۰۷/۲۷) — اپ نماینده

تسویه‌ها از این پس **برای ارائه‌دهنده** ثبت می‌شوند و به‌جای نمایندگی/فروشگاه منفرد، کل «نمایندگی‌ها» ارائه‌دهنده را یک‌جا می‌پردازند.

**تغییر قرارداد `GET /api/Companion/Settlement` (و `/{id}`):**

- لیست حالا تسویه‌های ارائه‌دهنده‌ی همین نمایندگی را (فقط همین استخر) برمی‌گرداند؛ پارامترهای `companionId/storeId/providerId/kind` را نفرستید (نادیده گرفته می‌شوند).
- فیلدهای جدید در هر ردیف: `providerId` (عدد)، `kind` (`1` نمایندگی‌ها، `2` فروشگاه‌ها)، `provider` (`{ id, userId, active, user }`).
- **در تسویه‌های جدید `companionId`, `storeId`, `companion`, `store` برابر `null` هستند.** فقط ردیف‌های قدیمی (قبل از این تغییر) آن‌ها را دارند. UI نباید روی این فیلدها برای نمایش «گیرنده» تکیه کند؛ برای نمایش از «ارائه‌دهنده + استخر» استفاده کنید.
- `paidPrice` جمع همه‌ی رزرو/خرید/ثبت‌نام آن تسویه (در همه‌ی نمایندگی‌ها ارائه‌دهنده) است و `itemCount` تعداد آن‌ها؛ ریز هر مورد در این endpoint نیست.
- دسترسی به `GET /Settlement/{id}`: فقط تسویه‌ی ارائه‌دهنده‌ی همین نمایندگی (و همین استخر)؛ در غیر این‌صورت `isSuccess=false` با پیام عدم دسترسی.

**بدون تغییر:** گزارش مالی `/Companion/FinanceCompanion` (ریز و جمع سهم‌ها، `Permitted`)، کارت‌های بانکی، و اینکه نمایندگی نمی‌تواند خودش درخواست تسویه ثبت کند (فقط ادمین).
**نکته‌ی نمایش:** ریز رزرو/خرید/ثبت‌نام هر نمایندگی همچنان از گزارش مالی همان نمایندگی می‌آید، ولی «تسویه‌شدن» برای کل ارائه‌دهنده‌ی اوست؛ اگر ارائه‌دهنده چند نمایندگی دارد، مبلغ یک تسویه به یک نمایندگی تقسیم نشده است.
