# نقش/تخصص اعضای تیم کلینیک، مربی و آرایشگاه — اپ نماینده و پنل وب‌اپ

**مخاطب:** توسعه‌دهنده‌ی **اپ نماینده** (Flutter) و توسعه‌دهنده‌ی **وب‌اپ** (پنل‌های `clinicProfile` و `groomerProfile` و بخش مربی).
**تاریخ:** ۱۴۰۵/۰۸/۰۶ (2026-10-28)
**وضعیت بک‌اند:** کد و تست آماده است. **نه دیپلوی شده و نه مایگریشن اجرا شده** (`backend/scripts/VenueStaffExpertise.sql`). تا اعلام، اندپوینت‌های جدید وجود ندارند.

---

## ۱) مشکل و آنچه درست شد
گزارش: «تخصص (expertise) برای پنل نماینده کار نمی‌کند و نقش‌های تیم را نمی‌آورد.»

| علت | اصلاح |
|---|---|
| فقط تیمِ **نمایندگی قدیمی** (Companion) جای نقش/تخصص داشت. جدول تیم کلینیک، مربی و آرایشگاه اصلاً چنین فیلدی نداشت، پس چیزی ذخیره نمی‌شد که برگردد. | برای هر عضو تیم کلینیک/مربی/آرایشگاه **تا ۱۰ نقش/تخصص** ذخیره می‌شود (مثل تیم نمایندگی). اولین مورد «اصلی» است. |
| تخصصِ پروفایل کاربر فقط برای مالک/عضو نمایندگی مجاز بود. مالک یا پرسنل کلینیک، مربی، آرایشگاه و ارائه‌دهنده خطا می‌گرفتند یا تخصصشان بی‌صدا پاک می‌شد. | مالک و پرسنل پذیرفته‌شده‌ی این مرکزها و کاربرِ ارائه‌دهنده هم می‌توانند تخصص بگذارند. `canSetExpertise` در اطلاعات کاربر برایشان `true` می‌شود. |
| لیست تخصص‌ها (`GET api/Expertise`) فقط با **شناسه‌ی عددی نقش** فیلتر می‌شد که پنل ندارد. لیست گروه‌ها هم فقط برای ادمین بود. | فیلتر با **برچسب نقش** (`?ProviderRole=Clinic`) و اندپوینت عمومی گروه‌ها اضافه شد. |
| لیست عمومی اعضای مرکز نقش را از روی نام خدمت‌ها **حدس** می‌زد. | اگر برای عضو نقش تعیین شده باشد، همان نمایش داده می‌شود. |

## ۲) قواعد عمومی
- **پاسخ‌ها:** HTTP 200 با `{ isSuccess, messages: [{ item1 }], data }`. در خطا، `messages[0].item1` را نشان دهید.
- **دسترسی:** همه‌ی اندپوینت‌های تیم (`api/Companion/{Clinic|Coach|Groomer}User…`) توکن **مالک مرکز** را می‌خواهند. کاربر دیگر خطای «شما به این بخش دسترسی ندارید» می‌گیرد.
- **`{Kind}` در این مستند:** یکی از `Clinic`، `Coach`، `Groomer` است، و پارامتر شناسه‌ی مرکز به ترتیب `clinicId`، `coachId`، `groomerId`.

---

## ۳) لیست تخصص‌ها برای انتخاب (عمومی، بدون توکن)
```
GET /api/Expertise?ProviderRole=Clinic&PageIndex=1&PageSize=100
GET /api/Expertise?ProviderRole=Coach&...
GET /api/Expertise?ProviderRole=Groomer&...
```
- خروجی شامل تخصص‌های **همان نقش** به‌اضافه‌ی **تخصص‌های عمومی** (بدون نقش) است. فقط تخصص‌های فعال برمی‌گردند.
- `Q` برای جستجو در نام است.
- شکل پاسخ، لیست صفحه‌بندی‌شده‌ی معمول است. هر آیتم: `{ "id": 7, "name": "دامپزشک", "priority": 1, "active": true, "providerRoleId": 3, "providerRoleName": "کلینیک", "providerRoleLabel": "Clinic" }`.

**گروه‌ها** (اختیاری، اگر بخواهید تخصص‌ها را گروه‌بندی کنید):
```
GET /api/Expertise/groups   →   [ { "id": 3, "name": "کلینیک", "label": "Clinic" }, … ]
```

> تخصص‌ها را ادمین پاستیل در پنل ادمین (بخش «تخصص‌ها») تعریف می‌کند. اگر لیست برای یک نقش خالی است، یعنی هنوز تخصصی برای آن نقش تعریف نشده است.

## ۴) لیست تیم: حالا نقش‌ها را دارد
```
GET /api/Companion/{Kind}User?{kind}Id=5
```
هر عضو این فیلدهای جدید را دارد:
```json
{
  "id": 41, "clinicId": 5, "userId": 900, "firstName": "سارا", "lastName": "محمدی", "mobile": "0912…",
  "active": true, "activationValue": null, "userAccept": true, "inviteDate": "…",
  "expertiseId": 7,
  "expertises": [ { "id": 7, "name": "دامپزشک", "active": true }, { "id": 12, "name": "جراح", "active": true } ],
  "expertiseName": "دامپزشک، جراح"
}
```
- `expertiseId` نقش **اصلی** است (اولین مورد)، یا `null`.
- `expertises` لیست کامل است (فقط تخصص‌های فعال).
- `expertiseName` متن آماده‌ی نمایش است (`null` اگر نقشی نداشته باشد).

## ۵) تعیین/ویرایش نقش‌های یک عضو
```
PUT /api/Companion/{Kind}User/Expertise
{ "id": 41, "expertiseIds": [7, 12] }
```
- `id` شناسه‌ی **ردیف عضو تیم** است (همان `id` در لیست تیم)، نه `userId`.
- لیست ارسالی **کل** نقش‌ها را **جایگزین** می‌کند. اولین مورد «اصلی» می‌شود. **لیست خالی یعنی پاک کردن همه.**
- حداکثر ۱۰ مورد. تکراری‌ها حذف می‌شوند. فقط تخصص‌های فعال پذیرفته می‌شوند.
- **پاسخ موفق:** همان عضو با نقش‌های به‌روز (شکل بند ۴).
- **خطاها:**
  - «نقش/تخصص انتخاب‌شده معتبر نیست (حداکثر ۱۰ مورد از تخصص‌های فعال پاستیل).»
  - «موردی یافت نشد»: عضو پیدا نشد.
  - «شما به این بخش دسترسی ندارید»: کاربر مالک مرکز نیست.

**هنگام دعوت عضو جدید** (اختیاری) می‌شود نقش‌ها را هم فرستاد:
```
POST /api/Companion/{Kind}User
{ "clinicId": 5, "mobile": "09121234567", "expertiseIds": [7] }
```

## ۶) تخصصِ پروفایل خودِ کاربر
مسیرها همان قبلی‌اند: ویرایش پروفایل کاربر، و اطلاعات کاربر جاری.
- برای مالک یا پرسنلِ پذیرفته‌شده‌ی کلینیک/مربی/آرایشگاه و کاربرِ ارائه‌دهنده، `canSetExpertise = true` می‌آید. فیلد «تخصص» پروفایل را برای این کاربرها **نشان دهید و فعال کنید**.
- اگر مالک مرکز برای این کاربر نقش تعیین کرده باشد، `expertise` پروفایل همان نقش‌ها را نشان می‌دهد و متن آزاد کاربر جایگزینش نمی‌شود (مثل تیم نمایندگی).

---

## ۷) لیست عمومی اعضای مرکز (صفحه‌ی مرکز برای مشتری)
`GET /api/Clinic/{id}/Members` و `GET /api/Coach/{id}/Members` بدون تغییر قرارداد هستند. فقط `roleTitle` پرسنل حالا **نقش‌های تعیین‌شده** است (تا ۳ مورد، مثلاً «دامپزشک، جراح»). اگر نقشی تعیین نشده باشد، مثل قبل از نام خدمت‌ها یا «عضو تیم» ساخته می‌شود. این لیست ۶۰ ثانیه cache می‌شود.

---

## ۸) کار اپ نماینده (Flutter)
در صفحه‌ی «تیم» هر مرکز (کلینیک، مربی، آرایشگاه):
1. **نمایش:** زیر نام هر عضو، `expertiseName` (یا «بدون نقش» به رنگ خاکستری).
2. **ویرایش نقش:** با لمس عضو یا دکمه‌ی «نقش‌ها»:
   - یک صفحه/شیت با لیست چندانتخابی از `GET /api/Expertise?ProviderRole={Kind}`، با جستجو.
   - انتخاب‌های فعلی تیک‌خورده باشند (`expertises`).
   - یک مورد را بشود «اصلی» کرد (اول لیست ارسالی).
   - سقف ۱۰ مورد.
   - «ذخیره» ← `PUT …/{Kind}User/Expertise`.
3. **فرم دعوت:** یک انتخاب‌گر اختیاری «نقش» کنار موبایل (`expertiseIds`).
4. **پروفایل کاربر:** اگر `canSetExpertise` بود، فیلد تخصص را فعال کنید.

## ۹) کار وب‌اپ (پنل `clinicProfile` / `groomerProfile` / مربی)
### ۹-۱) مسیرهای مجاز سرور (allow-list) — **بدون این‌ها درخواست به بک‌اند نمی‌رسد**
در `app/server/utils/clinicRoutes.js` (و به همین شکل `groomerRoutes.js` و فایل مسیرهای مربی، اگر جداست):
```js
// PUBLIC_ROUTES
['GET', 'Expertise'],
['GET', 'Expertise/groups'],

// مسیرهای owner (کنار ClinicUser های فعلی)
['PUT', 'ClinicUser/Expertise'],
```
برای آرایشگاه `['PUT', 'GroomerUser/Expertise']`، و برای مربی `['PUT', 'CoachUser/Expertise']`.

### ۹-۲) توابع API — `app/composables/useClinicApi.ts`
```ts
// public
expertises: (q?: string) => call('public', 'Expertise', { query: { ProviderRole: kind === 'coach' ? 'Coach' : 'Clinic', PageIndex: 1, PageSize: 100, Q: q } }),
// owner
setStaffExpertise: (id: number, expertiseIds: number[]) => call('owner', 'ClinicUser/Expertise', { method: 'PUT', body: { id, expertiseIds } }),
```
(در کد آرایشگاه با `ProviderRole: 'Groomer'` و `GroomerUser/Expertise`.)
`addStaff` فعلی فقط `{ clinicId, mobile }` می‌فرستد. اگر نقش هنگام دعوت را هم می‌خواهید، `expertiseIds` را اضافه کنید.

### ۹-۳) صفحه — `pages/clinicProfile/[id]/staff.vue` (و معادل آرایشگاه/مربی)
- کارت هر عضو: `expertiseName` زیر نام (یا «بدون نقش»).
- دکمه‌ی «نقش‌ها» ← `BottomModal` با لیست چندانتخابی (`expertises()`)، تیک‌های فعلی از `member.expertises`، و جستجو.
- ذخیره ← `setStaffExpertise(member.id, ids)` ← در موفقیت لیست دوباره بارگذاری شود (یا `data` جایگزین شود).
- فرم دعوت: انتخاب‌گر اختیاری نقش.

### ۹-۴) پروفایل کاربر در وب‌اپ
هر جا فیلد تخصص با `canSetExpertise` کنترل می‌شود، تغییری لازم نیست؛ حالا برای این کاربرها `true` می‌آید.

---

## ۱۰) چک‌لیست تست (بعد از اجرای مایگریشن و دیپلوی)
1. `GET /api/Expertise?ProviderRole=Clinic` ← تخصص‌های کلینیک + عمومی.
2. پنل/اپ: لیست تیم کلینیک ← اعضا با `expertises: []`.
3. «نقش‌ها» برای یک عضو ← انتخاب «دامپزشک» و «جراح» ← ذخیره ← زیر نام: «دامپزشک، جراح».
4. دوباره فقط «جراح» ← ذخیره ← فقط «جراح».
5. پاک کردن همه ← «بدون نقش».
6. ۱۱ مورد ← خطای «معتبر نیست».
7. کاربر غیرمالک ← خطای دسترسی.
8. صفحه‌ی عمومی کلینیک برای مشتری ← اعضای تیم با همان نقش‌ها (حداکثر یک دقیقه تأخیر به‌خاطر cache).
9. ورود با حساب یکی از پرسنل پذیرفته‌شده‌ی کلینیک ← پروفایل ← فیلد تخصص فعال است (`canSetExpertise = true`).
10. همین تست‌ها برای مربی و آرایشگاه.
