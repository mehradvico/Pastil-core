## روش اجرای مورد توافق

ترتیب کار برای هر مورد ثابت است و مورد بعدی فقط پس از ثبت نتیجهٔ مورد قبلی شروع می‌شود:

```text
۱. بازتولید روی محیط تست + ذخیرهٔ request/response
۲. مشخص‌کردن لایهٔ مسئول (اپ، API، داده یا قرارداد)
۳. افزودن تستی که ابتدا شکست می‌خورد
۴. اصلاح کم‌دامنه و امن
۵. اجرای همان تست + regression test
۶. ثبت endpoint/قرارداد جدید یا تغییرکرده در همین سند
```

**قاعدهٔ کلیدی مالی:** اپ فقط مبلغ‌های نهایی بازگشتی از سرور را نمایش می‌دهد؛ محاسبه، جمع‌زدن، تخفیف، پیش‌پرداخت، مانده، کمیسیون و اعتبارسنجی مبلغ هیچ‌کدام در فرانت‌اند انجام نمی‌شود.

## 1. حذف مدرسه توسط نماینده

### یافتهٔ تأییدشده

مسیرهای فعلی پنل نماینده برای مدرسه عبارت‌اند از:

| Method | URL | وضعیت |
|---|---|---|
| `GET` | `/api/Companion/School` | فهرست مدرسه‌های مرکز جاری |
| `GET` | `/api/Companion/School/{id}` | جزئیات مدرسهٔ متعلق به مرکز جاری |
| `POST` | `/api/Companion/School` | ایجاد مدرسه |
| `PUT` | `/api/Companion/School` | ویرایش مدرسه |
| `PUT` | `/api/Companion/SchoolActive` | فعال/غیرفعال‌سازی |
| `DELETE` | `/api/Companion/School/{id}` | **وجود ندارد** |

همچنین entity `School` فیلد `Deleted` ندارد. حذف فیزیکی، به‌دلیل وابستگی دوره‌ها، جلسه‌ها، تصاویر، نظرها و ثبت‌نام‌های کاربران، قابل قبول نیست.

### تصمیم پیاده‌سازی

حذف باید **soft delete/آرشیو** باشد، نه پاک‌کردن دیتابیس:

1. افزودن `School.Deleted` و migration.
2. endpoint جدید زیر با بررسی مالکیت از token:

```http
DELETE /api/Companion/School/{id}
Authorization: Bearer <companion-token>
```

3. در تراکنش واحد، فقط برای مدرسهٔ همان `currentUser.companionId`:
   - `Deleted=true`
   - `Active=false`
   - `Approve=false`
   - `ShowToSite=false`
4. تمام queryهای مدرسه، جزئیات عمومی/نماینده و ایجاد دوره باید مدرسهٔ حذف‌شده را نادیده بگیرند.
5. سابقهٔ `SchoolReserve`، پرداخت و تسویه دست‌نخورده می‌ماند؛ فقط امکان رزرو/ویرایش/نمایش در فهرست جاری از بین می‌رود.
6. دوره‌های وابسته نباید برای رزرو جدید قابل استفاده باشند؛ حذف فیزیکی یا حذف کورکورانهٔ آن‌ها انجام نمی‌شود.

### قرارداد پاسخ

```json
{
  "isSuccess": true,
  "code": 0,
  "messages": []
}
```

حالت‌های خطا:

| حالت | پاسخ مورد انتظار |
|---|---|
| مدرسه وجود ندارد یا قبلاً حذف شده | `isSuccess:false`، `NothingFound` |
| مدرسه متعلق به مرکز دیگری است | عدم افشای وجود رکورد؛ `NotFound` یا `AccessDenied` طبق قرارداد نهایی endpoint |
| token نامعتبر | `401` |
| کاربر companion فعال ندارد | `403` یا `NotFound` طبق guard کنترلر |

### سناریوهای تست قبل و بعد

| Test ID | سناریو | نتیجهٔ قبل از اصلاح | معیار قبولی بعد از اصلاح |
|---|---|---|---|
| SCH-DEL-01 | مالک مرکز، مدرسهٔ خودش را حذف می‌کند | endpoint وجود ندارد | پاسخ موفق و حذف شدن از `GET /api/Companion/School` |
| SCH-DEL-02 | همان مدرسه در جست‌وجوی عمومی | ممکن است دیده شود | در هیچ خروجی عمومی دیده نشود |
| SCH-DEL-03 | مرکز دیگر، id مدرسهٔ دیگری را حذف می‌کند | نامشخص/endpoint ندارد | بدون تغییر داده و خطای دسترسی |
| SCH-DEL-04 | مدرسه دارای دوره و ثبت‌نام پرداخت‌شده | حذف فیزیکی خطرناک است | سابقهٔ رزرو قابل خواندن، رزرو جدید ناممکن |

### تغییر UI

- در کارت مدرسه: منوی سه‌نقطه → «حذف مدرسه».
- dialog تأیید با متن روشن: «مدرسه از فهرست و رزرو جدید حذف می‌شود؛ سوابق رزرو پاک نمی‌شوند.»
- در زمان درخواست، دکمه disable و پس از موفقیت حذف optimistic فقط با امکان rollback در صورت خطا.
- امکان حذف را با «فعال/غیرفعال» یکی نکنید؛ فعال بودن یک وضعیت عملیاتی است، حذف آرشیو کسب‌وکاری است.

## 2. آیکون تماس با پشتیبانی در هدر

### یافتهٔ اولیه

backend فعلی endpoint عمومی `POST /api/ContactUs` و سیستم تیکت دارد، اما شمارهٔ تماس رسمی پشتیبانی در configهای موجود پیدا نشد. بنابراین هیچ شماره‌ای نباید hard-code یا حدس زده شود.

### طراحی پیشنهادی

- آیکون `support_agent` یا تلفن در هدر، کنار زنگوله و با tooltip «تماس با پشتیبانی پاستیل».
- با tap/click یک bottom sheet یا dialog باز شود؛ شمارهٔ رسمی، ساعات پاسخ‌گویی و دکمهٔ «تماس» نمایش داده شود.
- عمل تماس فقط بعد از تأیید کاربر با URI استاندارد انجام شود:

```text
tel:<official-support-number>
```

- اگر دستگاه امکان تماس ندارد، شماره قابل copy و CTA «ثبت تیکت» نمایش داده شود؛ صفحه نباید بی‌صدا هیچ‌کاری نکند.

### منبع شماره و قرارداد لازم

قبل از اجرا، کسب‌وکار باید شمارهٔ رسمی را تأیید کند. پیشنهاد فنی: مقدار از remote configuration یا endpoint تنظیمات عمومی بیاید تا برای تغییر شماره نیاز به انتشار اپ نباشد. تا وقتی API موجود نیست، مقدار build-time configuration با validation E.164/ایران و fallback «ثبت تیکت» قابل استفاده است.

## 3. خطا در حرکت از ویرایش خدمت به مرحلهٔ پکیج

### قراردادهای backend موجود

| عمل | endpoint | نکتهٔ امنیتی/داده‌ای |
|---|---|---|
| خواندن خدمت | `GET /api/Companion/CompanionAssistance/{id}` | باید متعلق به companion جاری باشد. |
| ویرایش خدمت | `PUT /api/Companion/CompanionAssistance` | سرور `Active=false` می‌گذارد تا بازبینی مجدد انجام شود. |
| خواندن پکیج | `GET /api/Companion/CompanionAssistancePackage/{id}` | پاسخ شامل `types` و اطلاعات service است. |
| فهرست پکیج‌ها | `GET /api/Companion/CompanionAssistancePackage?companionAssistanceId={id}` | فقط پکیج‌های حذف‌نشده را برمی‌گرداند. |
| ویرایش پکیج | `PUT /api/Companion/CompanionAssistancePackage` | مالکیت پکیج بررسی می‌شود؛ `companionAssistanceId` از رکورد موجود بازنویسی می‌شود. |

### فرضیه‌های قابل بررسی

1. wizard بعد از PUT خدمت، پاسخ `isSuccess:false` با HTTP 200 را مانند success می‌خواند یا برعکس.
2. `id` خدمت هنگام navigation از دست می‌رود و مرحلهٔ پکیج `companionAssistanceId=0/null` می‌فرستد.
3. بدنهٔ پکیج شامل `types` تکراری، قیمت منفی، `prePaymentPrice > price` یا mode نامعتبر است؛ سرور عمداً `InvalidData` برمی‌گرداند.
4. پس از ویرایش، `Active=false` شدن خدمت به‌اشتباه توسط اپ به معنی «خدمت/پکیج وجود ندارد» تفسیر می‌شود.
5. دادهٔ cache قبل از PUT با پاسخ جدید ادغام نشده و `companionAssistanceId` اشتباه به مرحلهٔ بعد می‌رود.

### دادهٔ لازم برای تشخیص قطعی

برای یک بار بازتولید، این چهار مورد باید همراه با زمان رخداد ثبت شوند (بدون token و اطلاعات شخصی):

- endpoint، method، request body و status HTTP مرحلهٔ PUT خدمت؛
- body پاسخ wrapper (`isSuccess`, `messages`, `data`)، حتی اگر HTTP 200 است؛
- endpoint و body اولین درخواست مرحلهٔ پکیج؛
- stack trace/UI error و نسخهٔ اپ.

### تست بازتولید و معیار قبولی

| Test ID | سناریو | معیار قبولی |
|---|---|---|
| SVC-PKG-01 | خدمت فعال با پکیج قدیمی، ویرایش متن خدمت → مرحلهٔ پکیج | بدون خطا و با همان `companionAssistanceId` وارد مرحلهٔ پکیج شود. |
| SVC-PKG-02 | خدمت دارای `types` چندگانه | هر نوع دقیقاً یک بار، `price>0` و `0≤prePayment≤price` ارسال شود. |
| SVC-PKG-03 | پاسخ business error با HTTP 200 | پیام `messages[0]` نمایش داده شود و navigation انجام نشود. |
| SVC-PKG-04 | پاسخ success و `active=false` | wizard ادامه یابد؛ وضعیت در انتظار بررسی فقط اطلاع‌رسانی شود. |
| SVC-PKG-05 | خروج و ورود مجدد به wizard | id از route/state پایدار و از URL/cache نامعتبر خوانده نشود. |

### اقدام رفع پس از بازتولید

ابتدا تست فرانت برای payload خطادار نوشته می‌شود. سپس یکی از این اصلاح‌ها، فقط مطابق trace واقعی، اعمال می‌شود: نگه‌داری ID در route state، اصلاح mapping DTO، نمایش business error، یا افزودن validation سمت UI پیش از فراخوانی. validation UI فقط برای تجربهٔ بهتر است و جای validation سرور را نمی‌گیرد.

## 4. badge تعداد رزروهای تکمیل‌نشده در bottom navigation

### تعریف لازم پیش از کدنویسی

واژهٔ «تکمیل‌نشده» باید برای همهٔ منابع یک تعریف صریح داشته باشد. پیشنهاد اولیه:

| نوع | تکمیل‌نشده به‌شمار می‌آید اگر |
|---|---|
| رزرو خدمت (`CompanionReserve`) | پرداخت/رزرو قطعی شده، لغو نشده و `DoneDate` ندارد. |
| رزرو مدرسه (`SchoolReserve`) | پرداخت‌شده و هنوز `Complete` نشده است. |
| رزرو پانسیون (`PansionReserve`) | در وضعیت نهایی/لغوشده نیست؛ enum نهایی باید از بک‌اند تعیین شود. |
| مشاوره آنلاین | فقط اگر قرار است در منوی «رزروها» دیده شود؛ وضعیت‌های Purchased/Paid/Active باید صریحاً تعیین شوند. |

### وضعیت API فعلی

- endpointهای جداگانهٔ فهرست وجود دارند: `CompanionReserve`، `SchoolReserve` و `PansionReserve`.
- endpoint یکپارچهٔ موجود فقط برای Admin است و کل رزروهای مورد نیاز پنل نماینده را پوشش نمی‌دهد.
- تعداد itemهای فهرست، جایگزین badge نیست: pagination، filter و تفاوت تعریف status نتیجهٔ نادرست می‌دهد.

### قرارداد پیشنهادی backend

```http
GET /api/Companion/ReserveSummary
Authorization: Bearer <companion-token>
```

```json
{
  "isSuccess": true,
  "data": {
    "incompleteCount": 7,
    "serviceIncompleteCount": 3,
    "schoolIncompleteCount": 2,
    "pansionIncompleteCount": 2,
    "generatedAt": "2026-10-01T10:00:00Z"
  }
}
```

مقادیر فقط از شناسهٔ مرکز استخراج‌شده از token محاسبه می‌شوند؛ `companionId` از query/body پذیرفته نمی‌شود. فرانت فقط `incompleteCount` را نمایش می‌دهد، جمعِ محلی از لیست‌ها ممنوع است.

### رفتار UI

- badge در بالای tab رزرو؛ `0` مخفی، `1..99` عدد، `99+` برای مقدار بزرگ‌تر.
- reload پس از ورود، برگشت از صفحهٔ جزئیات/تغییر وضعیت و pull-to-refresh.
- cache کوتاه (مثلاً 60 ثانیه) برای جلوگیری از درخواست پشت‌سرهم؛ منبع نهایی API است.
- در خطا، badge قبلی را به «صفر» تبدیل نکنید؛ آن را مخفی یا stale نگه دارید و retry کنترل‌شده داشته باشید.

## 5. بازکردن مسیریاب‌های نصب‌شده روی دستگاه

### تشخیص فنی

نمایش یا اجرای مسیریاب، مسئول backend نیست. سرور فقط latitude/longitude و آدرس مقصد را برمی‌گرداند. فهرست برنامه‌های نصب‌شده، permission و intent از طریق Android/iOS انجام می‌شود؛ API وب نمی‌تواند آن را به‌جای گوشی کشف کند.

### قرارداد ورودی موردنیاز در UI

پیش از بازکردن modal:

```ts
type RouteDestination = {
  latitude: number;
  longitude: number;
  title?: string;
  address?: string;
};
```

اگر هر کدام از مختصات نامعتبر/خالی است، modal providerها نمایش داده نشود و UI پیام «موقعیت مقصد کامل نیست» بدهد. آدرس متنی نباید به‌تنهایی جای مختصات را برای مسیریابی دقیق بگیرد.

### پیاده‌سازی پیشنهادی

| پلتفرم | رفتار درست |
|---|---|
| Android | ساخت geo URI (`geo:lat,lng?q=lat,lng(label)`) و `ACTION_VIEW`/chooser سیستم؛ سیستم فقط برنامه‌های سازگار نصب‌شده را نشان می‌دهد. |
| iOS | امکان enumerate عمومی همهٔ اپ‌های نصب‌شده وجود ندارد. providerهای پشتیبانی‌شده با `canOpenURL` بررسی و فقط همان‌ها نشان داده شوند؛ fallback به Apple Maps/نقشهٔ وب. |
| Flutter | wrapper واحد باید نتیجهٔ launch را برگرداند؛ tap ناموفق نباید silent fail باشد. برای Android از intent/chooser و برای iOS از URL schemeهای allow-list استفاده شود. |

### الزامات UI

- هر گزینهٔ modal باید `canLaunch`/بررسی provider داشته باشد؛ گزینهٔ غیرقابل اجرا نمایش داده نشود.
- tap موفق modal را می‌بندد؛ tap ناموفق پیام actionable و fallback «کپی آدرس»/«بازکردن نقشهٔ وب» می‌دهد.
- نام و مختصات مقصد URL-encode شوند؛ هیچ مختصاتی از دست کاربر ساخته یا round نشود.
- permission location برای **مقصد** لازم نیست؛ فقط برای مسیر از موقعیت فعلی، انتخاب کاربر و permission جداگانه لازم است.

## 6. مبلغ رزرو و جلوگیری از دوبارشماری پیش‌پرداخت

### یافتهٔ تأییدشده از backend

در رزرو خدمت (`CompanionReserve`) سرور هنگام ثبت رزرو، پس از quote کردن پکیج‌ها این مقادیر را ذخیره می‌کند:

```text
packagePrice    = مجموع قیمت پکیج‌ها × تعداد پت
prePaymentPrice = مجموع پیش‌پرداخت پکیج‌ها × تعداد پت
paymentPrice    = prePaymentPrice
```

بنابراین در لحظهٔ آغاز رزرو، `paymentPrice` و `prePaymentPrice` می‌توانند هر دو مثلاً `10,000,000` باشند، اما **دو مبلغ مستقل برای جمع‌زدن نیستند**. اولی مبلغ فعلی قابل پرداخت/ثبت‌شده در رکورد است و دومی quote پیش‌پرداخت است. نمایش هر دو با عنوان «پرداختی» یا جمع‌زدن آن‌ها، همان پیش‌پرداخت را دو بار نشان می‌دهد.

در پاسخ‌های فعلی رزرو همچنین `packagePrice`، `rebatePrice`، `walletPrice`، `operatorFinalPrice`، `paymentPrice`، `prePaymentPrice`، `companionShare` و `siteShare` وجود دارند. این نام‌ها برای نمایش مستقیم و عمومی کافی نیستند و UI را به محاسبهٔ محلی سوق می‌دهند.

### اصل قرارداد جدید

یک view مالیِ canonical باید فقط در backend ساخته شود و برای هر detail/list رزرو برگردد. نام‌های داخلی موجود برای backward compatibility می‌مانند، اما UI جدید فقط از بلوک زیر استفاده می‌کند:

```json
{
  "financial": {
    "currency": "IRR",
    "packageGrossAmount": 50000000,
    "discountAmount": 0,
    "payableNowAmount": 10000000,
    "paidAmount": 10000000,
    "outstandingAmount": 40000000,
    "petResanPayableAmount": 0,
    "totalPayableNowAmount": 10000000,
    "paymentState": "prepayment_paid"
  }
}
```

معنا:

| فیلد | تعریف server-side |
|---|---|
| `packageGrossAmount` | قیمت کل پکیج/خدمت قبل از تخفیف و مستقل از سفر پت‌رسان |
| `discountAmount` | مجموع تخفیف/ریبیت معتبر؛ هرگز از مبلغ پایه بیشتر نیست |
| `payableNowAmount` | فقط مبلغی که در مرحلهٔ فعلی باید پرداخت شود |
| `paidAmount` | مبلغ پرداخت موفق و ثبت‌شده؛ نه quote و نه مبلغ درخواست‌شدهٔ ناموفق |
| `outstandingAmount` | بدهی واقعی با فرمول server-side و کف صفر |
| `petResanPayableAmount` | فقط سهم سفر پت‌رسان، در صورت وجود و پرداخت جداگانه |
| `totalPayableNowAmount` | تنها عددی که UI در CTA پرداخت نشان می‌دهد |
| `paymentState` | وضعیت محدود و قابل نمایش مانند `unpaid`، `prepayment_paid`، `paid`، `cancelled` |

### قواعد اجرای backend

1. quote فقط از پکیج/نوع خدمت ذخیره‌شده در سرور و در یک transaction ساخته شود؛ `price` یا `prePaymentPrice` ارسالی کلاینت پذیرفته نشود.
2. callback پرداخت idempotent باشد؛ callback تکراری نباید `paidAmount`، سهم مرکز یا سهم سایت را دو بار تغییر دهد.
3. تغییر پکیج/تخفیف/کیف پول پس از شروع پرداخت فعال مسدود بماند؛ این guard اکنون در چند مسیر وجود دارد و باید یکپارچه شود.
4. سفر پت‌رسان یک financial component جداست؛ فقط `totalPayableNowAmount` سرور اجازهٔ نمایش جمع آن با رزرو را دارد.
5. مبالغ داخلی `double` در این مرحله تغییر schema نمی‌کنند، اما calculator جدید باید با `decimal` کار کند و در مرز DTO تبدیل کنترل‌شده داشته باشد. migration کامل مالی به `decimal` یک کار مستقل و پرریسک است.

- نمایش‌های فعلی `prePaymentPrice + paymentPrice` یا هر جمع client-side حذف شوند.
- کارت رزرو فقط labelهای مالی canonical را نشان دهد: «قیمت کل»، «پرداخت‌شده»، «مانده»، «مبلغ قابل پرداخت اکنون».
- تا زمان آماده‌شدن `financial`، fix موقت UI این است که `paymentPrice` و `prePaymentPrice` هرگز با هم جمع نشوند؛ اما اصلاح نهایی، استفادهٔ انحصاری از response canonical backend است.

## لاگ و دادهٔ لازم برای بازتولید واقعی

برای اینکه «مرحلهٔ تست» نتیجهٔ قابل استناد بدهد، برای هر رخداد این داده‌ها ثبت می‌شود:

| مورد | دادهٔ لازم | دادهٔ ممنوع در گزارش |
|---|---|---|
| ویرایش خدمت/پکیج | endpoint، method، sanitized request/response، `isSuccess`، `messages`، status، نسخهٔ اپ | Bearer token، refresh token، شماره/نام کاربر |
| مبلغ رزرو | `reserveId` تست، snapshot response مالی، callback test ID، زمان و status پرداخت | اطلاعات کارت، token درگاه، PII غیرلازم |
| مسیریابی | پلتفرم، نسخهٔ OS، providerهای قابل launch، مختصات تست | موقعیت واقعی کاربر در production |
| تماس پشتیبانی | platform، نتیجهٔ launch `tel:` | شمارهٔ شخصی کاربر |

## Definition of Done مشترک

یک مورد فقط وقتی «رفع‌شده» است که همهٔ شرط‌های زیر برقرار باشند:

- [ ] تست بازتولید قبل از اصلاح ثبت شده است.
- [ ] تست regression خودکار backend یا UI اضافه/به‌روز شده است.
- [ ] مالکیت و authorization در endpoint جدید بررسی می‌شود.
- [ ] پاسخ business error با HTTP 200 نیز در UI درست مدیریت می‌شود.
- [ ] در تغییرات مالی، کلاینت هیچ مبلغی را محاسبه نمی‌کند.
- [ ] تست پس از اصلاح روی دادهٔ تست و، برای native UI، روی دستگاه واقعی سبز است.
- [ ] قرارداد endpoint و تغییر رفتار در همین سند به‌روزرسانی می‌شود.
- [ ] تست‌های نامرتبط baseline دوباره گزارش می‌شوند و failure خارجی جدا نگه داشته می‌شود.
