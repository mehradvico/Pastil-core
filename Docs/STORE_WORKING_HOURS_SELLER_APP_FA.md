## ۱. خلاصه در یک نگاه

- فروشنده برای فروشگاهش **ساعت شروع و پایان کار** ثبت می‌کند.
- **خارج از این ساعت، گزینه‌ی «ارسال اکسپرس» به مشتری نمایش داده نمی‌شود** و اگر مشتری قبلاً انتخابش کرده باشد، هنگام انتخاب/پرداخت پذیرفته نمی‌شود.
- «ارسال با انتخاب روز و بازه» (میاره‌ی عادی) و بقیه‌ی روش‌های ارسال **هیچ تغییری نمی‌کنند**.
- اپ فقط دو درخواست لازم دارد:
  - `GET  api/Seller/StoreWorkingHour` ← خواندن
  - `PUT  api/Seller/StoreWorkingHour` ← ذخیره
- فروشگاه از **توکن کاربر** تشخیص داده می‌شود؛ `storeId` در آدرس یا بدنه **فرستاده نمی‌شود**.

## ۲. ساعت کاری دقیقاً چه کاری می‌کند

اکسپرس فقط وقتی به مشتری پیشنهاد می‌شود که **همه‌ی** شرط‌های زیر برقرار باشند (شرط‌های ۱ تا ۴ از قبل وجود داشتند، شرط ۵ جدید است):

| # | شرط | چه کسی تنظیم می‌کند |
|---|---|---|
| ۱ | کلید کلی اکسپرس روی سرور روشن باشد | تنظیمات سرور |
| ۲ | اکسپرس برای این فروشگاه فعال باشد (`expressShippingEnabled = true`) | فروشنده / ادمین |
| ۳ | ساعت فعلی داخل **بازه‌ی کلی اکسپرس** باشد (پیش‌فرض سرور: ۰۹:۰۰ تا ۲۰:۰۰) | تنظیمات سرور |
| ۴ | فاصله‌ی فروشگاه تا آدرس مشتری مجاز باشد و فروشگاه لوکیشن داشته باشد | خودکار |
| ۵ | **ساعت فعلی داخل ساعت کاری خودِ فروشگاه باشد** | **فروشنده (این مستند)** |

نکته‌ها:

- **همه‌ی ساعت‌ها به وقت تهران** هستند، مستقل از ساعت گوشی کاربر.
- بازه به شکل **[شروع، پایان)** است: ساعت شروع جزو ساعت کاری است، ساعت پایان نیست. مثال: «۰۹:۰۰ تا ۲۱:۰۰» یعنی ۲۰:۵۹ باز و ۲۱:۰۰ بسته.
- اگر فروشگاه **هیچ ساعت کاری ثبت نکرده باشد**، محدودیت روزانه ندارد و فقط شرط ۳ (بازه‌ی کلی سرور) اعمال می‌شود؛ یعنی رفتار قبل از این قابلیت.
- اگر ساعت کاری فروشگاه وسیع‌تر از بازه‌ی کلی سرور باشد، **بازه‌ی کلی برنده است**. مثال: فروشگاه ۰۸:۰۰ تا ۲۳:۰۰ ثبت کند و بازه‌ی کلی ۰۹:۰۰ تا ۲۰:۰۰ باشد ← اکسپرس عملاً ۰۹:۰۰ تا ۲۰:۰۰ فعال است. این را در UI به فروشنده بگویید (بخش ۶).

## ۳. مدل داده

API ساعت کاری را **برای هر روز هفته جداگانه** نگه می‌دارد (حداکثر یک بازه برای هر روز). پنل ادمین و پیشنهاد این مستند برای اپ، **یک بازه‌ی یکسان برای هر ۷ روز** است؛ یعنی اپ همان ساعت را برای ۷ روز می‌فرستد. (پشتیبانی روز به روز در API آماده است ولی فعلاً در UI لازم نیست؛ بخش ۹.)

### `StoreWorkingHourDto`

| فیلد | نوع | توضیح |
|---|---|---|
| `dayOfWeek` | `int` (۰ تا ۶) | روز هفته طبق `System.DayOfWeek` **.NET**: `0` = یکشنبه، `1` = دوشنبه، `2` = سه‌شنبه، `3` = چهارشنبه، `4` = پنج‌شنبه، `5` = جمعه، `6` = شنبه |
| `openTime` | `string` | ساعت شروع، دقیقاً با قالب `HH:mm` (۲۴ ساعته، دو رقمی، اعداد لاتین)؛ مثال `"09:00"` |
| `closeTime` | `string` | ساعت پایان با همان قالب؛ مثال `"21:00"` |

> ⚠️ دقت کنید: در .NET روز اول هفته **یکشنبه = ۰** است، نه شنبه. شنبه = `6`. ترتیب نمایش در اپ همان ترتیب ایرانی (شنبه تا جمعه) باشد ولی مقدار ارسالی طبق جدول بالا.

| روز (نمایش) | `dayOfWeek` |
|---|---|
| شنبه | 6 |
| یکشنبه | 0 |
| دوشنبه | 1 |
| سه‌شنبه | 2 |
| چهارشنبه | 3 |
| پنج‌شنبه | 4 |
| جمعه | 5 |

## ۴. Endpointها

همه‌ی درخواست‌ها با هدر معمول اپ:

```http
Authorization: Bearer {accessToken}
Accept-Language: fa
```

پاسخ‌ها مثل بقیه‌ی بک‌اند **همیشه HTTP 200** هستند با پوشه‌ی `{ isSuccess, code, messages, data }`. موفقیت را از `isSuccess` بخوانید، نه از کد HTTP. متن خطا در `messages[0].item1` است.

### ۴-۱) خواندن ساعت کاری

```http
GET api/Seller/StoreWorkingHour
```

پاسخ موفق — ساعت ثبت شده (ترتیب: شنبه اول):

```json
{
  "isSuccess": true,
  "code": 0,
  "messages": [],
  "data": [
    { "dayOfWeek": 6, "openTime": "09:00", "closeTime": "21:00" },
    { "dayOfWeek": 0, "openTime": "09:00", "closeTime": "21:00" },
    { "dayOfWeek": 1, "openTime": "09:00", "closeTime": "21:00" },
    { "dayOfWeek": 2, "openTime": "09:00", "closeTime": "21:00" },
    { "dayOfWeek": 3, "openTime": "09:00", "closeTime": "21:00" },
    { "dayOfWeek": 4, "openTime": "09:00", "closeTime": "21:00" },
    { "dayOfWeek": 5, "openTime": "09:00", "closeTime": "21:00" }
  ]
}
```

پاسخ موفق — هنوز ساعتی ثبت نشده (یعنی بدون محدودیت):

```json
{ "isSuccess": true, "code": 0, "messages": [], "data": [] }
```

### ۴-۲) ذخیره‌ی ساعت کاری

```http
PUT api/Seller/StoreWorkingHour
Content-Type: application/json
```

بدنه: **آرایه‌ی کامل هفته**. این درخواست **همه‌ی** ساعت‌های قبلی فروشگاه را پاک می‌کند و همین آرایه را جایگزین می‌کند (جزئی/patch نیست).

ثبت یک بازه برای همه‌ی روزها (حالت پیشنهادی):

```json
[
  { "dayOfWeek": 6, "openTime": "09:00", "closeTime": "21:00" },
  { "dayOfWeek": 0, "openTime": "09:00", "closeTime": "21:00" },
  { "dayOfWeek": 1, "openTime": "09:00", "closeTime": "21:00" },
  { "dayOfWeek": 2, "openTime": "09:00", "closeTime": "21:00" },
  { "dayOfWeek": 3, "openTime": "09:00", "closeTime": "21:00" },
  { "dayOfWeek": 4, "openTime": "09:00", "closeTime": "21:00" },
  { "dayOfWeek": 5, "openTime": "09:00", "closeTime": "21:00" }
]
```

حذف محدودیت (برگشت به «بدون محدودیت»):

```json
[]
```

پاسخ موفق:

```json
{ "isSuccess": true, "code": 0, "messages": [{ "item1": "با موفقیت انجام شد", "item2": "" }] }
```

بعد از ذخیره‌ی موفق، اپ می‌تواند `GET` را دوباره بزند تا مقدار ذخیره‌شده را نمایش دهد (اختیاری؛ ذخیره دقیقاً همان چیزی است که فرستادید).

## ۵. قوانین اعتبارسنجی و پیام خطاها

سرور کل آرایه را بررسی می‌کند و اگر **حتی یک آیتم** نامعتبر باشد، **هیچ چیز ذخیره نمی‌شود** (ساعت‌های قبلی دست‌نخورده می‌مانند).

| حالت | نتیجه |
|---|---|
| `openTime` یا `closeTime` خالی/بدون قالب `HH:mm` (مثلاً `"9:00"`، `"09:00:00"`، `"۰۹:۰۰"`) | خطا |
| `closeTime` مساوی یا قبل از `openTime` (مثلاً `22:00` تا `02:00`) | خطا — بازه‌ی شبانه‌روزی که از نیمه‌شب رد شود پشتیبانی **نمی‌شود** |
| `dayOfWeek` خارج از ۰ تا ۶ | خطا |
| یک روز دو بار در آرایه | خطا |
| کاربر به هیچ فروشگاهی وصل نیست | خطای دسترسی |

متن‌ها (در `messages[0].item1`، همان را به کاربر نشان دهید):

| موقعیت | `isSuccess` | متن |
|---|---|---|
| ساعت نامعتبر | `false` | ساعت کاری نامعتبر است؛ هر روز فقط یک بازه با ساعت شروع کمتر از پایان (HH:mm) ثبت کنید. |
| کاربر فروشگاه ندارد | `false` | شما به این بخش دسترسی ندارید |
| موفق | `true` | با موفقیت انجام شد |

> پیشنهاد: همین قوانین را **قبل از ارسال** در اپ هم چک کنید تا کاربر خطای سرور نبیند (بخش ۶-۴).

## ۶. طراحی صفحه در اپ

### ۶-۱) کجا قرار بگیرد

در **تنظیمات فروشگاه**، دقیقاً **زیر سوییچ «ارسال اکسپرس»** (همان سوییچی که در مستند اکسپرس بخش ۲ آمده). بخش ساعت کاری:

- فقط وقتی **اکسپرس روشن است** نمایش داده شود.
- اگر فروشنده اکسپرس را **خاموش** کند، بخش ساعت کاری پنهان شود (لازم نیست ساعت‌ها را پاک کنید؛ پنل ادمین موقع خاموش کردن اکسپرس ساعت‌ها را خالی می‌کند — اپ هم می‌تواند همین کار را بکند: هنگام ذخیره‌ی «اکسپرس خاموش»، `PUT` با `[]`).

### ۶-۲) اجزای صفحه (از بالا به پایین)

```
┌──────────────────────────────────────────────┐
│ ⚡ ارسال اکسپرس                    [ سوییچ ●] │
├──────────────────────────────────────────────┤
│ ساعت کاری فروشگاه                            │
│                                              │
│  شروع کار              پایان کار             │
│ ┌──────────────┐      ┌──────────────┐       │
│ │ 🕘   09:00    │      │ 🕘   21:00    │       │
│ └──────────────┘      └──────────────┘       │
│                                              │
│ ⓘ اکسپرس فقط در این ساعت به مشتری نمایش      │
│   داده می‌شود (به وقت تهران).                 │
│                                              │
│ [        ذخیره ساعت کاری        ]            │
└──────────────────────────────────────────────┘
```

1. **عنوان:** «ساعت کاری فروشگاه».
2. **دو فیلد کنار هم:** «شروع کار» و «پایان کار».
   - با لمس هر فیلد یک **Time Picker چرخ‌دار (Cupertino)** از پایین صفحه باز شود: ستون ساعت ۰۰ تا ۲۳ و ستون دقیقه (پیشنهاد: گام ۵ دقیقه، ۰۰ تا ۵۵)، دکمه‌های «انصراف» و «تأیید». (همان الگوی پنل ادمین.)
   - نمایش مقدار با اعداد فارسی مجاز است ولی **مقدار ارسالی حتماً لاتین و `HH:mm`** باشد.
   - ۲۴ ساعته؛ بدون ق.ظ/ب.ظ.
3. **یک خط راهنما** کوتاه زیر فیلدها (بالا).
4. **دکمه‌ی ذخیره** (اگر تنظیمات فروشگاه یک دکمه‌ی ذخیره‌ی کلی دارد، ساعت کاری را همان‌جا و بعد از ذخیره‌ی فروشگاه بفرستید؛ نیازی به دکمه‌ی جدا نیست).

### ۶-۳) مقدار اولیه

| پاسخ `GET` | مقدار نمایش‌داده‌شده |
|---|---|
| `data` خالی (`[]`) | پیش‌فرض **۰۹:۰۰** تا **۲۱:۰۰** (همان پیش‌فرض پنل) |
| `data` دارای آیتم | `openTime`/`closeTime` **اولین آیتم** |
| خطای شبکه | پیش‌فرض ۰۹:۰۰ تا ۲۱:۰۰ + پیام «دریافت ساعت کاری انجام نشد» و امکان تلاش دوباره |

### ۶-۴) ذخیره (منطق دقیق)

```text
اگر اکسپرس خاموش است:
    PUT [] (یا اصلاً نفرستید) — تمام
در غیر این صورت:
    اگر closeTime <= openTime:
        پیام: «ساعت پایان کار باید بعد از ساعت شروع باشد» و ارسال نکنید
    body = برای هر dayOfWeek در [6,0,1,2,3,4,5]:
               { dayOfWeek, openTime, closeTime }
    PUT api/Seller/StoreWorkingHour  body
    اگر isSuccess == false: messages[0].item1 را نشان دهید
    اگر موفق: اسنک‌بار «ساعت کاری ذخیره شد»
```

مقایسه‌ی `closeTime <= openTime` با رشته‌ی `HH:mm` درست کار می‌کند (چون صفر سمت چپ دارند)؛ یا به دقیقه تبدیل کنید.

### ۶-۵) حالت‌های UI

| حالت | رفتار |
|---|---|
| در حال دریافت | به‌جای دو فیلد، اسکلتون/لودر کوچک |
| در حال ذخیره | دکمه غیرفعال + لودر داخل دکمه |
| خطای ذخیره | متن `messages[0].item1` در اسنک‌بار؛ مقادیر فرم حفظ شود |
| دسترسی ندارد (`isSuccess=false` در GET) | بخش ساعت کاری را مخفی کنید |

### ۶-۶) دسترس‌پذیری

- هر فیلد زمان یک برچسب خوانا برای TalkBack/VoiceOver داشته باشد: «شروع کار، ۰۹:۰۰».
- ناحیه‌ی لمس فیلدها و دکمه‌ها حداقل ۴۴×۴۴.

## ۸. رفتار سمت مشتری

(برای اطلاع؛ اپ نماینده لازم نیست کاری انجام دهد.)

- در مرحله‌ی «اطلاعات ارسال»، اگر فروشگاه طبق ساعت کاری‌اش **بسته** باشد، گزینه‌ی «ارسال اکسپرس» **در لیست روش‌ها نمی‌آید**؛ «ارسال با میاره (انتخاب روز و بازه)» مثل قبل می‌آید.
- اگر مشتری اکسپرس را انتخاب کرده باشد و تا لحظه‌ی انتخاب/پرداخت ساعت کاری تمام شده باشد، پیام زیر را می‌گیرد و باید روش دیگری انتخاب کند:
  «ارسال اکسپرس در حال حاضر در دسترس نیست (خارج از ساعت کاری یا غیرفعال است). ارسال با انتخاب روز را انتخاب کنید.»
- نشان «⚡ ارسال اکسپرس» روی کارت محصولات فقط به فعال بودن اکسپرسِ فروشگاه بستگی دارد، نه به ساعت فعلی.
- سفارش‌های اکسپرسی که **قبلاً پرداخت شده‌اند** تحت تأثیر تغییر ساعت کاری قرار **نمی‌گیرند**؛ فروشنده همچنان باید «درخواست پیک» بزند.

## ۹. نکات و موارد مرزی

- **ساعت شبانه (عبور از نیمه‌شب)** پشتیبانی نمی‌شود: `22:00` تا `02:00` خطا می‌دهد. اگر لازم شد، اطلاع دهید.
- **روزهای تعطیل جداگانه:** API از آن پشتیبانی می‌کند — کافی است روز تعطیل را **در آرایه نفرستید** (مثلاً فقط ۶ روز بدون جمعه). در آن صورت در روز نفرستاده‌شده اکسپرس ارائه نمی‌شود. ⚠️ در حال حاضر پنل ادمین فقط «یک بازه برای همه‌ی روزها» را نمایش و ذخیره می‌کند؛ اگر اپ روزها را جدا ذخیره کند و بعد ادمین در پنل فروشگاه را ذخیره کند، همه‌ی روزها یکسان می‌شوند. پس فعلاً همان «یک بازه برای ۷ روز» را پیاده کنید.
- **خالی کردن ساعت‌ها** (`PUT []`) یعنی بدون محدودیت روزانه، نه «همیشه بسته».
- **تغییر ساعت فوراً اعمال می‌شود**؛ کش ندارد.
- `storeId` از توکن خوانده می‌شود؛ اگر کاربر چند فروشگاه دارد، فروشگاهی که سرور برای توکن برمی‌گرداند (همان فروشگاهی که بقیه‌ی `api/Seller/*` با آن کار می‌کنند) ملاک است.
- ساعت گوشی کاربر اهمیتی ندارد؛ فقط ساعت سرور به وقت تهران.

## ۱۰. چک‌لیست پیاده‌سازی و تست

پیاده‌سازی:

1. [ ] بخش «ساعت کاری فروشگاه» زیر سوییچ اکسپرس، فقط وقتی اکسپرس روشن است.
2. [ ] `GET api/Seller/StoreWorkingHour` هنگام باز شدن تنظیمات فروشگاه؛ پیش‌فرض ۰۹:۰۰–۲۱:۰۰ وقتی خالی است.
3. [ ] Time Picker چرخ‌دار ۲۴ ساعته برای هر دو فیلد؛ خروجی `HH:mm` لاتین.
4. [ ] اعتبارسنجی محلی `closeTime > openTime` قبل از ارسال.
5. [ ] `PUT` با آرایه‌ی ۷ روزه (`dayOfWeek` طبق جدول بخش ۳)؛ با خاموش شدن اکسپرس `PUT []`.
6. [ ] نمایش `messages[0].item1` در خطا؛ اسنک‌بار موفقیت.

تست:

1. [ ] فروشگاه بدون ساعت: GET خالی ← فرم ۰۹:۰۰–۲۱:۰۰ نشان می‌دهد.
2. [ ] ذخیره ۱۰:۰۰–۱۸:۰۰ ← GET دوباره ۷ آیتم با همین ساعت برمی‌گرداند (شنبه اول).
3. [ ] ذخیره ۱۸:۰۰–۱۰:۰۰ ← خطای محلی، هیچ درخواستی ارسال نمی‌شود.
4. [ ] ارسال دستی `"9:00"` (بدون صفر) ← خطای «ساعت کاری نامعتبر است…» و ساعت قبلی دست‌نخورده.
5. [ ] خاموش کردن اکسپرس ← بخش پنهان، GET بعدی خالی.
6. [ ] با حساب مشتری در وب‌اپ: داخل ساعت کاری گزینه‌ی اکسپرس دیده شود، بعد از ساعت پایان دیده نشود.
7. [ ] کاربر بدون فروشگاه ← GET با `isSuccess=false` و بخش مخفی.
