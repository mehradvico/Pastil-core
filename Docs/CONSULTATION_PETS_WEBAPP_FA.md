# انتخاب پت هنگام خرید مشاوره‌ی آنلاین — راهنمای وب‌اپ (مشتری)

**مخاطب:** توسعه‌دهنده‌ی وب‌اپ مشتری (و اپ موبایل مشتری، اگر همین API را صدا می‌زند)
**تاریخ:** ۱۴۰۵/۰۸/۰۵ (2026-10-27)
**وضعیت بک‌اند:** کد و تست آماده است، ولی **هنوز روی سرور دیپلوی نشده**. مایگریشن `ConsultationPurchasePets` باید اول روی دیتابیس اجرا شود (اسکریپت: `backend/scripts/ConsultationPurchasePets.sql`)، بعد Api دیپلوی شود.

> **هشدار مهم:** از لحظه‌ی دیپلوی این نسخه، خرید مشاوره **بدون انتخاب پت رد می‌شود**. وب‌اپ باید **قبل یا هم‌زمان** با دیپلوی بک‌اند آپدیت شود، وگرنه دکمه‌ی خرید مشاوره برای همه‌ی کاربران خطا می‌دهد.

---

## ۱) چه چیزی عوض شد
تا امروز مشتری مشاوره‌ی آنلاین (کلینیک، مربی یا نمایندگی) را «برای خودش» می‌خرید و نماینده نمی‌دانست مشاوره درباره‌ی کدام پت است.

از این نسخه:
1. مشتری هنگام خرید باید **حداقل ۱ و حداکثر ۵ پت** از پت‌های خودش انتخاب کند.
2. پت‌های انتخاب‌شده به خرید وصل می‌شوند و کلینیک/مربی **پروفایل و سابقه‌ی پزشکی همین پت‌ها** را می‌بیند (نه همه‌ی پت‌های کاربر).
3. در «مشاوره‌های من» و جزئیات هر خرید، فهرست پت‌های آن مشاوره برمی‌گردد.

این قاعده برای **همه‌ی پکیج‌های مشاوره** است: فوری و نوبت‌دار (Bookable)، کلینیک، مربی و نمایندگی.

---

## ۲) تغییر در درخواست خرید

**اندپوینت (بدون تغییر):** `POST /api/EndUser/ConsultationPurchase`

**فیلد جدید و الزامی در بدنه:**

| فیلد | نوع | الزامی | توضیح |
|---|---|---|---|
| `userPetIds` | `long[]` | **بله** | شناسه‌ی `UserPet` پت‌های خود کاربر. حداقل ۱، حداکثر ۵. تکراری‌ها خودکار حذف می‌شوند. |

بقیه‌ی فیلدها (`packageId`، `fromWallet`، `merchantId`، `rebateCode`، `scheduledStart`) دقیقاً مثل قبل‌اند.

نمونه:

```json
{
  "packageId": 42,
  "fromWallet": false,
  "merchantId": 1,
  "rebateCode": null,
  "scheduledStart": null,
  "userPetIds": [1017, 1020]
}
```

### پاسخ‌های خطای جدید
پاسخ مثل همه‌ی API‌ها HTTP 200 با `isSuccess = false` است؛ پیام را از `messages[0]` نشان دهید.

| حالت | پیام (فارسی، از سرور) |
|---|---|
| `userPetIds` خالی/نامعتبر یا بیش از ۵ پت | «حداقل یک پت را برای مشاوره انتخاب کنید (حداکثر ۵ پت).» |
| یکی از پت‌ها مال کاربر نیست یا حذف شده | «پت انتخاب‌شده متعلق به شما نیست یا حذف شده است.» |

ترتیب بررسی در سرور: اعتبار پکیج ← نوبت/آنلاین بودن نماینده ← کاربر ← **پت‌ها** ← تخفیف و پرداخت. پس خطای پت قبل از رفتن به درگاه برمی‌گردد و هیچ پولی کم نمی‌شود.

---

## ۳) فهرست پت‌های کاربر برای انتخاب
از همان اندپوینت فعلی پت‌های کاربر استفاده کنید (چیز جدیدی اضافه نشده):

`GET /api/EndUser/UserPet` (پت‌های کاربر جاری)

- فقط پت‌های **حذف‌نشده** را نمایش دهید؛ سرور پت حذف‌شده را رد می‌کند.
- از هر آیتم `id` را در `userPetIds` بفرستید.

---

## ۴) تغییر در پاسخ «مشاوره‌های من» و جزئیات خرید

| اندپوینت |
|---|
| `GET /api/EndUser/ConsultationPurchase` (فهرست) |
| `GET /api/EndUser/ConsultationPurchase/{id}` (جزئیات) |

به هر آیتم فیلد `pets` اضافه شده:

| فیلد | نوع | توضیح |
|---|---|---|
| `pets` | `array` | پت‌های این مشاوره. برای خریدهای **قبل از این نسخه** آرایه‌ی خالی `[]` است. |
| `pets[].userPetId` | `long` | شناسه‌ی پت کاربر |
| `pets[].name` | `string` | اسم پت (مثلاً «رکس») |
| `pets[].petName` | `string` | نوع حیوان (سگ، گربه، …) |
| `pets[].pictureUrl` | `string \| null` | آدرس نسبی عکس روی سرور فایل (مثل بقیه‌ی تصاویر، با آدرس سرور فایل ترکیب شود) |

نمونه:

```json
{
  "id": 9252,
  "purchaseCode": "CNS-20261026-1253-9252",
  "packageName": "مشاوره رفتاری",
  "status": 2,
  "pets": [
    { "userPetId": 1017, "name": "رکس", "petName": "سگ", "pictureUrl": "Pictures/2026/10/abc.jpg" }
  ]
}
```

## ۵) رابط کاربری پیشنهادی (UX)
1. در صفحه‌ی پکیج، **قبل از** دکمه‌ی پرداخت یک بخش «این مشاوره برای کدام پت است؟» بگذارید.
2. پت‌های کاربر به‌صورت کارت قابل‌انتخاب (چندانتخابی) با عکس، اسم و نوع نمایش داده شوند.
3. اگر کاربر **فقط یک پت** دارد، همان را پیش‌فرض انتخاب کنید.
4. اگر کاربر **هیچ پتی ندارد**، دکمه‌ی خرید غیرفعال باشد و لینک «افزودن پت» نمایش داده شود؛ بعد از افزودن، به همین صفحه برگردد.
5. بعد از انتخاب ۵ پت، بقیه‌ی کارت‌ها غیرفعال شوند و پیام «حداکثر ۵ پت» نمایش داده شود.
6. یک خط توضیح: «کلینیک/مربی پروفایل و سابقه‌ی پزشکی پت‌های انتخاب‌شده را می‌بیند.»
7. در «مشاوره‌های من» و صفحه‌ی جزئیات، عکس و اسم پت‌ها را زیر نام پکیج نشان دهید. اگر `pets` خالی بود (خرید قدیمی)، چیزی نمایش ندهید.

---

## ۶) سازگاری و ترتیب انتشار
- این تغییر **شکستن قرارداد** (breaking) است: نسخه‌ی قدیمی وب‌اپ که `userPetIds` نمی‌فرستد، بعد از دیپلوی دیگر نمی‌تواند مشاوره بخرد.
- ترتیب پیشنهادی: ۱) آماده‌کردن وب‌اپ با فرستادن `userPetIds` (فرستادن این فیلد قبل از دیپلوی بک‌اند بی‌ضرر است و نادیده گرفته می‌شود) ← ۲) اجرای اسکریپت دیتابیس ← ۳) دیپلوی Api ← ۴) انتشار وب‌اپ.
- فیلد `pets` در پاسخ را **اختیاری** در نظر بگیرید (قبل از دیپلوی نمی‌آید).

---

## ۷) چک‌لیست تست
- [ ] خرید با یک پت ← موفق؛ در «مشاوره‌های من» همان پت دیده می‌شود.
- [ ] خرید با دو پت ← موفق؛ هر دو دیده می‌شوند.
- [ ] خرید بدون پت ← خطای «حداقل یک پت…» و رفتن به درگاه اتفاق نمی‌افتد.
- [ ] خرید با ۶ پت ← همان خطا (UI هم نباید اجازه بدهد).
- [ ] خرید با شناسه‌ی پت کاربر دیگر ← خطای «پت انتخاب‌شده متعلق به شما نیست…».
- [ ] پکیج نوبت‌دار (Bookable) با `scheduledStart` و پت ← موفق.
- [ ] خرید قدیمی در «مشاوره‌های من» ← `pets` خالی و UI بدون خطا.
