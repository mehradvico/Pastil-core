# مستند اپ نماینده: پرونده و سوابق پزشکی پت

**مخاطب:** اپ نماینده / نیروی ارائه‌دهندهٔ خدمت پاستیل  
**Scope:** مشاهدهٔ اطلاعات پزشکی پت در رزروِ متعلق به مرکز و ثبت timeline سابقهٔ پزشکی توسط نماینده.

> API فعلی «پروندهٔ پزشکی ساختاریافته» نیست. اطلاعات بالینی جاری در `UserPet` نگهداری می‌شود و `UserPetRecord` فقط یک یادداشت تاریخچهٔ بدون ویرایش است. در UI آن را «سوابق ثبت‌شده» بنامید، نه نسخه یا پروندهٔ درمانی کامل.

---

## 1. مدل داده و سطح دسترسی

### 1.1 اطلاعات پزشکی جاری پت

در جزئیات رزروِ مرکز، هر `UserPet` این داده‌های relevant را دارد:

| فیلد | معنی | رفتار نماینده |
| --- | --- | --- |
| `id` | شناسهٔ پت کاربر (`userPetId`) | کلید ثبت و فیلتر سابقه |
| `name`، `pet`، `petBreed`، `birthday`، `weight`، `isMale`، `isSterile` | مشخصات پایه | فقط نمایش |
| `specificDisease` | بیماری خاص ثبت‌شده توسط صاحب پت | فقط نمایش؛ خالی‌بودن یعنی بیماری خاصی ثبت نشده، نه تأیید سلامت پزشکی |
| `specificMedicene` | دارو/درمان ثبت‌شده توسط صاحب پت؛ املای API فعلی همین است | فقط نمایش |
| `microChipCode` | شمارهٔ میکروچیپ | حساس؛ فقط در صفحهٔ پرونده و نه فهرست عمومی |
| `userPetRecords` | خلاصهٔ سوابق | ممکن است در پاسخ جزئیات رزرو موجود نباشد؛ برای history روی endpoint اختصاصی تکیه کنید |

نماینده نباید این مقادیر را از اپ نماینده تغییر دهد: endpoint ویرایش `UserPet` برای نماینده وجود ندارد. اگر بیماری یا داروی جاری اشتباه است، باید از مسیر مالک پت اصلاح شود؛ نماینده می‌تواند صرفاً یک سابقهٔ جدید با توضیح وضعیت مشاهده‌شده ثبت کند.

### 1.2 منبع پرونده برای نماینده

پت را از جزئیات رزروی باز کنید که متعلق به مرکز کاربر است:

```http
GET /api/Companion/CompanionReserve/{reserveId}
```

از آرایهٔ `userPets` در پاسخ، `userPetId` و اطلاعات پزشکی جاری را بردارید. پاسخ فقط وقتی برای نماینده قابل‌اعتماد است که همان center/companion در scope توکن باشد؛ `reserveId` را از deep link یا ورودی آزاد بدون دریافت مجدد جزئیات، معتبر فرض نکنید.

---

## 2. محدودیت مجوزِ ثبت سابقه

ثبت سابقه فقط از route زیر انجام می‌شود:

```http
POST /api/Operator/UserPetRecord
```

server، `operatorId` را از توکن جایگزین می‌کند و پیش از ثبت بررسی می‌کند که برای همان `userPetId` یک **رزرو خدمات (`CompanionReserve`) فعال و لغونشده** وجود داشته باشد و یکی از شروط زیر برقرار باشد:

1. کاربر جاری نیروی فعال تخصیص‌داده‌شده به همان رزرو باشد؛ یا
2. کاربر جاری مالک مرکز ارائه‌دهندهٔ خدمت باشد.

در غیر این صورت پاسخ ناموفق با `AccessDenied` است. `operatorId`، `userId`، `reserveId` یا شناسهٔ نمایندهٔ دلخواه را در payload نفرستید/به آن‌ها تکیه نکنید.

### محدودیت مهم برای پانسیون

بررسی مجوز فعلی فقط `CompanionReserve` را بررسی می‌کند، **نه `PansionReserve`**. بنابراین نماینده‌ای که فقط رزرو پانسیونِ پت را دارد، با API فعلی نمی‌تواند سابقهٔ پزشکی ثبت کند و باید خطای دسترسی را نمایش دهد. اگر ثبت پرونده برای اقامت پانسیون هم لازم است، توسعهٔ backend جداگانه لازم است؛ اپ نباید با دورزدن یا جعل شناسه تلاش کند آن را حل کند.

## 3. مشاهدهٔ سوابقی که خود نماینده ثبت کرده است

```http
GET /api/Operator/UserPetRecord?UserPetId={userPetId}&PageIndex=1&PageSize=30&SortBy=New
GET /api/Operator/UserPetRecord/{recordId}
```

Backend در list، `operatorId` را اجباری از توکن کاربر جاری قرار می‌دهد. در نتیجه:

- نماینده فقط یادداشت‌هایی را می‌بیند که **خودش** ثبت کرده است؛
- سوابق ثبت‌شده توسط نماینده یا مرکز دیگر در این endpoint در دسترس نیست؛
- `GET /{recordId}` نیز اگر `operatorId` رکورد با کاربر جاری یکی نباشد، `AccessDenied` می‌دهد؛
- فیلتر `UserPetId` برای صفحهٔ پرونده الزامی است؛ pagination را از پاسخ API نگه دارید.

هر item حداقل شامل این‌هاست:

```ts
type UserPetRecord = {
  id: number
  name: string             // متن اصلی سابقه
  userPetId: number
  operatorId: number
  createDate: string       // زمان server؛ قابل انتخاب توسط کاربر نیست
  userPet?: object
  operator?: { id: number; firstName?: string; lastName?: string }
}
```

در UI، `createDate` را مبنای ترتیب بگذارید و با نام نماینده نمایش دهید. کاربر نباید بتواند تاریخ رخداد درمانی را جدا از زمان ثبت وارد کند، چون چنین فیلدی در API وجود ندارد.

## 4. ثبت سابقهٔ جدید

### 4.1 قرارداد API

```http
POST /api/Operator/UserPetRecord
Content-Type: application/json
Authorization: Bearer {accessToken}
```

```json
{
  "name": "معاینه اولیه: بی‌حالی مشاهده شد؛ مالک برای مراجعه به دامپزشک مطلع شد.",
  "userPetId": 981,
  "operatorId": 0
}
```

`operatorId` در body اختیاریِ عملی نیست؛ مقدار نهایی همیشه از token می‌آید. برای جلوگیری از ابهام، اپ می‌تواند آن را کلاً نفرستد:

```json
{
  "name": "پیگیری درمان: مصرف داروی اعلام‌شده توسط مالک بررسی شد.",
  "userPetId": 981
}
```

در پاسخ موفق، ID و `createDate` ثبت‌شده را از server بگیرید؛ سپس `GET /api/Operator/UserPetRecord?UserPetId=981...` را refresh کنید.

### 4.2 قواعد فرم

| موضوع | الزام UI |
| --- | --- |
| متن سابقه (`name`) | اجباری، trim‌شده، خالی نبودن؛ متن را مستقیم و قابل‌فهم بنویسید. |
| پت | فقط از `userPets` در رزرو جاری انتخاب شود؛ شناسه دستی یا جست‌وجوی عمومی پت نداشته باشید. |
| ثبت‌کننده و زمان | readonly؛ server تعیین می‌کند. |
| تکرار ارسال | دکمهٔ ثبت تا دریافت پاسخ disable باشد. در timeout، ابتدا list همان پت را refresh کنید و متن/زمان تقریبی را جست‌وجو کنید؛ API فعلی `Idempotency-Key` ندارد. |
| خطای دسترسی | پیام «برای ثبت سابقه باید روی یک رزرو فعالِ همین پت مجاز باشید» نمایش دهید؛ متن را محلی به ثبت نهایی‌شده تبدیل نکنید. |

### الگوی پیشنهادی متن

چون API فقط یک فیلد متن دارد، اپ یک ساختار نوشتاری ثابت پیشنهاد دهد، اما آن را به payloadهای فیک تبدیل نکند:

```text
[نوع رخداد] — [مشاهده/اقدام] — [نتیجه یا اقدام بعدی]

مثال:
معاینه — کاهش اشتها از صبح گزارش شد — مالک مطلع شد؛ ارجاع دامپزشکی پیشنهاد شد.
دارو — مصرف داروی اعلام‌شده توسط مالک بررسی شد — مورد غیرعادی مشاهده نشد.
واکسن — کارت واکسیناسیون مشاهده شد — تاریخ بعدی در پروندهٔ مالک ثبت است.
```

از ثبت تشخیص قطعی، مقدار دارو، اطلاعات مالی، اطلاعات کارت بانکی، رمز، کدمل یا جزئیات غیرضروری مالک در این متن خودداری کنید. این سابقه جایگزین نظر دامپزشک یا نسخهٔ درمانی نیست.

## 5. append-only بودن سوابق

در Area `Operator` فقط `GET` و `POST` برای `UserPetRecord` وجود دارد؛ endpoint `PUT` یا `DELETE` در اختیار نماینده نیست.

پس در تجربهٔ کاربر:

- برای رکورد ثبت‌شده دکمهٔ «ویرایش» یا «حذف» نسازید؛
- اگر متن اشتباه بود، یک سابقهٔ اصلاحی تازه ثبت کنید، مثلاً: «اصلاح سابقهٔ {تاریخ}: ...»؛
- در صفحهٔ list باید badge «ثبت‌شده / غیرقابل‌ویرایش» نشان داده شود؛
- draft محلیِ ارسال‌نشده را می‌توان ویرایش یا پاک کرد، ولی پس از پاسخ موفق server، دیگر آن را optimistic mutate نکنید.

این محدودیت به audit trail کمک می‌کند، اما API فعلی هیچ فیلد `amendsRecordId` ندارد؛ ارتباط سابقهٔ اصلاحی با رکورد قبلی فقط در متن ثبت می‌شود.

## 6. جریان پیشنهادی UI

```text
فهرست/جزئیات رزرو مجاز مرکز
  → انتخاب پت از userPets
  → نمایش اطلاعات پزشکی جاری (بیماری، دارو، مشخصات ضروری)
  → GET سوابق خود نماینده با userPetId
  → «ثبت سابقه» فقط برای رزرو خدمات فعال و پتِ همان رزرو
  → POST سابقه
  → refresh list و نمایش زمان server
```

state حداقلی:

```ts
type PetMedicalRecordScreenState = {
  reserveId: number
  userPetId: number
  petName: string
  specificDisease?: string | null
  specificMedicene?: string | null
  records: UserPetRecord[]
  nextPage?: number
  isEligibleToRecord?: boolean // از context رزرو؛ server authority نهایی است
  isSubmitting: boolean
}
```

در بازگشت از background، ورود دوباره به صفحه یا پس از ثبت نامعلوم، اطلاعات پزشکی و سوابق را refresh کنید. medical data را در notification، crash log، analytics، deep-link، clipboard یا cache دائمی ذخیره نکنید. cache حافظهٔ کوتاه‌عمر باید با خروج از حساب پاک شود.

## 7. چک‌لیست QA اپ نماینده

- [ ] پرونده فقط از جزئیات رزرو همان مرکز باز می‌شود و `userPetId` از `userPets` پاسخ گرفته می‌شود.
- [ ] بیماری و داروی جاری readonly هستند؛ اپ نماینده آن‌ها را به‌روزرسانی نمی‌کند.
- [ ] list سابقه با route `Operator` و فیلتر `UserPetId` صدا زده می‌شود و فقط سوابق خود کاربر را نشان می‌دهد.
- [ ] POST مقدار `operatorId` را از UI نمی‌پذیرد و server authority است.
- [ ] نمایندهٔ فاقد رزرو فعال یا نماینده‌ای که فقط رزرو پانسیون دارد، خطای AccessDenied قابل‌فهم می‌بیند.
- [ ] دکمهٔ ثبت در زمان request disable است و recovery timeout با refresh انجام می‌شود.
- [ ] پس از ثبت موفق edit/delete ارائه نمی‌شود و اصلاح با رکورد جدید انجام می‌گیرد.
- [ ] متن‌های پزشکی و داده‌های حساس پت/مالک در log، analytics، push یا deep link قرار نمی‌گیرند.

**وضعیت سند:** منطبق با backend فعلی پاستیل در ۲۱ سپتامبر ۲۰۲۶.
