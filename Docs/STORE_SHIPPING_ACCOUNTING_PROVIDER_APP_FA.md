# تفکیک سهم کالا، کمیسیون و ارسال فروشگاه — قرارداد اپ نماینده

تاریخ: ۲۰۲۶-۱۱-۱۸. تغییر در سورس بک‌اند و پنل ادمین انجام شده؛ انتشار برنامه روی سرور انجام نشده است. با درخواست صریح مالک پروژه، سهم ۴ سفارش قبلی در دیتابیس اصلی اصلاح و دوباره کنترل شد: ۱٬۱۵۲٬۳۰۰ تومان از سهم فروشگاه به سهم پاستیل منتقل شد، بدون تغییر پرداخت مشتری یا تخفیف‌ها. اپ Flutter نماینده در این تسک تغییر نکرده و این سند تحویل تیم اپ است. این سند در موضوع سهم ارسال بر فرمول‌های قدیمی `PASTIL_FUNDED_DISCOUNT_FA.md` و مستند قیمت‌گذاری مقدم است.

## ۱. تصمیم قطعی حسابداری

کالا متعلق به فروشگاه است و پاستیل کمیسیون کالا را از آن کم می‌کند. **کل هزینه ارسالِ پیش‌پرداخت سهم پاستیل است؛ فروشگاه هیچ سهمی از آن ندارد و روی خودِ ارسال کمیسیون محاسبه نمی‌شود.** این مبلغ دریافتی پاستیل است؛ هزینه‌ای که پاستیل بعداً به پیک می‌دهد با «سود خالص پاستیل» یکی نیست و در این تغییر محاسبه نمی‌شود.

تمام مبلغ‌های این قرارداد **تومان** هستند، از جمله ارسال. تبدیل تومان/ریال برای درگاه موضوع این صفحه نیست. درصد ۱۰ یعنی ۱۰٪، نه ۰٫۱. اپ مبلغ‌ها را دوباره محاسبه یا گرد نکند؛ عدد پاسخ سرور مرجع است. برای نمایش از جداکننده هزارگان و واحد «تومان» استفاده شود؛ مبلغ منفی به صفر تبدیل نشود.

## ۲. فرمول دقیق

برای هر `ProductOrderStore` فعال:

```text
P = ProductOrderStore.PaymentPrice
D = ProductOrderStore.DeliveryPrice
F = SUM(PastilDiscountUnit × Count) برای آیتم غیرحذف‌شده با Count > 0
C = Store.CommissionPercent

goodsPrice          = P − D
commissionBase      = goodsPrice + F
commissionAmount    = commissionBase × C / 100
storeShare          = commissionBase − commissionAmount
netCommissionAmount = commissionAmount − F
siteShare           = netCommissionAmount + D
storeShare + siteShare = P
```

`goodsPrice` قیمت کالا بعد از تخفیف‌های محصول است. تخفیف خود فروشگاه پیش از این مرحله قیمت کالا را کاهش داده؛ `F` فقط تخفیف تأمین‌شده توسط پاستیل است و برای حفظ طلب فروشگاه به مبنای کمیسیون برمی‌گردد. `F` یک‌بار از کمیسیون پاستیل کم می‌شود. آن را دوباره از فروشگاه یا ارسال کم نکنید. شناسه/نرخ فعلی کالا را برای بازسازی تخفیف سفارش قدیمی به کار نبرید؛ snapshot آیتم سفارش مرجع تخفیف است.

**کد تخفیف سفارش و مزیت ارسال باشگاه:** قرارداد قبلی حفظ شده: `P` قبل از `RebatePrice` و `ClubDeliveryDiscount` است ولی `ProductOrder.PaymentPrice` پرداخت واقعی مشتری بعد از آن‌هاست. بنابراین در این موارد `storeShare + siteShare` لزوماً با `paymentPrice` ردیف گزارش برابر نیست؛ اختلاف، هزینه این مزایا با پاستیل است. `siteShare` سهم ثبت‌شده پیش از این دو هزینه است، نه سود/وجه خالص بعد از همه هزینه‌ها. اپ نباید این اختلاف را به فروشگاه تحمیل کند یا برای رفع آن سهم‌ها را دوباره محاسبه کند.

در سطح سفارش چندفروشگاهی، سهم‌ها جمع ردیف‌های فروشگاه‌ها هستند. مسیر جاری checkout یک فروشگاه فعال را ثبت می‌کند؛ محدودیت سفارش‌های قدیمی مشترک در بخش ۷ آمده است.

## ۴. API اپ نماینده

```http
GET /api/Seller/FinanceStore
Authorization: Bearer <access-token>
Accept-Language: fa
```

پارامترهای اختیاری: `Permitted=true|false` (نبودنش = همه)، `UserDelivery=0|1|2` (نبودنش = همه؛ ۰ منتظر پاسخ در وضعیت ارسال، ۱ تحویل‌گرفته، ۲ تحویل‌نگرفته). کنترلر Seller، `StoreId` را از هویت جاری سرور تعیین می‌کند؛ ارسال StoreId دلخواه، مجوز دسترسی به فروشگاه دیگری نیست. کارکنان پنل ارائه‌دهنده باید طبق قرارداد فعلی نقش‌ها `X-Provider-Id` و مجوز endpoint را داشته باشند. منطق احراز هویت موجود اپ حفظ شود.

این گزارش و جمع‌های آن فقط سفارش‌های `IsPaid=true` را شامل می‌شوند. `GET /api/Seller/ProductOrder` نیز فقط سفارش‌های پرداخت‌شده را برمی‌گرداند؛ فیلتر قبل از صفحه‌بندی اعمال می‌شود و `totalCount` تعداد دقیقِ همهٔ سفارش‌های منطبق، مستقل از `PageSize` است. برای شمارش «ثبت‌شده‌ها» در داشبورد `ProductOrderStatusEnum=15` (`Insert`) را بفرستید و `totalCount` را بخوانید؛ مقدار `18` یعنی `Delivered`. شمارش ردیف‌های صفحهٔ اول با `PageSize=100` سقف ۱۰۰ دارد.

همتای پنل: `GET /api/Admin/FinanceStore?StoreId=<id>` با همان پاسخ و فیلترها و همان شرط پرداخت‌شده. `PUT` همین مسیر ادمین فقط درصد فروشگاه را تغییر می‌دهد؛ مجوزی برای تغییر سهمِ سفارش‌های گذشته نیست.

پاسخ HTTP 200 به‌تنهایی موفقیت نیست؛ ابتدا `isSuccess` بررسی شود. خطای کسب‌وکار از `messages[].item1` نمایش داده شود. 401/403 طبق مدیریت نشست و دسترسی موجود اپ، و خطای شبکه با retry صریح کاربر مدیریت شود.

## ۵. معنی فیلدها و نحوه مصرف در اپ

| فیلد ردیف | معنی و نمایش |
|---|---|
| `paymentPrice` | پرداخت واقعی کل سفارش بعد از مزایای سفارش؛ برای همه روش‌های پرداخت، نه فقط درگاه |
| `goodsPrice` | جمع مبلغ کالای ردیف‌های فعال، بعد از تخفیف محصول؛ عنوان «مبلغ کالا» |
| `deliveryPrice` | ارسال پیش‌پرداختِ متعلق به پاستیل؛ عنوان «هزینه ارسال — سهم پاستیل» |
| `commissionBase` | کالا با بازگرداندن تخفیف محصولِ پاستیل؛ مبنای کمیسیون |
| `commissionPercent` | درصد **فعلی** تنظیم‌شده فروشگاه؛ snapshot نرخ تاریخی در مدل موجود نیست |
| `commissionAmount` | کمیسیون ناخالص ثبت‌شده، از `commissionBase − storeShare` استخراج می‌شود تا تاریخچه با نرخ فعلی بازقیمت‌گذاری نشود |
| `pastilFundedAmount` | هزینه تخفیف محصول پاستیل؛ فقط یک‌بار از کمیسیون ناخالص کم شده |
| `netCommissionAmount` | کمیسیون ثبت‌شده خالص پس از تخفیف محصول پاستیل؛ `siteShare − deliveryPrice` |
| `storeShare` | طلب ثبت‌شده فروشگاه بابت کالا بعد از کسر کمیسیون؛ پول پیک داخلش نیست (برای رکوردهای مطابق قاعده جدید) |
| `siteShare` | سهم ثبت‌شده پاستیل؛ کمیسیون خالص کالا + کل ارسال پیش‌پرداخت |
| `accountingReviewRequired` | ردیف تاریخی/مشترک یا اختلاف نرخ فعلی؛ اعداد ثبت‌شده را مرجع نگه دارید و هشدار بررسی مالی نشان دهید |
| `permitted` | وضعیت تأیید/تسویه مالی فعلی سیستم؛ اثبات تحویل مشتری نیست |
| `userReceived` | null بی‌پاسخ، true تحویل‌گرفته، false تحویل‌نگرفته؛ false باید با هشدار مستقل نمایش داده شود |
| `userReceivedAuto` | تأیید دریافت خودکار؛ از تأیید صریح مشتری متمایز شود |

فیلدهای جمع `totalGoodsPrice`، `totalDeliveryPrice`، `totalCommissionAmount`، `totalNetCommissionAmount`، `totalStoreShare`، `totalSiteShare` و `totalPastilFundedAmount` دقیقاً جمع ردیف‌های پاسخ **بعد از اعمال فیلترها** هستند. `productOrderCount` تعداد همان ردیف‌هاست؛ این endpoint صفحه‌بندی ندارد. مجموع سفارش‌های پرداخت‌شده را موجودی قابل تسویه ننامید: سفارش لغوشده هم ممکن است در گزارش حاضر باشد و قواعد استخر تسویه مسیر خودش را دارد.

## ۶. صفحه حسابداری در اپ

کارت «سهم فروشگاه» = `totalStoreShare` با توضیح «فروش کالا پس از کسر کمیسیون؛ بدون هزینه ارسال». کارت «سهم پاستیل» = `totalSiteShare` و دو زیرردیف «کمیسیون خالص کالا» = `totalNetCommissionAmount` و «هزینه ارسال» = `totalDeliveryPrice`. اگر هزینه تخفیف محصول پاستیل مثبت بود، زیر کمیسیون ناخالص نشان داده شود؛ دوباره از سهم نهایی کسر نشود.

در هر سفارش: کد عمومی قابل کپی، مبلغ کالا، پرداخت مشتری، کمیسیون ناخالص، تخفیف پاستیل (در صورت مثبت)، کمیسیون خالص، ارسال، سهم نهایی پاستیل، سهم نهایی فروشگاه و وضعیت دریافت/تسویه نمایش داده شوند. مبلغ صفر با «۰ تومان» نمایش داده شود. شناسه داخلی جای کد عمومی نشان داده نشود.

در حالت loading، مقادیر قبلی را به صفر تبدیل نکنید. خطای درخواست با «فروش صفر» یکی نیست. empty state تنها وقتی پاسخ موفق و لیست خالی است. هنگام تغییر فیلتر، کارت‌ها و لیست از همان پاسخ به‌روز شوند. پاسخ دیررس فیلتر قبلی نباید فیلتر جدید را بازنویسی کند.

برای سازگاری انتشار، فیلد **غایب** را با صفر اشتباه نگیرید. اگر `deliveryPrice`/`totalDeliveryPrice` در پاسخ نیست، ریز جدید را مخفی کنید؛ از کم‌کردن/تقسیم حدسی مبالغ استفاده نکنید. پس از انتشار Api، فیلدها حاضر خواهند بود.

## ۷. سفارش‌های قبلی و تسویه

گزارش‌ها سهم‌های ذخیره‌شده را خودکار تغییر نمی‌دهند. برای سفارش‌های دارای سهم، `accountingReviewRequired` وقتی روشن می‌شود که سهم فروشگاه با فرمول جدید و درصد فعلی اختلاف بیش از ۰٫۰۱ تومان داشته باشد یا بیش از یک ردیف فروشگاه فعال وجود داشته باشد. این **تشخیص قطعی علت نیست**: تغییر نرخ کمیسیون هم می‌تواند هشدار بدهد. برای رکورد تاریخیِ هشدار‌دار، زیرمبلغ‌های مشتق‌شده ممکن است منفی/غیرمنتظره باشند؛ با محاسبه در اپ پنهان یا «اصلاح» نشوند.

گزارش فعلی برای سفارش قدیمی مشترک، مبالغ **کل سفارش** را برمی‌گرداند، نه سهم مجزای فروشگاه انتخاب‌شده. سازوکار تسویه نیز در سطح سفارش است؛ این تغییر مدل چندفروشگاهی/تسویه را مهاجرت نمی‌دهد. وقتی هشدار روشن است، اپ آن سفارش را سهم قطعی همین فروشگاه معرفی نکند؛ ارجاع به پشتیبانی مالی و بررسی ادمین لازم است.

پیش‌نمایش تسویه ادمین: `GET /api/Admin/ProviderFinance/{providerId}/pending?kind=2`. در `items` از نوع `Order` فیلدهای `goodsPrice`, `deliveryPrice`, `commissionAmount`, `netCommissionAmount`, `pastilFundedAmount`, `accountingReviewRequired` اضافه شده‌اند؛ `providerShare` همان سهم ثبت‌شده فروشگاه است. برای انواع غیرسفارش، فیلدهای عددی جدید null هستند. این endpoint ادمین است و نباید با توکن Seller فراخوانی شود. رفتار فعلی مجوز/ثبت تسویه عوض نشده و هشدار جدید به‌تنهایی backend را از تسویه منع نمی‌کند.

اسکریپت `scripts/database/RepairStoreShippingShares.sql` به‌طور پیش‌فرض **فقط پیش‌نمایش و rollback** است. تنها سفارش پرداخت‌شده، لغونشده، تسویه‌نشده، تک‌فروشگاهی و دقیقاً منطبق با فرمول قدیمی/درصد فعلی را پیشنهاد می‌کند. رکورد تسویه‌شده یا دارای لینک `SettlementStores`، کمیسیون تاریخی نامعلوم و سفارش مشترک خودکار اصلاح نمی‌شوند. اجرای واقعی با `@Apply=1` فقط بعد از بازبینی خروجی، بکاپ و اجازه صریح مالک پروژه. در ۲۰۲۶-۱۱-۱۸ با اجازه صریح کاربر و کنترل تعداد ۴ و مبلغ ۱٬۱۵۲٬۳۰۰ اجرا شد. آمار پس از اصلاح: ۴ منطبق با فرمول جدید، صفر فرمول قدیمی و صفر نیازمند بررسی دستی در سفارش‌های پرداخت‌شده/لغونشده با ارسال پیش‌پرداخت. مقدارهای قبل در `backups/store-shipping-shares-before-20261118.json` در ریشه ورک‌اسپیس و خروجی تغییر در فایل `store-shipping-shares-applied-20261118.json` همان پوشه محفوظ است؛ این‌ها backup همین دو سهم هستند، نه بکاپ کامل دیتابیس.

## ۸. انتشار و چک‌لیست نهایی

Api و Payment هر دو از Application مشترک استفاده می‌کنند؛ **با هم منتشر شوند** تا callback درگاه و پرداخت کیف پول یک قاعده داشته باشند. پنل و اپ پس از API منتشر شوند. نیازی به ستون جدید یا migration نیست. سفارش پرداخت‌شده قبلی با callback تکراری دوباره سهم‌بندی نمی‌شود. اصلاح/کاهش آیتم از قاعده مشترک جدید استفاده می‌کند.
