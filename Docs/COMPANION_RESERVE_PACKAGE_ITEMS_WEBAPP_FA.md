# نمایش وضعیت پکیج‌های رزرو برای کاربر (تأییدشده / لغوشده / در انتظار) — مستند مو‌به‌مو برای وب‌اپ (آرمان)

> بک پیاده شد، **دیپلوی نشده**. قرارداد و قواعد مالی: [COMPANION_RESERVE_PACKAGE_ITEMS_FA.md](COMPANION_RESERVE_PACKAGE_ITEMS_FA.md)
> پاسخ‌ها **همیشه HTTP 200** با `{ isSuccess, messages, data }`؛ فیلدها camelCase؛ همه‌ی endpointها `Authorization: Bearer …`.

## ۱) چه چیزی عوض شد
نماینده می‌تواند از پکیج‌های یک رزرو بعضی را **تأیید** و بعضی را **لغو** کند. کاربر باید در «رزروهای من» (فهرست و جزئیات) بداند هر پکیج چه وضعیتی دارد و چقدر به کیف پولش برگشته. کاربر خودش اینجا کاری نمی‌کند (فقط مشاهده).

وضعیت هر پکیج: `1` در انتظار تأیید نماینده · `2` تأییدشده · `3` لغوشده.

## ۲) از کجا بخوانید
۱. **جزئیات رزرو**: `GET /api/EndUser/CompanionReserve/{id}` (BFF فعلی `reserveInfo…`) حالا فیلد `packageItems` دارد (ساختار پایین).
۲. یا endpoint سبک: `GET /api/EndUser/CompanionReservePackage/{reserveId}` ⇒ همان ساختار. فقط رزرو خود کاربر.

```json
"packageItems": {
  "reserveId": 123,
  "canManage": false,
  "items": [
    { "id": 55, "packageId": 9, "packageName": "حمام کامل", "petCount": 2, "price": 600000,
      "status": 2, "statusReason": null, "statusChangedDate": "2026-10-04T11:00:00", "statusChangedByAdmin": false,
      "refundAmount": 0, "refundDate": null, "addedAfterPayment": false },
    { "id": 56, "packageId": 11, "packageName": "کوتاهی ناخن", "petCount": 2, "price": 200000,
      "status": 3, "statusReason": "در این ساعت امکان ارائه‌ی این خدمت نیست", "statusChangedDate": "2026-10-04T11:05:00",
      "refundAmount": 100000, "refundDate": "2026-10-04T11:05:00", "addedAfterPayment": false }
  ],
  "summary": { "total": 2, "pending": 0, "approved": 1, "cancelled": 1, "refundedTotal": 100000 }
}
```
(`canManage` مخصوص نماینده است؛ در وب‌اپ کاربر نادیده بگیرید.) `items[].id == 0` یعنی رزرو قدیمی که ردیف ندارد؛ نمایش مثل بقیه است (وضعیت «در انتظار»، یا «تأییدشده» اگر خدمت کامل شده).

## ۳) نمایش پیشنهادی

### جزئیات رزرو (بخش «پکیج‌های رزرو»)
هر آیتم یک کارت: نام، قیمت، «برای N پت»، و نشان:

| `status` | نشان |
| --- | --- |
| `1` | «در انتظار تأیید نماینده» — زرد |
| `2` | «تأیید شد» — سبز |
| `3` | «لغو شد» — قرمز؛ زیرش «دلیل: `statusReason`» و اگر `refundAmount > 0` «{مبلغ} تومان به کیف پول شما برگشت» (تاریخ `refundDate`) |

- بالای لیست خلاصه: «۶ تأییدشده، ۳ در انتظار، ۱ لغوشده» از `summary`.
- اگر `summary.refundedTotal > 0` یک نوار سبز: «مجموعاً {refundedTotal} تومان از این رزرو به کیف پول شما برگشت داده شد» + لینک به «کیف پول».
- `addedAfterPayment=true`: برچسب کوچک «توسط نماینده بعد از پرداخت اضافه شد» و توضیح: «هزینه‌ی این مورد در مبلغ نهایی خدمت حساب می‌شود».
- پکیج‌های لغوشده را خاکستری/خط‌خورده نشان دهید و **از جمع «هزینه‌ی رزرو» حذف‌شده فرض کنید** (بک `packagePrice`/`paymentPrice` رزرو را بعد از لغو کم‌شده برمی‌گرداند؛ همان را نمایش دهید، خودتان جمع نزنید).
- اگر همه‌ی پکیج‌ها لغو شدند رزرو خودش `isCancel=true` می‌شود (وضعیت «لغو شده» با `cancelDetail` = دلیل آخرین لغو) و کل پرداختی برگشته است.

### فهرست رزروها
اگر خواستید نشان کوچک اضافه کنید: از جزئیات استفاده نکنید (فهرست `packageItems` ندارد). اختیاری و بعداً؛ نیازی نیست.

## ۴) پوش‌ها (ورودی جدید)
- **۹۱** `PushCompanionReservePackageApproved`: «نماینده پکیج «X» رزرو شما را تأیید کرد.»
- **۹۲** `PushCompanionReservePackageCancelled`: «پکیج «X» رزرو شما لغو شد و N تومان به کیف پول شما برگشت داده شد.»
لینک هر دو `/reserve/{شناسه‌ی رزرو}` است (مثل پوش‌های «کامل/لغو» فعلی)؛ نیاز به تغییر روتر نیست. پس از کلیک، صفحه‌ی جزئیات را تازه بگیرید تا وضعیت جدید دیده شود.

## ۵) رفتار کیف پول
مبلغ برگشتی یک ردیف «افزایشی» در کیف پول با نام `CompanionPackageRefund:{id}` است. در صفحه‌ی کیف پول/تراکنش‌ها همان نام فعلی را نشان می‌دهید؛ اگر تبدیل نام به متن فارسی دارید («بازگشت وجه پکیج رزرو» برای نام‌های با این پیشوند) اضافه کنید. چیز دیگری لازم نیست.

## ۶) سناریوهای تست (بعد از SQL و دیپلوی)
۱. رزرو پرداخت‌شده با ۳ پکیج ⇒ ۳ «در انتظار تأیید».
۲. نماینده یکی را تأیید کند ⇒ سبز + پوش ۹۱.
۳. نماینده یکی را لغو کند ⇒ قرمز + دلیل + مبلغ برگشتی؛ موجودی کیف پول به همان اندازه زیاد؛ پوش ۹۲.
۴. نماینده آخرین پکیج فعال را لغو کند ⇒ رزرو «لغو شده»، کل باقی‌مانده برگشته.
۵. رزرو قدیمی ⇒ همه «در انتظار» (یا «تأییدشده» برای کامل‌شده) بدون خطا.
۶. کاربر دیگری `GET …/CompanionReservePackage/{reserveId}` با رزرو غیر خودش ⇒ `isSuccess:false`.
