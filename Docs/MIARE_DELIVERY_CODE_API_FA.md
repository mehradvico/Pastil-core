# مستند API: کد تحویل (Delivery Code) — یکپارچه‌سازی پاستیل با میاره

| | |
|---|---|
| مخاطب | تیم فنی میاره (برای درج در مستندات فنی) |
| نسخه | ۱.۰ |
| ارائه‌دهنده | پاستیل (Pastil) — فروشگاه اینترنتی محصولات حیوانات خانگی |
| دامنه | سفارش‌های فروشگاه که با پیک میاره ارسال می‌شوند (ارسال عادی و اکسپرس) |

## ۱. خلاصه

کد تحویل یک رمز ۵ رقمی است که **پاستیل برای هر سفارش می‌سازد** و هنگام ثبت سفر در فیلد `delivery_code` به میاره می‌دهد. مشتری آن را از پاستیل (پیامک، اعلان و صفحهٔ سفارش) دریافت می‌کند و **بعد از دریافت و بررسی کالا** به پیک می‌گوید. پیک کد را در اپ میاره وارد می‌کند و میاره تحویل را ثبت می‌کند. پاستیل نتیجه را از طریق وب‌هوک میاره می‌گیرد.

در این طرح **پاستیل هیچ endpointـی برای اعتبارسنجی کد ارائه نمی‌دهد** و میاره برای اعتبارسنجی با سرور پاستیل تماس نمی‌گیرد. اعتبارسنجی کامل در سمت میاره انجام می‌شود (مقایسهٔ کد واردشده با `delivery_code` ثبت‌شده روی سفر).

```
پاستیل                          میاره                         مشتری
  │  ساخت کد ۵ رقمی (هنگام پرداخت)  │                              │
  │── POST /trips/ (delivery_code) ▶│                              │
  │◀─ id سفر، tracking_url ─────────│                              │
  │                                 │  پیک کالا را از فروشگاه می‌گیرد
  │◀─ وب‌هوک state=dropoff ─────────│                              │
  │── پیامک و اعلان با کد ─────────────────────────────────────────▶│
  │                                 │◀── مشتری کد را به پیک می‌گوید ─│
  │                                 │  پیک کد را در اپ وارد می‌کند
  │◀─ وب‌هوک state=delivered ───────│                              │
```

## ۲. مشخصات کد

| ویژگی | مقدار |
|---|---|
| قالب | رشتهٔ عددی دقیقاً ۵ رقم، بین `10000` و `99999` (بدون صفر ابتدایی) |
| نوع در JSON | **string** (نه number) |
| تولید | تصادفی امن (CSPRNG) سمت پاستیل |
| زمان تولید | هنگام ثبت پرداخت سفارش؛ قبل از ساخت سفر در میاره |
| دامنه | یک کد برای هر سفر (هر مرسوله یک `course`). یکتا بودن سراسری تضمین نمی‌شود؛ اعتبارسنجی همیشه روی همان سفر/مقصد انجام شود |
| ساخت مجدد سفر | اگر سفر به‌خاطر لغو از سمت میاره دوباره ساخته شود، **همان کد قبلی** فرستاده می‌شود |
| سفارش چندفروشگاهی | هر فروشگاه یک سفر مستقل و یک کد مستقل دارد |

## ۳. ساخت سفر با کد تحویل

**`POST {MIARE_BASE_URL}/trips/`**

هدرها:

| هدر | مقدار |
|---|---|
| `Authorization` | `Token {API_KEY}` |
| `Content-Type` | `application/json` |

نمونهٔ بدنه:

```json
{
  "pickup": {
    "name": "فروشگاه نمونه",
    "phone_number": "09120000000",
    "address": "تهران، ...",
    "location": { "latitude": 35.7000, "longitude": 51.4000 },
    "deadline": "2026-11-16T08:30:00Z",
    "image": "https://example.com/store.jpg"
  },
  "courses": [
    {
      "bill_number": "PST-123456",
      "delivery_code": "48213",
      "name": "نام گیرنده",
      "phone_number": "09130000000",
      "address": "تهران، ...",
      "location": { "latitude": 35.7500, "longitude": 51.4500 }
    }
  ],
  "boost": { "level": 1 }
}
```

| فیلد | الزامی | توضیح |
|---|---|---|
| `courses[].delivery_code` | بله (برای سفارش‌های پاستیل) | رشتهٔ ۵ رقمی. در پاستیل همیشه فرستاده می‌شود؛ فقط در حالت نادر نبودن کد، فیلد کلاً حذف می‌شود (مقدار `null` فرستاده نمی‌شود) |
| `courses[].bill_number` | بله | شمارهٔ سفارش پاستیل؛ برای ارجاع پشتیبانی |
| `pickup.deadline` | بله | قالب UTC با پسوند `Z` (مثلاً `2026-11-16T08:30:00Z`) |
| `boost.level` | خیر | فقط برای ارسال اکسپرس |

پاسخ موفق (فیلدهایی که پاستیل می‌خواند):

```json
{
  "id": "trip-id",
  "courses": [ { "tracking_url": "https://..." } ]
}
```

درخواست لغو: `POST {MIARE_BASE_URL}/trips/{id}/cancel/` با همان هدر `Authorization`.

## ۴. رفتار مورد انتظار در اپ پیک (از میاره)

این بخش قرارداد رفتاری است که پاستیل به آن تکیه می‌کند:

1. وقتی `delivery_code` روی سفر ثبت شده باشد، پیک **قبل از ثبت تحویل** باید کد را از مشتری بگیرد و در اپ وارد کند.
2. کد **نباید به پیک نمایش داده شود** (نه در اپ، نه در پیامک پیک، نه در پاسخ API)، چون هدف اثبات حضور مشتری و دریافت کالاست.
3. وب‌هوک `delivered` فقط وقتی فرستاده شود که کد صحیح وارد شده باشد.
4. اگر مشتری کد را در اختیار نداشت یا کد اشتباه بود، سفر نباید «تحویل‌شده» ثبت شود و باید طبق روال میاره (بازگشت کالا یا `returning`) ادامه یابد.
5. `delivery_code` در بدنهٔ وب‌هوک‌ها و پاسخ‌های GET Trip که به پاستیل می‌رسد نیاید. پاستیل برای احتیاط آن را از payloadهای ذخیره‌شده حذف می‌کند.

> ✅ موارد ۳ و ۴ را لطفاً میاره تأیید کند. پاستیل از وب‌هوک `delivered` نتیجه می‌گیرد که تحویل با کد انجام شده است.

## ۵. وب‌هوک‌هایی که پاستیل دریافت می‌کند

**`POST https://{PASTIL_API_HOST}/api/webhooks/miare`**

| هدر | مقدار |
|---|---|
| `Authorization` | `Token {API_KEY}` (همان کلید حساب پاستیل در میاره) |
| `Content-Type` | `application/json` |

- پاسخ موفق `200`. هدر نامعتبر → `401`. خطای پردازش → `500` (میاره طبق مستند خودش تا ۵ بار تلاش مجدد می‌کند).
- پردازش **idempotent** و **مقاوم در برابر جابه‌جایی ترتیب** است؛ وضعیت فقط رو به جلو می‌رود و بعد از وضعیت نهایی عوض نمی‌شود. ارسال تکراری یک رویداد بی‌خطر است.
- دو قالب پذیرفته می‌شود:

```json
{ "event": "delivered", "trip": { "id": "trip-id", "state": "delivered", "delivery_cost": 45000 } }
```

یا خودِ شیء سفر (بدون `event`/`trip`) با فیلدهای `id` و `state`.

نگاشت وضعیت‌ها در پاستیل:

| `state` میاره | معادل `event` (اگر `state` نبود) | معنی در پاستیل |
|---|---|---|
| `assign_queue` | — | سفر در صف تخصیص پیک؛ وضعیت «درخواست‌شده» |
| `pickup` | `assigned` | پیک تخصیص یافت و به‌سمت فروشگاه است |
| `dropoff` | `picked_up`، `course_dropped_off` | پیک کالا را از فروشگاه گرفت. **همین لحظه کد تحویل به مشتری نمایش داده/ارسال می‌شود** |
| `delivered` | `delivered` | پیک با کد صحیح تحویل داد. فیلد `delivery_cost` (عدد، تومان) خوانده می‌شود |
| `returning` | `returning` | کالا برمی‌گردد؛ سفارش وارد بررسی/استرداد می‌شود |
| `canceled_by_delay` / `canceled_by_miare` | همان نام | لغو از سمت میاره؛ پاستیل در صورت وجود زمان، یک‌بار سفر جدید با **همان کد** می‌سازد |
| `canceled_by_client` | `canceled_by_client` | لغو از سمت پاستیل |

> نکته: نام‌های `pickup`/`dropoff` همان‌طور که در پیاده‌سازی میاره آمده‌اند تفسیر شده‌اند (`pickup` = پیک در مسیر دریافت کالا، `dropoff` = کالا دست پیک است و به‌سمت مشتری می‌رود).

## ۶. نمایش کد به مشتری (سمت پاستیل — فقط اطلاع)

میاره این بخش را فراخوانی نمی‌کند؛ برای فهم تجربهٔ کاربر آمده است.

- **پیامک و اعلان:** بعد از وب‌هوک `dropoff` یک‌بار. پیامک شامل متن «سلامت فیزیکی کالا را بررسی کنید و در صورت تأیید، کد تحویل را اعلام کنید. اعلام کد به منزلهٔ تأیید دریافت است.» و کد است؛ اعلان فقط کد و شمارهٔ سفارش را نشان می‌دهد.
- **صفحهٔ سفارش مشتری:** `GET /api/EndUser/ProductOrder/{id}` (احراز هویت با JWT مشتری). فیلد `productOrderStores[].shipmentDeliveryCode` فقط وقتی مرسوله دست پیک است (یا تحویل شده) پر است؛ قبل از آن `null` است.
- فروشنده و ادمین پاستیل **هرگز** کد را نمی‌بینند.
- هر مرسوله کد جدا دارد؛ سفارش دو فروشگاهی دو کد دارد.

## ۷. حالت‌های خاص

| حالت | رفتار پاستیل |
|---|---|
| پیک «تحویل» را بدون کد ثبت کند / مشتری کد نداده باشد | مرسوله «تحویل‌شده» می‌شود، ولی سفارش را فقط مشتری نهایی می‌کند. در پایان بازهٔ تحویل از او پرسیده می‌شود «تحویل گرفتید؟». اگر «خیر» بگوید، موضوع به پشتیبانی پاستیل می‌رود و پاستیل با پشتیبانی میاره پیگیری می‌کند |
| مشتری پیامک را گم کرده | کد از صفحهٔ سفارش در وب‌اپ/اپ قابل مشاهده است (بعد از دریافت کالا توسط پیک) |
| سفر لغو و دوباره ساخته شود | همان `delivery_code` تکرار می‌شود |
| وب‌هوک نرسد | پاستیل به‌صورت دوره‌ای `GET {MIARE_BASE_URL}/trips/{id}/` را می‌خواند و وضعیت را جبران می‌کند |
