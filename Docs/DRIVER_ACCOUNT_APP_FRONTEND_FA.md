# حساب راننده — مستند پیاده‌سازی سمت App (webapp)

این مستند مو‌به‌مو توضیح می‌ده راننده چطور ثبت‌نام می‌کنه، چطور تایید می‌شه، و **چرا اگه این مراحل درست طی نشن، هیچ‌کدوم از endpoint های پت‌رسان (قبول‌کردن سفر، اعلام مراحل، لغو) کار نمی‌کنن** — دقیقاً همون مشکلی که چند بار امروز پیش اومد (خطای `FK_Trips_Drivers_DriverId` و «لطفا وضعیت را تغییر دهید»).

> برای فلوی خودِ سفر (بعد از اینکه راننده تایید شد)، به [PETRASAN_APP_FRONTEND_FA.md](PETRASAN_APP_FRONTEND_FA.md) مراجعه کن. این سند فقط حساب/هویت راننده رو پوشش می‌ده.

---

## ۰. نقشه‌ی کلی — از صفر تا سفر اول

```
۱. کاربر با موبایل ثبت‌نام/لاگین می‌کنه (فلوی عمومی احراز هویت — این سند نیست)
        ↓
۲. همون کاربر فرم «ثبت‌نام راننده» رو پر می‌کنه → POST /Driver/Driver یا /EndUser/Driver   (بخش ۲ همین سند)
        ↓
۳. رکورد Driver ساخته می‌شه با وضعیت «در انتظار بررسی» (DriverRequestStatus_Requested)      (بخش ۳)
        ↓
۴. ادمین توی پنل (/admin/driver) درخواست رو تایید یا رد می‌کنه — این بخش با اپ کاری نداره
        ↓
۵. اگه تایید شد → از این لحظه، توکن همین کاربر یک DriverId معتبر برمی‌گردونه            (بخش ۴ — حیاتی!)
        ↓
۶. حالا و فقط حالا، endpoint های Driver-area سفر (TripAvailable، UpdateTripDriverStatus، ...) کار می‌کنن
   → برو سراغ PETRASAN_APP_FRONTEND_FA.md
```

⚠️ اگه مرحله‌ی ۴ طی نشده باشه (یعنی راننده هنوز تایید نشده)، مرحله‌ی ۶ با خطای واقعیِ دیتابیسی (FK) یا پیام مبهم شکست می‌خوره — این یک باگ نیست، انتظار می‌ره.

---

## ۱. قراردادهای عمومی

- Area برای ثبت‌نام اولیه: **`EndUser`** (`POST /EndUser/Driver`) — چون در این لحظه کاربر هنوز راننده نیست، توکنش فقط `UserId` معتبر داره.
- Area برای مدیریت پروفایل بعد از ثبت‌نام (ویرایش/ارسال مجدد): هم `EndUser` هم `Driver` — هر دو یک متد سرویس صدا می‌زنن (`ResubmitAsyncDto`)، فرقی نمی‌کنه از کدوم بزنی.
- آپلود عکس (مدرک/کارت خودرو/پروفایل): سرویس **جدا (File)**، نه سرویس اصلی API — بخش ۲.۲ رو ببین.
- پاسخ‌ها همون قرارداد همیشگی: `{ isSuccess, code, messages, data }`، همیشه HTTP 200.

## ۲. ثبت‌نام راننده

### ۲.۱ فیلدهای فرم (`POST /EndUser/Driver`)

Body (`DriverDto`):

```jsonc
{
  "name": "امیرعلی محمدی",              // اجباری
  "phone": "09120000001",               // اجباری
  "vehicle": "پژو 206",                 // اجباری
  "licensePlateNumber": "11 ت 223 67",  // اجباری
  "cityId": 1,                          // اجباری — از GET /Common/City?... یا /Common/City/GetAll
  "neighborhoodId": 5,                  // اختیاری — اگه فرستادی باید واقعاً توی همون cityId باشه
  "certificatePictureId": 1042,         // اجباری — عکس مدرک/گواهی‌نامه، شناسه از آپلود (بخش ۲.۲)
  "vehicleCardPictureId": 1043,         // اجباری — عکس کارت خودرو
  "profilePictureId": 1044,             // اختیاری — عکس پروفایل راننده
  "ownerDetail": "توضیح اختیاری"
  // statusId, ownerId رو نفرست — بک‌اند خودش از توکن پر می‌کنه و روی
  // DriverRequestStatus_Requested (82) قفل می‌کنه، هرچی بفرستی نادیده گرفته می‌شه
}
```

قوانین اعتبارسنجی (پیام‌های فارسی مستقیم قابل‌نمایش، هرکدوم جدا برمی‌گردن توی `messages`):

| فیلد | قانون | پیام خطا |
|---|---|---|
| `name` | اجباری | «لطفا نام را وارد کنید» |
| `phone` | اجباری | «لطفا تلفن را وارد کنید» |
| `vehicle` | اجباری | «لطفا خودرو را وارد کنید» |
| `licensePlateNumber` | اجباری | «لطفا شماره پلاک را وارد کنید» |
| `cityId` | اجباری، باید توی جدول شهرها موجود باشه | «شهر انتخاب‌شده نامعتبر است» |
| `neighborhoodId` | اگه پر شد، باید متعلق به همون `cityId` باشه | «محله انتخاب‌شده در این شهر نیست» |
| `certificatePictureId` | **اجباری** (باید قبلش آپلود بشه) | «عکس مدرک راننده الزامی است» |
| `vehicleCardPictureId` | **اجباری** | «عکس کارت خودرو الزامی است» |
| `profilePictureId` | اختیاری، ولی اگه فرستادی باید یک Picture واقعی باشه | «عکس پروفایل نامعتبر است» |

⚠️ **یک کاربر فقط یک‌بار می‌تونه درخواست راننده بده** — اگه از قبل یک ردیف Driver (غیرحذف‌شده) برای همین کاربر باشه (فرقی نمی‌کنه در انتظار/تاییدشده/ردشده)، این درخواست با پیام «شما در حال حاضر راننده هستید» رد می‌شه. برای «دوباره تلاش کردن» بعد از رد شدن، باید از **ویرایش/ارسال مجدد** استفاده کرد (بخش ۲.۳)، نه ثبت‌نام دوباره.

پاسخ موفق: `BaseResultDto<DriverDto>` با `id` تازه‌ساخته‌شده، `statusId = 82` (Requested).

### ۲.۲ آپلود عکس (پیش‌نیاز ۲.۱)

⚠️ **این روی سرویس دیگه‌ایه، نه همون Api که بقیه‌ی این پروژه روشه** — طبق `docs/ai/ARCHITECTURE.md`، یک سرویس جدای «File» هست (پورت ۵۰۰۱ روی محیط dev؛ روی پروداکشن از دامنه‌ی مربوطه بپرس اگه مطمئن نیستی).

```
POST /api/PictureUpload
Content-Type: multipart/form-data
```

Body: یک فیلد فرم به اسم دقیقاً **`PictureFile`** (case-sensitive) با فایل تصویر.

- فرمت‌های مجاز: `.jpg` `.jpeg` `.png` `.webp` (ویدیو هم پشتیبانی می‌شه: `.mp4` `.webm` `.ogg`، ولی برای عکس‌های راننده کاربردی نداره)
- حداکثر حجم: **۵ مگابایت**
- حداکثر ابعاد: ۸۰۰۰×۸۰۰۰ پیکسل و حداکثر ۲۵ مگاپیکسل
- عکس‌ها خودکار به‌صورت webp ذخیره و ۳ سایز thumbnail (`lg`/`md`/`sm`) هم ساخته می‌شه — چیزی از این بابت لازم نیست بفرستی.

پاسخ: `BaseResultDto<PictureDto>` — همون `data.id` رو بگیر و بذار توی `certificatePictureId`/`vehicleCardPictureId`/`profilePictureId` بخش ۲.۱.

**ترتیب درست UX**: کاربر عکس رو انتخاب می‌کنه → بلافاصله (قبل از submit نهایی فرم) `POST /api/PictureUpload` بزن → `id` برگشتی رو نگه دار (مثلاً توی state فرم) → موقع submit نهایی فرم راننده، همون `id`ها رو بفرست. یعنی آپلود عکس و ثبت فرم دو تا request جدا هستن.

### ۲.۳ ویرایش / ارسال مجدد بعد از رد شدن

```
PUT /EndUser/Driver
PUT /Driver/Driver
```

(هر دو یکی هستن، فرقی نداره کدوم Area — از همونی استفاده کن که توکنش رو داری.)

Body: همون `DriverDto` بخش ۲.۱ به‌علاوه‌ی `id` (شناسه‌ی همون Driver که قبلاً ساخته شده).

⚠️ **نکته‌ی مهم رفتاری**: این فقط برای «رد شده که می‌خواد دوباره تلاش کنه» نیست — **حتی یک راننده‌ی از قبل تاییدشده هم اگه پروفایلش رو با این endpoint ویرایش کنه، خودکار از حالت تاییدشده خارج می‌شه** و برمی‌گرده به `DriverRequestStatus_Requested`، `Active=false`، `Approved=false` — یعنی تا ادمین دوباره تاییدش نکنه، دیگه نمی‌تونه سفر بگیره. این عمدیه (چون شاید خودرو/پلاک عوض شده باشه)، نه باگ. **قبل از اینکه کاربر روی دکمه‌ی «ذخیره‌ی تغییرات پروفایل» بزنه، این رو بهش هشدار بده.**

(فیلد `rate` امتیاز راننده حین این عملیات حفظ می‌شه، صفر نمی‌شه.)

## ۳. وضعیت درخواست راننده — `DriverRequestStatus` (⚠️ با `Driver_Status` اشتباه نگیر)

این دقیقاً همون چیزیه که امروز چند بار مشکل ایجاد کرد — **دو تا گروه Code شبیه‌هم ولی کاملاً بی‌ربط به هم وجود داره**:

| گروه Code | برای چی؟ | مقادیر | استفاده می‌شه روی |
|---|---|---|---|
| `DriverRequestStatus` | **تایید/رد خودِ حساب راننده** | Requested=82, Accepted=83, Rejected=84 | `Driver.StatusId` |
| `Driver_Status` | وضعیت راننده *داخل یک سفر مشخص* (چیز کاملاً متفاوتی) | Requested=79, Accepted=80, Rejected=81 | `Trip.DriverStatusId` |

**هیچ‌وقت این دو تا رو قاطی نکن.** برای خوندن وضعیت تایید حساب راننده (`driver.statusId`)، همیشه از دیکشنری گروه **`DriverRequestStatus`** بخون:

```
GET /Driver/Code?codeGroupLabel=DriverRequestStatus
GET /EndUser/Code?codeGroupLabel=DriverRequestStatus
```

(همون endpoint دیکشنری Code که توی PETRASAN_APP_FRONTEND_FA.md بخش ۳.۳ توضیح داده شده.)

| Label | معنی |
|---|---|
| `DriverRequestStatus_Requested` | ثبت شده، منتظر بررسی ادمین |
| `DriverRequestStatus_Accepted` | تاییدشده — می‌تونه سفر بگیره |
| `DriverRequestStatus_Rejected` | ردشده — `driver.adminDetail` دلیل رد رو داره |

### ۳.۱ گرفتن وضعیت فعلی خودِ راننده

```
GET /Driver/Driver
GET /EndUser/Driver
```

بدون هیچ فیلتری، خودکار روی `ownerId = کاربر توکن` فیلتر می‌شه — یعنی همیشه فقط رکورد(های) خودِ همون کاربر رو برمی‌گردونه. جواب شامل:

```jsonc
{
  "id": 1,
  "statusId": 83,                 // برای معنی، به دیکشنری DriverRequestStatus نگاه کن
  "approved": true,
  "active": true,
  "adminDetail": null,            // فقط وقتی rejected باشه پر می‌شه — دلیل رد
  // ...بقیه‌ی فیلدهای فرم
}
```

صفحه‌ی «وضعیت درخواست راننده‌ی من» توی اپ باید این رو صدا بزنه و بر اساس `statusId` سه حالت مختلف نشون بده:
- **Requested**: «درخواست شما در حال بررسیه»
- **Accepted**: دسترسی به بخش راننده باز بشه (منوی پت‌رسان راننده)
- **Rejected**: `adminDetail` رو به‌عنوان دلیل نشون بده + دکمه‌ی «ویرایش و ارسال مجدد» → بخش ۲.۳

## ۴. ⚠️ چرا `driverId` گاهی صفر/نامعتبره — این خیلی مهمه

توکن هر کاربر (چه Area=`EndUser` چه `Driver`) هربار از دیتابیس تازه خونده می‌شه، نه از یک claim ثابت داخل JWT. مقدار `driverId` که سمت بک‌اند برای همه‌ی عملیات‌های Driver-area سفر استفاده می‌شه (قبول‌کردن سفر، رد‌کردن، لغو، اعلام مراحل...) این‌طوری محاسبه می‌شه:

```csharp
DriverId = (User.Driver != null && !User.Driver.Deleted
            && User.Driver.StatusId == DriverRequestStatus_Accepted)
    ? Driver.Id
    : null   // → که برای عملیات‌های سفر معادل صفر می‌شه
```

یعنی `driverId` معتبر (غیرصفر) **فقط و فقط** وقتی برمی‌گرده که:
1. این کاربر اصلاً یک رکورد Driver داره (فرم بخش ۲ رو کامل کرده)، **و**
2. اون رکورد `Deleted=false` هست، **و**
3. `StatusId` دقیقاً `DriverRequestStatus_Accepted` (۸۳) باشه — یعنی ادمین تاییدش کرده

اگه هرکدوم از این سه شرط برقرار نباشه (کاربر اصلاً فرم نداده، یا داده ولی هنوز Requested/Rejaste)، `driverId` صفر می‌شه. الان (نسخه‌ی جدید بک‌اند) این حالت با پیام تمیز «دسترسی غیرمجاز» جواب داده می‌شه؛ **قبلاً همین حالت باعث می‌شد درخواست قبول‌کردن سفر با خطای خام دیتابیسی (Foreign Key) کرش کنه** — اگه همچنان همچین خطایی دیدی، یعنی نسخه‌ی جدید بک‌اند هنوز روی سرور دیپلوی نشده، نه اینکه مشکل داده باشه.

**نتیجه‌ی عملی برای UI**: قبل از نمایش دادن هر صفحه‌ی مخصوص راننده (لیست سفرهای در دسترس، دکمه‌ی قبول سفر، ...)، حتماً اول بخش ۳.۱ رو چک کن و مطمئن شو `statusId == DriverRequestStatus_Accepted` هست. اگه نیست، کاربر رو به صفحه‌ی «وضعیت درخواست» بفرست، نه به صفحه‌ی سفرها.

## ۷. نکات پیاده‌سازی و UX

1. **همیشه قبل از نمایش صفحات پت‌رسانِ سمت راننده، وضعیت تایید رو چک کن** (بخش ۳.۱ + ۴) — این تنها راه جلوگیری از خطاهای گیج‌کننده‌ی «امکان تغییر وضعیت وجود ندارد» / «دسترسی غیرمجاز» روی صفحات سفره.
2. **آپلود عکس دو مرحله‌ایه** — اول `POST /api/PictureUpload` (سرویس File)، بعد `id` برگشتی رو توی فرم اصلی (سرویس Api) بفرست. این دو تا request به دو تا سرویس مختلف می‌رن؛ اگه فرض کنی همه‌چیز روی یک base URL ـه، آپلود fail می‌شه.
3. **مدرک/کارت خودرو اجباری‌ان، پروفایل نه** — فرم رو طوری طراحی کن که submit دکمه‌ش تا وقتی این دو تا آپلود نشدن غیرفعال باشه، نه اینکه بذاری submit بشه و بعد خطای فارسی «عکس مدرک راننده الزامی است» رو نشون بدی.
4. **ویرایش پروفایل = ریست تایید** — قبل از ذخیره‌ی تغییرات یک confirm/هشدار بده («با ذخیره‌ی تغییرات، حساب شما دوباره نیاز به تایید ادمین داره») تا کاربر غافلگیر نشه که چرا یهو دیگه نمی‌تونه سفر بگیره.
5. **یک کاربر = حداکثر یک درخواست راننده** — اگه از قبل درخواست داده (فرقی نکنه چه وضعیتی)، فرم «ثبت‌نام جدید» رو نشونش نده؛ به‌جاش وضعیت فعلیش (بخش ۳.۱) رو نشون بده.
