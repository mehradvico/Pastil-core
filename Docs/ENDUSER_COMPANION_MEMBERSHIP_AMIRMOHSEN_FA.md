# مستند تأیید عضویت کاربر در نمایندگی برای EndUser

این مستند برای نمایش و پاسخ‌دادن به دعوت عضویت در نمایندگی داخل پروفایل کاربر `app.pastil.pet` تهیه شده است.

## فرایند کلی

1. نماینده یا ادمین، کاربر را به یک نمایندگی دعوت می‌کند.
2. دعوت با وضعیت `userAccept = null` و `active = false` ساخته می‌شود.
3. کاربر دعوت را در پروفایل خود مشاهده می‌کند.
4. کاربر فقط یک‌بار آن را قبول یا رد می‌کند.
5. در صورت قبول، بک هم‌زمان `userAccept = true` و `active = true` ثبت می‌کند.
6. در صورت رد، بک هم‌زمان `userAccept = false` و `active = false` ثبت می‌کند.

## دریافت دعوت‌ها و عضویت‌ها

```http
GET /api/EndUser/CompanionUser?PageIndex=1&PageSize=50&SortBy=1
Authorization: Bearer {accessToken}
```

`UserId` از توکن استخراج می‌شود. فرانت نباید `UserId` ارسال کند.

این API تمام وضعیت‌های متعلق به کاربر را برمی‌گرداند؛ از جمله دعوت در انتظار که هنوز `active = false` است.

نمونه آیتم:

```json
{
  "id": 15,
  "companionId": 7,
  "userId": 42,
  "userAccept": null,
  "active": false,
  "companion": {
    "id": 7,
    "name": "کلینیک پت دریم",
    "phone": "09120000000",
    "picture": {
      "id": 108,
      "url": "/StaticPicture/..."
    }
  }
}
```

## وضعیت‌ها در رابط کاربری

| `userAccept` | `active` | وضعیت UI |
|---|---|---|
| `null` | `false` | در انتظار پاسخ؛ دکمه تأیید و رد نمایش داده شود |
| `true` | `true` | عضویت تأیید و فعال است |
| `false` | `false` | دعوت توسط کاربر رد شده است |
| `true` | `false` | عضویت پذیرفته شده ولی توسط ادمین/نماینده غیرفعال شده است |

دکمه‌های قبول و رد فقط وقتی نمایش داده شوند که `userAccept === null` باشد.

## تأیید دعوت

Endpoint پیشنهادی:

```http
PATCH /api/EndUser/CompanionUser/{id}/decision
Authorization: Bearer {accessToken}
Content-Type: application/json
```

بدنه تأیید:

```json
{
  "userAccept": true
}
```

بدنه رد:

```json
{
  "userAccept": false
}
```

`id` شناسه خود رکورد `CompanionUser` است، نه `companionId`.

فرانت نباید `userId`، `active` یا `companionId` را در درخواست تصمیم‌گیری ارسال کند. مالکیت دعوت از روی توکن کنترل می‌شود و وضعیت `active` را خود بک تعیین می‌کند.

## Endpoint سازگار با نسخه قدیمی

نسخه قدیمی همچنان پشتیبانی می‌شود:

```http
POST /api/EndUser/CompanionUser
Authorization: Bearer {accessToken}
Content-Type: application/json
```

```json
{
  "id": 15,
  "userAccept": true
}
```

برای توسعه جدید از Endpoint `PATCH .../{id}/decision` استفاده شود.

## پاسخ موفق

```json
{
  "isSuccess": true,
  "messages": [],
  "code": 0
}
```

پس از موفقیت:

1. دکمه‌ها غیرفعال شوند.
2. لیست با GET مجدد تازه‌سازی شود.
3. وضعیت محلی حدس زده نشود؛ پاسخ GET معیار نمایش باشد.

## پاسخ‌های ناموفق

اگر کاربر قبلاً تصمیم گرفته باشد، `isSuccess: false` با پیام «قبلاً انتخاب شده است» برمی‌گردد. تصمیم کاربر فقط یک‌بار ثبت می‌شود.

اگر ID متعلق به کاربر لاگین‌شده نباشد یا حذف شده باشد، پاسخ دسترسی غیرمجاز در `messages` برمی‌گردد.

اگر `userAccept` ارسال نشود یا `null` باشد، درخواست نامعتبر است.

متن خطا از مسیر زیر خوانده شود:

```ts
response.messages?.[0]?.item1
```

## نکات UI/UX

- بخش «دعوت‌های نمایندگی» در پروفایل حتی اگر فقط یک دعوت در انتظار وجود دارد نمایش داده شود.
- هنگام ارسال تصمیم، هر دو دکمه موقتاً disabled شوند.
- دوبار کلیک کنترل شود.
- در خطای شبکه، کارت دعوت و دکمه‌ها حذف نشوند.
- برای دعوت ردشده امکان پاسخ مجدد نمایش داده نشود.
- تصویر نمایندگی با سرویس فایل و URL کامل نمایش داده شود.

## نکات امنیتی بک

- کاربر فقط دعوت متعلق به `UserId` داخل توکن خودش را می‌تواند پاسخ دهد.
- پذیرش و فعال‌سازی در یک SQL Update اتمیک انجام می‌شود.
- رد و غیرفعال‌سازی نیز در همان Update انجام می‌شود.
- پاسخ دوم یا هم‌زمان روی همان دعوت ثبت نمی‌شود.
- کاربر تنها زمانی قابل تخصیص به خدمات نمایندگی است که `userAccept = true` و `active = true` باشد.
