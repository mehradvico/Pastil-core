# پت‌رسان — مستند پیاده‌سازی سمت App (webapp)

این مستند برای تیم فرانت (Nuxt 4 — `webapp/`) نوشته شده تا بخش کاربر (صاحب پت) و بخش راننده‌ی فیچر **پت‌رسان** رو پیاده‌سازی کنن. بک‌اند این فیچر کامل و build-clean هست؛ این سند قرارداد API رو دقیق و کامل توضیح می‌ده.

> بک‌اند مرتبط: `Application/Services/TripSrv/TripSrv/*`, کنترلرهای `Api/Areas/{EndUser,Driver}/Controllers/Trip*`. برای معماری کلی و تصمیم‌های طراحی، به سند «معماری پت‌رسان» (Artifact این پروژه) مراجعه کن.

> ⚠️ **پیش‌نیاز اجباری**: تمام endpoint های Driver-area این سند (پذیرش سفر، اعلام مراحل، لغو، ...) فقط وقتی کار می‌کنن که راننده از قبل ثبت‌نام کرده و **توسط ادمین تاییدشده** باشه — وگرنه با خطای «دسترسی غیرمجاز» (یا در نسخه‌های قدیمی‌تر بک‌اند، یک خطای خام دیتابیسی) رد می‌شن. قبل از پیاده‌سازی هر بخشی از این سند، اول [DRIVER_ACCOUNT_APP_FRONTEND_FA.md](DRIVER_ACCOUNT_APP_FRONTEND_FA.md) رو بخون.

## ۱. سه حالت فیچر

| | حالت یک — لحظه‌ای (مثل اسنپ) | حالت دو — متصل به رزرو | حالت سه — تاریخ‌دار (⚠️ جدید) |
|---|---|---|---|
| کاربر چطور شروع می‌کنه | باز کردن نقشه، انتخاب مبدا/مقصد، جستجوی راننده | از داخل یک رزرو کلینیک/همراه‌دار، انتخاب «راننده هم بیاد» | باز کردن نقشه، انتخاب مبدا/مقصد + یک تاریخ/ساعت دلخواه در آینده |
| راننده کِی مشخص می‌شه | Broadcast فوری، هرکی زودتر قبول کنه | Broadcast از همون لحظه‌ی ثبت رزرو (نه لحظه‌ی حرکت) | Broadcast فوری، هرکی زودتر قبول کنه |
| Endpoint شروع | `POST /EndUser/TripCurrent` | `POST /EndUser/TripReservation` | `POST /EndUser/TripScheduled` |
| به چی وصله | هیچی | `CompanionReserveId` | هیچی — فقط `ScheduledDepartureAt` |

هر سه حالت روی **همون Entity Trip** پیاده شدن و از **همون مکانیزم Broadcast/Accept/Reject/لغو/پیشرفت/پرداخت/کیف‌پول/کد تخفیف** (بخش‌های ۴ و ۶ همین سند) استفاده می‌کنن — تفاوت فقط در نحوه‌ی *ساخته‌شدن* اولیه‌ی سفره، نه در ادامه‌ی فلو. تفاوتشون فقط توی مقدار `CompanionReserveId`/`ScheduledDepartureAt`ـه.

⚠️ **یک محدودیت مشترک بین هر سه حالت**: هر کاربر در آن واحد فقط می‌تونه **یک سفرِ آنلاینِ فعال** (`isOnline=true` و وضعیتش `Requested` یا `Accepted`) داشته باشه — چه لحظه‌ای، چه رزروی، چه تاریخ‌دار. تا وقتی سفر قبلی به نتیجه نرسیده (پذیرفته/لغو/تکمیل نشده)، درخواست جدید (از هر سه نوع) با خطای «شما از قبل یک سفر آنلاین فعال دارید» رد می‌شه.

## ۲. قراردادهای عمومی

- **Base URL**: طبق `docs/ai/API_MAP.md` — سرویس Api روی پورت `5000`.
- **همه‌ی مسیرها**: `POST/GET/PUT https://{host}/api/{Area}/{Controller}[/{id}]`
  - Area برای کاربر (صاحب پت): `EndUser`
  - Area برای راننده: `Driver`
- **احراز هویت**: هدر `Authorization: Bearer {token}` روی همه‌ی این endpoint ها اجباریه (`[Authorize]`).
- **پاسخ همیشه HTTP 200** با پوشش زیر (هیچ‌وقت از HTTP status برای تشخیص موفقیت استفاده نکن، همیشه `isSuccess` رو چک کن):

```json
{
  "isSuccess": true,
  "code": 200,
  "messages": [],
  "data": { }
}
```

فیلدهای پاسخ camelCase هستن (`isSuccess`, `data`, ...) چون سریالایزیشن پیش‌فرض ASP.NET Core camelCase هست.

- **خطاها**: وقتی `isSuccess: false` باشه، متن خطا (فارسی، قابل‌نمایش مستقیم به کاربر) توی `messages` یا `data`-adjacent فیلد پیام میاد — دقیقاً مثل بقیه‌ی فرم‌های اپ.

## ۳. Enum های کلیدی

### `TripStatusId` (وضعیت کلی سفر — Code-backed، از `GET /EndUser/Code?groupLabel=Trip_Status` یا دیکشنری کد قابل خوندنه)

| Label | مقدار (id واقعی از DB میاد، این‌ها اسم‌ها هستن) | معنی |
|---|---|---|
| `TripStatus_Requested` | — | سفر ثبت شده، منتظر پذیرفتن راننده |
| `TripStatus_Accepted` | — | راننده پذیرفته، سفر «فعال»ه — فقط تو این حالت پولینگ لوکیشن زنده معنی داره |
| `TripStatus_Canceled` | — | لغو شده (کاربر یا راننده یا سیستم) |
| `TripStatus_Compeleted` | — | تمام شده |

> ⚠️ **مقدار عددی این‌ها رو هاردکد نکن** — همیشه از endpoint دیکشنری کد (`Code`/`CodeGroup`) بخون، دقیقاً مثل بقیه‌ی enum های Code-backed پروژه (`ProductStatus`, `OrderStatus` و ...). گروه‌شون `Trip_Status` و `Driver_Status` هست. برای اینکه چطور این دیکشنری رو بخونی، بخش ۳.۳ رو ببین (این بخش از سند تا الان وجود نداشت و نسخه‌ی قبلی endpoint اشتباهی رو مثال زده بود).

### ۳.۱ `CancelInitiatorId` (چه کسی سفر را لغو کرده — **فقط یک عدد int ساده، Code-backed نیست**، فقط وقتی `tripStatusId == Canceled` معنی داره)

| مقدار | معنی |
|---|---|
| `1` | راننده لغو کرده |
| `2` | کاربر لغو کرده |
| `null` | سفر لغو نشده |

### ۳.۲ `CancelReasonCode` / `CancelReasonCodeId` / `CancelReasonDetail` (دلیل لغو — Code-backed، جدا برای راننده و کاربر)

وقتی سفری لغو می‌شه (بخش ۴.۸ و ۶.۵ رو ببین)، سه فیلد جدید روی `TripDto`/`TripVDto` پر می‌شه:

| فیلد | نوع | توضیح |
|---|---|---|
| `cancelInitiatorId` | `number \| null` | طبق جدول ۳.۱ |
| `cancelReasonCodeId` | `number \| null` | شناسه‌ی ردیف انتخاب‌شده از دیکشنری دلیل لغو |
| `cancelReasonCode` | `{ id, name, label } \| null` | همون Code به‌صورت باز‌شده — `cancelReasonCode.name` متن فارسی قابل‌نمایشه |
| `cancelReasonDetail` | `string \| null` | توضیح آزاد اختیاری که کاربر/راننده کنار دلیل انتخابی نوشته |

⚠️ دو تا گروه **کاملاً جدا**ست — لیست دلایل راننده با لیست دلایل کاربر فرق داره:

- گروه دلایل راننده: `TripCancelReason_Driver`
- گروه دلایل کاربر: `TripCancelReason_User`

این لیست‌ها از پنل ادمین قابل مدیریت‌ان (اضافه/ویرایش/غیرفعال‌کردن گزینه)، پس **هاردکد نکن** — همیشه در لحظه‌ی نمایش فرم لغو، از endpoint زیر بخون.

### ۳.۳ دیکشنری Code/CodeGroup — endpoint واقعی (قبلاً توی این سند اشتباه مستند شده بود)

```
GET /EndUser/Code?codeGroupLabel={label}
GET /Driver/Code?codeGroupLabel={label}
```

⚠️ اسم query param **`codeGroupLabel`** هست، نه `groupLabel` (نسخه‌ی قبلی این سند اشتباه نوشته بود و اصلاً چنین endpoint ای هم وجود نداشت — این دو مسیر تازه اضافه شدن). مثال:

```
GET /EndUser/Code?codeGroupLabel=TripCancelReason_User
GET /Driver/Code?codeGroupLabel=TripCancelReason_Driver
```

پاسخ یک `CodeSearchDto` صفحه‌بندی‌شده‌ست (شبیه بقیه‌ی لیست‌های پروژه)، هر آیتمش:

```jsonc
{ "id": 138, "name": "منصرف شدم", "label": "TripCancelReason_User_ChangedMind", "value": "...", "priority": 60, "active": true }
```

- برای نمایش به کاربر از `name` استفاده کن (فارسی، قابل‌نمایش مستقیم).
- گزینه‌های `active: false` رو توی فرم انتخاب نشون نده.
- بر اساس `priority` (نزولی) مرتب کن.
- همین دو مسیر برای هر گروه Code دیگه‌ای هم (مثلاً `Trip_Status`، `Driver_Status` که در بخش ۳ اشاره شد) کار می‌کنه — یعنی دیگه لازم نیست این مقادیر رو هاردکد کنی.

### `ProgressStageId` (مرحله‌ی ریز پیشرفت — **فقط یک عدد int ساده، Code-backed نیست**، فقط وقتی `TripStatusId == Accepted`معنی داره)

| مقدار | معنی |
|---|---|
| `0` | هنوز شروع نشده (None) |
| `1` | راننده در مسیر مبدا (EnRouteOrigin) |
| `2` | راننده به مبدا رسید (ArrivedOrigin) |
| `3` | پت تحویل گرفته شد، سفر آغاز شد (PetPickedUp) |
| `4` | به مقصد رسید (ArrivedDestination) |

این عدد رو مستقیم توی `TripDto`/`TripVDto`/`TripLiveDto` می‌گیری، نیازی به دیکشنری کد نیست.

**نکته‌ی رفت‌وبرگشت (`RoundTrip`)**: اگه سفر رفت‌وبرگشت باشه، وقتی راننده به مقصد می‌رسه (مرحله ۴)، اگه هنوز مسیر برگشت شروع نشده باشه (`isReturnLeg == false`)، بک‌اند خودش مبدا/مقصد رو جابه‌جا می‌کنه و `ProgressStageId` رو دوباره به `1` برمی‌گردونه و `IsReturnLeg = true` می‌کنه. یعنی UI باید به `isReturnLeg` هم نگاه کنه، نه فقط `progressStageId`، تا بفهمه توی کدوم لگ از سفره.

## ۴. حالت یک — سفر لحظه‌ای

### ۴.۱ پیش‌نمایش قیمت (قبل از ثبت نهایی)

```
POST /EndUser/PriceCalculation
```
Body: یک `TripDto` نیمه‌پر (حداقل `Origin`, `Destination`, گزینه‌های انتخابی) → پاسخ شامل قیمت محاسبه‌شده. این یه endpoint موجود از قبل بود، تغییری نکرده.

### ۴.۲ ثبت سفر

```
POST /EndUser/TripCurrent
```

Body (`TripDto` — فقط فیلدهای مرتبط با پت‌رسان رو لیست می‌کنم، بقیه‌ی فیلدهای عمومی سفر قبلاً بوده):

```jsonc
{
  "origin": { "x": 51.389, "y": 35.6892 },       // x=lng, y=lat
  "destination": { "x": 51.41, "y": 35.70 },
  "fromAddress": "string",
  "toAddress": "string",
  "roundTrip": false,
  "userPetIds": [12, 15],                          // ← جدید: چند پت در یک سفر
  "tripOptionIds": [1, 2],                          // گزینه‌های سفر (قبلاً بوده)
  "userDetail": "توضیح کاربر (اختیاری)"
  // userId توسط بک‌اند از توکن پر می‌شه، لازم نیست بفرستی
}
```

> `userPetIds` جایگزین فیلد قدیمی `userPetId` شده. فیلد قدیمی هنوز برای سازگاری عقب‌رو پر می‌شه (اولین پت لیست) ولی **در UI جدید همیشه از `userPetIds` استفاده کن**.

پاسخ: `BaseResultDto<TripVDto>` — شامل `id` سفر تازه‌ساخته‌شده، که برای مراحل بعدی لازمشه.

پت‌ها رو از `GET /EndUser/UserPet` (endpoint موجود) بگیر و به کاربر چندانتخابی نشون بده.

### ۴.۳ گرفتن سفر جاری / پولینگ وضعیت کلی

```
GET /EndUser/TripCurrent
```

اگه سفر فعالی وجود نداشته باشه `data: null` برمی‌گرده. این رو هر چند ثانیه (مثلاً هر ۵ ثانیه، قبل از پذیرفته‌شدن توسط راننده) صدا بزن تا بفهمی راننده پذیرفته یا نه (`tripStatusId` عوض میشه).

### ۴.۴ موقعیت زنده‌ی راننده (فقط وقتی سفر `Accepted` شد)

```
GET /EndUser/TripLive/{tripId}
```

پاسخ (`TripLiveDto`):

```jsonc
{
  "tripStatusId": 76,               // Accepted
  "progressStageId": 2,             // ArrivedOrigin
  "isReturnLeg": false,
  "counterpartLocation": { "x": 51.395, "y": 35.691 },   // آخرین موقعیت شناخته‌شده‌ی راننده
  "counterpartLocationUpdatedAt": "2026-08-24T10:15:03"
}
```

- **Polling interval پیشنهادی: هر ۳ تا ۵ ثانیه** (طبق تصمیم پروژه — نه SignalR، چون WebSocket روی سرور فعلی مشکل ۵۰۴ داره).
- اگه سفر `Accepted` نباشه، این endpoint خطای «سفر در حال حاضر فعال نیست» برمی‌گردونه — یعنی UI باید فقط وقتی وارد صفحه‌ی «سفر فعال» شدی این رو صدا بزنی، نه همیشه.
- `counterpartLocation` ممکنه `null` باشه اگه راننده هنوز هیچ لوکیشنی نفرستاده — این حالت رو توی UI هندل کن (مثلاً «در حال دریافت موقعیت راننده...»).

### ۴.۵ نمایش مراحل پیشرفت

همون `GET /EndUser/TripCurrent` یا `GET /EndUser/TripLive/{id}` مقدار `progressStageId`/`isReturnLeg` رو می‌ده — طبق جدول بخش ۳ روی UI (مثلاً یک stepper ۴ مرحله‌ای) نمایش بده. **کاربر خودش این مرحله رو تغییر نمی‌ده — فقط راننده.**

### ۴.۶ کد تخفیف و کیف‌پول — فرایند کامل و دقیق

⚠️ **قانون مشترک همه‌ی endpoint های این بخش**: فقط وقتی سفر `tripStatusId == Accepted` باشه کار می‌کنن (یعنی حتماً بعد از پذیرشِ راننده — بخش ۶.۳) و فقط تا وقتی که یک پرداخت فعال/موفق برای همون سفر شروع نشده. اگه پرداخت شروع شده باشه، خطای «اطلاعات مالی سفر پس از شروع پرداخت قفل است» می‌گیری — یعنی UI باید بعد از رفتن به مرحله‌ی پرداخت (۴.۷)، دیگه اجازه‌ی برگشتن و تغییر کد تخفیف/کیف‌پول رو نده.

هر دو تا، مستقیم روی همون فیلدهای خودِ `Trip` اثر می‌ذارن — یعنی همون سفری که با `TripCurrent`/`TripReservation`/`TripScheduled` گرفتی، بعد از این تغییرات دوباره بگیرش تا مبلغ نهایی به‌روز رو ببینی.

#### ۴.۶.۱ اعمال کد تخفیف

```
PUT /EndUser/TripSetRebate
```
Body: `{ "id": 4210, "rebateCode": "pastil-club-20" }`

منطق دقیق سمت بک‌اند:
1. کد تخفیف اعتبارسنجی می‌شه (فعال بودن، بازه‌ی تاریخ، سقف تعداد کلی/هر‌کاربر، حداقل مبلغ، اختصاصی‌بودن به کاربر) — همون قوانین عمومیِ موتور تخفیف پروژه، مخصوص پت‌رسان نیست.
2. اگه معتبر بود: `trip.rebateId` پر می‌شه، `trip.rebatePrice` = مبلغ تخفیف محاسبه‌شده، و **`trip.paymentPrice = trip.price - trip.rebatePrice`** — یعنی مبلغِ نهایی‌ای که باید پرداخت بشه همینه، نه `price` خام.
3. اگه نامعتبر بود (منقضی، سقف تمام‌شده، ...): پیام خطای دقیق برمی‌گرده (مثلاً «این کد تخفیف منقضی شده است»)، چیزی تغییر نمی‌کنه.

⚠️ کدهای تخفیف بر اساس `TypeId` محدود به یک فرایند خاص‌ان — کدی که برای رزرو نماینده ساخته شده، برای پت‌رسان قابل استفاده نیست و برعکس (Label مربوطه: `RebateType_Trip`). این محدودیت رو خودِ بک‌اند چک می‌کنه.

#### ۴.۶.۲ حذف کد تخفیف

```
PUT /EndUser/TripRemoveRebate?id={tripId}
```
بدون body — `id` توی query string میاد، نه توی route و نه توی body. با موفقیت، `rebateId`/`rebatePrice` صفر می‌شن و `paymentPrice` برمی‌گرده به `price` کامل (به‌علاوه‌ی سهم کیف‌پول اگه فعال بود — بخش بعدی).

#### ۴.۶.۳ استفاده از کیف‌پول

```
PUT /EndUser/TripSetWallet
```
Body: `{ "id": 4210, "fromWallet": true }` (یا `false` برای غیرفعال‌کردن)

⚠️ نکته‌ی مهم که ممکنه گیج‌کننده باشه: زدن `fromWallet: true` فقط **نیت استفاده از کیف‌پول** رو ثبت می‌کنه، نه مبلغ دقیق کسرشده رو. سمت بک‌اند فقط `trip.fromWallet = true` و `trip.walletPrice = trip.paymentPrice` (یعنی فرض اولیه: کل مبلغ باقیمانده از کیف‌پول). محاسبه‌ی واقعیِ اینکه موجودی کیف‌پول کاربر واقعاً کافیه یا نه، و چقدرش رو واقعاً می‌شه از کیف‌پول کم کرد، **دیرتر، لحظه‌ی شروع پرداخت** (بخش ۴.۷) انجام می‌شه:
- اگه موجودی کیف‌پول ≥ کل مبلغ باقیمانده: کل پرداخت داخل همون کیف‌پول تسویه می‌شه، اصلاً نیازی به درگاه/redirect نیست.
- اگه موجودی کیف‌پول کمتر بود: فقط همون مقدار از کیف‌پول کسر می‌شه، باقیمونده می‌ره به درگاه (تستی یا واقعی).
- برداشتِ واقعی از کیف‌پول **فقط بعد از تایید نهایی/Callback موفق پرداخت** قطعی می‌شه — یعنی اگه پرداخت (بخشِ باقیمانده از درگاه) fail بشه، از کیف‌پول هم چیزی کم نمی‌شه.

برای غیرفعال‌کردن، همین endpoint رو با `fromWallet: false` بزن — `walletPrice` صفر می‌شه.

#### ۴.۶.۴ ترتیب پیشنهادی برای UI

1. بعد از پذیرش راننده (بخش ۶.۳)، صفحه‌ی «تایید و پرداخت» رو باز کن — `trip.price` رو به‌عنوان مبلغ پایه نشون بده.
2. اگه کاربر کد تخفیف داره، فیلد کد تخفیف رو نشون بده → با تایید، `TripSetRebate` بزن → دوباره سفر رو بگیر (`TripCurrent`/معادلش) و `paymentPrice` جدید رو نشون بده.
3. اگه کاربر کیف‌پول فعال داره، سوییچ «پرداخت از کیف‌پول» رو نشون بده → با فعال‌کردن، `TripSetWallet` بزن.
4. مبلغ نهاییِ واقعاً قابل‌پرداخت از درگاه = همیشه از پاسخِ خودِ `TripPayment` (بخش ۴.۷، فیلد `amount`) بخون، نه چیزی که خودت حساب کنی — چون فقط بک‌اند دقیقاً می‌دونه بعد از کسر کیف‌پول/تخفیف چقدر واقعاً باید از درگاه گرفته بشه.
5. برای جزئیات کامل‌تر پاسخ شروع پرداخت (سه حالت تسویه، ساختار دقیق JSON، حالت تست) به [PAYMENT_TEST_MODE_SITE_FA.md](PAYMENT_TEST_MODE_SITE_FA.md) مراجعه کن — این سند برای *همه‌ی* فرایندهای پرداخت پروژه (نه فقط پت‌رسان) قرارداد یکسانی داره.

### ۴.۷ پرداخت

```
POST /EndUser/TripPayment
```

⚠️ برای این بخش (شروع پرداخت، سه حالت تسویه، حالت تست، ساختار دقیق پاسخ، کد نمونه‌ی `continuePayment()`، و endpoint های کد تخفیف/کیف‌پول مخصوص سفر — `TripSetRebate`/`TripRemoveRebate`/`TripSetWallet`) به‌جای تکرار اینجا، مستند اختصاصی و کامل‌تری هست که از قبل نوشته شده و پرداخت سفر رو هم صراحتاً پوشش می‌ده: **[PAYMENT_TEST_MODE_SITE_FA.md](PAYMENT_TEST_MODE_SITE_FA.md)**. حتماً قبل از پیاده‌سازی این بخش، اون سند رو کامل بخون — چیزی سمت بک‌اند کم نیست، فقط باید همون قرارداد رو دقیق پیاده کنی.

### ۴.۸ لغو توسط کاربر (⚠️ endpoint و قرارداد عوض شده — تغییر breaking نسبت به نسخه‌ی قبلی این سند)

`PUT /EndUser/UpdateTripUserStatus` با `tripStatusId: <Canceled>` **دیگه کار نمی‌کنه** — همیشه خطای «امکان تغییر وضعیت وجود ندارد» برمی‌گردونه. لغو سفر الان یک endpoint اختصاصی داره چون **ثبت دلیل لغو اجباریه**:

```
PUT /EndUser/TripUserCancel
```

Body (`TripUserCancelDto`):

```jsonc
{
  "id": 4210,                    // شناسه‌ی سفر
  "cancelReasonCodeId": 141,     // اجباری — از GET /EndUser/Code?codeGroupLabel=TripCancelReason_User (بخش ۳.۳)
  "cancelDetail": "توضیح آزاد اختیاری کاربر (اختیاری، می‌تونه خالی/null باشه)"
}
```

پاسخ: `BaseResultDto<TripVDto>` با `tripStatusId = Canceled`، `cancelInitiatorId = 2` (کاربر)، `cancelReasonCodeId`/`cancelReasonCode`/`cancelReasonDetail` پر شده.

قوانین رد شدن (پیام فارسی مستقیم قابل‌نمایش):
- اگه `progressStageId >= 3` (پت از قبل تحویل گرفته شده): «پت تحویل گرفته شده و سفر دیگر از این مسیر قابل لغو نیست.» — **دکمه‌ی «لغو سفر» رو توی UI بعد از این مرحله غیرفعال/مخفی کن**.
- اگه سفر از قبل `Compeleted` یا `Canceled` باشه: «امکان تغییر وضعیت وجود ندارد».
- اگه `cancelReasonCodeId` معتبر نباشه یا از گروه `TripCancelReason_User` نباشه (مثلاً اشتباهی شناسه‌ی یک دلیل راننده فرستاده بشه): همون خطای بالا.

⚠️ **این لغو دیگه «بازنشانی» نیست — قطعیه (مختومه/terminal)**. برخلاف رفتار قدیمی سیستم (لغو راننده که خودکار سفر رو دوباره به حالت بی‌راننده برمی‌گردوند)، از این به بعد یک سفرِ لغوشده **برای همیشه لغو باقی می‌مونه** — نه خودش دوباره فعال می‌شه، نه خودکار به راننده‌های دیگه Broadcast می‌شه. اگه کاربر هنوز می‌خواد سفر بگیره، باید **درخواست جدید ثبت کنه** — بخش ۴.۸.۱ رو ببین.

اگه سفر یک راننده‌ی پذیرفته‌شده داشت (`driverId` پر بود)، راننده یک پوش «سفر توسط کاربر لغو شد» می‌گیره (پوش جدید `PushTripUserCanceled`) — کاری از UI لازم نیست، فقط اگه لازم بود deep-link مناسب بزن.

### ۴.۸.۱ بعد از لغو — ثبت درخواست جدید (pre-filled resubmit)

طبق فلوی مورد نظر پروڑه: بعد از لغو (چه توسط کاربر خودش از ۴.۸، چه توسط راننده — بخش ۶.۵)، **UI باید کاربر رو به همون صفحه‌ی «درخواست سفر» برگردونه، با تمام اطلاعات سفر قبلی از پیش پرشده** (مبدا/مقصد/پت‌ها/گزینه‌ها/...)، تا کاربر بتونه بدون تغییر یا با ویرایش دوباره ثبت کنه.

وقتی کاربر دکمه‌ی ثبت رو دوباره می‌زنه، دقیقاً همون `POST /EndUser/TripCurrent` قبلی (بخش ۴.۲) رو صدا بزن، **فقط با یک فیلد جدید اضافه**:

```jsonc
{
  // ... همون فیلدهای همیشگی بخش ۴.۲ (origin, destination, userPetIds, ...) ...
  "previousTripId": 4210   // ⚠️ جدید — شناسه‌ی سفرِ لغوشده‌ای که این درخواست جایگزینش می‌شه
}
```

اهمیت `previousTripId`: بک‌اند با این فیلد می‌فهمه این یک درخواست جایگزین (resubmit) هست، نه یک سفر کاملاً بی‌ربط، و در نتیجه:
- **اگه سفر قبلی توسط یک راننده‌ی مشخص لغو شده بود**، همون راننده در سفر جدید هم مستثنا می‌مونه — یعنی نه پوش «سفر جدید» می‌گیره، نه توی لیست سفرهای در دسترسش (`GET /Driver/TripAvailable`، بخش ۶.۱) می‌بینتش.
- بقیه‌ی راننده‌ها عادی سفر جدید رو می‌بینن و می‌تونن قبولش کنن؛ هر کدوم که قبول کرد، فلو دقیقاً مثل بخش ۴.۲ به بعد ادامه پیدا می‌کنه.

اگه `previousTripId` رو نفرستی (یا سفر قبلی مال همین کاربر نبود یا لغو نشده بود)، بک‌اند این فیلد رو نادیده می‌گیره و رفتار عادی (بدون هیچ استثنایی) اجرا می‌شه — یعنی فرستادنش برای یک سفر کاملاً تازه (بدون سفر لغوشده‌ی قبلی) ضرری نداره، فقط لازم نیست.

### ۴.۹ پایان سفر و امتیازدهی

بعد از `TripStatus_Compeleted`، فلوی امتیازدهی/نظر (فیلدهای `userRate`/`userComment` روی همون `Trip`) از قبل موجوده — تغییری نکرده.

## ۵. حالت دو — سفر متصل به رزرو

### ۵.۱ پیش‌نیاز: کاربر باید از قبل یک رزرو (Companion) داشته باشه

از `GET /EndUser/CompanionReserve` (endpoint موجود) رزروهای آینده‌ی کاربر رو بگیر و توی صفحه‌ی رزرو، گزینه‌ی «راننده هم بیاد» رو نشون بده.

### ۵.۲ ثبت سفر رزروی

```
POST /EndUser/TripReservation
```

Body (`TripReservationCreateDto`):

```jsonc
{
  "companionReserveId": 4021,
  "origin": { "x": 51.389, "y": 35.6892 },
  "destination": { "x": 51.41, "y": 35.70 },
  "fromAddress": "string",
  "toAddress": "string",
  "scheduledLeadMinutes": 60,        // فقط 60 یا 120 مجازه — گزینه‌ی رادیویی به کاربر بده، نه ورودی آزاد
  "ownerRidesAlong": true,
  "userPetIds": [12]
}
```

خطاهای رایج که ممکنه برگرده (پیام‌های فارسی مستقیم قابل‌نمایش):
- فاصله‌ی زمانی غیر از ۶۰/۱۲۰ → «فاصله‌ی زمانی حرکت راننده فقط می‌تواند ۶۰ یا ۱۲۰ دقیقه باشد.»
- رزرو پیدا نشد یا مال این کاربر نیست → پیام «یافت نشد»
- زمان محاسبه‌شده‌ی حرکت (`DoDate - leadMinutes`) از الان گذشته باشه → رد می‌شه (رزرو خیلی نزدیکه، دیگه نمی‌شه راننده رزرو کرد)
- برای همون رزرو قبلاً یه سفر پت‌رسان ثبت شده → رد می‌شه (هر رزرو فقط یک سفر متصل می‌تونه داشته باشه)

پاسخ موفق: `TripDto` تازه‌ساخته‌شده با `tripStatusId = Requested` و `driverId = null` — **راننده هنوز مشخص نیست**، ولی قیمت (`price`) از همون لحظه محاسبه و پر شده — نمایشش بده.

⚠️ **مهم — این متد ممکنه با پیام مشخص رد بشه، نه فقط چیزهای بخش ۵.۲**: اگه برای ساعتِ دقیقِ حرکتِ محاسبه‌شده (`DoDate - leadMinutes`) هیچ ردیف قیمت‌گذاری‌ای توی بک‌اند تنظیم نشده باشه، قیمت صفر درمیاد و کل درخواست رد می‌شه (پیام: «قیمت نهایی در دسترس نیست»). این یعنی رزرو برای بعضی ساعت‌های خاص ممکنه شکست بخوره حتی وقتی همه‌چیز درسته — تقصیر UI نیست، تنظیمات قیمت‌گذاریِ اون بازه‌ی ساعتی ادمین رو باید چک کرد.

### ۵.۳ چی بعدش اتفاق می‌افته — ⚠️ کاملاً عوض شد (تغییر breaking نسبت به نسخه‌ی قبلی این سند)

رفتار قدیمی (auto-dispatch نزدیک‌ترین راننده دقیقاً در لحظه‌ی حرکت) **حذف شد**. الان دقیقاً مثل حالت یک عمل می‌کنه:

- همون لحظه‌ی ثبت درخواست (نه لحظه‌ی حرکت)، به همه‌ی راننده‌های فعال Broadcast می‌شه (`PushTripRequestAvailable`) — یعنی راننده‌ها از همون الان می‌تونن قبول کنن، نه فقط دقیقه‌ی آخر.
- **ثبت رزرو معطل این نمی‌مونه** — این endpoint فوراً برمی‌گرده، بدون اینکه منتظر تایید هیچ راننده‌ای بمونه. کاربر می‌تونه مسیر رزروش رو عادی ادامه بده.
- هر راننده‌ای که زودتر قبول کنه (از همون مسیر بخش ۶.۱-۶.۳ — `GET /Driver/TripAvailable` و `PUT /Driver/UpdateTripDriverStatus`)، سفر مال اونه.
- **اگه تا نزدیکی موعد حرکت هیچ راننده‌ای قبول نکنه**: دیگه سیستم خودکار کسی رو اختصاص نمی‌ده. یک یادآوری برای ادمین می‌ره تا از پنل یک راننده رو دستی انتخاب کنه (`PUT /Admin/TripChooseDriver`) — این هم دقیقاً همون اثر «راننده قبول کرد» رو داره (سفر مستقیم Accepted می‌شه).

### ۵.۴ نمایش وضعیت به کاربر — «فلان راننده تایید کرد» (⚠️ endpoint جدید)

چون پذیرش دیگه فوری نیست (ممکنه چند دقیقه یا حتی ساعت طول بکشه تا یه راننده Broadcast رو قبول کنه)، توی صفحه‌ی جزئیات همون رزرو (نه صفحه‌ی عمومی «سفر جاری») باید بشه وضعیتِ دقیقاً همون سفرِ متصل‌به‌این‌رزرو رو دید:

```
GET /EndUser/TripReservation/{companionReserveId}
```

پاسخ: `BaseResultDto<TripVDto>`. اگه `data.driverId` پر بود یعنی `data.driver.name` رو نشون بده («فلان راننده سفر شما رو پذیرفت»)؛ اگه `data` اصلاً `null`/`isSuccess:false` بود یعنی هنوز هیچ سفری برای این رزرو ثبت نشده (یا رزرو، پت‌رسان نداره)؛ اگه `data` بود ولی `driverId` هنوز `null` بود یعنی «در انتظار تایید راننده»‌ست. همین یک endpoint رو هر چند ثانیه (وقتی کاربر توی همین صفحه‌ست) پولینگ کن — نیازی به `GET /EndUser/TripCurrent` برای این منظور نیست (اون فقط برای سفر لحظه‌ایِ *فعال* معنی داره، نه برای پیگیریِ یک رزرو مشخص در طول زمان).

## ۵.۵ حالت سه — سفر تاریخ‌دار (⚠️ کاملاً جدید)

برای وقتی کاربر می‌خواد پت‌رسان رو برای یک تاریخ/ساعت مشخص در آینده رزرو کنه، **بدون** اینکه به هیچ رزرو کلینیکی وصل باشه (مثلاً می‌خواد فردا ساعت ۵ عصر پتش رو جایی ببره).

### ۵.۵.۱ ثبت درخواست

```
POST /EndUser/TripScheduled
```

Body (`TripScheduledCreateDto`):

```jsonc
{
  "origin": { "x": 51.389, "y": 35.6892 },
  "destination": { "x": 51.41, "y": 35.70 },
  "fromAddress": "string",
  "toAddress": "string",
  "scheduledDepartureAt": "2026-09-02T17:00:00",  // تاریخ/ساعتِ دقیقی که راننده باید در مبدا حاضر باشه — باید در آینده باشه
  "roundTrip": false,
  "ownerRidesAlong": true,
  "userPetIds": [12],
  "tripOptionIds": [1, 2]
}
```

خطاهای رایج (پیام‌های فارسی مستقیم قابل‌نمایش):
- مبدا/مقصد خالی → پیام مشخص برای هرکدوم
- `scheduledDepartureAt` در گذشته باشه → «امکان انتخاب زمان گذشته وجود ندارد.»
- کاربر از قبل یک سفر آنلاین فعال دیگه داشته باشه (هر سه حالت) → «شما از قبل یک سفر آنلاین فعال دارید»
- قیمتِ محاسبه‌شده برای اون ساعتِ خاص صفر دربیاد (تنظیمات قیمت‌گذاری اون بازه‌ی ساعتی رو پوشش نمی‌ده) → «قیمت نهایی در دسترس نیست» — دقیقاً همون مشکلی که برای حالت دو هم توضیح داده شد (بخش ۵.۲)، اینجا هم می‌تونه پیش بیاد چون ساعتِ دلخواهِ کاربر می‌تونه هر ساعتی از شبانه‌روز باشه.

پاسخ موفق: `TripDto` تازه‌ساخته‌شده با `tripStatusId = Requested`، `driverId = null`، `price` پر شده. **همون لحظه به همه‌ی راننده‌ها Broadcast می‌شه** — دقیقاً مثل حالت یک، نه مثل رفتار قدیمیِ حالت دو. ثبت این درخواست معطل تایید هیچ راننده‌ای نمی‌مونه.

### ۵.۵.۲ ادامه‌ی فلو — دقیقاً مثل حالت یک

از اینجا به بعد **هیچ تفاوتی با حالت یک نداره**:
- راننده از `GET /Driver/TripAvailable` می‌بینتش و با `PUT /Driver/UpdateTripDriverStatus` قبول/رد می‌کنه (بخش ۶.۱-۶.۳).
- بعد از پذیرش، پرداخت امکان‌پذیر می‌شه (بخش ۴.۷ و ۴.۷.۱ زیر — کیف‌پول و کد تخفیف هم همونجا).
- در همون تاریخ/ساعتِ `scheduledDepartureAt`، راننده باید حاضر بشه و مراحل رو طی کنه (`TripArrivedOrigin` → `TripPetPickedUp` → `TripArrivedDestination`، بخش ۶.۴) — بک‌اند زمان‌بندی رو خودش اجباری نمی‌کنه (راننده هر وقت واقعاً برسه می‌تونه بزنه)، این یک تعهدِ زمانی UX سطح بالاست، نه یک قفلِ فنی.
- اگه تا نزدیکی موعد هیچ راننده‌ای قبول نکنه، دقیقاً مثل حالت دو (بخش ۵.۳)، ادمین می‌تونه از پنل دستی یک راننده انتخاب کنه.

برای پیگیری وضعیت («کدوم راننده قبول کرد»)، همون `GET /EndUser/TripCurrent` رو پولینگ کن (چون این سفر هم `isOnline=true` هست، دقیقاً مثل حالت یک رفتار می‌کنه — برخلاف حالت دو که یک endpoint اختصاصی داره، چون حالت دو باید برای *رزروِ خاص* پیگیری بشه نه برای «سفر جاری کاربر»).

## ۶. سمت راننده

### ۶.۱ سفرهای در دسترس — Broadcast (⚠️ این بخش قبلاً اصلاً مستند نشده بود)

وقتی یک کاربر سفر لحظه‌ای (حالت ۱) ثبت می‌کنه، بک‌اند به **همه‌ی راننده‌های فعال و تاییدشده** پوش می‌فرسته (`PushTripRequestAvailable`) — این یک انتخاب‌شونده‌ی تکی نیست، سفر برای همه باز نمایش داده می‌شه تا هرکی زودتر قبول کنه ببرتش (دقیقاً مثل اسنپ). صفحه‌ی «سفرهای پیشنهادی» راننده باید این لیست رو نشون بده:

```
GET /Driver/TripAvailable
```

پاسخ: `BaseResultDto<TripVDto[]>` — همه‌ی سفرهای `tripStatusId == Requested && driverId == null && isOnline == true`، قدیمی‌ترین اول، **به‌جز سفرهایی که همین راننده قبلاً رد کرده یا (در نسخه‌ی قبلی‌شون) لغو کرده** — بک‌اند خودش این فیلتر رو انجام می‌ده، لازم نیست UI چیزی فیلتر کنه.

⚠️ **این endpoint توکن راننده رو می‌خونه** (`driverId` از `Authorize` توکن استخراج می‌شه) — یعنی نتیجه‌ش برای هر راننده می‌تونه فرق کنه حتی برای سفرهای عمومیِ یکسان.

پیشنهاد UX: این لیست رو هر چند ثانیه پولینگ کن (مثل بقیه‌ی جاهای این فیچر، ۳-۵ ثانیه) وقتی صفحه‌ی «سفرهای پیشنهادی» بازه، و روی دریافت پوش `PushTripRequestAvailable` هم بلافاصله رفرش کن.

### ۶.۲ سفر جاری/پذیرفته‌شده

```
GET /Driver/TripCurrent
```

سفری که همین راننده الان `Requested` یا `Accepted` داره (نه لیست عمومی — فقط سفر خودش).

### ۶.۳ پذیرش/رد سفر

```
PUT /Driver/UpdateTripDriverStatus
```
Body: `{ id: tripId, driverStatusId: <Accepted|Rejected> }` — `driverId` رو خودت نفرست، بک‌اند از توکن راننده پر می‌کنه.

**قبول (`Accepted`)**:
- اتمیک/race-safe — اگه دو راننده هم‌زمان قبول بزنن، فقط اولی که واقعاً commit بشه برنده‌ست؛ دومی خطای «این سفر برای راننده‌ی دیگری رزرو شده است.» می‌گیره. **دکمه‌ی قبول رو بعد از تپ کردن غیرفعال کن و منتظر پاسخ بمون** — این خطا توی UI طبیعیه، پیام رو نشون بده و کاربر رو به لیست سفرهای در دسترس (۶.۱) برگردون.
- بک‌اند خودکار `progressStageId` رو `1` (EnRouteOrigin) می‌کنه و سفر از لیست سایر راننده‌ها (۶.۱) ناپدید می‌شه.

**رد (`Rejected`)**:
- ⚠️ رد کردن **سفر رو نمی‌بنده** — سفر همچنان `Requested`/بی‌راننده باقی می‌مونه و برای بقیه‌ی راننده‌ها قابل دیدن/قبول‌شدنه. فقط برای **همین راننده** دیگه توی `GET /Driver/TripAvailable` نشون داده نمی‌شه (نه یک وضعیت مشترک روی خود سفر — مخصوص هر راننده جداست).
- بعد از رد کردن، UI باید همون سفر رو از لیست محلی حذف کنه (یا لیست رو رفرش کنه) و به سفر بعدی بره — دیگه هیچ‌وقت این سفر رو برای این راننده نشون نده (حتی بعد از رفرش/باز‌کردن دوباره‌ی اپ، چون این استثنا سمت سرور دائمیه).

### ۶.۴ اعلام مراحل (هر سه‌تا فقط `PUT`، بدون body، `id` توی route)

```
PUT /Driver/TripArrivedOrigin/{tripId}      → به مبدا رسیدم
PUT /Driver/TripPetPickedUp/{tripId}         → پت رو تحویل گرفتم
PUT /Driver/TripArrivedDestination/{tripId}  → به مقصد رسیدم
```

قوانین مهم که باید توی UI رعایت بشه (بک‌اند هم اجباری می‌کنه، ولی بهتره دکمه‌ها رو هم UI-side غیرفعال کنی تا خطای بی‌مورد نگیره):
- **ترتیب اجباریه** — نمی‌شه مرحله رو رد کرد یا برگردوند عقب. اگه `progressStageId` فعلی `1` باشه فقط `TripArrivedOrigin` مجازه، بعدش فقط `TripPetPickedUp`، بعدش فقط `TripArrivedDestination`.
- سفر باید `TripStatusId == Accepted` باشه، وگرنه خطای «مرحله‌ی درخواستی با توالی مجاز سفر همخوانی ندارد.» می‌گیری.
- بعد از هر مرحله، پوش خودکار برای کاربر می‌ره (نیازی به کاری از UI نیست).
- روی `TripArrivedDestination` برای سفر رفت‌وبرگشت: اگه هنوز لگ برگشت شروع نشده، همون درخواست باعث می‌شه `progressStageId` دوباره `1` بشه (رفتن به لگ برگشت) — یعنی دکمه‌ی بعدی که باید فعال بشه دوباره «به مبدا رسیدم» می‌شه، نه «پایان سفر». به `isReturnLeg` نگاه کن تا بفهمی این آخرین‌باره یا لگ برگشته.

### ۶.۵ لغو توسط راننده (⚠️ endpoint و قرارداد عوض شده — این بخش قبلاً اصلاً مستند نشده بود)

```
PUT /Driver/TripDriverCancel
```

Body (`TripDriverCancelDto` — قبلاً این endpoint فقط `PUT /Driver/TripDriverCancel/{id}` بدون body بود؛ الان body اجباریه چون دلیل لغو باید ثبت بشه):

```jsonc
{
  "id": 4210,
  "cancelReasonCodeId": 121,   // اجباری — از GET /Driver/Code?codeGroupLabel=TripCancelReason_Driver (بخش ۳.۳)
  "cancelDetail": "توضیح آزاد اختیاری راننده"
}
```

پاسخ: `BaseResultDto<TripVDto>` با `tripStatusId = Canceled`، `cancelInitiatorId = 1` (راننده).

قوانین رد شدن:
- فقط سفرِ **همین راننده** (سفری که `driverId` خودشه) و فقط وقتی `tripStatusId == Accepted`.
- اگه `progressStageId >= 3` (پت از قبل تحویل گرفته شده): «سفر پس از تحویل‌گرفتن پت توسط راننده قابل لغو نیست.»
- اگه `cancelReasonCodeId` معتبر نباشه یا از گروه `TripCancelReason_Driver` نباشه: خطای «امکان تغییر وضعیت وجود ندارد».

⚠️ **رفتار قدیمی حذف شده**: قبلاً لغو راننده باعث می‌شد سفر خودکار به حالت بی‌راننده برگرده و دوباره برای همه Broadcast بشه (بدون ثبت هیچ دلیلی). این رفتار **کاملاً برداشته شده**. الان لغو راننده یعنی سفر **قطعاً بسته می‌شه** (مختومه) — سیستم خودش هیچ سفر جدیدی نمی‌سازه. کاربر یک پوش می‌گیره (`PushTripDriverCanceled`، بدون تغییر) و باید طبق بخش ۴.۸.۱ به صفحه‌ی درخواست با اطلاعات پرشده برگرده و خودش دوباره ثبت کنه — آن سفرِ جدید دیگر برای همین راننده نمایش داده نخواهد شد.

### ۶.۶ موقعیت زنده‌ی کاربر (برای نمایش روی نقشه‌ی راننده)

```
GET /Driver/TripLive/{tripId}
```

دقیقاً همون شکل `TripLiveDto`ی بخش ۴.۴ ولی `counterpartLocation` اینجا موقعیت **کاربره**، نه راننده.

## ۷. گزارش موقعیت زنده (هم کاربر هم راننده)

یک endpoint مشترک — **چه کاربر باشی چه راننده، از همین یکی استفاده می‌کنی** (چون لوکیشن راننده روی `User.Id` خودِ راننده (نه `Driver.Id`) ذخیره می‌شه):

```
POST /EndUser/UserCurrentLocation
```
Body: `{ "location": { "x": 51.395, "y": 35.691 } }`

- این endpoint هیچ ربطی به سفر نداره — فقط «آخرین موقعیت این کاربر» رو ست/آپدیت می‌کنه. حتی توی صفحه‌ی راننده (که Area توکنش `Driver`ه)، همین مسیر `EndUser/UserCurrentLocation` رو صدا بزن، چون توکن همیشه به یک `User` واحد وصله.
- **باید در طول کل سفر فعال (`Accepted`) هر ۳ تا ۵ ثانیه صدا زده بشه** — هم از اپ کاربر (اگه `ownerRidesAlong` یا برای نمایش به راننده لازمه) و هم از اپ راننده. وقتی سفر فعال نیست، لازم نیست پیوسته بفرستی (میشه کمتر/فقط periodic عادی).
- این همون جدولیه که پنل ادمین هم برای نقشه‌ی زنده‌ش استفاده می‌کنه — یعنی اگه این رو درست پیاده کنی، همزمان توی پنل ادمین هم دیده می‌شه، تست دوطرفه‌ی ساده‌ای داری.

## ۸. پوش نوتیفیکیشن‌ها (جهت اطلاع — سمت بک‌اند خودکار ارسال می‌شه)

این‌ها رو UI لازم نیست خودش trigger کنه، فقط بدونه چه پوشی کِی میاد تا اگه لازم بود روی کلیک پوش، deep-link مناسب بزنه:

| رویداد | گیرنده | متن |
|---|---|---|
| راننده به مبدا رسید | کاربر | «راننده به مبدا رسید» |
| پت تحویل گرفته شد | کاربر | «پت شما تحویل گرفته شد، سفر آغاز شد» |
| راننده به مقصد رسید | کاربر | «پت شما به مقصد رسید» |
| سفر تکمیل شد | کاربر | «سفر پت‌رسان تکمیل شد — لطفا به راننده امتیاز دهید» |
| سفر لغو شد (توسط راننده) | کاربر | «سفر پت‌رسان لغو شد» (`PushTripDriverCanceled`) |
| سفر لغو شد (توسط کاربر) | راننده (اگه پذیرفته بود) | «سفر توسط کاربر لغو شد» (`PushTripUserCanceled` — جدید) |
| سفر جدید در دسترسه | همه‌ی راننده‌های فعال/تاییدشده (به‌جز راننده‌های مستثناشده، بخش ۶.۱) | «سفر جدیدی در دسترس است» (`PushTripRequestAvailable`) |
| تایید/رد احراز هویت راننده | راننده | (مرتبط با فلوی ثبت‌نام راننده، نه سفر) |

## ۱۰. نکات پیاده‌سازی و UX

1. **Polling، نه SignalR** — روی سرور فعلی WebSocket مشکل ۵۰۴ داره؛ همه‌ی لحظه‌به‌لحظه‌ها با فاصله‌ی ۳-۵ ثانیه پیاده بشن (`setInterval` + پاک‌کردنش روی unmount کامپوننت — حواست به memory leak باشه).
2. **پولینگ رو فقط وقتی صفحه‌ی مرتبط بازه انجام بده** — مثلاً `TripLive` رو فقط توی صفحه‌ی «سفر فعال» صدا بزن، نه همیشه در background، هم برای مصرف باتری هم برای فشار روی سرور.
3. **`PointDto`**: همیشه `{ x: longitude, y: latitude }` — دقیقاً برعکس ترتیب معمول `lat,lng`. توی همه‌ی endpoint های پت‌رسان همینه.
4. **دکمه‌های مرحله‌ی راننده رو state-machine مانند پیاده کن** — بر اساس `progressStageId` فقط دکمه‌ی مرحله‌ی بعدی فعال باشه، بقیه غیرفعال/مخفی.
5. **چندپتی بودن سفر** (`userPetIds`) یعنی UI باید یک چندانتخابی پت داشته باشه، نه یک select تکی مثل قبل.
6. **دکمه‌ی لغو سفر** بعد از `progressStageId >= 3` باید مخفی/غیرفعال بشه (بک‌اند رد می‌کنه، ولی بهتره UX از قبل جلوش رو بگیره).
7. برای حالت ۲، فیلد `scheduledLeadMinutes` **باید یک انتخاب محدود (۱ ساعت / ۲ ساعت)** باشه، نه input آزاد عددی — چون بک‌اند فقط این دو مقدار رو قبول می‌کنه.
8. **فرم لغو سفر (هم کاربر، هم راننده) باید یک لیست انتخابی از دلایل باشه، نه فیلد متنی آزاد تنها** — دقیقاً طبق طرح خواسته‌شده: یک «سوال» با گزینه‌های از پیش‌تعیین‌شده (از `GET .../Code?codeGroupLabel=...`، بخش ۳.۳)، به‌علاوه‌ی یک فیلد توضیح آزاد اختیاری (`cancelDetail`) کنارش. **دو لیست کاملاً جداگانه‌اند** — فرم لغو کاربر از `TripCancelReason_User` می‌خونه، فرم لغو راننده از `TripCancelReason_Driver` — این دو رو با هم قاطی نکن.
9. **بعد از هر لغو (کاربر یا راننده)، سفر دیگه هیچ‌وقت خودش برنمی‌گرده** — قبلاً (لغو راننده) خودکار ریست می‌شد، الان نه. تنها راه ادامه، ثبت درخواست جدید طبق بخش ۴.۸.۱ (با `previousTripId`) از سمت کاربره؛ راننده فقط منتظر Broadcast بعدی می‌مونه.
10. `previousTripId` (بخش ۴.۸.۱) رو فقط وقتی بفرست که کاربر واقعاً از صفحه‌ی «سفر لغوشده» resubmit می‌کنه — برای یک سفر کاملاً تازه (که ربطی به سفر لغوشده‌ی قبلی نداره) این فیلد رو نفرست یا `null`/`undefined` بذار.
