# تحویل‌گیری سفارش توسط کاربر — مستند وب‌اپ (مشتری + بک‌آفیس فروشنده داخل وب‌اپ)

> مخاطب: تیم وب‌اپ (Nuxt) · قرارداد کامل API و قواعد: [PRODUCT_ORDER_USER_DELIVERY_FA.md](PRODUCT_ORDER_USER_DELIVERY_FA.md) (حتماً اول بخوانید)
> وضعیت بک: پیاده شد، **دیپلوی نشده**. تا اجرای SQL و دیپلوی Api، endpoint جدید خطا می‌دهد.
> پاسخ‌های بک **همیشه HTTP 200** با `{ isSuccess, messages, data }` هستند؛ موفقیت را از `isSuccess` بخوانید. فیلدها camelCase. BFFهای وب‌اپ (`app/server/api/**`) همان پاسخ را برمی‌گردانند.

## ۱) خلاصه‌ی تغییر

| بخش | کار |
| --- | --- |
| **سفارش‌های من (مشتری)** | دو دکمه‌ی **«تحویل گرفتم»** و **«تحویل نگرفتم»** روی سفارش‌هایی که `canConfirmDelivery == true`؛ نمایش پاسخ ثبت‌شده؛ BFF جدید |
| **سفارش‌های فروشگاه (بک‌آفیس فروشنده در وب‌اپ)** | نمایش وضعیت تحویل‌گیری مشتری روی کارت/جزئیات، فیلتر، و **حذف گزینه‌ی «تحویل داده شد»** از انتخاب وضعیت |
| ادمین | در پنل انجام شد (کاری برای وب‌اپ نیست) |

## ۲) BFF جدید: ثبت پاسخ کاربر

فایل پیشنهادی `app/server/api/productOrder/delivery.put.js` (همان الگوی BFFهای فعلی، مثل `ProductOrderChangeStatus.put.js`):

```js
export default defineEventHandler(async (event) => {
  const { public: { baseUrl } } = useRuntimeConfig()
  const token = getCookie(event, 'token')
  const body = await readBody(event) // { id, received, note }
  try {
    return await $fetch(`${baseUrl}/api/EndUser/ProductOrderDelivery`, {
      method: 'PUT',
      headers: { Accept: 'application/json', Authorization: `Bearer ${token}` },
      body: { id: body.id, received: !!body.received, note: body.note || null }
    })
  } catch (error) {
    // خطای شبکه/۴۰۱: همان رفتار سایر BFFها
    return error?.data ?? { isSuccess: false, messages: [] }
  }
})
```

درخواست از کلاینت: `$fetch('/api/productOrder/delivery', { method: 'PUT', body: { id, received, note } })`.
- `id` = `order.id` (**رشته‌ی guid**) نه `orderCode`.
- `received: true` ⇒ سفارش نهایی می‌شود (وضعیت «تحویل داده شد»)؛ `received: false` ⇒ فقط ثبت می‌شود.
- `note` فقط برای «تحویل نگرفتم»، اختیاری، حداکثر ۵۰۰ نویسه.

## ۳) صفحه‌ی «سفارش‌های من» (`pages/orders/index.vue` و `pages/orders/[orderId].vue`)

سفارش‌ها از `GET /api/EndUser/ProductOrder` (BFF `productOrder.get.js`) و جزئیات از `…/{id}` (BFF `productOrderInfo.get.js`) می‌آیند و حالا فیلدهای جدید دارند: `userReceived`، `userReceivedDate`، `userReceiveNote`، `canConfirmDelivery`.

### نمایش (به ترتیب اولویت)
| شرط | نمایش |
| --- | --- |
| `canConfirmDelivery == true` | بنر/کارت «بسته را دریافت کردید؟» با دو دکمه: **تحویل گرفتم** (سبز) و **تحویل نگرفتم** (قرمز/خنثی) |
| `userReceived == true` | نشان سبز «تحویل گرفتید» + تاریخ (`userReceivedDate`)؛ **بدون دکمه** (نهایی است) |
| `userReceived == false` (و هنوز `canConfirmDelivery`) | نشان «تحویل نگرفتم ثبت شد» + توضیح (`userReceiveNote`) و **هر دو دکمه هنوز فعال**: کاربر می‌تواند بعداً «تحویل گرفتم» بزند یا توضیح را عوض کند |
| بقیه | هیچ‌چیز (سفارش هنوز «ارسال شده» نیست، پرداخت‌نشده یا لغو شده است) |

دکمه‌ها را **فقط** با `canConfirmDelivery` نشان بدهید (سرور وضعیت/پرداخت/لغو را حساب کرده است).

### رفتار دکمه‌ها
1. **تحویل گرفتم:** modal تأیید «با تأیید تحویل، سفارش نهایی می‌شود و قابل برگشت نیست» ⇒ `received: true`. موفق ⇒ سفارش را دوباره بگیرید (وضعیت می‌شود «تحویل داده شد»، `userReceived: true`)، toast موفقیت، دکمه‌ها برداشته شوند.
2. **تحویل نگرفتم:** modal با فیلد توضیح اختیاری (۵۰۰ نویسه؛ شمارنده) و متن «فروشگاه و پشتیبانی پاستیل پیگیری می‌کنند» ⇒ `received: false, note`. موفق ⇒ سفارش را دوباره بگیرید؛ وضعیت سفارش همچنان «ارسال شده» است ولی نشان «تحویل نگرفتم» دیده شود.
3. دکمه‌ها حین ارسال غیرفعال (ضدکلیک دوبل).
4. خطاها از `messages`:
   - «تحویل این سفارش قبلاً توسط شما تأیید شده است.» ⇒ سفارش را تازه کنید و دکمه‌ها را بردارید.
   - «تحویل‌گیری فقط برای سفارش پرداخت‌شده‌ی لغو‌نشده‌ای که وضعیتش «ارسال شده» است قابل ثبت است.» ⇒ سفارش را تازه کنید (وضعیت عوض شده).
   - «چیزی یافت نشد» ⇒ سفارش مال این کاربر نیست؛ برگشت به فهرست.
5. برای اینکه کاربر فراموش نکند: روی کارت سفارش‌های «ارسال شده» در فهرست، همان نشان «در انتظار تأیید تحویل شما» را نشان بدهید (فیلتر `userDelivery=0` برای «نیازمند اقدام»).

## ۴) بک‌آفیس فروشنده داخل وب‌اپ (`pages/sellerProfile/orders/index.vue`)

فهرست از BFF `server/api/seller/sellerOrders.get.js` می‌آید (که `GET /api/Seller/ProductOrder` را صدا می‌زند) و فیلدهای جدید را همراه دارد.

1. **نمایش روی هر سفارش** (کارت/ردیف و جزئیات):
   | `userReceived` | `canConfirmDelivery` | نشان |
   | --- | --- | --- |
   | `true` | — | «مشتری تحویل گرفت (نهایی)» سبز |
   | `false` | — | «مشتری تحویل نگرفته» **قرمز** + `userReceiveNote` (توضیح) + تاریخ؛ نیازمند پیگیری |
   | `null` | `true` | «منتظر تأیید تحویل مشتری» زرد |
   | `null` | `false` | نشان نمی‌دهیم |
2. **فیلتر** (کنار فیلتر وضعیت): «همه / منتظر پاسخ مشتری / تحویل گرفته / تحویل نگرفته» ⇒ `userDelivery` = خالی / `0` / `1` / `2` در همان query فهرست (BFF باید query را پاس بدهد؛ الان `getQuery` را عبور می‌دهد).
3. **انتخاب وضعیت (modal «مرسوله در چه فازی قرار دارد؟»):** گزینه‌ی **«تحویل داده شد» (`ProductOrderStatus_Delivered`) را نشان ندهید/غیرفعال کنید** و زیرش بنویسید «تحویل داده شد را خود مشتری تأیید می‌کند». بک هم این انتخاب را رد می‌کند («… فقط با تأیید خود مشتری …»)؛ پیام را در toast نشان دهید.
   - اگر سفارش `userReceived == true` است، کل modal تغییر وضعیت را غیرفعال کنید («مشتری تحویل را تأیید کرده؛ وضعیت قابل تغییر نیست»).
4. نشان «نیازمند پیگیری» (قرمز) را در شمارش بالای صفحه هم بیاورید (تعداد `userReceived == false`) تا فروشنده سفارش‌های مشکل‌دار را از دست ندهد.
5. **پوش ۹۰** (`PushProductOrderNotReceivedStore`) هنگام «تحویل نگرفتم» مشتری به کاربران فروشگاه می‌رسد؛ مقصد `/sellerProfile/orders`. در handler پوش بشناسید و صفحه‌ی سفارش‌ها را (ترجیحاً با فیلتر `userDelivery=2`) باز کنید.


## ۴٫۱) تأیید خودکار بعد از ۷ روز (جدید)

اگر مشتری ۷ روز بعد از «ارسال شده» هیچ پاسخی ندهد، سیستم خودکار «تحویل گرفتم» را ثبت می‌کند (جزئیات قواعد: [PRODUCT_ORDER_USER_DELIVERY_FA.md](PRODUCT_ORDER_USER_DELIVERY_FA.md) بند ۳٫۱). «تحویل نگرفتم» **هرگز** خودکار تأیید نمی‌شود.

فیلدهای تازه روی هر سفارش (فهرست و جزئیات):

| فیلد | معنی |
| --- | --- |
| `autoConfirmDate` | زمانی که اگر مشتری پاسخ ندهد سفارش خودکار تأیید می‌شود. فقط وقتی هنوز منتظر پاسخ است (`userReceived == null`) و سفارش ارسال‌شده است پر می‌شود؛ وگرنه `null` |
| `userReceivedAuto` | `true` = سفارش را سیستم خودکار «تحویل گرفته» ثبت کرده (همراه `userReceived: true`) |

**مشتری (سفارش‌های من):**
- وقتی `canConfirmDelivery == true` و `autoConfirmDate` پر است، زیر دو دکمه بنویسید «اگر تا {تاریخ شمسی `autoConfirmDate`} پاسخ ندهید، خودکار «تحویل گرفته شد» ثبت می‌شود». شمارش معکوس روزها را از `autoConfirmDate − serverNow` بسازید (آفست را حذف کنید؛ مثل بقیه‌ی تاریخ‌های سرور، «بدون آفست» می‌آید).
- `userReceived == true && userReceivedAuto == true` ⇒ نشان «به‌صورت خودکار تأیید شد (۷ روز بدون پاسخ)» با تاریخ `userReceivedDate`، به‌جای «تحویل گرفتید»؛ دکمه‌ای نیست. یک لینک «بسته را دریافت نکردم؟ تماس با پشتیبانی» بگذارید.
- پوش‌های جدید (مقصد `/orders`): **۸۸** (۵ روز بعد از ارسال، فقط یک‌بار: «سفارش {کد} را تحویل گرفته‌اید؟…») و **۸۹** (بعد از تأیید خودکار). در handler پوش بشناسید و به «سفارش‌های من» ببرید.

**بک‌آفیس فروشنده:** نشان سبز «مشتری تحویل گرفت (نهایی)» را وقتی `userReceivedAuto == true` به «تأیید خودکار (۷ روز بدون پاسخ)» تغییر دهید. برای «منتظر تأیید مشتری» می‌توانید «تأیید خودکار تا {`autoConfirmDate`}» را هم نشان دهید.

## ۴٫۲) صفحه‌ی مالی فروشنده (`pages/sellerProfile/finance.vue`)

BFF `server/api/seller/finance.get.js` به `GET /api/Seller/FinanceStore` وصل است و حالا برای هر سفارش در `financeProductOrders` این‌ها را برمی‌گرداند: `userReceived` (`null`/`true`/`false`)، `userReceivedDate`، `userReceivedAuto`، `userReceiveNote`؛ و در ریشه‌ی پاسخ `notReceivedCount` و `receivedCount`.

1. در جدول سفارش‌ها ستون/نشان **«تحویل‌گیری مشتری»**: `true` ⇒ «تحویل گرفته» (اگر `userReceivedAuto` ⇒ «تأیید خودکار»)، `false` ⇒ «تحویل نگرفته» قرمز با `userReceiveNote` در tooltip/جزئیات، `null` ⇒ «—».
2. بالای جدول، اگر `notReceivedCount > 0` هشدار قرمز: «N سفارش را مشتری تحویل نگرفته است؛ پیگیری کنید».
3. فیلتر اختیاری: query `UserDelivery` = `0` منتظر پاسخ، `1` تحویل گرفته، `2` تحویل نگرفته (BFF `getQuery` را پاس می‌دهد؛ مقدار را اضافه کنید).
4. توضیح یک‌خطی برای فروشنده: «سهم شما با تأیید مالی ادمین پرداخت می‌شود؛ سفارش‌های تحویل‌نگرفته ممکن است پیش از تسویه بررسی شوند.» (تسویه خودکار مانع نمی‌شود؛ تصمیم با ادمین است.)
## ۵) مواردی که تغییر نمی‌کند
- فرایند پرداخت، ثبت سفارش، لغو، کد پیگیری، ارسال: بدون تغییر.
- وضعیت «ارسال شده» و ایجاد کد رهگیری مثل قبل توسط فروشگاه/ادمین.
- سفارش‌های قدیمیِ «تحویل داده شده» که قبلاً ادمین/فروشنده زده‌اند: `userReceived` آن‌ها `null` و `canConfirmDelivery` `false` است؛ چیزی نشان نمی‌دهیم.

## ۶) سناریوی تست (استیجینگ بعد از SQL و دیپلوی)
۱. سفارش پرداخت‌شده ⇒ فروشنده «ارسال شده» ⇒ مشتری دو دکمه را ببیند.
۲. مشتری «تحویل نگرفتم» + توضیح ⇒ فروشنده نشان قرمز و توضیح را ببیند؛ ادمین (پنل) هم؛ سفارش «ارسال شده» می‌ماند.
۳. مشتری بعداً «تحویل گرفتم» ⇒ سفارش «تحویل داده شد»؛ دکمه‌ها ناپدید؛ فروشنده دیگر نمی‌تواند وضعیت را عوض کند.
۴. فروشنده تلاش کند «تحویل داده شد» بزند (با UI قدیمی) ⇒ خطای «فقط با تأیید خود مشتری».
۵. فیلتر `userDelivery` = ۰/۱/۲ در فهرست فروشنده.
۶. مشتری روی سفارشِ «در حال پردازش» دکمه نبیند؛ و روی سفارش لغو شده هم نه.
