# موقعیت (لوکیشن) پانسیون/مهد — مستند برای اپ نماینده

از این به بعد **خودِ پانسیون/مهد** یک موقعیت دقیق روی نقشه دارد (قبلاً فقط استان، شهر و آدرس متنی بود و فقط خود «نماینده» لوکیشن داشت). ثبت این موقعیت هنگام ساخت و ویرایش پانسیون **الزامی** است.

## تغییر در API
فیلد جدید `location` به همان سه endpoint قبلی اضافه شد؛ آدرس‌ها عوض نشده‌اند.

| عملیات | Endpoint |
|---|---|
| ساخت پانسیون | `POST api/Companion/Pansion` |
| ویرایش/ارسال مجدد | `PUT api/Companion/Pansion` |
| دریافت جزئیات | `GET api/Companion/Pansion/{id}` (و لیست‌ها) — پاسخ حالا `location` دارد |

### قالب
همان قالب لوکیشن نماینده/فروشگاه:

```json
"location": { "x": 51.389, "y": 35.6892 }
```

- `x` = **طول جغرافیایی (longitude)**، حدود ۵۱ برای تهران
- `y` = **عرض جغرافیایی (latitude)**، حدود ۳۵ برای تهران
- ترتیب مهم است؛ اگر جابه‌جا بفرستید نقطه در اقیانوس می‌افتد.

### اعتبارسنجی (سمت سرور)
- بدون `location` → خطای «موقعیت دقیق پانسیون را روی نقشه مشخص کنید» (فیلد `Location`).
- `x` خارج از ‎-180..180 یا `y` خارج از ‎-90..90 → «مختصات موقعیت پانسیون معتبر نیست».
- پاسخ‌ها مثل بقیه‌ی API: HTTP 200 و `IsSuccess` / `Messages` (`Item1` = متن، `Item2` = نام فیلد).

## کاری که اپ باید بکند
1. در فرم ساخت و ویرایش پانسیون/مهد یک **انتخاب‌گر نقشه** بگذارید (مثل انتخاب لوکیشن فروشگاه/آدرس: پین ثابت وسط نقشه، جابه‌جایی نقشه زیر پین، جستجوی محله و دکمه‌ی GPS).
2. موقعیت پیش‌فرض نقشه تهران است (۳۵٫۶۸۹۲ , ۵۱٫۳۸۹)، ولی **تا کاربر نقشه را جابه‌جا نکرده** `location` را پر نکنید؛ وگرنه همه‌ی پانسیون‌ها وسط تهران ثبت می‌شوند.
3. در ویرایش، `location` پاسخ `GET` را روی نقشه نمایش دهید و همان را (یا مقدار جدید) در `PUT` بفرستید. پانسیون‌های قدیمی `location = null` دارند؛ اپ باید فرم را تا انتخاب موقعیت ذخیره‌نشدنی بگذارد (سرور هم رد می‌کند).
4. اگر لازم است آدرس متنی خودکار پر شود، از reverse geocode موجود (`/api/location/reverse` در وب‌اپ) استفاده کنید؛ سرور آدرس متنی را از روی مختصات پر نمی‌کند و `addressValue` همچنان الزامی است.
5. نکته‌ی نمایشی: نمایش لینک «مسیریابی» یا نقشه‌ی کوچک در صفحه‌ی جزئیات پانسیون برای مشتری ممکن است؛ `location` در پاسخ عمومی (`api/Pansion/...`) هم هست.

## وب‌اپ و پنل ادمین (انجام‌شده)
- پنل نماینده در وب‌اپ: `webapp/app/pages/companionProfile/pansion/insert[id].vue` با `LocationPickerMap`.
- پنل ادمین: فرم پانسیون (تب «موقعیت و آدرس») با `LocationPicker` و نمایش نقشه در صفحه‌ی جزئیات.

## دیتابیس
مایگریشن `AddPansionLocation`: ستون nullable از نوع `geography` روی جدول `Pansions`. اسکریپت idempotent: `backend/scripts/AddPansionLocation.sql` (روی همان زنجیره‌ی قبلی؛ بدون داده‌ی قبلی هیچ مقداری پر نمی‌شود).

# مدرسه‌ی تربیت پت (School) — همین قرارداد

مدرسه هم دقیقاً مثل پانسیون یک `location` الزامی دارد (قالب، ترتیب `x` = طول و `y` = عرض، و رفتار نقشه همان بخش‌های بالا).

| عملیات | Endpoint |
|---|---|
| ساخت مدرسه | `POST api/Companion/School` |
| ویرایش | `PUT api/Companion/School` |
| دریافت جزئیات | `GET api/Companion/School/{id}` — پاسخ `location` دارد |

- بدون `location` (در ساخت و ویرایش) → «موقعیت دقیق مدرسه را روی نقشه مشخص کنید»؛ مختصات خارج از بازه → «مختصات موقعیت مدرسه معتبر نیست».
- مدرسه‌های قدیمی `location = null` دارند؛ ویرایششان (حتی تغییر قیمت یا توضیح) تا انتخاب موقعیت رد می‌شود.
- در وب‌اپ صفحه‌ی مدیریت مدرسه‌ی نماینده وجود ندارد؛ مدیریت مدرسه فقط از اپ نماینده و پنل ادمین است. پنل ادمین (`SchoolEditor`) انجام شد.
- دیتابیس: مایگریشن `AddSchoolLocation` و اسکریپت `backend/scripts/AddSchoolLocation.sql` (ستون nullable از نوع `geography` روی `Schools`).
