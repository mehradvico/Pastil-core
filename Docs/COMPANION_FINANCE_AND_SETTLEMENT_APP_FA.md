# حسابداری و تسویهٔ اپ نماینده (Companion)

> وضعیت قرارداد: بر اساس کد فعلی بک‌اند در ۲۰۲۶-۰۹-۲۲. این سند برای اپ نماینده/کلینیک است، نه پنل ادمین. هر جا قابلیتی هنوز API نماینده ندارد، صریحاً با «فعلاً موجود نیست» مشخص شده است.

## نتیجهٔ مهم

اپ نماینده در حال حاضر می‌تواند این سه کار را انجام دهد:

1. ریز و جمع سهم مالی رزروهای خود را ببیند.
2. سابقهٔ تسویه‌هایی را که ادمین برای همان نماینده ثبت کرده ببیند.
3. کارت بانکی کاربرِ لاگین‌شده را ثبت و وضعیت تأیید آن را پیگیری کند.

اما **ثبت درخواست تسویه توسط نماینده در API فعلی وجود ندارد**. مسیر `POST /api/Admin/Settlement` فقط برای ادمین است؛ اپ نماینده نباید آن را فراخوانی کند و نباید دکمهٔ «درخواست تسویه» را به‌عنوان عملیات واقعی نمایش دهد.

```text
رزرو معتبر و لغونشده
        │
        ▼
GET /api/Companion/FinanceCompanion?Permitted=false
        │  ← گزارش سهمِ هنوز واردِ یک تسویه نشده
        ▼
ادمین، خارج از اپ نماینده، تسویه را ثبت می‌کند
        │  ← رزروها Permitted=true می‌شوند
        ▼
GET /api/Companion/Settlement
        │
        ▼
اپ فقط سابقهٔ «ثبت‌شده در تسویه» را نمایش می‌دهد
```

`Permitted=true` به معنی «پرداخت پول به حساب نماینده» نیست؛ فقط یعنی رزرو در رکورد تسویه قرار گرفته است. مدل فعلی `Settlement` وضعیت پرداخت، زمان واریز یا رسید انتقال ندارد. بنابراین در UI از عنوان‌هایی مانند «پرداخت قطعی شد» یا «موجودی قابل برداشت» استفاده نکنید.

## قواعد عمومی API

- پایهٔ API: `https://api.pastil.pet/api`
- همهٔ endpointهای این سند نیازمند JWT کاربر لاگین‌شده هستند:

  ```http
  Authorization: Bearer <token>
  Accept-Language: fa-IR
  ```

- پاسخ‌های عملیاتی معمولاً با HTTP `200` برمی‌گردند؛ نتیجهٔ واقعی را از `isSuccess` بخوانید، نه فقط HTTP status.
- پاسخ جست‌وجویی Settlement یک `BaseSearchDto` مستقیم است و `isSuccess` ندارد؛ فیلدهای مهم آن `totalCount` و `list` هستند.
- نام فیلدها در JSON به‌صورت camelCase است.
- مبلغ‌ها فقط عدد هستند و API واحد پول نمی‌فرستد. رابط فعلی وب آن‌ها را «تومان» نمایش می‌دهد، اما اپ نباید تبدیل ریال/تومان را خودش حدس بزند؛ واحد نمایش باید با تصمیم محصول یکسان باشد.

## ۱. گزارش حسابداری نماینده

### دریافت گزارش

```http
GET /api/Companion/FinanceCompanion?Permitted=false
```

پارامتر `companionId` را نفرستید: کنترلر آن را از توکن کاربر می‌گیرد و مقدار کلاینت را override می‌کند. اگر کاربر لاگین‌شده `companionId` نداشته باشد، پاسخ HTTP `403` برمی‌گردد.

| پارامتر | کاربرد واقعی |
|---|---|
| `Permitted=false` | فقط رزروهایی که هنوز در یک Settlement قرار نگرفته‌اند. مناسب صفحهٔ «مبالغ در انتظار بررسی/تسویه». |
| `Permitted=true` | رزروهایی که در Settlement ثبت شده‌اند؛ این فیلتر به‌تنهایی رسید پرداخت نیست. |
| بدون `Permitted` | هر دو گروه را برمی‌گرداند. |

`pageIndex` و `pageSize` در این endpoint اثر ندارند؛ پاسخ همهٔ موارد منطبق را یک‌جا برمی‌گرداند. فعلاً فیلتر تاریخ، خدمت، نوع رزرو یا مرتب‌سازی قراردادی ندارد.

### شکل پاسخ موفق

```json
{
  "isSuccess": true,
  "code": 0,
  "messages": [],
  "data": {
    "companionId": 42,
    "reserveCount": 2,
    "totalCompanionShare": 850000,
    "totalSiteShare": 150000,
    "financeCompanionReserves": [
      {
        "reserveId": "912",
        "reserveCode": "CR-...",
        "bookerFullName": "نام کاربر",
        "paymentPrice": 500000,
        "commissionPercent": 15,
        "companionShare": 425000,
        "siteShare": 75000,
        "statusLabel": "...",
        "isPansion": false,
        "permitted": false
      }
    ]
  }
}
```

### معنی دقیق داده‌ها

گزارش، دو نوع رزرو را با هم ادغام می‌کند:

- رزرو خدمت Companion؛ `isPansion=false`
- رزرو پانسیون متعلق به همان Companion؛ `isPansion=true`

فقط رکوردهای `isReserved=true` و `isCancel=false` وارد گزارش می‌شوند. جمع‌ها از همان آیتم‌های برگشتی محاسبه می‌شوند:

| فیلد | معنی |
|---|---|
| `paymentPrice` | مبلغ ثبت‌شده برای آن رزرو. |
| `commissionPercent` | درصد کمیسیون ثبت‌شده روی همان خدمت؛ برای پانسیون، درصد روزانه یا ساعتی بر مبنای `dayCount`. |
| `companionShare` | سهم ثبت‌شده برای نماینده؛ این مقدار را فرانت دوباره محاسبه نکند. |
| `siteShare` | سهم ثبت‌شدهٔ پاستیل. |
| `statusLabel` | نام وضعیت رزرو، نه وضعیت پرداخت/تسویه. |
| `permitted` | آیا رکورد وارد یک Settlement شده است یا خیر. |
| `totalCompanionShare` | مجموع `companionShare` موارد همین پاسخ. |
| `totalSiteShare` | مجموع `siteShare` موارد همین پاسخ. |

### رفتار پیشنهادی UI

- صفحهٔ پیش‌فرض را با `Permitted=false` باز کنید و عنوان آن را «رزروهای ثبت‌نشده در تسویه» یا «مبالغ در انتظار بررسی» بگذارید.
- بخش دیگری با `Permitted=true` می‌تواند «رزروهای ثبت‌شده در تسویه» باشد، اما این صفحه جای تاریخچهٔ Settlement نیست.
- تعداد و جمع‌ها را از پاسخ بگیرید؛ منبع حقیقت برای محاسبهٔ کمیسیون، فرانت نیست.
- دادهٔ این endpoint تاریخ ایجاد رزرو ندارد. نمودار «درآمد ۷ روز اخیر»، فیلتر زمانی یا روند روزانه با قرارداد فعلی قابل اتکا نیست و نباید از مقدار ساختگی/صفر تولید شود.
- نام مشتری را فقط در همان صفحهٔ عملیاتی نمایش دهید؛ آن را در analytics، log یا share sheet ثبت نکنید.

## ۲. تاریخچهٔ تسویهٔ نماینده

### فهرست

```http
GET /api/Companion/Settlement?PageIndex=1&PageSize=20&SortBy=New
```

کنترلر `companionId` را از توکن می‌گیرد، بنابراین اپ نباید شناسهٔ نمایندهٔ دیگری بفرستد. `storeId` نیز مربوط به این اپ نیست و نباید ارسال شود.

پاسخ این endpoint یک آبجکت صفحه‌بندی مستقیم است:

```json
{
  "pageIndex": 1,
  "pageSize": 20,
  "totalCount": 1,
  "list": [
    {
      "id": 77,
      "companionId": 42,
      "createDate": "2026-09-22T10:30:00",
      "userBankCardId": 9,
      "trackingCode": "پیگیری ادمین",
      "paidPrice": 850000,
      "itemCount": 2,
      "userBankCard": { "id": 9, "cardNumber": "..." },
      "companion": { "id": 42, "name": "..." }
    }
  ]
}
```

پارامترهای مؤثر `pageIndex`، `pageSize` و `sortBy` هستند؛ پیش‌فرض‌ها به‌ترتیب `1`، `20` و `New` هستند. فیلدهای عمومی `q` و `available` در سرویس Settlement فیلتر اعمال نمی‌کنند.

> نکتهٔ قرارداد: فایل Swagger قدیمی پاسخ Companion Settlement را با DTO ساده نشان می‌دهد؛ کد فعلی کنترلر `SettlementVDto` را برمی‌گرداند. اپ باید فیلدهای نمایشی بالا را بر اساس قرارداد واقعی سرویس بخواند و برای missing/null مقاوم باشد.

### جزئیات یک تسویه

```http
GET /api/Companion/Settlement/77
```

سرور پس از خواندن رکورد، مالکیت `companionId` را با نمایندهٔ لاگین‌شده چک می‌کند. در صورت عدم دسترسی، پاسخ `200` با `isSuccess=false` و پیام `AccessDenied` می‌دهد.

### برچسب‌های صحیح در رابط

| فیلد | برچسب پیشنهادی |
|---|---|
| `createDate` | زمان ثبت تسویه در سامانه |
| `paidPrice` | مبلغ ثبت‌شده در تسویه |
| `itemCount` | تعداد رزروهای قرارگرفته در تسویه |
| `trackingCode` | کد/توضیح پیگیری ثبت‌شده توسط ادمین |
| `userBankCard` | کارت مقصد ثبت‌شده در تسویه |

`paidPrice` نام فنی فیلد است، نه اثبات واریز بانکی. تا وقتی مدل بک‌اند وضعیت پرداخت یا رسید واریز نداشته باشد، نام UI باید «مبلغ ثبت‌شده در تسویه» بماند.

شمارهٔ کارت در `userBankCard.cardNumber` ممکن است در پاسخ باشد. فقط چهار رقم آخر را نمایش دهید، مثال: `•••• ۱۲۳۴`؛ هرگز شمارهٔ کامل را در لاگ، اعلان یا screenshot غیرضروری نگذارید.

## ۳. کارت مقصد تسویه

برای نماینده controller جداگانه‌ای وجود ندارد. چون نماینده یک کاربر لاگین‌شده هم هست، اپ باید API کاربر نهایی را برای کارت خودش استفاده کند:

| کار | API |
|---|---|
| فهرست کارت‌های خود | `GET /api/EndUser/UserBankCard?PageIndex=1&PageSize=20` |
| ثبت کارت | `POST /api/EndUser/UserBankCard` |
| ویرایش کارت | `PUT /api/EndUser/UserBankCard` |
| حذف کارت | `DELETE /api/EndUser/UserBankCard/{id}` |

برای فرم ثبت، فقط این ورودی‌ها معنادارند:

```json
{
  "cardHolderName": "نام دارنده کارت",
  "cardNumber": "1234567890123456",
  "shebaNumber": "IRxxxxxxxxxxxxxxxxxxxxxxxx",
  "bankCardId": 0
}
```

- `userId` از توکن گرفته می‌شود؛ کلاینت نباید آن را مالکیت‌ساز تلقی کند.
- `bankCardId` از BIN شش رقم اول کارت توسط سرور تعیین می‌شود؛ کلاینت نباید به مقدار ارسالی اعتماد کند.
- شمارهٔ کارت پس از حذف جداکننده باید ۱۶ رقم باشد. شبای اختیاری، اگر وارد شود، باید ۲۴ رقم بعد از `IR` باشد.
- CVV2، رمز، تاریخ انقضا یا هر دادهٔ پرداختی دیگر در این جریان جایی ندارد و نباید درخواست/ذخیره شود.
- کارت جدید ابتدا `approved=false` است. ادمین آن را تأیید یا رد می‌کند و در حالت رد، `adminDetail` علت را دارد.
- فقط کارت `approved=true` باید با برچسب «آماده برای تسویه» نشان داده شود. کارت Pending/Rejected نباید گزینهٔ مقصد تسویه باشد.
- پس از تغییر کارت، سرویس مجدداً آن را Pending می‌کند. امکان ویرایش کاربر پس از ثبت در کد فعلی بسیار محدود است؛ اگر API `EditIsNotAvailable` برگرداند، متن سرور را نمایش دهید و کاربر را به ثبت کارت جدید یا پشتیبانی هدایت کنید.

راهنمای کامل‌تر تجربهٔ کارت بانکی در [USER_BANK_CARD_FRONTEND_AMIRMOHSEN_FA.md](USER_BANK_CARD_FRONTEND_AMIRMOHSEN_FA.md) است؛ اما آن سند وجود درخواست تسویهٔ Companion را ایجاد نمی‌کند.

## ۴. «درخواست تسویه» در نسخهٔ فعلی

### آنچه نباید انجام شود

- `POST /api/Companion/Settlement` وجود ندارد.
- `POST /api/Admin/Settlement` نباید از اپ نماینده فراخوانی شود؛ این endpoint متعلق به ادمین است.
- اپ نباید با جمع `totalCompanionShare` یک درخواست فرضی بسازد یا وضعیت `permitted` را سمت کلاینت تغییر دهد.
- ارسال `userBankCardId` به‌تنهایی هیچ درخواست تسویه‌ای ثبت نمی‌کند.

### رفتار عملیاتی فعلی ادمین

ادمین پس از انتخاب نماینده و کارت مقصد، `POST /api/Admin/Settlement` را اجرا می‌کند. سرویس تمام رزروهای معتبرِ `permitted=false` همان Companion (رزرو خدمت و پانسیون) را به Settlement لینک می‌کند و بلافاصله `permitted=true` می‌گذارد؛ مقدار `paidPrice` و `itemCount` نیز از همان اقلام ساخته می‌شود.

این فرایند «تسویهٔ کامل همهٔ اقلام باز» است، نه درخواست مبلغ دلخواه یا تسویهٔ جزئی. در مدل فعلی وضعیت‌هایی مانند Draft/Requested/Approved/Paid/Rejected، مبلغ درخواستی، رسید واریز و تاریخ پرداخت وجود ندارد.

### تصمیم لازم پیش از ساخت قابلیت درخواست

اگر محصول می‌خواهد نماینده واقعاً درخواست ثبت کند، ابتدا باید یک API اختصاصی و مدل وضعیت تعریف شود. موارد زیر تصمیم محصول/بک‌اند هستند و در قرارداد فعلی پیاده‌سازی نشده‌اند:

1. درخواست کامل همهٔ اقلام باز است یا مبلغ/اقلام انتخابی و تسویهٔ جزئی هم مجاز است؟
2. وضعیت‌ها و انتقال معتبرشان چیستند: مثلاً `Requested → Approved/Rejected → Paid`؟
3. آیا نماینده می‌تواند کارت تأییدشده را انتخاب کند و آیا سرور مالکیت کارت و `approved=true` را دوباره کنترل می‌کند؟
4. کاربر چه زمانی کد پیگیری، دلیل رد، رسید و تاریخ واریز را می‌بیند؟
5. در برابر دو بار زدن دکمه، retry شبکه و چند درخواست هم‌زمان چه idempotency/قفل‌گذاری‌ای لازم است؟

تا پاسخ این تصمیم‌ها و API جدید، UI صحیح شامل گزارش مالی، کارت‌ها و تاریخچهٔ read-only است؛ CTA درخواست تسویه باید پنهان یا با متن «این قابلیت پس از فعال‌سازی مالی در دسترس قرار می‌گیرد» غیرفعال باشد.

## سناریوهای پذیرش اپ

- [ ] کاربر Companion بدون `companionId` به صفحهٔ مالی می‌رود: خطای دسترسی را می‌بیند و دادهٔ مالی خالی/کاربر دیگر نمایش داده نمی‌شود.
- [ ] `Permitted=false` فقط رزروهای بازِ همان نماینده را نشان می‌دهد و جمع دقیقاً از همان لیست ساخته می‌شود.
- [ ] آیتم پانسیون با `isPansion=true` از رزرو خدمت قابل تشخیص است.
- [ ] در تاریخچه، pagination با `totalCount` و `list` انجام می‌شود، نه با `isSuccess`.
- [ ] باز کردن Settlement نمایندهٔ دیگر به داده منتهی نمی‌شود.
- [ ] کارت Pending/Rejected در جایگاه کارت مقصد قابل انتخاب نیست و علت رد در صورت وجود نمایش داده می‌شود.
- [ ] شمارهٔ کارت در تاریخچه ماسک می‌شود و در log/analytics ذخیره نمی‌شود.
- [ ] هیچ CTA یا درخواست شبکه‌ای به `POST /api/Admin/Settlement` از اپ نماینده انجام نمی‌شود.
- [ ] اپ عنوان «پرداخت‌شده» یا «قابل برداشت» را صرفاً بر مبنای `permitted` یا `paidPrice` نشان نمی‌دهد.
