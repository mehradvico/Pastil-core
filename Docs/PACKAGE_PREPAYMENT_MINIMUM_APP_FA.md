# حداقل و حداکثر پیش‌پرداخت پکیج ارائه‌دهنده — مستند اپ نماینده/ارائه‌دهنده

> مخاطب: توسعه‌دهنده‌ی اپ نماینده/ارائه‌دهنده (Flutter) · وضعیت بک: **پیاده و build شد، دیپلوی نشده** (بدون SQL/migration). تست: `Application.Tests/PackagePrepaymentTests.cs`.
> پاسخ‌های بک **همیشه HTTP 200** با `{ isSuccess, messages, data }`؛ موفقیت را از `isSuccess` بخوانید و پیام خطا از `messages[0].item1` (فارسی، همراه با مبلغ).

## ۱) قاعده

برای هر پکیج (و هر «نحوه‌ی ارائه» آن) که ارائه‌دهنده ثبت یا ویرایش می‌کند:

```
حداقل پیش‌پرداخت = مبلغ کل × درصد پاستیل ÷ ۱۰۰      (رو به بالا، تومان)
حداکثر پیش‌پرداخت = مبلغ کل
```

- **درصد پاستیل** = `effectiveCommissionPercent` همان خدمت (درصد خودِ خدمت اگر > ۰، وگرنه کمیسیون اصلی مرکز). درصد را **ادمین** تعیین می‌کند؛ ارائه‌دهنده نمی‌تواند تغییرش دهد.
- **مبلغ کل**: قیمت همان پکیج/نحوه‌ی ارائه (`price`). فقط برای **مربی – پانسیون آموزشی (mode=38)**: `price + dailyPrice × stayDays` (هزینه‌ی دوره + پانسیون روزانه).
- اگر درصد ۰ باشد حداقل ۰ است (فقط سقف اعمال می‌شود).
- روی **کلینیک، مربی و آرایشگاه** (`Clinic/Coach/Groomer`) اعمال می‌شود. ادمین (پنل) از قید «حداقل» معاف است؛ «حداکثر» برای همه برقرار است.

## ۲) از کجا درصد را بخوانیم (داینامیک)

endpointهای لیست خدمات همان‌هایی‌اند که اپ الان استفاده می‌کند؛ فیلد جدید روی **هر خدمت** آمده:

| نوع | لیست خدمات (اپ) | فیلد |
| --- | --- | --- |
| کلینیک | `GET /api/Companion/ClinicService?clinicId=` | `effectiveCommissionPercent` |
| مربی | `GET /api/Companion/CoachService?coachId=` | `effectiveCommissionPercent` |
| آرایشگاه | `GET /api/Companion/GroomerService?groomerId=` | `effectiveCommissionPercent` |

نمونه (یک خدمت در پاسخ): `{ "id": 12, "commissionPercent": 0, "effectiveCommissionPercent": 20, "packages": [ ... ] }`
(`commissionPercent` درصد خودِ خدمت است و ممکن است ۰ باشد؛ **برای محاسبه فقط `effectiveCommissionPercent`** را بخوانید.)

## ۳) رفتار UI (پیشنهاد دقیق)

در فرم ثبت/ویرایش پکیج، کنار فیلد «پیش‌پرداخت»:

1. هر بار که کاربر **مبلغ** را تغییر می‌دهد، حداقل را حساب کنید:
   ```dart
   int minPrepay(num total, num percent) =>
       (percent <= 0 || total <= 0) ? 0 : (total * percent / 100 - 1e-6).ceil();
   ```
   (برای پانسیون آموزشی `total = price + dailyPrice * stayDays`.)
2. زیر فیلد متن کمکی نشان دهید: «حداقل پیش‌پرداخت: **۲۰۰٬۰۰۰ تومان** (۲۰٪ مبلغ کل، سهم پاستیل) · حداکثر: ۱٬۰۰۰٬۰۰۰ تومان».
3. اگر «پیش‌پرداخت» خالی/۰ است و حداقل > ۰، همان حداقل را به‌عنوان مقدار پیش‌فرض بگذارید.
4. اگر مبلغ را تغییر داد و پیش‌پرداخت کمتر از حداقل جدید شد، فیلد را قرمز و دکمه‌ی «ثبت» را غیرفعال کنید (تا قبل از ارسال به سرور خطا نخورد).
5. پکیجی که چند «نحوه‌ی ارائه» (`types`) دارد: همین محاسبه **به‌ازای هر نحوه** جدا انجام شود (هر ردیف `price`/`prePaymentPrice` خودش را دارد).
6. اعداد را فارسی/جداکننده‌ی هزارگان نمایش دهید؛ به سرور **عدد خام** بفرستید.

> سرور در هر حال خودش هم اعتبارسنجی می‌کند؛ اپ فقط تجربه‌ی بهتر می‌دهد.

## ۴) خطاهای سرور

`POST/PUT /api/Companion/{ClinicService|CoachService|GroomerService}/Package` در صورت تخطی `isSuccess=false` برمی‌گرداند و **چیزی ذخیره نمی‌شود**:

| وضعیت | پیام (`messages[0].item1`) |
| --- | --- |
| پیش‌پرداخت > کل مبلغ | «پیش‌پرداخت نمی‌تواند بیشتر از کل مبلغ (۱٬۰۰۰٬۰۰۰ تومان) باشد.» |
| پیش‌پرداخت < حداقل | «پیش‌پرداخت باید حداقل ۲۰۰٬۰۰۰ تومان (۲۰٪ مبلغ کل، سهم پاستیل) باشد.» |
| مبلغ نامعتبر (≤ ۰/NaN) یا پیش‌پرداخت منفی | همان پیام‌های قبلی «قیمت پکیج نامعتبر است» |

(مبلغ‌های داخل پیام با جداکننده‌ی هزارگان انگلیسی «1,000,000» می‌آیند؛ اگر خواستید فارسی نشان دهید فقط متن را مستقیم نمایش ندهید و از محاسبه‌ی خودتان در بخش ۳ استفاده کنید.)

## ۵) نکته‌های عملیاتی

- **ویرایش پکیج‌های قدیمی:** اگر ادمین بعداً درصد را بالا ببرد، پکیج‌هایی که پیش‌پرداختشان کمتر از حداقل جدید است تا زمانی که ارائه‌دهنده آن‌ها را **ویرایش نکند** همان‌طور می‌مانند (رزروهای موجود تغییر نمی‌کنند)؛ در اولین ویرایش باید پیش‌پرداخت را به حداقل جدید برساند. پیشنهاد: اپ در لیست پکیج‌ها اگر `prePaymentPrice < minPrepay(price, effectiveCommissionPercent)` بود نشان «نیاز به اصلاح پیش‌پرداخت» بگذارد.
- **درصد خدمت هنگام تأیید ادمین ثبت می‌شود:** قبل از تأیید ممکن است `effectiveCommissionPercent` فقط همان کمیسیون اصلی مرکز باشد (یا ۰)؛ بعد از تأیید با درصد خودِ خدمت جایگزین می‌شود. اپ بعد از هر بار لود لیست خدمات مقدار را از سرور بگیرد، نه ذخیره‌ی محلی.
- پانسیون و مدرسه این قاعده را ندارند (پکیجِ پیش‌پرداختی در آن‌ها نیست).

## ۶) چک‌لیست تست

1. خدمتی با `effectiveCommissionPercent=20`، پکیج ۱٬۰۰۰٬۰۰۰: پیش‌پرداخت ۱۰۰٬۰۰۰ ← خطای «حداقل ۲۰۰٬۰۰۰».
2. همان با ۲۰۰٬۰۰۰ و ۱٬۰۰۰٬۰۰۰ ← موفق؛ ۱٬۰۰۱٬۰۰۰ ← خطای «بیشتر از کل مبلغ».
3. پکیج دو نحوه‌ی ارائه (حضوری/آنلاین): فقط یکی زیر حداقل ← کل درخواست رد می‌شود (چیزی ذخیره نمی‌شود).
4. مربی – پانسیون آموزشی: price=۵۰۰٬۰۰۰، dailyPrice=۱۰۰٬۰۰۰، stayDays=۵ ← کل ۱٬۰۰۰٬۰۰۰؛ حداقل با ۲۰٪ = ۲۰۰٬۰۰۰.
5. درصد ۰ ← هر پیش‌پرداخت بین ۰ و کل مبلغ مجاز است.
6. ویرایش پکیج با `PUT .../Package` همین قواعد را دارد.
