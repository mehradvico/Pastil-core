# تطبیق هوشمند: نمایش «همه‌ی محصولات کاتالوگ» (موجود، ناموجود، بدون آیتم فروش) — راهنمای فرانت (اپ فروشنده)

مکمل `FLUTTER_AI_PRODUCT_MATCH_INTEGRATION_FA.md`. Base URL: `https://api.pastil.pet`، همه‌ی endpointها `Authorization: Bearer {accessToken}`.

> **وضعیت:** تغییر بک‌اند نوشته و build شده ولی **هنوز deploy نشده**. تا deploy، سرور همان رفتار قبلی را دارد.
> اپ برای هر دو حالت (قبل/بعد از deploy) بدون تغییر در قرارداد JSON کار می‌کند؛ فقط رفتارِ «چه محصولی در `matches[]` می‌آید» عوض می‌شود.
> هر چیزی که تست واقعی نشده با **⚠️** علامت خورده.

---

## ۱. خلاصه

- **قرارداد JSON هیچ تغییری نکرده.** هیچ فیلدی اضافه/حذف/rename نشده.
- **رفتار جدید سرور:** فروشنده باید همه‌ی محصولات شبیه در کاتالوگ را ببیند، چه فروشگاهی آن را بفروشد و چه نه. یعنی در `matches[]` از این به بعد این‌ها هم می‌آیند:
  1. محصولی که **در هیچ فروشگاهی موجود نیست** (ناموجود).
  2. محصولی که **هیچ `ProductItem` (آیتم فروش) ندارد**؛ هدف دقیقاً این است که فروشنده آن را به فروشگاه خودش اضافه کند.
- **پیش‌نویسِ فروشگاه‌های دیگر** (محصولی که فروشگاه دیگری ساخته و ادمین هنوز تأیید نکرده) در `matches[]` **نمی‌آید.** پیش‌نویسِ خودِ همین فروشگاه می‌آید.
- بین «موجود» و «ناموجود» در ترتیب یا اولویت پیشنهادها هیچ فرقی گذاشته نمی‌شود؛ فقط شباهت اسم مهم است.

**بدون تغییر:** حداکثر ۳ پیشنهاد برای هر ردیف (`matches[]`)، و فقط پیشنهادهای با شباهت حداقل ۶۰٪ (`confidence ≥ 0.6`).

## ۲. چه کاری از فرانت لازم است

### ۲-۱. `matches[]` را بر اساس موجود/ناموجود فیلتر نکنید
هر کاندید را با هر وضعیتی نمایش بدهید. **فیلد «موجود/ناموجود» در پاسخ وجود ندارد** و لازم هم نیست؛ اگر بخواهید برچسب مثل «هنوز در هیچ فروشگاهی نیست» نشان بدهید، بک‌اند باید فیلد جدید اضافه کند (فعلاً نشده).

پیشنهاد متن کنار کاندید: «این محصول در کاتالوگ پاستیل هست؛ قیمت و تعداد فروشگاه خودتان را وارد کنید.»

### ۲-۲. کاندیدی که `productItems` آن **خالی** است (⚠️ مهم)
برای محصولی که هیچ آیتم فروشی ندارد، فعلاً `matches[].productItems` برابر `[]` برمی‌گردد (بک‌اند در حال اصلاح آن است؛ بعد از اصلاح یک گزینه‌ی «بدون تنوع» با `productItemId: null` می‌آید). **کاندید با `productItems` خالی را دور نیندازید و «قابل انتخاب نیست» نکنید.**

**راه‌حل تا زمان اصلاح بک‌اند (با endpoint موجود):** وقتی فروشنده چنین کاندیدی را انتخاب کرد، فرم قیمت‌گذاری همان محصول را بگیرید:

```http
GET /api/Seller/ProductItem/id?id={productId}
```

پاسخ (مثال تقریبی؛ ⚠️ از روی خواندن کد سرور نوشته شده و با اجرای واقعی تست نشده):

```json
{
  "isSuccess": true,
  "data": {
    "productId": 4821,
    "storeId": 7,
    "productItems": [
      { "id": 0, "productId": 4821, "basePrice": 0, "quantity": 0, "varietyItemId": null, "varietyItem2Id": null, "active": true, "warranty": null }
    ]
  }
}
```

- محصول **بدون تنوع** → یک سطر با `varietyItemId: null`.
- محصول **با تنوع** (که ادمین تعریف کرده، مثل رنگ/سایز) → یک سطر به‌ازای هر ترکیب، با `varietyItem` (شامل `name`) برای نمایش.
- `id: 0` یعنی هنوز برای این فروشگاه ساخته نشده؛ `id` مقدار دارد یعنی آپدیت.
- سطرها را با قیمت/تعداد پر کنید و مطابق بخش ۳ سند اصلی به `POST /api/Seller/ProductItem` بفرستید.

بعد از اصلاح بک‌اند، همین کاندیدها یک گزینه‌ی آماده در `productItems` خواهند داشت و همان مسیر معمولی (بخش ۳ سند اصلی) کار می‌کند؛ اپ باید هر دو حالت را تحمل کند.

### ۲-۳. اعتبارسنجی قیمت و تعداد سمت اپ (⚠️ الزامی)
سرور برای **آیتم جدید** فقط وقتی ردیف می‌سازد که `basePrice > 0` **و** `quantity > 0` باشد. اگر یکی صفر باشد، پاسخ `isSuccess: true` برمی‌گردد ولی **هیچ آیتمی ساخته نمی‌شود** (بی‌صدا نادیده گرفته می‌شود؛ از روی کد تأیید شده).
- برای آیتم جدید هر دو را حداقل ۱ بگیرید و قبل از ارسال کاربر را متوجه کنید.
- سطرهای پرنشده (قیمت/تعداد صفر) را اصلاً در `POST` نفرستید.
- آپدیت آیتم موجود با `quantity: 0` مجاز است (موجودی صفر می‌شود).

### ۲-۴. `matches` خالی
اگر بعد از deploy هم `matches` خالی بود یعنی واقعاً چیزی شبیه پیدا نشد (یا شباهت‌ها زیر ۶۰٪ بود). طبق سند اصلی: کاربر دستی جست‌وجو کند، یا محصول را از مسیر «محصولات ثبت‌نشده» (`FLUTTER_MISSING_PRODUCT_FA.md`) پیشنهاد بدهد. `catalogMatchFailed=true` را همچنان «ناموجود» گزارش نکنید.

### ۲-۵. برچسب «در کاتالوگ نیست» را فقط برای حالت درست نشان بدهید (⚠️ مهم)
«در کاتالوگ نیست» فقط وقتی درست است که `matches` **خالی** باشد **و** `issues` شامل «در کاتالوگ پاستیل پیدا نشد» باشد. اپ نباید فقط بر اساس `productId == null` این برچسب را بزند. حالت‌های زیر همه `productId` خالی دارند ولی «در کاتالوگ نیست» **نیستند**:

| `issues[]` | `matches` | یعنی | نمایش پیشنهادی |
|---|---|---|---|
| «در کاتالوگ پاستیل پیدا نشد» | خالی | واقعاً کاندیدی پیدا نشد | «در کاتالوگ نیست» + پیشنهاد ثبت به‌عنوان «محصول ثبت‌نشده» |
| «امکان تطبیق خودکار وجود نداشت…» | خالی یا پر | مدل مطمئن نبود؛ اگر `matches` پر است پیشنهادها را نشان بدهید | «انتخاب دستی» + فهرست `matches` |
| «چند محصول مشابه یافت شد…» | پر | دو کاندید خیلی نزدیک‌اند | فهرست `matches` را برجسته نشان بدهید |
| «تطبیق با کاتالوگ کامل نشد…» (و `catalogMatchFailed: true`) | خالی | خطا/timeout سمت سرور، **نه** نبودن در کاتالوگ | «نامشخص» + دکمه‌ی «تلاش دوباره» |

اگر بعد از deploy باز هم ردیفی اشتباهاً «در کاتالوگ نیست» شد، JSON همان ردیف (`issues`، `matches`، `catalogMatchFailed`) را برای بک‌اند بفرستید؛ با همین چهار متن علت مشخص می‌شود.

### ۲-۶. بدون تغییر لازم
`analyze`، `analyze/start`، فیلدهای `items[]`، کدهای خطا، `boundingBoxes` و بخش ۳ سند اصلی همان قبلی است. (`sourcePictureId` بعداً حذف شد — `FLUTTER_AI_PRODUCT_MATCH_RESULT_STATES_FA.md`.)

## ۳. چیزهایی که بعداً می‌آید و **الان پیاده نکنید**

بک‌اند در حال ساخت قابلیت «تعریف تنوع توسط فروشنده + مخزن مشترک مقدارها» است (سند بک‌اند: `BACKEND_PRODUCT_VARIETY_MIGRATION_FA.md`). طرح endpointها هنوز **پیشنهاد** است و نهایی نشده؛ سند فرانت جدا بعد از تمام‌شدنش می‌آید. فقط دو نکته برای آگاهی:
- `POST /api/Seller/ProductItem` بعداً سخت‌گیرانه‌تر می‌شود: `varietyItemId` باید متعلق به تنوع همان محصول باشد. اگر همیشه مقدارها را از پاسخ خود سرور (`GET ProductItem/id` یا `matches[].productItems`) بردارید، مشکلی پیش نمی‌آید.
- شکل JSON فعلی `ProductItem` تغییر نمی‌کند (فقط افزودنی).

## ۴. چک‌لیست تست فرانت (بعد از deploy)

1. عکس قفسه‌ای که شامل محصولی است که هیچ فروشگاهی ندارد → محصول در `matches[]` بیاید و انتخاب‌شدنی باشد.
2. کاندید با `productItems` خالی → فرم قیمت/تعداد با `GET /api/Seller/ProductItem/id` باز شود و با `POST` ذخیره شود.
3. ذخیره با `quantity: 0` برای آیتم جدید → اپ قبل از ارسال جلویش را بگیرد.
4. بعد از ذخیره، همان محصول برای فروشگاه دوباره باز شود → آیتم ساخته‌شده دیده شود (`existsForCurrentStore: true`).
5. حداکثر ۳ پیشنهاد برای هر ردیف و بدون هیچ برچسب/مرتب‌سازی بر اساس موجودی.

## ۵. تأییدنشده‌ها

- شکل دقیق پاسخ `GET /api/Seller/ProductItem/id` با اجرای واقعی دیده نشده (از روی کد).
- deploy انجام نشده؛ تست کامل روی سرور واقعی هنوز نشده.
- رفتار تحلیل عکس با هوش مصنوعی روی این ماشین قابل اجرا نبود (کلید API نیست)؛ فقط جست‌وجوی کاتالوگ با SQL روی دیتابیس موقت تست شده است.
