# مدرسه زیر «ارائه‌دهنده» — راهنمای اپ ارائه‌دهنده

**مخاطب:** توسعه‌دهنده‌ی اپ ارائه‌دهنده (بخش «مدرسه‌ی من»: ساخت/ویرایش مدرسه، دوره، جلسه، ویدیو، پخش زنده، ثبت‌نام‌ها)
**تاریخ:** ۱۴۰۵/۰۸/۰۴ (2026-10-26)
**وضعیت بک‌اند:** کد و تست آماده است، ولی **هنوز دیپلوی نشده** (مایگریشن `SchoolProviderOwner` اجرا نشده). تا اعلام دیپلوی، رفتار سرور همان قبلی است.
**دلیل:** گزارش «مشکل اضافه نشدن مدرسه». تا امروز مدرسه فقط زیر یک «نمایندگی» (Companion) ساخته می‌شد. ارائه‌دهنده‌ای که نمایندگی نداشت (مثلاً فقط کلینیک یا مربی داشت، یا تازه از ثبت‌نام ارائه‌دهنده آمده بود) جواب ۴۰۳ خالی می‌گرفت و اپ نمی‌توانست علت را نشان دهد.

---

## ۱) خلاصه‌ی تغییر
- مالک مدرسه حالا **ارائه‌دهنده** است (`providerId`). نمایندگی (`companionId`) **اختیاری** است و فقط برای مدرسه‌های قدیمی باقی می‌ماند.
- ارائه‌دهنده‌ای که نقش **«مدرسه» (School)** برایش تأیید شده، بدون هیچ نمایندگی می‌تواند مدرسه بسازد.
- مسیرها (URL) **عوض نشده‌اند**. همه‌ی اندپوینت‌های `api/Companion/School…` مثل قبل‌اند.
- خطای ساخت مدرسه دیگر ۴۰۳ خالی نیست و مثل بقیه‌ی API، HTTP 200 با `isSuccess=false` و پیام روشن برمی‌گردد.
- مدرسه‌های موجود سر جایشان می‌مانند و ارائه‌دهنده‌ی نمایندگی‌شان خودکار مالکشان می‌شود.

## ۲) پیش‌نیاز ساخت مدرسه
کاربر باید یکی از این دو حالت را داشته باشد:

| حالت | نتیجه |
|---|---|
| حساب ارائه‌دهنده‌ی **فعال و تأییدشده** با نقش **«مدرسه»** تأییدشده | مدرسه با `providerId` همین ارائه‌دهنده ساخته می‌شود. نمایندگی لازم نیست. |
| نقش «مدرسه» ندارد، ولی یک نمایندگی فعال و تأییدشده دارد (مسیر قدیمی) | مدرسه زیر همان نمایندگی ساخته می‌شود و ارائه‌دهنده‌ی آن نمایندگی هم مالک ثبت می‌شود. |
| هیچ‌کدام | خطای `SchoolNeedsProviderRole` (بند ۴) |

نقش «مدرسه» را ادمین پاستیل در پنل به ارائه‌دهنده می‌دهد (صفحه‌ی ارائه‌دهنده ← نقش‌ها). اپ نباید خودش این نقش را بسازد.

## ۳) ساخت مدرسه — `POST /api/Companion/School`
بدنه مثل قبل است. فقط قاعده‌ی دو فیلد زیر عوض شده:

| فیلد | قاعده‌ی جدید |
|---|---|
| `companionId` | **اختیاری.** اگر کاربر چند نمایندگی دارد و می‌خواهد مدرسه زیر یکی از آن‌ها باشد، آن را بفرستد. برای ارائه‌دهنده‌ی دارای نقش «مدرسه» لازم نیست؛ اگر نیاید، مدرسه فقط به ارائه‌دهنده وصل می‌شود. اگر بیاید، باید مال خود کاربر باشد. |
| `providerId` | **نفرستید.** سرور از روی کاربر پر می‌کند و مقدار ارسالی را نادیده می‌گیرد. |

بقیه‌ی فیلدها و اعتبارسنجی‌ها مثل قبل‌اند: نام الزامی، موقعیت، استان، شهر و … . مدرسه‌ی جدید مثل قبل **غیرفعال و در انتظار تأیید ادمین** ساخته می‌شود.

پاسخ موفق:
```json
{ "isSuccess": true, "data": { "id": 57, "name": "…", "providerId": 14, "companionId": null, "active": false, "approve": false, "…": "…" } }
```

## ۴) پیام‌های خطای ساخت (همه HTTP 200 با `isSuccess=false`)
متن را از `messages` بخوانید و همان را نشان دهید:

| کلید | متن فارسی | کار اپ |
|---|---|---|
| `SchoolNeedsProviderRole` | برای افزودن مدرسه، حساب ارائه‌دهنده‌ی شما باید فعال و تأییدشده باشد و نقش «مدرسه» برایش تأیید شده باشد. با پشتیبانی پاستیل تماس بگیرید. | پیام را نشان دهید، به همراه دکمه‌ی «تماس با پشتیبانی». |
| `SchoolChooseCompanion` | چند نمایندگی دارید؛ لطفاً نمایندگی‌ای را که مدرسه زیر آن ثبت شود انتخاب کنید. | فقط برای کاربرِ بدون نقش «مدرسه» با چند نمایندگی. فهرست نمایندگی‌ها را نشان دهید و دوباره با `companionId` بفرستید. |
| `AccessDenied` | دسترسی ندارید | `companionId` ارسالی مال این کاربر نیست. |
| (قبلی) نام/موقعیت | مثل قبل | مثل قبل |

## ۵) مدل‌های پاسخ
در پاسخ‌های مدرسه (`GET /api/Companion/School`، `GET /api/Companion/School/{id}` و همین‌طور فهرست‌های عمومی):
- `companionId` حالا **nullable** است. مدرسه‌ی جدید ارائه‌دهنده معمولاً `companionId: null` دارد. کد اپ نباید فرض کند این فیلد همیشه مقدار دارد.
- `providerId` (nullable) و `providerName` اضافه شده‌اند.
- شیء `companion` هم ممکن است `null` باشد. برای نمایش نام مالک، اول `providerName` و بعد نام نمایندگی را بخوانید.

## ۶) بقیه‌ی بخش‌ها (بدون تغییر قرارداد)
دوره، جلسه، ویدیو، پخش زنده، حیوان‌های دوره، عکس‌ها، فعال/غیرفعال، حذف و «تکمیل ثبت‌نام» (`api/Companion/School…`) با همان مسیر و بدنه کار می‌کنند. فرق فقط این است که مالکیت حالا با **ارائه‌دهنده یا نمایندگیِ** مدرسه سنجیده می‌شود.
- **نوشتن** (ساخت، ویرایش، حذف، شروع پخش زنده) نیاز دارد ارائه‌دهنده (یا نمایندگیِ مدرسه‌های قدیمی) **فعال و تأییدشده** باشد.
- **خواندن** مال خود کاربر همیشه آزاد است.
- **پخش زنده:** شناسه‌ی میزبان در LiveKit از `companion-{id}` به **`school-{schoolId}`** تغییر کرد و نام نمایشی میزبان حالا نام مدرسه است. اگر اپ میزبان را با پیشوند `companion-` تشخیص می‌داد (مثلاً برای جدا کردن قاب مدرس از شرکت‌کننده‌ها)، پیشوند `school-` را هم بپذیرد.

## ۷) مالی و تسویه (برای اطلاع)
مالی مدرسه **جدا** است: هر ارائه‌دهنده یک استخر تسویه‌ی «مدرسه» دارد (نوع تسویه `6`) که همه‌ی ثبت‌نام‌های مدرسه‌هایش را دارد، جدا از نمایندگی، کلینیک، مربی و … . تاریخچه‌ی تسویه‌های مدرسه برای خود ارائه‌دهنده: `GET /api/Companion/SchoolSettlement` و `GET /api/Companion/SchoolSettlement/{id}` (همان شکل `CoachSettlement`). اگر اپ صفحه‌ی «تسویه‌های من» را بر اساس نوع جدا نشان می‌دهد، برگه‌ی «مدرسه» را با همین اندپوینت اضافه کند.

## ۸) سازگاری با نسخه‌ی فعلی سرور (تا قبل از دیپلوی)
- تا دیپلوی، سرور قدیمی برای کاربرِ بدون نمایندگی همان **۴۰۳ خالی** را برمی‌گرداند. اپ پاسخ ۴۰۳ را هم با یک پیام عمومی مدیریت کند («امکان ثبت مدرسه برای حساب شما فعال نیست؛ با پشتیبانی تماس بگیرید»).
- `providerId` و `providerName` در سرور قدیمی نمی‌آیند. nullable تعریف کنید.

```kotlin
@Serializable
data class SchoolItem(
    val id: Long,
    val name: String,
    val companionId: Long? = null,   // nullable شد
    val providerId: Long? = null,    // جدید
    val providerName: String? = null,// جدید
    val active: Boolean = false,
    val approve: Boolean = false,
)
```

## ۹) چک‌لیست تست روی دستگاه (بعد از اعلام دیپلوی)
1. ارائه‌دهنده‌ی بدون نقش «مدرسه» و بدون نمایندگی ← «افزودن مدرسه» ← باید پیام `SchoolNeedsProviderRole` بیاید، نه خطای خالی.
2. ادمین نقش «مدرسه» را به همان ارائه‌دهنده بدهد ← دوباره «افزودن مدرسه» ← مدرسه ساخته شود با `providerId` پر و `companionId: null`، و وضعیت «در انتظار تأیید» داشته باشد.
3. مدرسه در «مدرسه‌های من» (`GET /api/Companion/School`) دیده شود.
4. دوره، جلسه و ویدیو اضافه شود (همان مسیرهای قبلی).
5. ادمین مدرسه را تأیید کند ← در اپ مشتری دیده شود ← یک ثبت‌نام آزمایشی ← در «ثبت‌نام‌ها» بیاید و «تکمیل» کار کند.
6. کاربر قدیمی با یک نمایندگی (بدون نقش «مدرسه») ← مدرسه‌ی جدید مثل قبل زیر نمایندگی‌اش ساخته شود.
7. کاربر دیگر نتواند مدرسه‌ی این ارائه‌دهنده را ویرایش کند (`NotFound` یا `AccessDenied`).
