# تطبیق هوشمند قفسه: چهار وضعیتِ هر ردیف — راهنمای فرانت (اپ فروشنده)

مکمل `FLUTTER_AI_PRODUCT_MATCH_INTEGRATION_FA.md` و `FLUTTER_AI_PRODUCT_MATCH_ALL_PRODUCTS_FA.md`.
Base URL: `https://api.pastil.pet` — همه‌ی endpointها `Authorization: Bearer {accessToken}`.

> **قرارداد JSON هیچ تغییری نکرده.** هیچ فیلدی اضافه/حذف/rename نشده. این سند فقط می‌گوید فیلدهای موجود
> باید چطور خوانده شوند. تغییرات بک‌اند در بخش ۴ آمده است.

---

## ۱. مشکلی که دیده شد

در اسکن قفسه، هوش مصنوعی هر ۶ محصول را **درست** خواند (`detectedName` دقیق بود) ولی اپ برای هر ۶
برچسب «نامشخص» زد و شمارنده‌ی پایین صفحه شد «۰ در کاتالوگ / ۶ نامشخص» — در حالی که چند تا از آن
محصولات در کاتالوگ پاستیل وجود دارند. قبل‌تر همین حالت «در کاتالوگ نیست» نمایش داده می‌شد.

دو علت داشت و هر دو باید درست شود:

1. **سمت بک‌اند:** وقتی مرحله‌ی تطبیق با مدل کامل نمی‌شد (تمام‌شدن بودجه‌ی زمانی یا خطای Provider)،
   ردیف با `catalogMatchFailed: true` و `matches: []` برمی‌گشت — حتی وقتی محصولِ درست بین کاندیدهای
   پیداشده بود. **درست شد** (بخش ۴).
2. **سمت اپ:** اپ نتیجه را دووضعیتی می‌بیند (`productId != null` → «در کاتالوگ»، وگرنه «نامشخص»).
   پاسخ سرور **چهار** وضعیت دارد و سه‌تای آن‌ها `productId == null` دارند ولی معنی‌شان کاملاً فرق
   می‌کند. **این بخش باید در اپ اصلاح شود.**

---

## ۲. چهار وضعیت — فقط از روی سه فیلد، بدون تطبیق متن فارسی

وضعیت هر آیتم `items[]` **فقط** با این سه فیلد تعیین می‌شود:
`catalogMatchFailed` (bool) · `productId` (long?) · `matches` (array)

| # | `catalogMatchFailed` | `productId` | `matches` | معنی | نمایش در اپ |
|---|---|---|---|---|---|
| A | `false` | مقدار دارد | معمولاً پر | سرور با اطمینان بالا محصول را انتخاب کرده | ✅ **در کاتالوگ** — فرم قیمت/تعداد مستقیم باز شود |
| B | `false` | `null` | **پر** | محصول در کاتالوگ هست، ولی انتخاب قطعی با فروشنده است | 🟡 **انتخاب از فهرست** — `matches` را (تا ۳ تا) نشان بده و با یک ضربه انتخاب شود |
| C | `false` | `null` | **خالی** | واقعاً چیزی شبیه این در کاتالوگ نیست | ⚪️ **در کاتالوگ نیست** — مسیر «محصول ثبت‌نشده» (`FLUTTER_MISSING_PRODUCT_FA.md`) |
| D | `true` | `null` | خالی | خطا/timeout سمت سرور — **نه** نبودن در کاتالوگ | 🔁 **نامشخص** — دکمه‌ی «تلاش دوباره» برای همان عکس |

> **مهم:** «نامشخص» فقط و فقط برای حالت D است. «در کاتالوگ نیست» فقط و فقط برای حالت C.
> حالت B هرگز نباید «نامشخص» یا «در کاتالوگ نیست» دیده شود — این دقیقاً باگ فعلی است و بعد از تغییر
> بک‌اند (بخش ۴) **بیشترِ** ردیف‌هایی که الان «نامشخص» می‌شوند، حالت B خواهند بود.

### ۲-۱. کد پیشنهادی (Dart)

```dart
enum MatchState { autoMatched, needsPick, notInCatalog, unknown }

MatchState stateOf(AiMatchItem item) {
  if (item.catalogMatchFailed) return MatchState.unknown;        // D
  if (item.productId != null)  return MatchState.autoMatched;    // A
  if (item.matches.isNotEmpty) return MatchState.needsPick;      // B
  return MatchState.notInCatalog;                                // C
}
```

- ترتیب شرط‌ها مهم است: اول `catalogMatchFailed`، بعد `productId`، بعد `matches`.
- **هرگز** وضعیت را از روی متن `issues[]` تشخیص ندهید. `issues[]` فقط برای نمایش توضیح به فروشنده
  است؛ متن‌هایش ممکن است ویرایش شوند.
- `confidence` را برای تصمیم‌گیری استفاده نکنید. سرور آستانه‌ها را خودش اعمال کرده؛ هر چیزی که در
  `matches` آمده یعنی «به فروشنده نشان بده».

### ۲-۲. شمارنده‌ی پایین صفحه

الان دو شمارنده است («X در کاتالوگ» / «Y نامشخص») و هر چیزی که `productId` ندارد در «نامشخص»
می‌افتد. باید سه‌تایی شود (یا دست‌کم A و B با هم شمرده شوند):

```dart
final inCatalog   = items.where((i) => stateOf(i) == MatchState.autoMatched
                                    || stateOf(i) == MatchState.needsPick).length;
final notInCatalog = items.where((i) => stateOf(i) == MatchState.notInCatalog).length;
final unknown      = items.where((i) => stateOf(i) == MatchState.unknown).length;
```

دکمه‌ی «پایان و ادامه (N در کاتالوگ)» باید `inCatalog` را بشمارد، نه فقط `productId != null` را —
وگرنه فروشنده‌ای که ۵ محصول قابل‌انتخاب دارد، «۰ در کاتالوگ» می‌بیند و دکمه را نمی‌زند.

## ۳. جزئیات نمایش هر وضعیت

### A — تطبیق خودکار (`productId` دارد)
- `productName` را نشان بده، نه `detectedName`.
- اگر `productItemId` مقدار دارد → همان تنوع از قبل انتخاب شده؛ فقط قیمت/تعداد.
- اگر `productItemId` خالی است ولی `matches[0].productItems` بیش از یک عضو دارد → فروشنده باید تنوع
  را انتخاب کند.
- امکان «این درست نیست» بگذار که فروشنده بتواند به حالت B (فهرست `matches`) برگردد.

### B — انتخاب از فهرست (جدید و مهم‌ترین بخش)
- `detectedName` را به‌عنوان «چیزی که از عکس خوانده شد» بالا نشان بده، و زیرش `matches` را:
  `matches[i].name` + یک دکمه‌ی انتخاب. حداکثر ۳ تاست، مرتب‌شده از بهترین به بدترین (خودِ سرور مرتب
  کرده؛ دوباره مرتب نکن).
- بعد از انتخاب، دقیقاً همان مسیر حالت A: از `matches[i].productItems` تنوع را بگیر.
- `productItems` خالی → کاندید را دور نینداز؛ طبق بخش ۲-۲ سند `..._ALL_PRODUCTS_FA.md` با
  `GET /api/Seller/ProductItem/id?id={productId}` فرم را باز کن.
- متن پیشنهادی: «شبیه‌ترین محصول‌های کاتالوگ — یکی را انتخاب کنید».

### C — در کاتالوگ نیست
- همین حالا هم درست کار می‌کند؛ فقط مطمئن شو که با D اشتباه گرفته نمی‌شود.
- `brand` و `packageSize` و `sourcePictureId` را برای پیش‌پرکردن فرم «محصول ثبت‌نشده» بفرست.
- اگر `confidence` (اطمینان از **خواندن نام**، نه از تطبیق) کمتر از ۰.۶ بود، پیشنهاد ثبت را ندهید؛
  احتمالاً نام از عکس درست خوانده نشده.

### D — نامشخص
- دکمه‌ی «تلاش دوباره» فقط همان عکس/عکس‌ها را دوباره `analyze` کند.
- این ردیف را در شمارش «ناموجود/در کاتالوگ نیست» نیاور و به مسیر «محصول ثبت‌نشده» نفرست.
- اگر بعد از دو بار تلاش دوباره باز هم D بود، JSON همان ردیف (`rowId`, `issues`, `matches`,
  `catalogMatchFailed`) را برای بک‌اند بفرست — با `rowId` لاگ سرور دقیقاً پیدا می‌شود.

## ۴. چه چیزی در بک‌اند عوض شد (بدون تغییر قرارداد)

1. **شبکه‌ی ایمنی مرحله‌ی تطبیق.** اگر مدل برای یک ردیف نتیجه‌ای برنگرداند (timeout بودجه، خطای
   Provider، یا پاسخ ناقص)، سرور به‌جای `catalogMatchFailed: true` با `matches: []`، همان کاندیدهای
   واقعی دیتابیس را با شباهت نام رتبه‌بندی می‌کند و در `matches` می‌گذارد → ردیف از حالت **D** به
   حالت **B** می‌آید. در این حالت `productId` عمداً خالی می‌ماند (بدون تأیید مدل روی
   نوع حیوان/برند/سایز، انتخاب خودکار یعنی ریسک ثبت موجودی روی محصول اشتباه).
   هزینه‌ی سرور: صفر — نه فراخوانی شبکه، نه Query اضافه.
2. **جست‌وجوی کاتالوگ سبک‌تر و دقیق‌تر.** حالت fuzzy دوحرفی برای این مسیر خاموش شد (برای نام کاملِ
   ۸-۱۲ کلمه‌ایِ خوانده‌شده از عکس فقط نویز بود): Scan سبک‌تر، ریسک timeout کمتر، و کاندیدهای بهتر
   در فهرست.
3. **بودجه‌ی زمانی متعادل‌تر.** سهم رزروشده برای مرحله‌ی تطبیق از ۱۵ به ۲۲ ثانیه و کل بودجه از ۴۵ به
   ۵۰ ثانیه رسید (همچنان زیر سقف ۶۰ ثانیه‌ی کلاینت). قبلاً یک استخراجِ کُندِ عکس می‌توانست تمام
   بودجه را بخورد و **همه‌ی** ردیف‌ها را D کند — همان چیزی که در اسکرین‌شات دیده شد.

**Timeout سمت اپ برای `POST /api/Seller/AiProductMatch/analyze` را کمتر از ۶۰ ثانیه نگذارید.**

## ۵. چک‌لیست تست اپ

1. عکس قفسه‌ای با چند محصول موجود در کاتالوگ → هیچ ردیفی نباید «نامشخص» باشد؛ ردیف‌ها یا A یا B.
2. ردیف حالت B → فهرست `matches` دیده شود، انتخاب‌شدنی باشد، و بعد از انتخاب فرم قیمت/تعداد باز شود.
3. شمارنده‌ی پایین صفحه A و B را با هم بشمارد؛ دکمه‌ی «پایان و ادامه» با ردیف‌های B هم فعال باشد.
4. محصولی که واقعاً در کاتالوگ نیست (مثلاً یک برند جدید) → C، با پیشنهاد «محصول ثبت‌نشده».
5. قطع کردن اینترنت وسط تحلیل / پاسخ ناقص → D با «تلاش دوباره»، و **بدون** برچسب «در کاتالوگ نیست».
6. ردیف A که فروشنده «این درست نیست» می‌زند → برگشت به فهرست `matches`.

## ۶. تأییدنشده‌ها

- تغییرات بک‌اند build و unit-test شده‌اند ولی **روی سرور واقعی با کلید Provider اجرا نشده‌اند**؛
  تست انتها-به-انتها بعد از deploy لازم است.
- اینکه بعد از deploy چند درصد ردیف‌ها A می‌شوند و چند درصد B، به سرعت پاسخ Provider بستگی دارد و
  اندازه‌گیری نشده. اپ باید هر دو را یکسان خوب هندل کند.
