# پت‌رسان (سرویس هفتگی): ساعت برگشت جدا از ساعت رفت — رفع باگ

**گزارش مرتبط:** «توی پت‌رسان (بخش سرویس) کاربر فقط می‌تونه یک روز و یک زمان در اون روز مشخص کنه؛ گزینه‌ی رفت‌وبرگشت کلی است و برای برگشت زمان مشخصی ندارد.» — گزارش‌دهنده: آرمان تاجیک، شدت فوری.

## ۱. تأیید و ریشه‌ی باگ
تأیید شد. در سرویس هفتگی پت‌رسان (`PetResanService`، جدا از رزرو/فوری)، هر ردیف زمان‌بندی فقط یک `Time` (ساعت رفت) داشت. «رفت‌وبرگشت» فقط یک **ضریب قیمت** بود (`RoundTrip: true` در `PriceCalculationService` تقریباً ۵۰٪ به قیمت اضافه می‌کند)، نه یک سفر واقعیِ دوم با ساعت خودش. یعنی هر هفته فقط **یک Trip واقعی** (رفت) ساخته می‌شد و کاربر هیچ‌وقت نمی‌توانست بگوید «رفت ساعت ۸، برگشت ساعت ۱۷».

## ۲. راه‌حل
به هر ردیف زمان‌بندی یک `ReturnTime` اختیاری اضافه شد.

- **`ReturnTime` خالی/نال (پیش‌فرض، سازگار با قبل):** دقیقاً رفتار قبلی — یک Trip «رفت‌وبرگشت» با قیمتِ شاملِ هر دو طرف، بدون سفر برگشت جداگانه.
- **`ReturnTime` پر باشد:** حالا **دو Trip واقعی و مستقل** ساخته می‌شود:
  - رفت: مبدا→مقصد، ساعت `Time`، یک‌طرفه.
  - برگشت: مقصد→مبدا، ساعت `ReturnTime`، یک‌طرفه، `Trip.IsReturnLeg=true`.
  
  هرکدام با **نرخ ساعت خودشان** قیمت می‌گیرند (نه یک نرخ مشترک) و هرکدام باید جدا توسط یک راننده قبول شود — دقیقاً مثل دو سفر پت‌رسانِ جدا، فقط این‌که هر هفته خودکار تکرار می‌شوند.

## ۳. قرارداد API (تغییر افزایشی، سازگار با عقب)

### بدنه‌ی درخواست (`POST /api/EndUser/PetResanService`, `preview-price`)
```jsonc
{
  "schedules": [
    { "weekDayId": 2, "time": "08:00" },                          // رفتار قبلی: بدون برگشت
    { "weekDayId": 2, "time": "08:00", "returnTime": "17:30" }     // جدید: رفت ۸ صبح، برگشت ۵:۳۰ عصر
  ],
  "roundTrip": true   // فقط روی ردیف‌های بدونِ returnTime اثر دارد
}
```
- `returnTime` باید بعد از `time` همان روز باشد، وگرنه خطا: «ساعت برگشت باید بعد از ساعت رفت باشد.»
- کلید یکتاییِ هر ردیف همچنان `(weekDayId, time)` است؛ `returnTime` در یکتایی شرکت ندارد (دو ردیف با `time` یکسان و `returnTime` متفاوت هنوز تکراری حساب می‌شوند — منطقی هم هست، یعنی فقط یک برگشت برای هر رفت).

### پاسخ (`PetResanServiceVDto.schedules[]`)
هر ردیف حالا `returnTime` هم دارد (`null` اگر تنظیم نشده).

### قیمت (`preview-price` و `PricePerOccurrence`/`PricePerWeek`)
عدد برگشتی از `preview-price` از قبل هم «مبلغ کل هفته» بود، الان هم همان معنا را دارد — فقط برای ردیف‌های دارای `returnTime`، به‌جای یک قیمتِ رفت‌وبرگشت، **جمع دو قیمت یک‌طرفه‌ی جدا** (هرکدام با نرخ ساعت خودش) حساب می‌شود. چیزی در ساختار پاسخ عوض نشده.

## ۴. چیزی که برای فرانت لازم است (وب‌اپ/اپ)
این یک قابلیت UI جدید است، نه فقط رفع باگ نامرئی — باید در فرم ساخت سرویس هفتگی اضافه شود:
1. برای هر روزِ انتخاب‌شده، علاوه بر ساعت رفت، یک فیلد اختیاری «ساعت برگشت» اضافه کنید.
2. اگر کاربر ساعت برگشت نزد، رفتار دقیقاً مثل الان است (فقط `time` بفرستید).
3. اگر ساعت برگشت زد، باید بعد از ساعت رفت باشد — همان اعتبارسنجی سمت کلاینت را هم بگذارید تا خطای سرور را زودتر بگیرید.
4. در نمایش «سفرهای این سرویس» یا تاریخچه، حالا ممکن است برای یک روز **دو Trip** ببینید (یکی با `isReturnLeg:false`، یکی `true`) — هرکدام راننده و وضعیت پذیرش خودش را دارد؛ جدا نمایش دهید، نه به‌عنوان یک سفر.
5. کد `UI متن پیشنهادی`: «ساعت رفت» / «ساعت برگشت (اختیاری)» — اگر خالی بماند، همان رفت‌وبرگشت کلی قبلی است.

## ۵. وضعیت بک‌اند
- مایگریشن: `PetResanServiceReturnTime` (یک ستون nullable، ساخته شده، اعمال نشده).
- کل solution بدون خطا بیلد شد، همه‌ی ۵۶۲ تست سبز.
- سرویس‌های قبلی که `ReturnTime` ندارند دقیقاً همان رفتار قبلی را دارند — این تغییر برای هیچ داده‌ی موجودی چیزی نمی‌شکند.
