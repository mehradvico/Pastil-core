# مشاوره آنلاین قابل‌رزرو — مستند اپ نماینده (ویژه امیرمحسن)

> مخاطب: توسعه‌دهنده‌ی اپ/وب‌اپ **نماینده/کلینیک** · طراحی بک: [ONLINE_CONSULTATION_BOOKING_FA.md](ONLINE_CONSULTATION_BOOKING_FA.md) · مستند کاربر: [CONSULTATION_BOOKING_USER_ARMAN_FA.md](CONSULTATION_BOOKING_USER_ARMAN_FA.md)
> پیش‌نیاز: صفحه‌ی «پکیج‌های مشاوره آنلاین» و «مشاوره‌های من/مدیریت» که همین الان برای خرید فوری وجود دارند ([ONLINE_CONSULTATION_APP_FA.md](ONLINE_CONSULTATION_APP_FA.md)). این مستند فقط **تفاوت‌ها و بخش‌های جدید** را می‌گوید.
> وضعیت بک: پیاده‌سازی و تست واحد شد؛ **مایگریشن روی سرور اجرا نشده** — تا وقتی اجرا نشود endpointهای جدید خطا می‌دهند (جدول `ConsultationAvailabilities` نیست). قبل از تست روی سرور از بک بپرسید.

همه‌ی endpointها `Authorization: Bearer …` می‌خواهند. پاسخ‌ها **همیشه HTTP 200** هستند: `{ isSuccess, messages, data }` — موفقیت را از `isSuccess` بخوانید. نام فیلدها camelCase است. خطاها متن فارسی در `messages` دارند.

## ۱) مفهوم در یک نگاه

یک پکیج مشاوره دو حالت دارد:

| | فوری (قبلی) | **قابل رزرو (جدید)** |
| --- | --- | --- |
| فیلد پکیج | `bookable: false` | `bookable: true` |
| کاربر | می‌خرد و منتظر می‌ماند | یک **ساعت** از ساعت‌های کاری کلینیک انتخاب می‌کند |
| نماینده | هر وقت «شروع» بزند | **از ۱۰ دقیقه قبل** از ساعت رزرو «شروع» می‌زند |

برای اینکه کاربر بتواند ساعت انتخاب کند، کلینیک باید **ساعت‌های کاری هفتگی** تعریف کند. بدون آن، پکیج bookable هیچ ساعتی ندارد.

## ۲) تعریف پکیج قابل‌رزرو

همان API پکیج‌ها، فقط یک فیلد جدید `bookable`:

`POST /api/Companion/ConsultationPackage` (ساخت) · `PUT /api/Companion/ConsultationPackage` (ویرایش، `id` الزامی) · `GET` (فهرست) · `DELETE ?id=`

```json
{
  "name": "ویدیوکال رزروی ۳۰ دقیقه‌ای",
  "channelId": 3,
  "durationMinutes": 30,
  "price": 250000,
  "active": true,
  "bookable": true,
  "description": "ساعت را خودتان انتخاب کنید",
  "pictureId": null
}
```

- `bookable` در **ساخت**: اگر نفرستید `false` است. در **ویرایش**: اگر نفرستید یا `null` بفرستید **تغییری نمی‌کند** (اپ‌های قدیمی تصادفاً پکیج را از حالت رزرو درنمی‌آورند). برای خاموش‌کردن صریحاً `false` بفرستید.
- در پاسخ `GET` همیشه `bookable: true/false` برمی‌گردد.
- بقیه‌ی قواعد قبلی (نام ۲ تا ۱۰۰ نویسه، مدت از `15/30/45/60/90`، `active` فقط با قیمت > ۰، نام تکراری زیر یک کانال ممنوع) بدون تغییر.
- هر کلینیک می‌تواند هم‌زمان پکیج فوری و قابل‌رزرو داشته باشد (حتی برای یک کانال).
- **UI پیشنهادی:** در فرم پکیج یک سوئیچ «قابل رزرو (کاربر ساعت انتخاب می‌کند)». روی کارت پکیج نشان «رزروی». اگر پکیج `bookable && active` است ولی برنامه‌ی هفتگی خالی است، هشدار بدهید: «برای این پکیج ساعت کاری تعریف نشده؛ کاربر ساعتی برای رزرو نمی‌بیند» + دکمه‌ی رفتن به صفحه‌ی ساعت‌های کاری.

## ۳) ساعت‌های کاری هفتگی کلینیک (صفحه‌ی جدید)

### خواندن
`GET /api/Companion/ConsultationAvailability`

```json
{ "isSuccess": true, "data": [
  { "weekDayId": 1, "start": "09:00", "end": "13:00", "capacity": 2 },
  { "weekDayId": 1, "start": "15:00", "end": "19:00", "capacity": 1 },
  { "weekDayId": 5, "start": "16:00", "end": "20:00", "capacity": 1 }
]}
```

### ذخیره (جایگزینی کامل)
`PUT /api/Companion/ConsultationAvailability` — **بدنه یک آرایه** است و کل برنامه‌ی هفتگی را جایگزین می‌کند (ردیف‌های ارسال‌نشده حذف می‌شوند). آرایه‌ی خالی `[]` یعنی «هیچ ساعتی؛ رزرو بسته». پاسخ: برنامه‌ی ذخیره‌شده (مثل GET).

| فیلد | قاعده |
| --- | --- |
| `weekDayId` | `1` شنبه، `2` یکشنبه، `3` دوشنبه، `4` سه‌شنبه، `5` چهارشنبه، `6` پنجشنبه، `7` جمعه (هفته از شنبه شروع می‌شود؛ همان قرارداد سایر خدمات) |
| `start` / `end` | رشته‌ی `"HH:mm"` ۲۴ ساعته (فقط ارقام لاتین). **باید روی ربع ساعت باشد** (`00/15/30/45`). `end` بعد از `start`؛ `"24:00"` برای پایان مجاز است. بازه‌ی شبانه از نیمه‌شب رد نمی‌شود: دو بازه بسازید (`22:00–24:00` در یک روز و `00:00–02:00` روز بعد) |
| `capacity` | تعداد **مشاوره‌ی هم‌زمان** در آن بازه، ۱ تا ۲۰. معمولاً تعداد نمایندگانی که در آن ساعت آماده‌اند. سرور تعداد نمایندگان واقعی را نمی‌داند؛ مالک تعیین می‌کند |
| هم‌پوشانی | دو بازه‌ی هم‌روز نباید هم‌پوشان باشند (`13:00` پایان و `13:00` شروع بازه‌ی بعد مجاز است) |
| سقف | حداکثر ۵۰ بازه در کل هفته |

خطا (هر مورد نامعتبر): «برنامه‌ی ساعت‌های کاری نامعتبر است (ساعت‌ها باید روی ربع ساعت باشند، پایان بعد از شروع، و بازه‌های یک روز هم‌پوشان نباشند).» — اعتبارسنجی را **قبل از ارسال هم در UI** انجام دهید تا خطای سرور نادر باشد.

**چطور اسلات‌ها ساخته می‌شوند (برای پیش‌نمایش در UI):** مشاوره‌ی `D` دقیقه‌ای فقط وقتی قابل رزرو است که کل `D` دقیقه داخل **یک** بازه بماند. مثال: بازه `15:00–19:00`، پکیج ۶۰ دقیقه‌ای ⇒ شروع‌های ممکن `15:00, 15:15, …, 18:00` (هر ربع ساعت). پکیج ۳۰ دقیقه‌ای تا `18:30` شروع می‌شود. کاربر در یک ساعت دو رزرو هم‌پوشان نمی‌گیرد و هر رزرو، اسلات‌های هم‌پوشان خودش را از `capacity` کم می‌کند.

### نکات مهم UI
- **تغییر ساعت‌ها رزروهای ثبت‌شده را لغو نمی‌کند.** اگر مالک بازه‌ای را حذف/کوتاه کرد، رزروهای قبلی همچنان معتبرند و نماینده باید انجامشان بدهد. قبل از ذخیره، اگر رزرو آینده‌ای (فهرست بند ۴ با `scheduledStart` در آینده) خارج از برنامه‌ی جدید می‌افتد، هشدار نشان دهید.
- همین الان (قبل از ذخیره) تغییر ساعت‌ها فقط روی **رزروهای جدید** اثر دارد.
- فقط **مالک کلینیک** (کسی که `CompanionId` او پر است) می‌تواند ببیند/ذخیره کند؛ بقیه `403` (Forbid) می‌گیرند.
- UI پیشنهادی: ۷ ردیف (شنبه تا جمعه)، هر روز چند بازه با انتخابگر ساعت (گام ۱۵ دقیقه) و ظرفیت (استپر ۱ تا ۲۰)، و یک دکمه‌ی «کپی ساعت‌های این روز به روزهای دیگر».

## ۴) مدیریت رزروها (مشاوره‌های من / مدیریت)

همان `GET /api/Companion/ConsultationSession`؛ دو فیلد جدید در هر آیتم:

```json
{
  "id": 21, "status": 2, "channelId": 3, "durationMinutes": 30,
  "scheduledStart": "2026-10-03T16:00:00",   // null = خرید فوری
  "scheduledEnd":   "2026-10-03T16:30:00",
  "startDeadline":  "2026-10-03T16:15:00",   // ساعت رزرو + ۱۵ دقیقه
  "canStart": false,                         // تا ۱۰ دقیقه قبل از scheduledStart false است
  "canAssign": true,
  "serverNow": "2026-10-03T13:05:00+03:30"
}
```

**رفتار:**
1. فهرست: آیتم‌های `status == 3` (در جریان) اول، بعد بقیه **به ترتیب `scheduledStart`** (خرید فوری به ترتیب `paidDate`). خریدهای فوری و رزروی در یک فهرست‌اند؛ با `scheduledStart != null` تشخیص بدهید.
2. کارت رزروی: «رزرو برای {تاریخ شمسی} ساعت {HH:mm}» + شمارش معکوس تا شروع (با `serverNow`، قاعده‌ی طلایی زمان). نشان «رزروی».
3. `canStart == false` و `status == 2` ⇒ دکمه‌ی «شروع» را غیرفعال کنید با متن «از {scheduledStart − ۱۰ دقیقه} فعال می‌شود». **خودتان از ساعت گوشی `canStart` نسازید**؛ فقط از سرور بخوانید و هر ۲۰–۳۰ ثانیه + هنگام فوکوس فهرست را تازه کنید.
4. `POST …/{id}/Start` قبل از ۱۰ دقیقه مانده خطا می‌دهد: «هنوز زود است؛ شروع مشاوره فقط از ۱۰ دقیقه قبل از ساعت رزرو ممکن است.» (اگر UI درست غیرفعال باشد نباید دیده شود.)
5. بعد از «شروع»: همه‌چیز مثل خرید فوری. **پنجره‌ی ۳۰/۶۰ دقیقه‌ای از لحظه‌ی واقعی «شروع» حساب می‌شود**، نه از ساعت رزرو؛ پس اگر نماینده ۵ دقیقه دیر شروع کند کاربر باز هم مدت کامل را می‌گیرد (`startDate/expireDate` را برای شمارنده بخوانید).
6. **دیرکرد:** اگر تا `startDeadline` (ساعت رزرو + ۱۵ دقیقه) کسی شروع نکند، سرور (job دقیقه‌ای) رزرو را `Expired` می‌کند و پول کامل به کیف پول کاربر برمی‌گردد و پوش ۷۴ به کاربر می‌رود. روی کارت، وقتی ساعت رزرو گذشته و هنوز `status == 2`، شمارنده‌ی هشدار «تا {deadline − now} دیگر لغو خودکار می‌شود» (قرمز) نشان دهید.
7. تخصیص (`canAssign`, `assignableAgents`، `…/Assign`) مثل قبل و روی رزروی هم کار می‌کند.
8. نماینده خودش رزرو کاربر را لغو نمی‌کند (فقط ادمین). اگر نماینده نمی‌تواند بیاید: مالک رزرو را به نماینده‌ی دیگر تخصیص بدهد.

**وضعیت‌ها** (`status`) همان جدول قبلی است؛ برای رزروی فقط متن‌ها فرق دارد: `2` = «رزرو شده — منتظر ساعت {X}».

## ۶) سناریوی کامل برای تست (روی استیجینگ، بعد از اجرای مایگریشن)

۱. با مالک: پکیج `bookable=true`، `channelId=3`، ۳۰ دقیقه، قیمت کم، `active=true`.
۲. `PUT ConsultationAvailability` برای امروز/فردا (مثلاً `weekDayId` فردا، `16:00–20:00`، `capacity=1`).
۳. با کاربر دیگر (دستور آرمان): رزرو ساعت `17:00` فردا با کیف پول → پوش ۸۳ به شما؛ فهرست `ConsultationSession` رزرو را با `scheduledStart` نشان دهد و `canStart=false`.
۴. ۳۰ دقیقه قبل: پوش ۸۵. ۱۰ دقیقه قبل: `canStart=true`. «شروع» → ویدیوکال → پایان پنجره.
۵. رزرو دوم را شروع نکنید تا `ساعت+۱۵ دقیقه`: باید `Expired` شود و بازپرداخت دیده شود.
۶. رزرو سوم در همان ساعتِ رزرو اول (ظرفیت ۱): کاربر دوم باید «ظرفیت این ساعت پر شده است» بگیرد.
