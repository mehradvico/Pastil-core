# حذف (نرم) پانسیون/مهد پت و مدرسه توسط نماینده — مستند اپ نماینده (ویژه امیرمحسن)

> مخاطب: توسعه‌دهنده‌ی اپ/وب‌اپ **نماینده/کلینیک** · وضعیت بک: پیاده‌سازی و بیلد شد؛ **ستون‌های جدید دیتابیس هنوز اجرا نشده** (بند ۹) — تا اجرا نشود، همه‌ی endpointهای پانسیون/مدرسه روی سرور خطا می‌دهند.
> پنل ادمین همین قابلیت را (حذف + بازگردانی + فیلتر «حذف‌شده‌ها») دارد.

همه‌ی پاسخ‌ها `{ isSuccess, messages, data }` هستند و فیلدها camelCase. **موفقیت را از `isSuccess` بخوانید.** (استثناها: `Forbid` ⇒ HTTP 403 و `NotFound` ⇒ HTTP 404 با بدنه‌ی `{isSuccess:false,…}` در بعضی GET ها؛ بند ۳.)

## ۱) چه چیزی اضافه شد

نماینده حالا می‌تواند **پانسیون/مهد پت** و **مدرسه‌ی** خودش را حذف کند. حذف **نرم** است:

- ردیف از دیتابیس پاک نمی‌شود؛ `deleted = true` می‌شود (+ زمان و کاربر حذف‌کننده ثبت می‌شود).
- از همه‌ی فهرست‌ها، جستجو، سایت و اپ کاربر، و **رزرو جدید** حذف می‌شود.
- **رزروهای قبلی، تسویه‌ها و گزارش مالی دست نمی‌خورند** (نماینده درآمد قبلی‌اش را همچنان می‌بیند).
- حذف همزمان آن را `active=false` و `showToSite=false` و `suggested=false` می‌کند.
- **بازگردانی فقط توسط ادمین** است (نماینده endpoint بازگردانی ندارد). اگر نماینده اشتباه حذف کرد، باید به پشتیبانی پیام بدهد. بعد از بازگردانی، آیتم **غیرفعال و منتشرنشده** برمی‌گردد و باید دوباره فعالش کنند.

## ۲) endpointها

همه `Authorization: Bearer …`، ناحیه‌ی `Companion`.

| کار | endpoint | بدنه |
| --- | --- | --- |
| حذف پانسیون/مهد پت | `DELETE /api/Companion/Pansion?id={pansionId}` | ندارد |
| حذف مدرسه | `DELETE /api/Companion/School?id={schoolId}` | ندارد |

- `id` را **در query** بفرستید (نه در مسیر، نه در body).
- فقط **مالک** کلینیک می‌تواند حذف کند (نه اعضای تیم/اپراتور). کاربری که `companionId` ندارد ⇒ HTTP 403.
- پاسخ موفق:

```json
{ "isSuccess": true, "messages": [ … «عملیات با موفقیت انجام شد» … ], "data": null }
```

- حذف **idempotent نیست**: بار دوم، چون آیتم حذف‌شده «پیدا نمی‌شود»، `isSuccess:false` با «چیزی یافت نشد» برمی‌گردد. اگر دو کلیک پشت‌سرهم زده شد و دومی خطا داد، فهرست را تازه کنید و خطا را نشان ندهید (آیتم رفته است).

## ۳) خطاها و نمایش پیشنهادی

| شرایط | پاسخ | کار اپ |
| --- | --- | --- |
| موفق | `isSuccess:true` | فهرست را دوباره بگیرید؛ آیتم ناپدید می‌شود؛ toast «حذف شد» |
| آیتم وجود ندارد / قبلاً حذف شده / مال کلینیک دیگری است | `isSuccess:false` + «چیزی یافت نشد» (یا «دسترسی ندارید» برای کلینیک دیگر) | فهرست را تازه کنید |
| کاربر مالک کلینیک نیست (عضو تیم) | `isSuccess:false` + «دسترسی ندارید» | دکمه‌ی «حذف» را برای غیرمالک اصلاً نشان ندهید؛ اگر زده شد پیام را نشان دهید |
| **رزرو فعال دارد** | `isSuccess:false` + پیام زیر | پیام را **عیناً** نشان دهید و به صفحه‌ی رزروها لینک بدهید |
| کاربر `companionId` ندارد | HTTP **403** بدون بدنه | «اجازه‌ی این کار را ندارید» |

پیام «رزرو فعال دارد» (فارسی):
- پانسیون: «این پانسیون رزرو فعال (پرداخت‌شده و انجام‌نشده) دارد؛ ابتدا آن رزروها را تکمیل یا لغو کنید و بعد حذف کنید.»
- مدرسه: «این مدرسه ثبت‌نام فعال (پرداخت‌شده و انجام‌نشده) دارد؛ ابتدا آن ثبت‌نام‌ها را تکمیل یا لغو کنید و بعد حذف کنید.»

### «رزرو فعال» یعنی چه؟
- **پانسیون:** رزروی که `isReserved == true` و `isCancel == false` و وضعیتش نه «ثبت‌شده/پرداخت‌نشده» است و نه «تکمیل‌شده» (یعنی عملاً **پرداخت‌شده (47)** و هنوز انجام/لغو نشده).
- **مدرسه:** ثبت‌نام (`SchoolReserve`) با `isReserved == true`، `isCancel == false` و `statusId == 2` (پرداخت‌شده) برای **هر دوره‌ی** آن مدرسه.
- رزروهای **پرداخت‌نشده/ثبت‌شده**، **لغوشده** و **تکمیل‌شده** مانع حذف **نیستند**.
- راه حل برای کاربر: رزروهای پرداخت‌شده را «تکمیل» یا «لغو» کند، بعد دوباره حذف را بزند. فهرست رزروها همان صفحه‌ی فعلی رزرو پانسیون/مدرسه است.

## ۴) رفتار اپ بعد از حذف (مو به مو)

بعد از `isSuccess:true`:

1. **فهرست پانسیون‌ها/مدرسه‌ها** (`GET /api/Companion/Pansion`، `GET /api/Companion/School`): آیتم حذف‌شده دیگر **نمی‌آید** (`totalCount` هم کم می‌شود). نیازی به فیلتر سمت اپ نیست؛ فقط فهرست را دوباره بگیرید یا آیتم را محلی بردارید.
2. **جزئیات** (`GET …/{id}`) برای آیتم حذف‌شده **HTTP 404** با `{isSuccess:false, …«چیزی یافت نشد»}` می‌دهد. اگر کاربر با لینک/صفحه‌ی بازمانده وارد شد، به فهرست برگردید.
3. **ویرایش (`PUT`)، تغییر وضعیت فعال/غیرفعال (`PansionActive`/`SchoolActive`)** برای آیتم حذف‌شده «چیزی یافت نشد» می‌دهد.
4. **پت‌ها، تصاویر و نظرهای پانسیون** و **تصاویر/پت‌های دوره‌های مدرسه** حذف‌شده در فهرست‌های «مال من» دیگر نمی‌آیند.
5. **رزروهای قبلی** همچنان در فهرست رزروها و صفحه‌ی مالی/تسویه هستند و نام پانسیون/مدرسه در آن‌ها دیده می‌شود. یعنی گزارش مالی نماینده تغییری نمی‌کند.
6. **ساخت دوباره:** نماینده می‌تواند همان لحظه یک پانسیون/مدرسه‌ی جدید بسازد (`POST`)؛ حذف‌شده‌ها سقف تعداد را مصرف نمی‌کنند (محدودیت تعداد وجود ندارد).
7. **دوره‌های مدرسه** (`SchoolCourse`) با مدرسه می‌مانند ولی دیگر برای کاربر یا در جستجو نمایش داده نمی‌شوند و برای ساخت دوره‌ی جدید روی مدرسه‌ی حذف‌شده «چیزی یافت نشد» می‌گیرید.
8. **کاربر نهایی:** پانسیون/مدرسه از سایت، جستجو، صفحه‌ی کلینیک (`pansions` در پاسخ کلینیک)، پوش گروهی و رزرو جدید حذف می‌شود. رزرو جدید روی آیتم حذف‌شده «داده نامعتبر/چیزی یافت نشد» می‌دهد.

## ۵) پاسخ‌های که فیلد جدید دارند

در `GET …/Pansion/{id}` و `GET …/School/{id}` و آیتم‌های فهرست دو فیلد جدید هست:

```json
{ "id": 12, "name": "…", "deleted": false, "deleteDate": null, … }
```

برای نماینده همیشه `deleted:false` است (حذف‌شده‌ها اصلاً برنمی‌گردند)؛ لازم نیست در UI چیزی برایش بسازید. **در `PUT` چیزی از این فیلدها نفرستید** (نادیده گرفته می‌شود).

## ۶) UI پیشنهادی

1. در صفحه‌ی جزئیات/ویرایش پانسیون و مدرسه، پایین صفحه بخش «ناحیه‌ی خطر» با دکمه‌ی قرمز **«حذف پانسیون»** / **«حذف مدرسه»** (فقط برای مالک).
2. تأیید دو مرحله‌ای (modal): عنوان «حذف {نام}؟» + متن: «از سایت و جستجو برداشته می‌شود و رزرو جدید نمی‌گیرد. رزروها و گزارش مالی قبلی می‌مانند. بازگردانی فقط با پشتیبانی ممکن است.» + دکمه‌ی «بله، حذف شود» (قرمز) و «انصراف».
3. حین ارسال دکمه غیرفعال/اسپینر؛ ضدکلیک دوبل.
4. موفق ⇒ برگشت به فهرست + toast «پانسیون حذف شد».
5. خطای «رزرو فعال دارد» ⇒ همان پیام در modal (بدون بستن)، همراه دکمه‌ی «مشاهده رزروها».
6. هیچ‌جا دکمه‌ی «بازگردانی» برای نماینده نگذارید.

## ۷) سناریوهای تست (استیجینگ، بعد از اجرای SQL)

۱. پانسیون بدون رزرو ⇒ حذف ⇒ `isSuccess:true` ⇒ در فهرست نیست؛ `GET /{id}` ⇒ 404.
۲. پانسیون با رزرو **پرداخت‌شده‌ی باز** ⇒ حذف ⇒ `isSuccess:false` + پیام «رزرو فعال». رزرو را تکمیل کن ⇒ حذف ⇒ موفق؛ رزرو همچنان در فهرست رزروها و گزارش مالی هست.
۳. مدرسه با ثبت‌نام پرداخت‌شده ⇒ مثل بالا.
۴. با عضو تیم (غیرمالک) ⇒ «دسترسی ندارید».
۵. حذف با لینک آیتم کلینیک دیگر ⇒ «چیزی یافت نشد/دسترسی ندارید».
۶. دو بار پشت‌سرهم ⇒ بار دوم «چیزی یافت نشد».
۷. بعد از حذف، `GET /api/EndUser/…` یا جستجوی سایت آیتم را نشان ندهد؛ ساخت پانسیون جدید ممکن باشد.
۸. ادمین از پنل بازگردانی کند ⇒ آیتم غیرفعال برمی‌گردد و در فهرست نماینده دوباره دیده می‌شود.

## ۸) محدودیت‌های شناخته‌شده

- رزرو **پرداخت‌نشده (ثبت‌شده)** مانع حذف نیست و خودکار لغو نمی‌شود. اگر کاربر بعد از حذف همان رزرو قدیمی را پرداخت کند، پرداخت انجام می‌شود و یک رزرو باز روی آیتم حذف‌شده می‌ماند؛ این ریسک کم است و ادمین می‌تواند لغوش کند یا آیتم را بازگرداند.
- نماینده «حذف شده‌ها» را نمی‌بیند و بازگردانی ندارد (عمداً).
- حذف، عکس/پت/نظرهای آیتم را پاک نمی‌کند؛ فقط از فهرست‌ها پنهان می‌شوند.
- اعضای تیم (اپراتور/دکتر) حذف نمی‌کنند؛ فقط مالک.

## ۹) پیش‌نیاز دیپلوی (از طرف بک)

۱. بکاپ دیتابیس. ۲. اجرای `backend/scripts/AddPansionSchoolSoftDelete.sql` (idempotent؛ ستون‌های `Deleted`, `DeleteDate`, `DeletedByUserId` روی `Pansions` و `Schools`) — **قبل از دیپلوی Api**، وگرنه همه‌ی کوئری‌های پانسیون/مدرسه خطای «ستون نامعتبر» می‌دهند. ۳. دیپلوی Api. ۴. در پنل ادمین «همگام‌سازی دسترسی‌ها» (برای اکشن‌های جدید `Delete`/`Restore`). ۵. دیپلوی پنل.
