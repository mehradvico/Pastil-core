# تحویل‌گیری سفارش توسط کاربر — مستند اپ فروشنده

> مخاطب: تیم اپ فروشنده · قرارداد کامل API، قواعد و پیام‌ها: [PRODUCT_ORDER_USER_DELIVERY_FA.md](PRODUCT_ORDER_USER_DELIVERY_FA.md)
> وضعیت بک: پیاده شد، **دیپلوی نشده** (تا اجرای SQL و دیپلوی Api فیلدهای جدید نمی‌آیند).
> پاسخ‌ها **همیشه HTTP 200** با `{ isSuccess, messages, data }`؛ موفقیت را از `isSuccess` بخوانید. فیلدها camelCase. همه‌ی endpointها `Authorization: Bearer …`.

## ۱) چه چیزی عوض شد

نهایی‌شدن سفارش («تحویل داده شد») **دست خود مشتری** است. فروشنده دیگر نمی‌تواند وضعیت را «تحویل داده شد» کند؛ مشتری در «سفارش‌های من» «تحویل گرفتم» یا «تحویل نگرفتم» را می‌زند و فروشنده نتیجه را در اپ می‌بیند.

| پاسخ مشتری | وضعیت سفارش | چه چیزی فروشنده می‌بیند |
| --- | --- | --- |
| هنوز نداده | «ارسال شده» | «منتظر تأیید تحویل مشتری» |
| **تحویل گرفتم** | «تحویل داده شد» (نهایی) | «مشتری تحویل گرفت» |
| **تحویل نگرفتم** | «ارسال شده» می‌ماند | «مشتری تحویل نگرفته» + توضیح مشتری (نیازمند پیگیری) |

## ۲) فهرست و جزئیات سفارش

`GET /api/Seller/ProductOrder` (فهرست) و جزئیات سفارش همان endpointهای فعلی‌اند؛ هر سفارش حالا این فیلدها را دارد:

| فیلد | معنی |
| --- | --- |
| `userReceived` | `null` = منتظر پاسخ، `true` = تحویل گرفت، `false` = تحویل نگرفت |
| `userReceivedDate` | زمان پاسخ مشتری (بدون آفست؛ ساعت سرور/ایران) |
| `userReceiveNote` | توضیح مشتری برای «تحویل نگرفتم» (ممکن است `null`) |
| `canConfirmDelivery` | `true` ⇒ مشتری هنوز می‌تواند پاسخ بدهد (سفارش ارسال‌شده، پرداخت‌شده، لغو‌نشده، هنوز «تحویل گرفتم» نزده). برای فروشنده معنی: «منتظر پاسخ مشتری» |

### نمایش پیشنهادی
| `userReceived` | `canConfirmDelivery` | نشان |
| --- | --- | --- |
| `true` | — | «مشتری تحویل گرفت (نهایی)» — سبز |
| `false` | — | «مشتری تحویل نگرفته» — **قرمز**، با `userReceiveNote` و تاریخ؛ دکمه‌ی «تماس با مشتری» (موبایل در همان سفارش) |
| `null` | `true` | «منتظر تأیید تحویل مشتری» — زرد |
| `null` | `false` | چیزی نشان ندهید |

## ۳) فیلتر فهرست
پارامتر جدید `userDelivery` روی `GET /api/Seller/ProductOrder`:

| مقدار | معنی |
| ---: | --- |
| `0` | منتظر پاسخ مشتری |
| `1` | تحویل گرفته |
| `2` | تحویل نگرفته (نیازمند پیگیری) |
| خالی | همه |

پیشنهاد: سه تب/چیپ «منتظر پاسخ»، «تحویل گرفته»، «تحویل نگرفته» کنار فیلتر وضعیت فعلی، و یک نشان تعداد روی «تحویل نگرفته».

## ۴) تغییر وضعیت (`PUT /api/Seller/ProductOrderChangeStatus`)

- گزینه‌ی **«تحویل داده شد»** (`ProductOrderStatus_Delivered`، شناسه‌ی ۱۸) را در انتخاب وضعیت **نشان ندهید**. اگر بفرستید بک رد می‌کند با «وضعیت «تحویل داده شد» فقط با تأیید خود مشتری ثبت می‌شود؛ فروشگاه و ادمین نمی‌توانند آن را تغییر دهند.» (`isSuccess:false`، HTTP 200).
- فقط «در حال پردازش»، «ارسال شده» (و درج) برای فروشنده قابل انتخاب است. زیر لیست یک راهنما بگذارید: «تحویل داده شد را خود مشتری تأیید می‌کند».
- اگر `userReceived == true` است، تغییر وضعیت را **غیرفعال** کنید؛ بک هم رد می‌کند: «مشتری تحویل این سفارش را تأیید کرده است و وضعیت آن دیگر قابل تغییر نیست.»
- خطاها را عیناً از `messages` در toast نشان دهید.

## ۵) پیگیری سفارش «تحویل نگرفتم»
- سفارش بدون هیچ تغییر خودکار در «ارسال شده» می‌ماند؛ فروشنده باید با مشتری تماس بگیرد (کد رهگیری، پیک، آدرس را چک کند).
- اگر مشکل حل شد، **مشتری** خودش «تحویل گرفتم» را می‌زند (فروشنده نمی‌تواند).
- اگر نیاز به لغو/بازپرداخت است، مثل قبل از مسیر درخواست لغو/پشتیبانی (ادمین) استفاده می‌شود.
- **پوش به فروشنده هنگام «تحویل نگرفتم» (جدید):** نوع **۹۰** `PushProductOrderNotReceivedStore` برای همه‌ی کاربران همان فروشگاه: «مشتری ({نام}) سفارش {کد} را تحویل نگرفته است. لطفاً با مشتری تماس بگیرید و پیگیری کنید.» یک‌بار برای هر سفارش. در handler پوش بشناسید و صفحه‌ی سفارش‌ها را با فیلتر `userDelivery=2` باز کنید (مقصد وب `/sellerProfile/orders`).


## ۵٫۱) تأیید خودکار بعد از ۷ روز (جدید)

اگر مشتری ۷ روز بعد از «ارسال شده» هیچ پاسخی ندهد، سفارش خودکار «تحویل داده شد» می‌شود (قواعد: [PRODUCT_ORDER_USER_DELIVERY_FA.md](PRODUCT_ORDER_USER_DELIVERY_FA.md) بند ۳٫۱). **«تحویل نگرفتم» هرگز خودکار تأیید نمی‌شود** و همچنان باید پیگیری شود.

فیلدهای تازه روی هر سفارش:
- `autoConfirmDate`: اگر مشتری پاسخ ندهد، سفارش در این زمان خودکار تأیید می‌شود (فقط وقتی `userReceived == null` و سفارش «ارسال شده» است؛ وگرنه `null`).
- `userReceivedAuto`: `true` = سیستم خودکار ثبت کرده (همراه `userReceived: true`).

نمایش: برای `userReceivedAuto == true` نشان «تأیید خودکار (۷ روز بدون پاسخ مشتری)» (سبز، ولی متمایز از «مشتری تحویل گرفت»)؛ برای «منتظر پاسخ» می‌توانید «تأیید خودکار تا {`autoConfirmDate`}» را زیر نشان زرد بنویسید. اگر مشتری بعد از تأیید خودکار ادعا کند بسته نرسیده، موضوع با پشتیبانی/ادمین رسیدگی می‌شود (در اپ برگشت وضعیت ندارید).

## ۵٫۲) صفحه‌ی مالی/تسویه‌ی فروشنده

`GET /api/Seller/FinanceStore` برای هر سفارش در `financeProductOrders` حالا `userReceived` (`null`/`true`/`false`)، `userReceivedDate`، `userReceivedAuto` و `userReceiveNote` را دارد؛ و در ریشه‌ی پاسخ `notReceivedCount` و `receivedCount`. فیلتر اختیاری `UserDelivery` (۰ منتظر پاسخ، ۱ تحویل گرفته، ۲ تحویل نگرفته) کنار `Permitted`.

- ستون/نشان «تحویل‌گیری مشتری» روی هر سفارش مالی (`true` ⇒ تحویل گرفته / تأیید خودکار، `false` ⇒ تحویل نگرفته قرمز با توضیح، `null` ⇒ —).
- هشدار قرمز بالای فهرست وقتی `notReceivedCount > 0`.
- تسویه را این فیلد قفل نمی‌کند؛ تصمیم پرداخت سهم با ادمین است. به فروشنده بگویید سفارش‌های «تحویل نگرفته» پیش از تسویه ممکن است بررسی شوند.
## ۶) سناریوی تست (بعد از SQL و دیپلوی)
۱. سفارش پرداخت‌شده ⇒ «ارسال شده» ⇒ نشان زرد «منتظر تأیید تحویل مشتری».
۲. مشتری «تحویل نگرفتم» + توضیح ⇒ نشان قرمز و توضیح؛ فیلتر `userDelivery=2` سفارش را بیاورد.
۳. مشتری «تحویل گرفتم» ⇒ نشان سبز؛ وضعیت «تحویل داده شد»؛ تغییر وضعیت غیرفعال.
۴. تلاش برای «تحویل داده شد» از اپ قدیمی ⇒ پیام خطا.
