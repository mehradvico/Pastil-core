# پت‌رسان سرویس هفتگی — اولین پرداخت توسط کاربر (تغییرات اپ/وب‌اپ)

تاریخ: ۱۴۰۵/۰۷/۱۶ (۲۰۲۶-۱۰-۰۸)

## چه چیزی عوض شد (بک‌اند)

قبلاً job ساخت نوبت‌های سرویس هفتگی (`GenerateOnePetResanTripAsync`) برای **هر** نوبت، مبلغ را همان لحظه از کیف پول کم می‌کرد. اگر موجودی کافی نبود، سفر بلافاصله با `CancelInitiator=System` لغو می‌شد؛ نه راننده آن را می‌دید و نه کاربر فرصتی برای پرداخت داشت.

حالا:

| نوبت | رفتار |
|---|---|
| **اولین پرداخت هر سرویس** (در همان سرویس هنوز هیچ Tripِ `IsPaid=true` وجود ندارد) | سفر ساخته می‌شود با `TripStatus=Requested`، `IsPaid=false`، `FromWallet=false`، `WalletPrice=0`. کیف پول کم **نمی‌شود**. سفر در `GET api/Driver/TripAvailable` برای رانندگان دیده می‌شود. بعد از قبول راننده، **کاربر خودش** مثل بقیه‌ی سفرهای پت‌رسان پرداخت می‌کند. |
| **نوبت‌های بعدی** (قبلاً یک نوبت پرداخت‌شده در همین سرویس هست) | مثل قبل: ساخت سفر + کسر خودکار از کیف پول. اگر موجودی کم بود، سفر لغو می‌شود و Notice «موجودی ناکافی» ثبت می‌شود. |

نکته‌ها:
- «اولین» به‌ازای **سرویس** حساب می‌شود، نه نوبت. تا وقتی یک Trip پرداخت‌شده در سرویس نباشد، نوبت‌های جدید هم پرداخت‌نشده ساخته می‌شوند.
- اگر سرویس `ReturnTime` دارد، روز اول دو سفر (رفت و برگشت) هر دو پرداخت‌نشده ساخته می‌شوند و کاربر هر دو را جداگانه پرداخت می‌کند.
- قرارداد کلی پت‌رسان تغییر نکرده: پرداخت فقط بعد از قبول راننده (`TripStatus=Accepted`) ممکن است.
- هیچ فیلد یا endpoint جدیدی اضافه نشده؛ فقط مقدارِ `isPaid` و `fromWallet` در پاسخ سفرها فرق می‌کند.

## کاری که اپ/وب‌اپ باید انجام دهد

### ۱) تشخیص «سفر سرویسِ قبول‌شده و پرداخت‌نشده»
از لیست/جزئیات سفر (`TripVDto`) شرط زیر:

```
petResanServiceScheduleId != null   // سفر از سرویس هفتگی آمده
&& tripStatusId == Accepted          // راننده قبول کرده
&& isPaid == false
```

برای چنین سفری کارت/صفحه‌ی سفر باید **دکمه‌ی «پرداخت»** نشان دهد (همان جریان پرداخت سفر لحظه‌ای/رزروی)، نه پیام «از کیف پول کسر می‌شود».

### ۲) جریان پرداخت (بدون تغییر در endpointها)
1. (اختیاری) کد تخفیف: `POST api/EndUser/TripSetRebate` / `TripRemoveRebate`
2. (اختیاری) استفاده از کیف پول: `PUT api/EndUser/TripSetWallet` با `FromWallet`
3. شروع پرداخت: `POST api/EndUser/TripPayment`
4. بازگشت از درگاه → سفر `IsPaid=true` می‌شود.

این‌ها قبلاً برای سفر لحظه‌ای/رزروی کار می‌کردند و برای سفر سرویس هم روی همین قفل‌ها (`Accepted` و `!IsPaid`) سوار هستند.

### ۳) متن‌ها و UI
- در صفحه‌ی ثبت سرویس هفتگی ([petResanWeeklyService.ts](../../webapp/app/utils/petResanWeeklyService.ts) خط ۸ و کامنت‌های مرتبط) متن فعلی می‌گوید «job مبلغ را از کیف پول کم می‌کند». باید اصلاح شود، مثلاً:
  «اولین سفر سرویس را بعد از تأیید راننده پرداخت می‌کنید؛ سفرهای بعدی خودکار از کیف پول کم می‌شوند — کیف پول خود را شارژ نگه دارید.»
- بعد از ثبت سرویس، پیام «اولین سفر پس از قبول راننده برای پرداخت به شما اطلاع داده می‌شود» نمایش داده شود.
- روی نوبت‌های بعدی، اگر موجودی کیف پول کمتر از قیمت نوبت‌های پیش‌رو است، هشدار «کیف پول را شارژ کنید» نشان داده شود (پیشنهادی؛ بک‌اند هنوز پوش یادآوری شارژ نمی‌فرستد).

### ۴) اپ راننده
- تغییری لازم نیست: سفر پرداخت‌نشده‌ی سرویس در `TripAvailable` می‌آید و راننده می‌تواند قبول کند.
- فقط اگر UI راننده فرض می‌کند «سفر سرویس همیشه پرداخت‌شده است»، آن فرض باید حذف شود.

## نکته‌ی رفتاری که باید بدانید
اگر کاربر بعد از قبول راننده پرداخت نکند، سفر Accepted و پرداخت‌نشده می‌ماند. فعلاً job‌ای برای لغو یا یادآوری آن ندارد؛ در صورت نیاز باید جداگانه اضافه شود.
