# راهنمای اتصال «تطبیق هوشمند محصولات» (AiProductMatch) برای اپ فروشنده‌ی فلاتر

این سند برای تیم فلاتر است — بخش فروشنده (Seller App). بک‌اند کامل پیاده و دیپلوی شده؛ از الان می‌تونید توسعه رو شروع کنید.

Base URL: `https://api.pastil.pet`

## ماجرا چیه

فروشنده به‌جای این‌که محصولات فروشگاهش رو یکی‌یکی دستی جستجو و اضافه کنه، یکی از این سه راه رو انجام می‌ده:
- عکس از قفسه/ویترین می‌گیره،
- یا فایل اکسل انبارش رو (نرم‌افزار انبار عمومی، سپیدار یا دامپزشکیار) آپلود می‌کنه،

و بک‌اند با کمک هوش مصنوعی هر ردیف/آیتم رو به یک محصول واقعی توی کاتالوگ پاستیل تطبیق می‌ده. فروشنده نتیجه رو تایید می‌کنه، اپ همون لحظه `ProductItem` (قیمت/موجودی فروشگاه) رو می‌سازه یا آپدیت می‌کنه.

## به‌روزرسانی (شهریور ۱۴۰۵) — فقط تغییرات پشت‌صحنه، بدون تغییر Contract

این بخش رو مخصوص چک کردن اینه که آیا چیزی سمت اپ لازمه عوض بشه یا نه. **خلاصه: هیچ فیلدی در JSON اضافه/حذف/rename نشده؛ هیچ اکشنی از سمت اپ لازم نیست.** فقط دقت تشخیص داخلی بهتر شده:

- **`confidence` دیگه فقط عدد خام مدل هوش مصنوعی نیست** — ترکیبی از امتیاز مدل + شباهت نام تشخیص‌داده‌شده با نام واقعی کاتالوگ + تطبیق برند است. عددش هنوز بین ۰ تا ۱ و همون معنی رو داره (بالای `AutoSelectConfidenceThreshold` یعنی می‌تونید پیش‌فرض تیک‌خورده نشون بدید)، فقط قابل‌اعتمادتر شده.
- **یک پیام جدید ممکنه توی `issues[]` ظاهر بشه:** `"چند محصول مشابه یافت شد؛ لطفاً به‌صورت دستی انتخاب کنید"`. این وقتیه که دو کاندید در `matches[]` خیلی به‌هم نزدیک‌ان (مثلاً دو سایز از یک محصول) و سیستم عمداً به‌جای انتخاب کورکورانه، `productId` سطح بالا رو خالی می‌ذاره تا فروشنده خودش از `matches[]` انتخاب کنه. نیازی به کد خاص نیست (چون `issues[]` از قبل هم متن آزاد بود و باید نمایش داده بشه)، ولی اگه خواستید می‌تونید این مورد رو با نمایش برجسته‌تر گزینه‌های `matches[]` جدا کنید.
- **برای `sourceType=shelf`: اگه دو یا چند عکسی که فرستادید هم‌پوشانی دارن** (مثلاً همون قفسه رو از دو زاویه گرفتید)، دیگه محصولات تکراری چند ردیف جدا در `items[]` برنمی‌گردن — فقط یک‌بار می‌آن. یعنی طول `items[]` ممکنه از قبل کمتر باشه برای همون تعداد عکس؛ این طبیعیه، باگ نیست.
- مدلی که پشت‌صحنه تصویر رو تحلیل می‌کنه عوض شده (فقط داخلی، هیچ فیلدی از response رو تغییر نمی‌ده) — هدفش دقیقاً حل همین بود: قبلاً بعضی وقت‌ها اسم محصول یا برند از روی عکس اشتباه تشخیص داده می‌شد یا محصول اشتباهی match می‌خورد؛ الان هم تشخیص اسم دقیق‌تره، هم برند اشتباه دیگه با اطمینان بالا match نمی‌خوره.

## به‌روزرسانی ۲ — اسکن هوشمند قفسه (بخش A سند `BACKEND_SHELF_SMART_SCAN_FA.md`)

### فیلدهای جدید در هر `items[]` (فقط افزودنی؛ هیچ فیلد قبلی عوض نشده)

| فیلد | نوع | توضیح |
|---|---|---|
| `brand` | string? | برند خوانده‌شده از روی بسته؛ خوانا نبود → `null` |
| `packageSize` | string? | مثل `"۴۰۰ گرم"` / `"۳.۵ کیلوگرم"`؛ خوانا نبود → `null` |
| `boundingBoxes` | array | هر عضو `{ x, y, width, height }` نسبی ۰..۱، مبدأ بالا-چپ، یک عضو به‌ازای هر بستهٔ قابل‌رؤیت. **خالی `[]` = مدل کادر قابل‌اعتماد نداد** (کادر اشتباه بدتر از بدون کادره). سمت سرور clamp می‌شود و کادر زیر ۲٪ حذف می‌شود |
| `catalogMatchFailed` | bool | `true` = مرحلهٔ تطبیق کاتالوگ برای این آیتم **کامل نشد** (خطای جست‌وجو/مدل یا تمام‌شدن بودجهٔ زمانی)، نه این‌که واقعاً در کاتالوگ نباشد. `matches` در این حالت خالی است ولی اپ **نباید** آن را «ناموجود» گزارش کند؛ فقط «نامشخص» + «تلاش دوباره». پیش‌فرض `false` |

قالب کادر فقط همین یکی است (بقیهٔ قالب‌هایی که اپ می‌پذیرد لازم نیست).

### معنی `confidence` (پاسخ سؤال ۲)

- آیتمی که `productId` گرفته: امتیاز تطبیق کاتالوگ (مثل قبل).
- آیتمی که `productId` ندارد (چه `matches` خالی چه پر): **اطمینان مدل از درست‌خوانده‌شدن نام** (۰..۱). قبلاً برای این آیتم‌ها همیشه `0` بود. پس آستانهٔ ۰.۶ شما برای «ناموجود» روی همین عدد کار می‌کند.
- ⚠️ این عدد را خود مدل گزارش می‌دهد و کالیبره‌شدنش را با داده‌ی واقعی ندیده‌ام؛ آستانه را بعد از چند اسکن واقعی چک کنید.
- برای `catalogMatchFailed=true` هم همین اطمینان نام برمی‌گردد، ولی نباید گزارش شود.

### مسیر همزمان یا Job (پاسخ سؤال ۱) — هر دو برای `shelf` با ۱ عکس کار می‌کنند

- `POST /analyze/start` با `sourceType=shelf` و ۱ فایل: `totalBatches = 1` و `result` نهایی **دقیقاً همان شکل** بالا (شامل `boundingBoxes`/`brand`/`packageSize`/`catalogMatchFailed`).
- ⚠️ progress برای تک‌عکس درشته: `completedBatches` بعد از **پایان استخراج از عکس** `1/1` می‌شود، ولی `status` تا پایان تطبیق کاتالوگ `"processing"` می‌ماند. نوار پیشرفت را از `completedBatches` نسازید؛ فقط `status` معتبره.
- با مسیر Job سقف ۶۰ ثانیه‌ی HTTP اپ دیگر مطرح نیست (هر درخواست فوری برمی‌گردد). پیشنهاد polling هر ۱–۲ ثانیه.

### بودجهٔ زمانی سرور

- کل تحلیل یک عکس سقف سخت **۵۰ ثانیه** دارد (تنظیم‌شدنی)؛ ۲۲ ثانیهٔ آخر برای جست‌وجوی کاتالوگ و تطبیق رزرو است. اگر تطبیق تمام نشود، **نتیجهٔ ناقص** با `catalogMatchFailed=true` برمی‌گردد، نه Timeout.
- اگر **استخراج** از عکس شکست بخورد/به سقف برسد (هیچ آیتمی از هیچ عکسی نیامد و علت خطای Provider بود): `isSuccess:false, code:5` («سرویس هوش مصنوعی موقتاً پاسخ نداد»). قبلاً این حالت اشتباهاً `code:3` بود. `code:3` فقط وقتی است که مدل عکس را دیده و واقعاً هیچ محصولی پیدا نکرده.
- **عکس قفسه هیچ‌جا ذخیره نمی‌شود.** فقط برای تحلیل به مدل می‌رود و بعد از برگشتن پاسخ دور ریخته می‌شود؛ هیچ رکورد `Picture` ساخته نمی‌شود. (فیلد `sourcePictureId` که قبلاً برمی‌گشت حذف شد — جایی مصرف نمی‌شد.)

### بخش B (`MissingProduct`) پیاده شده

راهنمای کامل: `FLUTTER_MISSING_PRODUCT_FA.md` (فروشنده) و `ADMIN_PANEL_MISSING_PRODUCT_FA.md` (پنل ادمین). تا زمانی که این نسخهٔ سرور deploy نشده، `404/405/501` را بی‌صدا رد کنید.

## ۱. چک وضعیت سرویس

```http
GET /api/Seller/AiProductMatch/status
Authorization: Bearer {accessToken}
```

```json
{ "isSuccess": true, "code": 0, "messages": [], "data": { "available": true, "provider": "GapGPT" } }
```

⚠️ `provider` اسم واقعی provider فعاله (الان `"GapGPT"`)، نه لزوماً `"Gemini"` — این مقدار رو فقط جهت اطلاع/لاگ نگه دارید، منطق UI نباید بهش وابسته باشه چون ممکنه سمت سرور عوض بشه.

اگه `available: false` بود (کلید API روی سرور تنظیم نشده)، دکمه‌ی این قابلیت رو غیرفعال/مخفی کنید — نه این‌که کاربر رو اجازه بدید وارد فلوی آنالیز بشه و بعد خطا بخوره. این چک رو موقع باز شدن صفحه‌ی مربوطه انجام بدید.

## ۲. آنالیز و تطبیق

```http
POST /api/Seller/AiProductMatch/analyze
Authorization: Bearer {accessToken}
Content-Type: multipart/form-data
```

فرم فیلدها (`multipart/form-data` — دقیقاً مثل آپلود عکس معمولی):

| فیلد | نوع | توضیح |
|---|---|---|
| `sourceType` | string | یکی از: `shelf` (عکس قفسه) \| `excel` \| `sepidar` \| `veterinary` |
| `images` | file[] | فقط برای `sourceType=shelf`؛ حداکثر ۸ عکس، هرکدام حداکثر ۸MB |
| `rowsJson` | string | فقط برای `excel`/`sepidar`/`veterinary`؛ رشته‌ی JSON آرایه (شکل دقیق در بخش ۲.۱) |
| `currency` | string | اختیاری، پیش‌فرض `"IRT"` |

⚠️ حجم کل درخواست سقف ۶۴MB داره (سمت سرور با `RequestSizeLimit` کنترل می‌شه) — اگه رد بشه، پاسخ HTTP واقعی `413` برمی‌گرده (نه `BaseResultDto` معمولی)؛ این یکی رو جدا از بقیه‌ی خطاها با چک کردن status code هندل کنید (نه از روی `code`).

### ۲.۱ شکل `rowsJson` (برای excel/sepidar/veterinary)

```json
[
  {
    "rowId": "row-1",
    "name": "غذای خشک گربه رویال کنین ۲ کیلویی",
    "externalCode": "SPD-10234",
    "price": 1250000,
    "quantity": 12,
    "unit": "عدد"
  }
]
```

- `rowId`: هر شناسه‌ی یکتای دلخواه (مثلاً شماره ردیف در فایل اکسل) — همون رو در پاسخ پس می‌گیرید تا بدونید کدوم ردیف مال کدومه.
- `externalCode`: کد داخلی انبار خودتون (سپیدار/دامپزشکیار) — فقط برای نمایش برمی‌گرده، کلید تطبیق نیست (کاتالوگ پاستیل بارکد استاندارد نداره).
- `price`/`quantity`/`unit`: مقادیر خام همونی که فروشنده وارد کرده — هوش مصنوعی این‌ها رو تغییر نمی‌ده، فقط برای نمایش/پیش‌پر کردن فرم نهایی استفاده می‌شن.

### ۲.۲ پاسخ

```json
{
  "isSuccess": true,
  "code": 0,
  "messages": [],
  "data": {
    "items": [
      {
        "rowId": "row-1",
        "detectedName": "رویال کنین ۲ کیلویی گربه بالغ",
        "externalCode": "SPD-10234",
        "price": 1250000,
        "quantity": 12,
        "productId": 4821,
        "productItemId": null,
        "productName": "غذای خشک گربه رویال کنین",
        "confidence": 0.91,
        "issues": [],
        "matches": [
          {
            "productId": 4821,
            "name": "غذای خشک گربه رویال کنین",
            "confidence": 0.91,
            "productItems": [
              { "productItemId": null, "label": "۲ کیلوگرم", "varietyItemId": 55, "varietyItem2Id": null, "existsForCurrentStore": false },
              { "productItemId": 9012, "label": "۴ کیلوگرم", "varietyItemId": 56, "varietyItem2Id": null, "existsForCurrentStore": true }
            ]
          }
        ]
      }
    ]
  }
}
```

نکات کلیدی برای UI:

- **`productId`/`productItemId` سطح بالای هر آیتم = بهترین حدسِ خودکار.** اگه `confidence` بالا بود (مثلاً بالای ۰.۸)، می‌تونید همینو پیش‌فرض تیک‌خورده نشون بدید؛ کاربر همیشه باید بتونه از بین `matches[].productItems` یه گزینه‌ی دیگه انتخاب کنه یا رد کنه.
- **نمایش محصول کاتالوگ با ID:** اگر `item.productId` مقدار داشت، همان شناسه‌ی قطعیِ محصول انتخاب‌شده در کاتالوگ پاستیل است و می‌توانید مستقیم محصول را نمایش/باز کنید. اگر `item.productId` خالی بود، به‌معنای نبود تطبیق قطعی است؛ برای نمایش گزینه‌ها از `item.matches[].productId` استفاده کنید. هر `matches[].productId` یک شناسه‌ی واقعی محصول کاتالوگ است؛ هرگز از `detectedName` برای ساختن یا حدس‌زدن شناسه استفاده نکنید.
- **`matches[]` = فهرست کوتاه کاندیدها** (نه کل کاتالوگ) — هر کاندید یک محصول کاتالوگ با `productId` واقعیه؛ زیرش `productItems[]` همه‌ی تنوع‌های معتبر اون محصوله (سایز/بسته‌بندی و غیره)، حتی اونایی که فروشگاه فعلی هنوز نداره.
- **`productItemId: null` توی `productItems[]`** یعنی این تنوع هنوز برای فروشگاه شما ساخته نشده. اگه کاربر همینو انتخاب کرد، اپ باید یک آیتم **جدید** بسازه (بخش ۳)، نه آپدیت.
- **`existsForCurrentStore: true/false`** دقیقاً همین تصمیم (مسیر «آپدیت موجودی» یا «ساخت آیتم جدید») رو مستقیم به شما می‌گه — لازم نیست خودتون حساب کنید.
- **`productItemId` سطح بالای آیتم ممکنه خالی باشه، حتی وقتی `productId` پره.** این یعنی محصول تشخیص داده شده اما سایز/طعم/تنوع از عکس با قطعیت کافی تشخیص داده نشده؛ در این حالت فروشنده باید یکی از `matches[].productItems` را انتخاب کند. اپ نباید صرفاً اولین تنوع یا تنوعی که قبلاً در فروشگاه وجود دارد را خودکار انتخاب کند.
- **`issues[]`**: پیام‌های هشدار مخصوص همون ردیف (مثلاً «تصویر این ردیف واضح نبود») — ردیف رو متوقف نمی‌کنه، فقط باید به کاربر نشون داده بشه تا با احتیاط بررسی کنه.
- **`matches` خالی** یعنی هیچ کاندید قابل‌اتکایی پیدا نشد — به کاربر بگید این ردیف رو خودش دستی جستجو/اضافه کنه (همون فلوی معمولی افزودن محصول). اگر `matches` پر ولی `productId` خالی بود، مدل فقط از انتخاب خودکار مطمئن نبوده و فروشنده می‌تواند یکی از `matches[]` را انتخاب کند.
- **`sourcePictureId` حذف شد** (قبلاً همیشه برمی‌گشت و هیچ مصرفی نداشت). عکس قفسه ذخیره نمی‌شود؛ اگر برای محصول ثبت‌نشده تصویر لازم دارید، `FLUTTER_AI_PRODUCT_MATCH_RESULT_STATES_FA.md` بخش ۳-C.

### ۲.۳ کدهای خطا (`code`)

تقریباً همیشه HTTP 200 برمی‌گرده؛ موفقیت/خطا رو فقط از `isSuccess`/`code` بخونید، نه از HTTP status (استثنا: ۴۰۱ از عدم لاگین، ۴۱۳ از حجم زیاد — این دو واقعاً همون status رو دارن):

| `code` | یعنی چی | پیام (`messages[0].item1`) |
|---:|---|---|
| 0 | موفق | — |
| 1 | ورودی نامعتبر (نه عکس نه rowsJson فرستاده شده، یا `sourceType` اشتباه) | «حداقل یکی از تصاویر یا داده جدول باید ارسال شود.» / «نوع منبع نامعتبر است.» |
| 2 | فروشگاه غیرفعال یا بدون دسترسی *(⚠️ فعلاً توسط بک‌اند تولید نمی‌شه — کد رو برای احتیاط هندل کنید ولی منتظرش نمونید)* | «فروشگاه شما غیرفعال یا فاقد دسترسی به این قابلیت است.» |
| 3 | تصویر/جدول قابل تحلیل نبود (مثلاً از هیچ عکسی آیتمی استخراج نشد) | «امکان تحلیل تصویر یا جدول ارسالی وجود نداشت.» |
| 5 | خطای موقت سرویس هوش مصنوعی — **حالا واقعاً برمی‌گردد**: وقتی استخراج از تمام عکس‌های ارسالی به‌خاطر خطای Provider/تمام‌شدن بودجه شکست خورد و هیچ ردیفی نیامد. اگر فقط بعضی عکس‌ها شکست بخورند، بقیه نتیجه می‌دهند و کد ۵ نمی‌آید | «سرویس هوش مصنوعی موقتاً پاسخ نداد.» |
| 6 | سرویس فعلاً در دسترس نیست (کلید تنظیم نشده یا `AiProductMatch:Enabled=false`) | «قابلیت تطبیق هوشمند محصول در حال حاضر در دسترس نیست.» |

## ۳. تایید نهایی — ساخت/آپدیت `ProductItem`

بعد از این‌که کاربر برای هر ردیف یک گزینه از `matches[].productItems` رو تایید کرد (یا خودتون بهترین حدس رو خودکار قبول کردید)، برای **هر محصول** (`productId`) یک درخواست جدا به Endpoint موجود زیر بفرستید — این Endpoint از قبل هست، تغییری نکرده:

```http
POST /api/Seller/ProductItem
Authorization: Bearer {accessToken}
Content-Type: application/json
```

```json
{
  "productId": 4821,
  "productItems": [
    {
      "id": 0,
      "productId": 4821,
      "basePrice": 1250000,
      "quantity": 12,
      "varietyItemId": 55,
      "varietyItem2Id": null,
      "active": true,
      "warranty": ""
    }
  ]
}
```

- `id`: اگه `productItemId` از پاسخ آنالیز `null` بود (تنوع جدید) → `id: 0` بفرستید (یعنی «بساز»). اگه `productItemId` مقدار داشت (یعنی `existsForCurrentStore: true`) → همون مقدار رو به‌عنوان `id` بفرستید (یعنی «آپدیت» — مثلاً فقط `quantity`/`basePrice` عوض بشه).
- `storeId` رو نفرستید — بک‌اند خودش از توکن لاگین استخراج می‌کنه؛ هر مقداری بفرستید نادیده گرفته می‌شه.
- `basePrice`/`quantity` رو از همون `price`/`quantity` که در پاسخ آنالیز (یا ورودی خام کاربر) داشتید پر کنید — این مقادیر رو هوش مصنوعی تغییر نمی‌ده، خودتون کنترل می‌کنید.
- اگه چند ردیف از آنالیز به یک `productId` یکسان تطبیق پیدا کردن (مثلاً چند تنوع از یک محصول در یک عکس)، می‌تونید همه‌شون رو توی یک درخواست با چند آیتم در `productItems[]` بفرستید — سریع‌تره.

پاسخ همون قرارداد استاندارد (`isSuccess`/`messages[0].item1` برای خطا) — دقیقاً مثل بقیه‌ی فرم‌های فروشنده در اپ.

## ۴. جریان پیشنهادی UI

1. ورود به صفحه → `GET /status` → اگه `available:false`، پیام «موقتاً در دسترس نیست» و برگشت به فلوی دستی معمولی.
2. کاربر یکی از منابع رو انتخاب می‌کنه: گرفتن/انتخاب عکس (۱ تا ۸ تا) یا آپلود/انتخاب فایل اکسل (پارس اکسل به `rowsJson` سمت اپ انجام می‌شه — بک‌اند فقط JSON آماده می‌گیره).
3. `POST /analyze` — نمایش Loading (ممکنه تا ۴۵ ثانیه طول بکشه، طبق تنظیم سرور).
4. برای هر آیتم پاسخ: نمایش `detectedName`/`price`/`quantity` خام + بهترین‌حدس تیک‌خورده + امکان تعویض از بین `matches`، یا رد کردن کامل ردیف اگه `issues` نگران‌کننده بود یا `matches` خالی بود.
5. دکمه‌ی «تایید همه» یا تایید تک‌تک → برای هر `productId` تایید‌شده یک `POST /api/Seller/ProductItem`.
6. نمایش خلاصه‌ی نهایی: چند مورد اضافه شد، چند مورد آپدیت شد، چند مورد رد شد.
