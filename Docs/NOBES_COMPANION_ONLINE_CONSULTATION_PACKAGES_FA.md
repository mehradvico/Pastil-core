# مستند اپ نماینده: تعریف پکیج چت، تماس و ویدیوکال

**مخاطب:** اپ نماینده / صاحب کلینیک پاستیل  
**Scope:** صفحهٔ «پکیج‌های مشاوره آنلاین» در خدمات کلینیک؛ تعریف قیمت و وضعیت فروش هر کانال و مدت. این سند مربوط به `ConsultationPackage` است، نه پکیج‌های عادی خدمات و نه `CompanionReserve`.

---

## 1. مدل محصول

هر پکیج دقیقاً ترکیب یک channel و یک duration است. server فقط این ۸ ترکیب را می‌پذیرد:

| `channelId` | عنوان UI | ۳۰ دقیقه | ۶۰ دقیقه | رفتار جلسه پس از خرید |
| --- | --- | --- | --- | --- |
| `1` | چت آنلاین | قیمت/کلید فروش | قیمت/کلید فروش | پیام‌رسانی داخل اپ |
| `2` | تماس صوتی داخل اپ | قیمت/کلید فروش | قیمت/کلید فروش | تماس WebRTC داخل اپ |
| `3` | تماس تصویری | قیمت/کلید فروش | قیمت/کلید فروش | ویدیوکال WebRTC داخل اپ |
| `4` | تماس تلفنی | قیمت/کلید فروش | قیمت/کلید فروش | تماس خارج اپ؛ اپ فقط زمان جلسه را نمایش می‌دهد |

مدت فقط `30` یا `60` دقیقه است. برای هر خانه قیمت و `active` مستقل وجود دارد؛ برای نمونه می‌توان چت ۳۰ دقیقه را فعال و تماس تصویری ۳۰ دقیقه را غیرفعال نگه داشت.

> این پکیج‌ها روی خدمت کاتالوگی «مشاوره آنلاین» ساخته می‌شوند و از تنظیمات/قیمت پکیج‌های عادی کلینیک مستقل‌اند.

---

## 2. دسترسی و API

همهٔ درخواست‌ها به Bearer token نیاز دارند. `companionId` از توکن خوانده می‌شود؛ app نباید `companionId` را در body یا query برای تعیین کلینیک بفرستد. اگر کاربر توکن companion معتبر نداشته باشد، server پاسخ `403 Forbidden` می‌دهد.

| کاربرد | Method | مسیر |
| --- | --- | --- |
| دریافت ماتریس کامل پکیج‌های کلینیک من | GET | `/api/Companion/ConsultationPackage` |
| ذخیرهٔ قیمت/فعال‌بودن ماتریس | PUT | `/api/Companion/ConsultationPackage` |
| مشاهدهٔ عمومی پکیج‌های قابل خرید توسط مشتری | GET | `/api/EndUser/ConsultationPackage?companionId={id}` |

```ts
type ConsultationPackageItem = {
  id: number                 // 0 یعنی این خانه هنوز در DB ذخیره نشده است
  channelId: 1 | 2 | 3 | 4
  durationMinutes: 30 | 60
  price: number
  active: boolean
}
```

`GET /api/Companion/ConsultationPackage` همیشه ۸ خانه را برمی‌گرداند. خانه‌ای که برای نخستین بار هنوز تعریف نشده، با `id: 0`، `price: 0` و `active: false` برمی‌گردد. این state طبیعی است و خطا نیست.

## 3. طراحی صفحهٔ پکیج‌ها

صفحه را به چهار card یا چهار ردیف channel تقسیم کنید و در هر کدام دو کنترل ۳۰ و ۶۰ دقیقه قرار دهید:

```text
چت آنلاین
  ۳۰ دقیقه: [قیمت] [فعال/غیرفعال]
  ۶۰ دقیقه: [قیمت] [فعال/غیرفعال]

تماس صوتی داخل اپ
  ...
```

برای هر خانه:

- input قیمت عددی و غیرمنفی باشد؛ جداکننده هزارگان فقط در UI است و مقدار ارسالی `number` باشد.
- switch فعال‌بودن تا زمانی که قیمت `> 0` نیست، disabled باشد یا هنگام روشن‌کردن، خطای inline «برای پکیج فعال قیمت مثبت وارد کنید» نشان دهد.
- غیرفعال‌کردن می‌تواند قیمت موجود را نگه دارد یا آن را صفر کند؛ در هر دو حالت `active: false` فروش جدید را می‌بندد.
- متن channel تلفنی باید روشن کند که تماس از خارج اپ انجام می‌شود؛ با فعال‌شدنش اپ مشتری یا نماینده نباید مسیر SignalR/WebRTC بسازد.

همهٔ تغییرها را تا زدن «ذخیرهٔ پکیج‌ها» در state محلی نگه دارید. پس از پاسخ موفق، کل matrix برگشتی server را جایگزین state محلی کنید؛ به update خوش‌بینانه تکیه نکنید.

## 4. دریافت و ذخیره‌سازی ماتریس

### 4.1 دریافت اولیه و refresh

```http
GET /api/Companion/ConsultationPackage
Authorization: Bearer {accessToken}
```

نمونه پاسخ `data`:

```json
[
  { "id": 801, "channelId": 1, "durationMinutes": 30, "price": 250000, "active": true },
  { "id": 802, "channelId": 1, "durationMinutes": 60, "price": 450000, "active": true },
  { "id": 0, "channelId": 2, "durationMinutes": 30, "price": 0, "active": false }
]
```

پس از ورود صفحه، بازگشت از background و خطای نامعلوم هنگام ذخیره، matrix را از همین endpoint refresh کنید.

### 4.2 ذخیره

```http
PUT /api/Companion/ConsultationPackage
Content-Type: application/json
Authorization: Bearer {accessToken}
```

همیشه هر ۸ خانه را بفرستید:

```json
{
  "items": [
    { "id": 801, "channelId": 1, "durationMinutes": 30, "price": 250000, "active": true },
    { "id": 802, "channelId": 1, "durationMinutes": 60, "price": 450000, "active": true },
    { "id": 0, "channelId": 2, "durationMinutes": 30, "price": 300000, "active": true },
    { "id": 0, "channelId": 2, "durationMinutes": 60, "price": 0, "active": false },
    { "id": 0, "channelId": 3, "durationMinutes": 30, "price": 0, "active": false },
    { "id": 0, "channelId": 3, "durationMinutes": 60, "price": 600000, "active": true },
    { "id": 0, "channelId": 4, "durationMinutes": 30, "price": 200000, "active": true },
    { "id": 0, "channelId": 4, "durationMinutes": 60, "price": 350000, "active": true }
  ]
}
```

server خانه را با `channelId + durationMinutes` پیدا می‌کند، نه با `id` ارسالی؛ بااین‌حال `id` پاسخ GET را حفظ و ارسال کنید تا state اپ قابل ردیابی بماند.

### چرا ارسال هر ۸ خانه لازم است؟

Backend فقط آیتم‌های فرستاده‌شده را upsert می‌کند و برای خانه‌ای که در body نیست دستور «حذف» یا «غیرفعال‌سازی» اجرا نمی‌کند. بنابراین ارسال ناقص می‌تواند یک پکیج قدیمیِ فعال را ناخواسته در فروش نگه دارد. source of truth فرم، ماتریس کامل GET + تمام تغییرهای کاربر است.

## 5. اعتبارسنجی و خطاها

| قانون backend | رفتار لازم در اپ |
| --- | --- |
| body خالی یا `items=[]` نامعتبر است | دکمهٔ ذخیره را بدون matrix فعال نکنید. |
| فقط channel ۱ تا ۴ و duration ۳۰/۶۰ معتبر است | constantهای app را از همین جدول بسازید؛ value آزاد نفرستید. |
| هر ترکیب فقط یک‌بار مجاز است | list را با کلید `channelId:durationMinutes` نگه دارید و duplicate تولید نکنید. |
| قیمت منفی نامعتبر است | عدد منفی و ورودی غیرعددی را پیش از API رد کنید. |
| `active=true` با `price<=0` نامعتبر است | switch را منع کنید و خطای قیمت نشان دهید. |

در خطای مبلغ، server پیام `AmountNotCorrect` و برای سایر دادهٔ ناقص/نامعتبر `InvalidData` برمی‌گرداند. پیام API را به کاربر نمایش دهید، دکمهٔ ذخیره را دوباره فعال کنید و draft را دور نریزید.

برای جلوگیری از دو save هم‌زمان، دکمه را تا پاسخ request disable کنید. API فعلی idempotency key ندارد؛ اگر timeout شد، قبل از retry ابتدا GET بزنید، matrix را با draft مقایسه کنید و تنها اگر تغییر ثبت نشده بود دوباره PUT کنید.

## 6. اثر فعال/غیرفعال‌سازی بر مشتری و خریدهای موجود

یک پکیج فقط وقتی به مشتری نشان داده می‌شود که هر دو شرط برقرار باشد:

1. کلینیک والد `Active` و `Approved` باشد؛
2. پکیج `active=true` و `price>0` داشته باشد.

ذخیرهٔ پکیج نیاز به approval جداگانه ندارد؛ اگر کلینیک فعال و تأییدشده باشد، نتیجهٔ PUT موفق در لیست عمومی قابل نمایش است.

| اقدام نماینده | اثر |
| --- | --- |
| قیمت پکیج فعال را تغییر می‌دهد | فقط checkoutهای بعدی قیمت تازه می‌گیرند. |
| پکیج را غیرفعال می‌کند | خرید جدید آن ترکیب متوقف می‌شود. |
| پکیج را دوباره فعال می‌کند | اگر کلینیک هم public باشد، دوباره قابل خرید می‌شود. |
| پکیج دارای خرید Paid یا Active را غیرفعال می‌کند | خرید/جلسهٔ قبلی لغو، refund یا قطع نمی‌شود؛ فقط فروش آینده بسته می‌شود. |

به‌جای دکمهٔ delete، برای توقف دائمی فروش همان خانه را `active: false` ذخیره کنید. حذف endpoint اختصاصی ندارد.

## 7. state و جریان پیشنهادی اپ

```ts
type ConsultationPackageEditorState = {
  items: Record<`${1 | 2 | 3 | 4}:${30 | 60}`, ConsultationPackageItem>
  isLoading: boolean
  isSaving: boolean
  lastLoadedAt?: string
}
```

```text
بازکردن صفحه
  → GET matrix کامل
  → ویرایش محلی قیمت/switch هر خانه
  → validate کامل ۸ خانه
  → PUT کامل matrix
  → جایگزین‌کردن state با پاسخ server
  → پیام «پکیج‌ها ذخیره شد»
```

در صفحهٔ profile/preview کلینیک، نمایش «مشاوره آنلاین فعال است» را از وجود حداقل یک item با `active=true` و `price>0` بسازید. این preview جای بررسی public بودن کلینیک را نمی‌گیرد؛ اگر کلینیک تأیید یا فعال نباشد، مشتری هیچ پکیجی نمی‌بیند.

## 8. چک‌لیست QA

- [ ] GET همیشه ۸ خانه را در UI نشان می‌دهد، حتی وقتی همه هنوز `id=0` هستند.
- [ ] چت، صوتی، تصویری و تلفنی با channelId درست ذخیره می‌شوند.
- [ ] فقط durationهای ۳۰ و ۶۰ دقیقه قابل انتخاب‌اند.
- [ ] switch پکیج بی‌قیمت یا با قیمت صفر فعال نمی‌شود.
- [ ] PUT هر ۸ خانه را ارسال می‌کند و هیچ combination تکراری ندارد.
- [ ] timeout ذخیره با GET recovery می‌شود، نه PUT کورکورانه.
- [ ] غیرفعال‌سازی پکیج، فروش جدید را می‌بندد اما UI ادعا نمی‌کند خریدهای قبلی cancel شده‌اند.
- [ ] برای تماس تلفنی، متن و مسیر کاربر اعلام می‌کند تماس خارج اپ است.
- [ ] پکیج‌ها فقط وقتی به مشتری نشان داده می‌شوند که کلینیک نیز active و approved باشد.

**وضعیت سند:** منطبق با backend فعلی پاستیل در ۲۱ سپتامبر ۲۰۲۶.
