# عکس پیشنهادی فروشگاه برای محصول (`ProductImageSuggestion`) — راهنمای کامل اپ نماینده‌ی فروشگاه (فلاتر)

Base URL: `https://api.pastil.pet` — همهٔ endpointها `Authorization: Bearer {accessToken}` می‌خواهند.
`StoreId` و `UserId` **همیشه از توکن** گرفته می‌شوند؛ هیچ‌جا در بدنه/مسیر نفرستید. پاسخ‌ها همان قالب استاندارد
`{ isSuccess, code, messages, data }` هستند و پیام خطا در `messages[0].item1` (فارسی و قابل‌نمایش مستقیم) است.
تقریباً همیشه HTTP 200؛ فقط `isSuccess`/`code` را بخوانید (استثنا: ۴۰۱ و ۴۱۳ و ۴۲۹).

> وضعیت: ساخته‌شده در بک‌اند و پنل (۱۴۰۵/۰۸/۲۴ = 2026-11-15) — **هنوز دیپلوی نشده** و SQL هم روی دیتابیس اجرا نشده
> (بخش «چک‌لیست دیپلوی» آخر همین سند). تا آن موقع endpointها در سرور وجود ندارند.

---

## ۱. ایده در یک نگاه

تا امروز نماینده‌ی فروشگاه (پت‌شاپ) محصولِ کاتالوگ را به فروشگاه خودش اضافه می‌کرد و **فقط قیمت و موجودی** می‌زد. حالا
می‌تواند **عکس خودش از همان محصول** را هم بفرستد. این عکس یک «پیشنهاد» است، نه تغییر مستقیم:

1. نماینده برای یک محصولی که **در فروشگاه خودش ثبت است**، عکس آپلود می‌کند → پیشنهاد با وضعیت `pending` ساخته می‌شود.
2. در **پنل ادمین** یک اعلان (زنگوله) می‌آید و پیشنهاد در صفحهٔ
   «مدیریت فروشگاه ← عکس های پیشنهادی محصولات» (`/admin/productimagesuggestion`) در صف بررسی می‌نشیند.
3. ادمین عکس پیشنهادی را کنار عکس فعلی محصول می‌بیند و **تأیید** یا **رد (با دلیل)** می‌کند.
4. **تأیید** = همان عکس می‌شود «تصویر اصلی» (`Product.PictureId`) محصول کاتالوگ — برای همهٔ فروشگاه‌ها و مشتری‌ها.
   - اگر محصول **عکس نداشت**: مستقیم ثبت می‌شود.
   - اگر محصول **از قبل عکس داشت**: پنل مودال «مطمئنید می‌خواهید جایگزین کنید؟» نشان می‌دهد و فقط با تأیید صریحِ ادمین عوض می‌شود. (بک‌اند هم همین را اجبار می‌کند.)
5. **رد** = دلیل متنی ثبت می‌شود؛ نماینده در اپ دلیل را می‌بیند و می‌تواند عکس دیگری بفرستد.

نکتهٔ مهم برای اپ: **نماینده هیچ‌وقت مستقیم عکس محصول کاتالوگ را عوض نمی‌کند** و بعد از تأیید هم اپ کاری
نمی‌کند — عکس جدید همان‌جا که محصول نمایش داده می‌شود (فهرست/جزئیات محصول) خودبه‌خود می‌آید.

## ۲. چرخهٔ وضعیت (`status`)

| `status` | یعنی | حذف توسط نماینده | نمایش در اپ |
|---|---|---|---|
| `pending` | در صف بررسی ادمین | ✅ (پس‌گرفتن) | چیپ «در انتظار بررسی» |
| `approved` | تأیید شد و عکس تصویر اصلی محصول شد | ❌ | چیپ «تأیید شد» |
| `rejected` | رد شد؛ دلیل در `rejectionReason` | ✅ | چیپ «رد شد» + دلیل + دکمهٔ «ارسال عکس دیگر» |

قواعد مهم:

- برای هر **(فروشگاه، محصول)** در هر لحظه **حداکثر یک** پیشنهاد `pending` وجود دارد. اگر نماینده
  وقتی پیشنهادش هنوز `pending` است عکس دیگری بفرستد، **همان پیشنهاد عوض می‌شود** (همان `id`، عکس جدید، دوباره آخرِ صف)
  و پیشنهاد دوم ساخته نمی‌شود. برای این حالت اعلان دوباره ساخته نمی‌شود.
- بعد از `rejected` یا `approved` ارسال تازه یک پیشنهاد **جدید** (با `id` جدید) می‌سازد.
- ادمین فقط یک‌بار تصمیم می‌گیرد؛ پیشنهادِ تصمیم‌گرفته‌شده دیگر قابل تأیید/رد نیست.

## ۳. مدل داده (`ProductImageSuggestionDto`)

| فیلد | نوع | توضیح |
|---|---|---|
| `id` | number | شناسهٔ پیشنهاد |
| `productId` | number | محصول کاتالوگ |
| `productName` | string? | نام محصول (برای نمایش در فهرست) |
| `pictureUrl` | string? | آدرس عکس **پیشنهادی همین فروشگاه** — مثل بقیهٔ تصویرهای API نسبی/کامل می‌آید؛ همان منطق ساخت URL تصاویر `MissingProduct` |
| `status` | string | `pending` \| `approved` \| `rejected` (حروف کوچک) |
| `rejectionReason` | string? | فقط وقتی `rejected` است |
| `createdAtUtc` | string (ISO, UTC) | زمان ارسال (برای `pending` تعویض‌شده = زمان آخرین عکس) |
| `reviewedAtUtc` | string? | زمان تصمیم ادمین |

پاسخ فهرست (`ProductImageSuggestionListDto`): `{ items: ProductImageSuggestionDto[], total: number }`.

## ۴. endpointها (ناحیهٔ Seller)

### ۴-۱. ارسال عکس پیشنهادی

`POST /api/Seller/ProductImageSuggestion` — `multipart/form-data`

| فیلد | نوع | توضیح |
|---|---|---|
| `productId` | text (عدد) | محصول کاتالوگ — **باید در همین فروشگاه ثبت شده باشد** (یعنی نماینده برایش قیمت/موجودی زده؛ آیتم حذف‌نشده) |
| `image` | فایل | `jpg` / `png` / `webp`، حداکثر **۸ مگابایت**. محتوای واقعی فایل (نه فقط پسوند) بررسی می‌شود |

- حد کل درخواست ۱۰MB است.
- **Rate limit:** سقف ۳۰ ارسال پشت‌سرهم برای هر کاربر، و بعد هر ۱۰ ثانیه یک ارسال آزاد می‌شود (برای ورود پیاپی محصولات کافی است). عبور از سقف → HTTP `429`؛ پیام «کمی صبر کنید و دوباره تلاش کنید» نشان بدهید.
- سقف **۳۰۰ پیشنهاد `pending`** برای هر فروشگاه؛ بیشتر از آن خطای `۱` با پیام فارسی می‌گیرد.

نمونه (Dio):

```dart
final form = FormData.fromMap({
  'productId': productId,
  'image': await MultipartFile.fromFile(file.path, filename: 'photo.jpg'),
});
final res = await dio.post('/api/Seller/ProductImageSuggestion', data: form);
if (res.data['isSuccess'] == true) {
  final suggestion = res.data['data']; // ProductImageSuggestionDto
}
```

موفق → `data` همان `ProductImageSuggestionDto` با `status: "pending"`.

خطاهای ممکن (`isSuccess=false`، پیام فارسی آمادهٔ نمایش است):

| `code` | وقتی | پیام (نمونه) |
|---|---|---|
| `1` | `productId`/فایل نامعتبر | «اطلاعات ارسال‌شده معتبر نیست.» |
| `3` | محصول وجود ندارد یا غیرفعال است | «محصول یافت نشد یا غیرفعال است.» |
| `1` | محصول در این فروشگاه ثبت نشده | «این محصول هنوز در فروشگاه شما ثبت نشده است؛ ابتدا قیمت و موجودی آن را وارد کنید.» |
| `1` | فایل تصویر معتبر نیست / بزرگ‌تر از ۸MB | «تصویر معتبر نیست؛ فقط jpg، png یا webp تا ۸ مگابایت.» |
| `1` | سقف پیشنهادهای در انتظار | «تعداد پیشنهادهای در انتظار بررسیِ فروشگاه شما به سقف رسیده است…» |
| `5` | آپلود به سرویس فایل ناموفق | «آپلود تصویر ناموفق بود؛ دوباره تلاش کنید.» (قابل تلاش مجدد) |

### ۴-۲. فهرست پیشنهادهای فروشگاه

`GET /api/Seller/ProductImageSuggestion?productId={id}&pageSize={n}`

- `productId` اختیاری — برای اینکه صفحهٔ یک محصول وضعیت پیشنهاد خودش را نشان بدهد.
- `pageSize` پیش‌فرض ۱۰۰، حداکثر ۲۰۰. جدیدترین اول.
- فقط پیشنهادهای **همین فروشگاه** برمی‌گردد.

### ۴-۳. حذف / پس‌گرفتن پیشنهاد

`DELETE /api/Seller/ProductImageSuggestion/{id}`

- فقط برای `pending` و `rejected` (پیشنهاد `approved` حذف نمی‌شود: خطای `۱`).
- پیشنهاد فروشندهٔ دیگر / نامعتبر: همان خطای `۳` «پیشنهاد تصویر یافت نشد.» (وجودش لو نمی‌رود).
- فایل عکس در سرویس فایل پاک نمی‌شود؛ فقط خود پیشنهاد حذف می‌شود.

## ۵. طراحی پیشنهادی UI در اپ

اپ فروشنده‌ی فلاتر (`provider_panel`) همین حالا دو جا قیمت/موجودی ثبت می‌کند: برگهٔ «افزودن به فروشگاه»
در `catalog_page.dart` (`_AddProductItemSheet`) و ویرایش در `products_page.dart`. پیشنهاد:

1. **در برگهٔ افزودن محصول از کاتالوگ** (بعد از فیلدهای قیمت و موجودی) یک بخش اختیاری:
   «عکس محصول را اضافه کنید» با دو دکمهٔ «دوربین» و «گالری». عکس انتخاب‌شده فقط پیش‌نمایش داده می‌شود
   و **بعد از اینکه `Seller/ProductItem` (ذخیرهٔ قیمت/موجودی) موفق شد** به `Seller/ProductImageSuggestion` فرستاده می‌شود
   (چون endpoint شرط می‌کند محصول از قبل در فروشگاه ثبت شده باشد). اگر ارسال عکس شکست خورد، **ثبت محصول را برنگردانید**؛
   فقط پیام «محصول ثبت شد، ولی ارسال عکس انجام نشد — دوباره تلاش کنید» و دکمهٔ تلاش مجدد.
2. **در کارت/جزئیات محصول فروشگاه** (`products_page.dart`):
   - اگر محصول **عکس ندارد** (`pictureUrl` خالی در پاسخ محصول): دکمهٔ برجستهٔ «ارسال عکس برای این محصول».
   - اگر **عکس دارد**: دکمهٔ کم‌رنگ‌تر «عکس بهتری دارید؟ پیشنهاد دهید». (مجاز است؛ ادمین با مودال جایگزینی تصمیم می‌گیرد.)
   - اگر پیشنهادی `pending` دارد: چیپ «عکس شما در انتظار بررسی است» و دکمهٔ «تغییر عکس» (همان `POST`؛ عکس pending را عوض می‌کند) و «پس‌گرفتن» (`DELETE`).
   - اگر `rejected`: دلیل رد (`rejectionReason`) با رنگ هشدار + «ارسال عکس دیگر».
   - وضعیت‌ها را با `GET ...?productId=` بگیرید (یا یک‌بار کل فهرست فروشگاه را بگیرید و در حافظه با `productId` گروه کنید).
3. **پردازش عکس قبل از ارسال** (اختیاری ولی توصیه‌شده): همان pipeline موجود `product_image_processor.dart`
   (سفیدسازی پس‌زمینهٔ سرور `POST /api/Seller/ProductImage/Enhance`، با fallback محلی) را قبل از ارسال اجرا کنید تا عکس‌ها کاتالوگی
   (پس‌زمینهٔ سفید، بوم مربع) باشند و احتمال تأیید بالا برود. توجه: Enhance سقف جدا و کمی دارد
   (۶ تلاش، هر ۲ دقیقه یکی)؛ برای ورود دسته‌ای محصول، Enhance را «اختیاری» بگذارید نه اجباری، و اگر `429` گرفتید عکس خام را بفرستید.
4. **پس از تأیید چیزی در اپ لازم نیست**: عکس جدید خودبه‌خود در همهٔ جاهایی که تصویر اصلی محصول نمایش داده می‌شود می‌آید
   (ممکن است کش تصویر روی دستگاه چند لحظه عکس قبلی را نشان دهد؛ با خروج/ورود به صفحه یا pull-to-refresh درست می‌شود).
5. یک صفحهٔ **«عکس‌های پیشنهادی من»** (اختیاری، مثلاً زیر منوی محصولات): فهرست `GET /Seller/ProductImageSuggestion` با
   چیپ وضعیت، نام محصول، پیش‌نمایش عکس، تاریخ، و دلیل رد.

متن‌های پیشنهادی (فارسی): «عکس پیشنهادی ارسال شد و بعد از بررسی تیم پاستیل جایگزین می‌شود.»،
«عکس شما رد شد: {rejectionReason}»، «عکس شما تأیید شد و تصویر اصلی محصول است.»

## ۶. آنچه سمت پنل ادمین ساخته شده (برای اطلاع)

- **اعلان زنگوله**: برچسب `ProductImageSuggestion.Submitted`، عنوان «تصویر پیشنهادی جدید برای محصول»، متن
  «فروشگاه «…» برای محصول «…» تصویر پیشنهاد داد.»، با کلیک به صفحهٔ صف می‌رود. اعلان فقط برای **پیشنهادِ جدید** ساخته می‌شود
  (تعویض عکسِ یک pending اعلان تازه نمی‌سازد).
- **صفحهٔ پنل**: `مدیریت فروشگاه ← عکس های پیشنهادی محصولات` (`/admin/productimagesuggestion`) — کارت‌های مقایسه (عکس فعلی ↔ پیشنهادی)،
  فیلتر وضعیت (در صف / تأییدشده / ردشده / همه) و جستجو در نام محصول یا فروشگاه. صف pending قدیمی‌ترین اول است.
- **API ادمین** (فقط نقش Admin، قابل تفویض به نقش دیگر نیست):
  - `GET /api/Admin/ProductImageSuggestion?status=pending|approved|rejected|all&q=&storeId=&productId=&pageNumber=&pageSize=`
  - `POST /api/Admin/ProductImageSuggestion/approve` بدنه `{ id, confirmReplace }` — اگر محصول از قبل تصویر دارد و `confirmReplace` نیست:
    `isSuccess=false` با **`code = 9`** («این محصول از قبل تصویر دارد؛ برای جایگزینی باید تأیید صریح بدهید.») و **هیچ چیز عوض نمی‌شود**.
  - `POST /api/Admin/ProductImageSuggestion/reject` بدنه `{ id, reason }` (دلیل لازم، حداکثر ۵۰۰ کاراکتر).
- تأیید فقط `Product.PictureId` (تصویر اصلی) را عوض می‌کند. عکس قبلی **پاک نمی‌شود** (شناسه‌اش در `ReplacedPictureId` پیشنهاد می‌ماند و
  پنل لینک «مشاهدهٔ تصویر قبلی» نشان می‌دهد)؛ گالری محصول (`ProductPictures`) دست نمی‌خورد.
- اگر چند فروشگاه برای یک محصول عکس بفرستند، همه در صف می‌مانند؛ تأیید اولی، تصویر محصول را ثبت می‌کند و برای بعدی‌ها مودال «از قبل عکس دارد» ظاهر می‌شود.

## ۷. آنچه هنوز نیست (تصمیم‌های باز)

- **پوش به نماینده بعد از تأیید/رد**: ساخته نشده (فقط اعلان ادمین خواسته شده بود). اگر لازم شد، مثل پوش‌های ۱۷۳/۱۷۴ (`MissingProduct`) با دو `PushType` جدید اضافه می‌شود؛
  تا آن موقع اپ باید وضعیت را با `GET` ببیند (مثلاً هنگام ورود به صفحهٔ محصول یا صفحهٔ «عکس‌های پیشنهادی من»).
- **اضافه‌شدن عکس تأییدشده به گالری** محصول: فعلاً فقط تصویر اصلی عوض می‌شود.
- **ردیابی کیفیت**: ادمین می‌تواند بدون دلیل خاص رد کند؛ مسدودسازی فروشگاهی که مدام عکس بد می‌فرستد وجود ندارد (فعلاً فقط سقف ۳۰۰ pending).

## ۸. چک‌لیست دیپلوی (برای تیم)

1. **SQL را اجرا کنید (پیش از دیپلوی Api):** `backend/scripts/ProductImageSuggestions.sql` — جدول `ProductImageSuggestions` + ردیف نوع اعلان
   `ProductImageSuggestion.Submitted`؛ idempotent است. (معادل migration `20261115120000_ProductImageSuggestions`.)
   بدون ردیف نوع اعلان، پیشنهاد ثبت می‌شود ولی اعلان زنگوله ساخته **نمی‌شود** (فقط لاگ هشدار).
2. **دیپلوی Api** (و پنل).
3. در پنل **«همگام‌سازی دسترسی‌ها» (Permission Sync)** را یک‌بار بزنید تا آیتم منوی «عکس های پیشنهادی محصولات» زیر «مدیریت فروشگاه» ساخته شود
   (این کنترلر `ForceMenuOnSync` است)؛ سپس یک‌بار خروج/ورود در پنل.
4. اگر نماینده‌ی فروشگاه با نقش تفویض‌شده (کارمند) کار می‌کند، این endpointها زیر بخش «محصولات» (`Sec.Product`) نقش‌های فروشگاه می‌آیند.
