# مشاوره آنلاین (چت / تماس / ویدیو / تلفنی) — مستند تیم اپ موبایل (نماینده و کاربر)

> مخاطب: توسعه‌دهنده‌ی اپ Flutter (اپ نماینده و اپ کاربر) · وب‌اپ همین رفتار را پیاده کرده است
> طراحی کامل و ماشین حالت: [ONLINE_CONSULTATION_PACKAGES_FA.md](ONLINE_CONSULTATION_PACKAGES_FA.md)

## ۱) جریان کلی

1. **کلینیک/نماینده** بسته‌ها را تعریف می‌کند: ۴ روش (چت، تماس درون‌برنامه، تماس تصویری، تلفنی) × ۲ مدت (**۳۰ یا ۶۰ دقیقه**) با قیمت و فعال/غیرفعال.
2. **کاربر** بسته را می‌خرد (کیف پول و/یا درگاه). خرید «پرداخت‌شده» می‌شود ولی **زمان هنوز شروع نشده**.
3. **نماینده** پوش «رزرو مشاوره جدید» می‌گیرد و از فهرست، «شروع مشاوره» را می‌زند. **از همین لحظه** پنجره‌ی ۳۰/۶۰ دقیقه‌ای شروع می‌شود (`expireDate = startDate + مدت`) و کاربر پوش می‌گیرد.
4. تا پایان پنجره هر دو طرف می‌توانند چت کنند/تماس بگیرند و **هر وقت بیرون افتادند برگردند**.
5. با پایان پنجره: چت **فقط‌خواندنی** می‌شود، تماس بسته می‌شود، وضعیت «پایان‌یافته» می‌شود و نوار/پاپ‌آپ بازگشت ناپدید می‌شود.

اگر نماینده تا **۲۴ ساعت** شروع نکند یا کاربر قبل از شروع لغو کند، خرید برگردانده می‌شود (بازپرداخت کامل به کیف پول + پوش).

## ۲) قانون طلایی زمان (اشتباه رایج ⇒ شمارنده ۰۰:۰۰)

همه‌ی تاریخ‌های مشاوره (`startDate`، `expireDate`، `startDeadline`، `serverNow`، …) **ساعت دیواری سرور** هستند، ولی:

- `serverNow` با آفست منطقه‌ی زمانی سرور می‌آید (مثلاً `2026-09-21T19:00:00+00:00` یا `...Z`)،
- بقیه‌ی تاریخ‌ها **بدون آفست** می‌آیند (`2026-09-21T19:20:00`).

اگر مستقیم `DateTime.parse` کنید، وقتی منطقه‌ی زمانی سرور با گوشی فرق دارد (سرور UTC، کاربر ایران) اختلاف حدود ۳٫۵ ساعت اضافه/کم می‌شود و «زمان باقی‌مانده» منفی/صفر می‌شود.

**راه درست:** آفست را از **همه‌ی** رشته‌ها حذف کنید و اختلافشان را حساب کنید؛ ساعت گوشی را فقط برای «چقدر از زمان دریافت پاسخ گذشته» استفاده کنید:

```dart
DateTime parseServerDate(String v) =>
    DateTime.parse(v.replaceFirst(RegExp(r'(Z|[+-]\d{2}:?\d{2})$', caseSensitive: false), ''));

// fetchedAt = لحظه‌ای که پاسخ را گرفتید (DateTime.now() گوشی)
Duration remaining(String expireDate, String serverNow, DateTime fetchedAt) =>
    parseServerDate(expireDate)
        .difference(parseServerDate(serverNow)) - DateTime.now().difference(fetchedAt);
```

- هر پاسخ جدید (`GET` فهرست/`Active`/جزئیات) `serverNow` تازه دارد؛ `fetchedAt` را دوباره بگذارید.
- نمایش: `mm:ss` (و `hh:mm:ss` اگر بیش از یک ساعت). هرگز عدد منفی نشان ندهید (`max(0, …)`).
- **ساعت گوشی را مبنای پایان قرار ندهید** (کاربر ساعت را دستی عوض می‌کند). سرور در هر حال ورود را می‌بندد.

## ۳) وضعیت‌ها (`status`)

| مقدار | معنی | نمایش پیشنهادی | عمل‌ها |
| ---: | --- | --- | --- |
| 1 | در انتظار پرداخت | — (در فهرست نماینده نمی‌آید) | — |
| 2 | پرداخت‌شده، منتظر شروع نماینده | «منتظر شروع نماینده» + مهلت شروع | نماینده: **شروع**؛ کاربر: **لغو و بازپرداخت** |
| 3 | در جریان | شمارنده‌ی معکوس | ورود/بازگشت به چت یا تماس |
| 4 | پایان‌یافته | «پایان‌یافته» | چت: فقط مشاهده (خواندنی) |
| 5 | منقضی‌شده (شروع نشد) | «منقضی‌شده» | — |
| 6 | لغوشده | «لغوشده» | — |
| 7 | بازپرداخت‌شده | «بازپرداخت‌شده» | — |

**پایان زنده:** وقتی `remaining ≤ 0` و `status == 3`، **همان لحظه در UI «پایان‌یافته»** نشان دهید و دکمه‌های ورود/بازگشت و بلوک زمان را بردارید؛ لازم نیست منتظر سرور بمانید. سرور هر دقیقه (job) وضعیت را واقعاً به ۴ می‌برد؛ بعد از پایان پنجره یک‌بار فهرست را دوباره بگیرید (حداکثر هر ~۱۵ ثانیه، بدون حلقه‌ی ثانیه‌ای).

## ۴) نماینده — فهرست، شروع، ورود

همه با `Authorization: Bearer …`. پاسخ‌ها **همیشه HTTP 200** با `{ isSuccess, messages, data }` هستند؛ موفقیت را از `isSuccess` بخوانید.

### فهرست رزروها
`GET /api/Companion/ConsultationSession`

  "channelId": 1,                 // ۱ چت، ۲ تماس درون‌برنامه، ۳ تصویری، ۴ تلفنی
  "durationMinutes": 30,
  "status": 2,
  "paidDate": "…", "startDeadline": "…", "startDate": null, "expireDate": null,
  "onlineSessionId": null,        // بعد از شروع پر می‌شود
  "userId": 5, "userFullName": "سارا احمدی", "userMobile": "0912…", "userPicture": { … },
  "agentUserId": null,
  "canStart": true,               // نماینده‌ی مجاز + وضعیت ۲ + مهلت نگذشته

### شروع مشاوره
`POST /api/Companion/ConsultationSession/{purchaseId}/Start` (بدون بدنه)

- اتمی است: دو کلیک/دو نماینده هم‌زمان فقط یک بار موفق می‌شود؛ پیام‌های خطا: «مهلت شروع این مشاوره گذشته است»، «این مشاوره قبلاً شروع شده است».
- پاسخ:

```json
{ "isSuccess": true, "data": {
  "purchaseId": 21, "onlineSessionId": 58, "channelId": 3,
  "startDate": "…", "expireDate": "…", "serverNow": "…",
  "userId": 5, "userFullName": "سارا احمدی", "userMobile": "0912…"
}}
```

**بعد از موفقیت (طبق `channelId`):**

| `channelId` | کاری که اپ می‌کند |
| ---: | --- |
| 1 چت | صفحه‌ی چت جلسه (`onlineSessionId`) |
| 2 / 3 | صفحه‌ی تماس جلسه (`onlineSessionId`) و اتصال به هاب (بند ۷) |
| 4 تلفنی | فقط پنجره شروع می‌شود؛ **شماره‌ی کاربر را نشان بدهید و دکمه‌ی تماس تلفن گوشی (`tel:`)** بگذارید. چیزی درون اپ برقرار نمی‌شود. |

### ورود مجدد
`POST /api/Companion/ConsultationSession/{purchaseId}/Enter` — همان پاسخ بالا؛ فقط وقتی `status == 3` و پنجره باز است. برای «بازگشت به تماس/چت» از همین یا از `onlineSessionId` فهرست استفاده کنید.

## ۵) کاربر — خرید، فهرست، بازگشت

| کار | endpoint |
| --- | --- |
| بسته‌های فعال یک کلینیک | `GET /api/EndUser/ConsultationPackage?companionId={id}` |
| خرید | `POST /api/EndUser/ConsultationPurchase` `{ packageId, fromWallet, merchantId?, rebateCode? }` + هدر `Idempotency-Key` (UUID) |
| مشاوره‌های من | `GET /api/EndUser/ConsultationPurchase` |
| جزئیات | `GET /api/EndUser/ConsultationPurchase/{id}` |
| لغو قبل از شروع | `PUT /api/EndUser/ConsultationPurchase/{id}/Cancel` |
| **پنجره‌های در جریان (برای نوار بازگشت)** | `GET /api/EndUser/ConsultationPurchase/Active` |

- قیمت را **هرگز از کلاینت** نفرستید؛ فقط `packageId`.
- پاسخ خرید همان پاسخ پرداخت است: اگر `paymentIsLink == true` باید `paymentUrl` (https) در مرورگر/وب‌ویو باز شود؛ اگر `false` یعنی کامل از کیف پول/تخفیف پرداخت شده و مشاوره «منتظر شروع» ثبت شده. در حالت **تست پرداخت**، `paymentUrl` همان صفحه‌ی callback است و پرداخت از قبل موفق ثبت شده.
- `GET …/Active` فقط آیتم‌های `status == 3` و بازِ این کاربر را می‌دهد؛ هر آیتم `purchaseId, onlineSessionId, channelId, durationMinutes, startDate, expireDate, serverNow, companionName, agentFullName` دارد.

## ۶) «برگشت به کال/چت» (نوار بازگشت — هر دو اپ)

هدف: اگر کاربر (یا نماینده) وسط مشاوره از صفحه‌ی چت/تماس خارج شد، همیشه راه برگشت داشته باشد.

**رفتار پیشنهادی (همان وب‌اپ):**
1. نوار ثابت بالای ناوبری پایین (یا بنر شناور) با متن «مشاوره‌ی {روش} با {نام} · mm:ss تا پایان · برای بازگشت ضربه بزنید».
2. داده: کاربر از `GET /api/EndUser/ConsultationPurchase/Active`؛ نماینده از فهرست `GET /api/Companion/ConsultationSession` (آیتم‌های `status == 3`). زمان: هر **۲۰ ثانیه** و هنگام برگشت به اپ (resume) و هنگام فوکوس. شمارش ثانیه‌ای فقط محلی (بند ۲).
3. نوار **را نشان ندهید** وقتی کاربر همین الان داخل همان چت/تماس است.
4. ضربه: چت ⇒ صفحه‌ی چت `onlineSessionId`؛ تماس درون‌برنامه/تصویری ⇒ صفحه‌ی تماس و **دوباره `JoinSessionCall`**؛ تلفنی ⇒ نوار غیرقابل‌ضربه («نماینده با شما تماس می‌گیرد») و برای نماینده دکمه‌ی `tel:`.
5. با `remaining ≤ 0` نوار **خودکار ناپدید** شود. اگر چند مشاوره هم‌زمان بود، اولی + شمارنده‌ی «+n».
6. اگر endpoint هنوز روی سرور نیست (۴۰۴)، چند دقیقه دوباره تلاش نکنید و خطا نشان ندهید.

## ۷) تماس درون‌برنامه/تصویری (SignalR + WebRTC)

- هاب: `wss://<api>/hubs/call?access_token=<JWT>` (احراز هویت با query). کلاینت SignalR رسمی Flutter (`signalr_netcore`) کافی است.
- **کلید جلسه در سیگنال‌ها منفیِ شناسه‌ی جلسه است**: `key = -onlineSessionId`.

| از اپ به سرور (`invoke`) | معنی |
| --- | --- |
| `JoinSessionCall(sessionId)` | ورود به اتاق تماس جلسه؛ **بعد از پایان پنجره رد می‌شود** |
| `SendSignal(key, type, payload)` | ارسال SDP/ICE (`type` فقط `offer` / `answer` / `ice`؛ `payload` رشته‌ی JSON تا ۳۲ کیلوبایت) |
| `EndCall()` | پایان تماس توسط این طرف |

| از سرور به اپ (`on`) | معنی |
| --- | --- |
| `waitingForPeer` | طرف مقابل هنوز وارد نشده |
| `callConnected(shouldOffer)` | هر دو حاضرند؛ فقط طرفی که `shouldOffer == true` است offer می‌سازد |
| `signal(type, payload)` | سیگنال طرف مقابل |
| `callEnded` | تماس بسته شد (پایان طرف مقابل **یا پایان پنجره‌ی زمانی**) |
| `callError(message)` | مثلاً «زمان مشاوره به پایان رسیده است.» |

**نکته‌های پیاده‌سازی (از تجربه‌ی وب):**
- سیگنال‌ها را **پشت‌سرهم و به‌ترتیب** پردازش کنید و ICE candidateهایی را که قبل از `setRemoteDescription` می‌رسند **صف** کنید و بعد از آن اعمال کنید (وگرنه صدا/تصویر نمی‌رسد).
- **برگشت به تماس:** اگر اتصال قطع شد یا کاربر از صفحه رفت، دوباره `JoinSessionCall(sessionId)` بزنید و PeerConnection تازه بسازید؛ تا پایان پنجره مجاز است.
- با `callEnded` یا `callError` حاوی «به پایان رسیده» صفحه را ببندید و به «پایان‌یافته» بروید؛ سرور دقیقاً در `expireDate` تماس را می‌بندد (`callEnded`).
- اجازه‌ی میکروفون/دوربین را **قبل** از join بگیرید. برای شبکه‌های متفاوت (موبایل ⇄ Wi‑Fi) **TURN** لازم است؛ فقط STUN همیشه کافی نیست.
- تماس تصویری: توقف ویدیو/میوت را در UI دارید ولی به سرور چیزی ارسال نمی‌شود.

## ۸) چت

- `GET /api/OnlineSessionMessage?OnlineSessionId=…&AfterMessageId=…&BeforeMessageId=…&PageSize=30`
- `POST /api/OnlineSessionMessage` `{ onlineSessionId, content, imageUrl?, imageThumbnailUrl? }`
- `PUT /api/OnlineSessionMessage/Read` `{ onlineSessionId, lastMessageId }`
- `GET /api/OnlineSession/{id}` — جزئیات جلسه: `expireDate` و `serverNow` (برای شمارنده)، `initiatorUser`، `targetUser`، `initiatorClinic`، برای نماینده `targetPets` (پت‌ها/گالری کاربر).
- تصویر: ابتدا آپلود از مسیر معمول اپ، بعد `imageUrl`.
- **بعد از `expireDate` سرور ارسال پیام را رد می‌کند** («زمان این مشاوره به پایان رسیده است»). در UI به‌جای کادر ورودی بنر «زمان مشاوره به پایان رسید؛ گفتگو فقط‌خواندنی است» بگذارید و شمارنده را در زیرعنوان هدر نشان دهید. پیام‌های قبلی همچنان قابل مشاهده‌اند.
- پیام‌ها را Poll (~۳–۵ ثانیه) یا با پوش ۶۷ تازه کنید.

## ۱۰) حالت‌های خطا/لبه که اپ باید درست نشان دهد

- **خرید بدون شروع:** کاربر «منتظر شروع نماینده» و مهلت (`startDeadline − serverNow`) را می‌بیند؛ نماینده همان مهلت را روی کارت می‌بیند.
- **پایان پنجره وسط تماس:** `callEnded` می‌رسد؛ صفحه‌ی تماس را ببندید و پیام «زمان مشاوره به پایان رسید» نشان دهید.
- **دو نماینده هم‌زمان Start:** یکی «قبلاً شروع شده است» می‌گیرد؛ فهرست را تازه کنید.
- **تلفنی:** اپ هیچ تماس درون‌برنامه‌ای نمی‌سازد؛ فقط `tel:`.
- **آفلاین/۴۰۴:** اگر endpoint هنوز دیپلوی نشده ۴۰۴ می‌دهد؛ بخش را ساکت مخفی کنید.
- **لغو کاربر:** فقط `status == 2`؛ بعد از شروع لغو ممکن نیست.

## ۱۱) چک‌لیست پیاده‌سازی

- [ ] `parseServerDate` (حذف آفست) در همه‌ی شمارنده‌ها
- [ ] شمارنده از `expireDate − serverNow − (now − fetchedAt)` و بستن UI در `≤ 0`
- [ ] وضعیت `status == 3` با `remaining ≤ 0` ⇒ «پایان‌یافته» (بدون ۰۰:۰۰ ماندن)
- [ ] فهرست نماینده: شروع/ورود/`tel:`؛ فهرست کاربر: لغو/بازگشت
- [ ] نوار بازگشت (poll ۲۰ ثانیه + resume) و مخفی در همان صفحه
- [ ] `JoinSessionCall` دوباره هنگام بازگشت؛ صف ICE؛ TURN
- [ ] چت فقط‌خواندنی بعد از پایان؛ پیام‌های ۶۶–۷۴ با مقصد درست
- [ ] `Idempotency-Key` در خرید؛ `paymentIsLink` برای درگاه
