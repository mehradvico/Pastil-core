# ارائه‌دهنده (Provider) و اشتراک — راهنمای کامل وب‌اپ (webapp)

> تاریخ: ۱۴۰۵/۰۷/۲۶ (۲۰۲۶-۱۰-۱۸) · وضعیت backend: Deploy شده، مایگریشن `AddProviders` روی دیتابیس اعمال شده.
> طراحی کلی و جدول‌ها: [PROVIDER_AND_SUBSCRIPTION_FA.md](PROVIDER_AND_SUBSCRIPTION_FA.md). این سند فقط «چه چیزی برای وب‌اپ عوض می‌شود و چه باید بکنید» را می‌گوید.

## ۰. خلاصه‌ی یک‌خطی

**هیچ endpoint موجودِ وب‌اپ نشکسته و هیچ فیلدی حذف یا تغییر نام نداده است.** تغییرات سمت سرور فقط افزودنی است (یک فیلد جدید در خروجی + برداشته شدن یک محدودیت). بنابراین وب‌اپ همین امروز بدون هیچ تغییری کار می‌کند؛ بقیه‌ی این سند کارهای «اختیاری ولی توصیه‌شده» و «مواردی که باید حواستان باشد» است.

## ۱. واژه‌نامه (از این به بعد در همه‌جا)

| قبلاً | حالا | معنی |
|---|---|---|
| نماینده (به‌عنوان شخص/حساب) | **ارائه‌دهنده (Provider)** | کاربری که صاحب یک یا چند کسب‌وکار است |
| Companion | هنوز `Companion` در API | **نمایندگی** خدماتی: کلینیک، آرایشگاه، مربی... (نام API عوض نشده) |
| Store | `Store` | فروشگاه؛ حالا به ارائه‌دهنده وصل است |
| حساب طلایی/نقره‌ای نماینده | **اشتراک ارائه‌دهنده** (نقره‌ای، طلایی، الماس) | روی خود ارائه‌دهنده است، نه روی هر نمایندگی |
| CompanionUser / StoreUser | **پرسنل** آن نمایندگی | همان قبلی؛ صاحب = ارائه‌دهنده |

> قاعده‌ی متن UI: وقتی از «صاحب کسب‌وکار» حرف می‌زنید بگویید «ارائه‌دهنده»؛ وقتی از خود مرکز حرف می‌زنید همان «کلینیک / آرایشگاه / فروشگاه / پانسیون» را بگویید. کلمه‌ی «نماینده» را فقط در جاهای قدیمی که هنوز عوض نکرده‌اید بگذارید بماند؛ تغییر متن اجباری نیست و به API ربطی ندارد.

## ۲. دقیقاً چه چیزی در API عوض شد

### ۲.۱ فیلد جدید `providerId` در خروجی Companion (افزودنی)

هر جا خروجی `CompanionVDto` یا `CompanionMinVDto` برمی‌گردد (جزئیات مرکز، لیست مراکز، جستجو، `GET /api/EndUser/Companion`، `GET /api/Companion/Companion/{id}` و ...) یک فیلد جدید هست:

```json
{
  "id": 41,
  "name": "کلینیک مهر",
  "ownerId": 1203,
  "providerId": 17,
  "isGold": true,
  "isSilver": false
}
```

- `providerId` می‌تواند `null` باشد (مرکزی که هنوز به ارائه‌دهنده وصل نشده؛ مثلاً ساخته‌شده توسط ادمین).
- `ownerId` همچنان هست و همان معنی قبلی را دارد؛ **حذف نشده و فعلاً حذف نمی‌شود**.
- نیازی به خواندن `providerId` ندارید مگر برای قابلیت‌های آینده (انتخاب نمایندگی، §۵).

### ۲.۲ `isGold` / `isSilver` / `goldAccountDate` / `silverAccountDate` — همان فیلدها، منبع تازه

این فیلدها در خروجی مراکز **همان قبلی‌اند و همان‌طور کار می‌کنند**؛ فقط الان از «اشتراک ارائه‌دهنده» پر می‌شوند:

| اشتراک ارائه‌دهنده | `isGold` | `isSilver` | تاریخ |
|---|---|---|---|
| ندارد / منقضی | `false` | `false` | هر دو `null` |
| نقره‌ای | `false` | `true` | `silverAccountDate` = پایان اشتراک |
| طلایی | `true` | `false` | `goldAccountDate` = پایان اشتراک |
| **الماس** | `true` | `false` | `goldAccountDate` = پایان اشتراک |

نکته‌ها:
- **الماس در UI فعلی مثل طلایی دیده می‌شود** (badge طلایی). اگر می‌خواهید بعداً badge جدا برای الماس بگذارید، به یک فیلد `subscriptionLevel` در خروجی نیاز است که **فعلاً وجود ندارد**؛ بخواهید اضافه می‌کنم.
- اشتراک ارائه‌دهنده برای **همه‌ی مراکز او** یکسان اعمال می‌شود (کلینیک و آرایشگاهِ یک نفر هر دو طلایی‌اند).
- مرتب‌سازی «ویژه‌ها بالاتر» و فیلتر `GoldAccount` / `SilverAccount` در جستجو بدون تغییر کار می‌کنند (چون روی همین فیلدها هستند).
- **تغییر رفتار:** قبلاً فقط **یک** مرکز در کل سیستم می‌توانست طلایی باشد؛ این محدودیت برداشته شد. ممکن است در لیست چند مرکز طلایی ببینید (و برای مرکزهای هم‌ارائه‌دهنده همیشه همین است). اگر UI فرض «حداکثر یک طلایی» داشت (مثلاً یک بنر ویژه)، باید چند مورد را هم تحمل کند.

### ۲.۳ برداشته شدن محدودیت «یک مرکز برای هر کاربر»

- `POST /api/EndUser/Companion` (ثبت درخواست مرکز/نمایندگی): قبلاً اگر کاربر از قبل مرکزی داشت خطای «قبلاً نماینده شده‌اید» (`AlreadyIsCompanion`) می‌داد؛ **حالا می‌پذیرد** و مرکز دوم ثبت می‌شود (با `active=false, approved=false` تا تأیید ادمین).
- `PUT /api/EndUser/Companion` (ویرایش/ارسال مجدد): خطای «قبلاً ثبت شده برای این مالک» (`CompanionAlreadyRegisteredForOwner`) دیگر برنمی‌گردد.
- **پیامد برای وب‌اپ:** هر کدی که فرض می‌کند «لیست مراکز من حداکثر یک عنصر است» ممکن است حالا اشتباه باشد. `GET /api/EndUser/Companion` (که خودش `OwnerId` را روی کاربر جاری می‌گذارد) ممکن است چند مورد برگرداند. جاهایی که `list[0]` می‌خوانند را به «نمایش لیست» یا «انتخاب نمایندگی» ارتقا دهید (§۴).
- درخواست فروشگاه (`POST /api/EndUser/Store`) **هنوز** برای هر کاربر یک درخواست باز می‌پذیرد (`StoreRequestAlreadyExistsForUser`)؛ فروشگاه دوم را فعلاً ادمین از پنل می‌سازد و به ارائه‌دهنده وصل می‌کند.

### ۲.۴ ثبت درخواست مرکز/فروشگاه، خودکار ارائه‌دهنده می‌سازد

- وقتی کاربر اولین درخواست مرکز یا فروشگاه را می‌فرستد، سرور برایش یک `Provider` می‌سازد (فعال، **تأییدنشده**) و مرکز/فروشگاه را به آن وصل می‌کند. وب‌اپ کاری نمی‌کند و چیزی در پاسخ‌ها عوض نمی‌شود.
- «تأییدنشده» بودن ارائه‌دهنده فعلاً هیچ دسترسی‌ای را نمی‌بندد؛ فقط در پنل ادمین برای بررسی نشان داده می‌شود.

### ۲.۵ چیزهایی که **عوض نشدند** (برای اطمینان)

- پاسخ «کاربر جاری» (CurrentUser): `companionId`، `storeId`، `isCompanionUser`، `canSetExpertise`، `driverId` دقیقاً مثل قبل (هنوز یک مقدار، اولین مرکز/فروشگاه فعال).
- `utils/workPanels.ts`: `hasCompanionPanel` (روی `companionId`) و `isCompanionStaff` و `hasSellerAccess` همان‌طور درست‌اند.
- `server/api/partner/[type].js` (`companion`, `store`, `pansion`, `driver`): آدرس‌ها و روش‌ها همان‌اند.
- همه‌ی endpointهای رزرو، پانسیون، مدرسه، مشاوره، مالی، پرداخت.
- ثبت‌نام و کد معرف.

### ۲.۶ جایگزینی endpointهای قدیمی ارتقای حساب (ادمین‌محور، به وب‌اپ مربوط نیست)

`PUT /api/Admin/CompanionUpdateGoldAccount` و `.../CompanionUpdateSilverAccount` دیگر ذخیره نمی‌کنند و پیام «سطح حساب ویژه اکنون از بخش اشتراک ارائه‌دهنده مدیریت می‌شود» برمی‌گردانند. این‌ها فقط پنل ادمین صدا می‌زد (که به‌روز شد). **وب‌اپ آن‌ها را صدا نمی‌زند**؛ اگر جایی صدا می‌زنید حذفش کنید.

## ۳. چیزهایی که **در وب‌اپ کار نمی‌کند (محدودیت‌های فعلی)**

این‌ها کدِ پنهان نیستند، محدودیت‌های شناخته‌شده‌ی فاز بعد هستند؛ قبل از اینکه کسی «دو کلینیک» را تست کند بدانید:

1. **پنل نماینده (`/companionProfile/*`) فقط یک مرکز را نشان می‌دهد.** سرور برای این پنل `companionId` کاربر جاری را «اولین مرکز فعال و تأییدشده‌اش» می‌گیرد و endpointهای ناحیه‌ی `Companion` (مثل `GET /api/Companion/Companion/{id}`) فارغ از `id` همان یک مرکز را برمی‌گردانند. پس ارائه‌دهنده‌ای که دو کلینیک دارد، در وب‌اپ فقط اولی را مدیریت می‌کند. **راه‌حل (backend + وب‌اپ) در §۵ طراحی شده و هنوز ساخته نشده است.**
2. **پنل فروشنده** با `GET /api/seller/stotreUser` لیست فروشگاه‌های کاربر را می‌گیرد (آرایه) و در کد فعلی احتمالاً اولی را استفاده می‌کند. برای فروشنده با دو فروشگاه باید انتخاب‌گر فروشگاه بگذارید (§۴.۳)؛ از سمت داده، فروشگاه دوم وقتی در پنل ادمین به ارائه‌دهنده و کاربر وصل شود در همان لیست می‌آید.
3. «مرکز جدید» و «فروشگاه جدید» در وب‌اپ همان فرم‌های قبلی‌اند؛ فرم اختصاصی «افزودن نمایندگی دوم» وجود ندارد.

## ۴. کارهای پیشنهادی در وب‌اپ (به ترتیب اولویت)

### ۴.۱ [مهم] لیست مراکز کاربر را تک‌عنصری فرض نکنید

نمایندگی‌هایی که `GET /api/EndUser/Companion` یا پاسخ `partner/companion` را می‌خوانند را بررسی کنید:
- `pages/agencyRequest.vue` (و هر صفحه‌ی «درخواست نمایندگی»): اگر لیست خالی نیست و اولین مورد را «درخواست من» نشان می‌دهد، حالا باید همه‌ی مورد‌ها را لیست کند (هرکدام با وضعیت: در انتظار / تأییدشده / رد شده / فعال).
- دکمه‌ی «ثبت درخواست جدید»: دیگر نباید با «شما قبلاً نماینده شده‌اید» غیرفعال شود؛ اگر چنین چکی سمت کلاینت دارید (مثلاً `if (list.length) disable`) حذفش کنید.
- متن خطای `AlreadyIsCompanion` را دیگر منتظر نباشید.

### ۴.۲ [اختیاری] نمایش اشتراک

بدون API جدید قابل انجام است: `isGold`/`isSilver` همان قبلی. اگر می‌خواهید «الماس» را جدا نشان دهید، ابتدا باید فیلد `subscriptionLevel` به خروجی اضافه شود (درخواست دهید).

### ۴.۳ [اختیاری] انتخاب‌گر فروشگاه در پنل فروشنده

برای فروشنده‌ی چندفروشگاهه: وقتی `stotreUser.data.length > 1` یک انتخاب‌گر در سربرگ `/sellerProfile` بگذارید و `storeId` انتخاب‌شده را در store (Pinia) نگه دارید؛ endpointهای فروشنده (`Seller/...`) فعلاً `storeId` را از کاربر جاری می‌گیرند و **همچنان اولین فروشگاه** را می‌بینند، پس انتخاب‌گر در UI تا اجرای §۵ فقط نمایشی است. توصیه: UI را ننویسید تا backend آماده شود.

### ۴.۴ [اختیاری] تغییر متن‌ها

جاهایی که «نماینده» به شخص صاحب کسب‌وکار اشاره دارد → «ارائه‌دهنده». مثال‌ها: عنوان صفحه‌ی `agencyRequest.vue`، پیام‌های موفقیت درخواست، متن‌های `/companionProfile`. نام صفحه‌ها و مسیرها (`/companionProfile`) را **عوض نکنید** (لینک‌های بیرونی و push navigation به آن‌ها وابسته‌اند).

### ۴.۵ [اختیاری] صفحه‌ی «کسب‌وکارهای من»

اگر خواستید یک صفحه‌ی خلاصه برای ارائه‌دهنده بسازید (لیست مراکز + فروشگاه‌ها + سطح اشتراک)، **قبلش به endpointی برای ارائه‌دهنده‌ی جاری نیاز است** (فعلاً فقط ناحیه‌ی Admin این اطلاعات را می‌دهد). در §۵ پیشنهادش آمده.

## ۵. پیشنهاد backend فاز بعد (**ساخته نشده**، برای هماهنگی)

برای اینکه ارائه‌دهنده‌ی چندنمایندگیه واقعاً در وب‌اپ و اپ کار کند، backend باید این‌ها را اضافه کند. تا نگفتم «ساخته شد»، وب‌اپ چیزی بر پایه‌ی آن‌ها نسازد:

1. `GET /api/EndUser/Provider/Me` — ارائه‌دهنده‌ی کاربر جاری: `{ id, active, approved, subscription: { planName, level, endDate } | null, capabilities: [...], companions: [{id, name, active, approved}], stores: [...] }`.
2. انتخاب نمایندگی فعال برای ناحیه‌ی `Companion`: یا هدر `X-Companion-Id` (سرور بررسی می‌کند نمایندگی مال کاربر یا پرسنل او باشد) یا پارامتر `companionId`. بدون هدر = رفتار فعلی (اولین مرکز).
3. همین مفهوم برای ناحیه‌ی `Seller` با `X-Store-Id`.
4. فیلد `subscriptionLevel` در خروجی مراکز.
5. اجازه‌ی ثبت درخواست فروشگاه دوم توسط خود ارائه‌دهنده.

## ۶. چک‌لیست تست وب‌اپ بعد از Deploy backend

1. کاربر عادی بدون مرکز → صفحه‌ی پروفایل بدون تغییر.
2. مالک یک مرکز تأییدشده → `/companionProfile` باز می‌شود؛ `companionId` همان قبلی؛ لیست مراکز در `agencyRequest` یک مورد.
3. در پنل ادمین: برای آن مالک (صفحه‌ی ارائه‌دهندگان) اشتراک «طلایی» بدهید → در لیست مراکز/جستجوی وب‌اپ همان مرکز badge طلایی بگیرد (در کش مرورگر/SSR تازه‌سازی شود).
4. اشتراک را «پایان فوری» کنید → badge برود.
5. همان مالک مرکز دوم را از `agencyRequest` ثبت کند → خطا نگیرد؛ دو مورد در لیست؛ **پنل نماینده همچنان فقط مرکز اول** (مورد انتظار، §۳.۱).
6. فروشنده با یک فروشگاه → پنل فروشنده بدون تغییر.
7. در Network: خروجی‌ها `providerId` دارند و هیچ فیلد قبلی کم نشده.

## ۷. پرسش‌های باز برای شما

- آیا badge «الماس» باید جدا از طلایی نمایش داده شود؟ (نیاز به `subscriptionLevel`)
- پنل چندنمایندگیه (§۵) را کِی لازم دارید؟ تا آن موقع پیشنهاد می‌کنم ارائه‌دهنده‌های چندنمایندگیه را فقط ادمین بسازد و به فروشنده/صاحب بگویید کدام مرکز در پنل نمایش داده می‌شود.

## تغییر در تسویه‌ها (۱۴۰۵/۰۷/۲۷) — وب‌اپ (پنل نماینده و فروشنده)

تسویه‌ها از این پس **برای ارائه‌دهنده** ثبت می‌شوند و به‌جای نمایندگی/فروشگاه منفرد، کل «نمایندگی‌ها (پنل نماینده) یا فروشگاه‌ها (پنل فروشنده)» ارائه‌دهنده را یک‌جا می‌پردازند.

**تغییر قرارداد `GET /api/Companion` و `/api/Seller/Settlement` (و `/{id}`):**

- لیست حالا تسویه‌های ارائه‌دهنده‌ی همین نمایندگی/فروشگاه را (فقط همین استخر) برمی‌گرداند؛ پارامترهای `companionId/storeId/providerId/kind` را نفرستید (نادیده گرفته می‌شوند).
- فیلدهای جدید در هر ردیف: `providerId` (عدد)، `kind` (`1` نمایندگی‌ها، `2` فروشگاه‌ها)، `provider` (`{ id, userId, active, user }`).
- **در تسویه‌های جدید `companionId`, `storeId`, `companion`, `store` برابر `null` هستند.** فقط ردیف‌های قدیمی (قبل از این تغییر) آن‌ها را دارند. UI نباید روی این فیلدها برای نمایش «گیرنده» تکیه کند؛ برای نمایش از «ارائه‌دهنده + استخر» استفاده کنید.
- `paidPrice` جمع همه‌ی رزرو یا سفارش آن تسویه (در همه‌ی نمایندگی‌ها/فروشگاه‌ها ارائه‌دهنده) است و `itemCount` تعداد آن‌ها؛ ریز هر مورد در این endpoint نیست.
- دسترسی به `GET /Settlement/{id}`: فقط تسویه‌ی ارائه‌دهنده‌ی همین نمایندگی/فروشگاه (و همین استخر)؛ در غیر این‌صورت `isSuccess=false` با پیام عدم دسترسی.
- **باگ برطرف‌شده در پنل فروشنده:** `GET /api/Seller/Settlement` قبلاً شناسه‌ی فروشگاه را به‌جای `CompanionId` فیلتر می‌کرد (فروشنده تسویه‌ی نمایندگی هم‌شناسه را می‌دید)؛ اکنون فقط تسویه‌ی ارائه‌دهنده‌ی خودش و فقط استخر فروشگاه‌ها را می‌بیند.

**بدون تغییر:** گزارش مالی `/Companion/FinanceCompanion` و `/Seller/FinanceStore` (ریز و جمع سهم‌ها، `Permitted`)، کارت‌های بانکی، و اینکه نمایندگی/فروشگاه نمی‌تواند خودش درخواست تسویه ثبت کند (فقط ادمین).
**نکته‌ی نمایش:** ریز رزرو یا سفارش هر نمایندگی/فروشگاه همچنان از گزارش مالی همان نمایندگی/فروشگاه می‌آید، ولی «تسویه‌شدن» برای کل ارائه‌دهنده‌ی اوست؛ اگر ارائه‌دهنده چند نمایندگی/فروشگاه دارد، مبلغ یک تسویه به یک نمایندگی/فروشگاه تقسیم نشده است.
