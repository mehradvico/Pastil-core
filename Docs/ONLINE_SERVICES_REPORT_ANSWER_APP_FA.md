# پاسخ بک‌اند به گزارش «مشکل خدمات آنلاین مربی و کلینیک»

**مخاطب:** تیم اپ (صفحه‌ی پروفایل مربی/کلینیک، کارت «خدمات آنلاین»)
**تاریخ:** ۱۴۰۵/۰۸/۰۳ (2026-10-25)
**نتیجه‌ی کوتاه:** داده روی production **هست** و مسیر «ب» گزارش (مسیر جدید روی خود Clinic/Coach) **از ۱۴۰۵/۰۸/۰۲ روی سرور فعال است**. اپ هنوز از اندپوینت‌های قدیمی می‌خواند. لازم نیست هیچ چیزی به Companion برگردد. فقط اپ باید اندپوینت را عوض کند.

---

## ۱) چرا اپ چیزی پیدا نمی‌کند
در ۱۴۰۵/۰۸/۰۲ مشاوره‌ی آنلاین کلینیک و مربی از Companion جدا شد (مستند `CONSULTATION_VENUE_OWNERS_FA.md`):
- بسته‌های چت/تماس که قبلاً روی Companionهای «لنگر» بودند، **به خود کلینیک/مربی منتقل شدند** (ستون‌های `clinicId` / `coachId`).
- برای همین `GET /api/EndUser/ConsultationPackage?companionId=…` برای آن شناسه‌ها حالا `data: []` می‌دهد و `LegacyCompanionId` هم `null` است. **این رفتار درست است**، نه خرابی داده.
- اپ هنوز با `companionId` / `LegacyCompanionId` می‌خواند، پس به داده‌ی جدید نمی‌رسد.

## ۳) اندپوینت‌هایی که اپ باید استفاده کند

### ۳-۱) فهرست خدمات آنلاین در پروفایل
```
GET /api/Coach/{coachId}/ConsultationPackages
GET /api/Clinic/{clinicId}/ConsultationPackages
```
یا با همان کنترلر قدیمی و پارامتر جدید (خروجی یکسان):
```
GET /api/EndUser/ConsultationPackage?coachId={id}
GET /api/EndUser/ConsultationPackage?clinicId={id}
```
بدون توکن کار می‌کند. نمونه‌ی هر آیتم:
```json
{
  "id": 101,
  "companionId": null,
  "clinicId": null,
  "coachId": 7,
  "channelId": 1,
  "durationMinutes": 30,
  "price": 250000,
  "name": "مشاوره رفتاری",
  "description": null,
  "picture": { "id": 66116, "url": "/Media/2026/10/25", "guidName": "…", "extension": ".webp", "orginalName": "…" },
  "sortOrder": 1,
  "companionOnline": false,
  "bookable": false
}
```
- فقط ردیف‌های **فعال با قیمت مثبت** از مرکزِ **فعال و تأییدشده** برمی‌گردند. اپ لازم نیست خودش فیلتر کند.
- `companionId` حالا `null` است. فقط یکی از `companionId` / `clinicId` / `coachId` پر است. مدل را nullable تعریف کنید.
- `companionOnline` با وجود نامش، وضعیت آنلاین **همین مرکز** است (هر کس از تیم مرکز «من آنلاینم» زده باشد).

### ۳-۲) ساختن کارت چهار‌کاناله‌ی طرح
خروجی **یک لیست تخت** از ردیف‌هاست، نه ساختار تو‌در‌توی `channels`. کارت طرح را در اپ با گروه‌بندی بسازید:
- گروه‌بندی بر اساس `channelId` (۱ چت، ۲ تماس صوتی داخل برنامه، ۳ تماس تصویری، ۴ تماس خارج برنامه).
- هر کانالی که ردیف ندارد، **نمایش داده نشود** (مثلاً Coach 2 فقط ردیف «تصویری» دارد).
- اگر یک کانال چند ردیف دارد (مثلاً Clinic 5 دو ردیف «تلفنی»)، همه را زیر همان کانال لیست کنید، به ترتیب `sortOrder` و بعد `durationMinutes`. سرور هم به همین ترتیب می‌فرستد.
- عنوان ردیف `name` است، و `description` و `picture` اختیاری‌اند.
- فیلد `prePaymentPrice` که در پیشنهاد گزارش آمده وجود ندارد. مشاوره‌ی آنلاین کل مبلغ را همان لحظه می‌گیرد.

**اندپوینت جدید `/OnlineServices` با ساختار پیشنهادی گزارش ساخته نمی‌شود**، چون همان داده با همین اندپوینت موجود است و فقط شکل نمایش فرق دارد.

### ۳-۳) نشان «آنلاین» روی کارت
```
GET /api/EndUser/ConsultationOnline?coachId={id}
GET /api/EndUser/ConsultationOnline?clinicId={id}
```
یا از `companionOnline` در خود آیتم‌ها استفاده کنید.

### ۳-۴) خرید یک ردیف
بدون تغییر. همان اندپوینت قبلی است و فقط `packageId` می‌خواهد. مالک (کلینیک/مربی) را سرور از خود بسته پیدا می‌کند:
```
POST /api/EndUser/ConsultationPurchase   (با توکن)
{ "packageId": 101, "fromWallet": true, "merchantId": null, "rebateCode": null, "scheduledStart": null }
```
- `scheduledStart` فقط برای ردیف‌های `bookable: true` الزامی است.
- بعد از پرداخت، جلسه‌ی چت/تماس (پیام‌ها، `CallHub`) **مثل قبل** ساخته می‌شود. در پاسخ‌های خرید و جلسه، `clinicId` / `coachId` پر است و `companionId` ممکن است `null` باشد.

معیار پذیرش ۳ گزارش (خرید یک ردیف جلسه را مثل قبل می‌سازد) با همین مسیر برقرار است.

## ۴) پرچم `ServiceOnline`
سرور الان در خروجی فهرست و جزئیات کلینیک/مربی، `ServiceOnline` را **محاسبه‌شده** برمی‌گرداند:

> `ServiceOnline = پرچم ذخیره‌شده‌ی مرکز && (بسته‌ی مشاوره‌ی آنلاین فعال با قیمت مثبت دارد || پکیج رزرو با حالت آنلاین Mode=37 دارد)`

بنابراین:
- Coach 2 و 7 درست `true` هستند. بسته‌ی مشاوره دارند، فقط ردیف `Mode=37` ندارند.
- مرکزی که هیچ پیشنهاد آنلاینی ندارد `false` می‌گیرد. معیار پذیرش ۲ برقرار است.
- اپ می‌تواند پنهان‌سازی دستی گزینه‌ی «آنلاین» را بردارد و به همین پرچم اعتماد کند.

## ۵) دو مفهوم جدا: «خدمات آنلاین» در برابر `Mode=37`
گزارش این دو را یکی گرفته است:

| | مشاوره‌ی آنلاین (این کارت) | `Mode=37` روی پکیج رزرو |
|---|---|---|
| جدول | `ConsultationPackage` | `CoachServicePackage` / `ClinicServicePackage` |
| کانال چت/صوتی/تصویری/تلفنی | ✅ دارد (`channelId`) | ❌ ندارد |
| خرید | فوری یا با ساعت (`bookable`)، جلسه‌ی چت/تماس داخل برنامه | رزرو نوبتی عادی مثل حضوری، فقط حالت «آنلاین» |
| اندپوینت | بند ۳ | مسیر رزرو عادی مربی/کلینیک |

ردیف‌های `Mode=37` (مثل «دوره مقدماتی» مربی ۳ و ردیف‌های کلینیک ۵) **عمداً می‌مانند**. معنی‌شان «رزرو نوبتی دوره/خدمت به صورت آنلاین» است و در بخش رزرو عادی نمایش داده می‌شوند، نه در کارت «خدمات آنلاین». کارت «خدمات آنلاین» فقط از بند ۳ پر می‌شود.

## ۶) تغییر آینده که باید از الان در نظر بگیرید
به‌زودی بسته‌های مشاوره‌ی کلینیک/مربی **تأیید ادمین** می‌خواهند. بسته‌ی جدید یا ویرایش‌شده تا تأیید پاستیل در اندپوینت‌های بند ۳ نمی‌آید. سمت مشتری **هیچ تغییری در کد لازم نیست**: سرور خودش فیلتر می‌کند و فقط ممکن است لیست کوتاه‌تر شود. جزئیات سمت نماینده: `CONSULTATION_PACKAGE_APPROVAL_NEMAYANDE_APP_FA.md`.

## ۷) کارهای اپ (چک‌لیست)
1. پروفایل مربی: به‌جای `EndUser/ConsultationPackage?companionId={LegacyCompanionId}` → `GET /api/Coach/{id}/ConsultationPackages`.
2. پروفایل کلینیک: → `GET /api/Clinic/{id}/ConsultationPackages`.
3. نشان آنلاین: `EndUser/ConsultationOnline?coachId=|clinicId=`.
4. مدل‌ها: `companionId` nullable، اضافه کردن `clinicId` و `coachId` (آیتم بسته، خرید، جلسه).
5. کارت را با گروه‌بندی `channelId` بسازید. کانال بدون ردیف نمایش داده نشود.
6. پنهان‌سازی دستی گزینه‌ی «آنلاین» را بردارید و از `ServiceOnline` سرور استفاده کنید.
7. هیچ وابستگی جدیدی به `LegacyCompanionId` برای مشاوره نسازید. برای این بخش کنار گذاشته شده است.

تست سریع (بدون توکن):
```bash
curl https://api.pastil.pet/api/Coach/7/ConsultationPackages
curl https://api.pastil.pet/api/Clinic/5/ConsultationPackages
```
