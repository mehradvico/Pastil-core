# ادمین اصلی (SuperAdmin) و نقش «ادمین»

تاریخ: ۱۴۰۵/۰۸/۲۴ (۲۰۲۶-۱۱-۱۵) — وضعیت: کد نوشته و تست‌شده؛ **دیپلوی نشده، SQL اجرا نشده**.

## مدل جدید

| | قبل | بعد |
|---|---|---|
| نقش RoleId = 2 (در دیتابیس «مدیر اصلی»، Label = `main-admin`) | بدون هیچ مجوزی به همه‌ی endpointهای Admin، همه‌ی تیکت‌ها، چت‌ها و ... | **نقش «ادمین»**: مثل هر نقش دیگر تابع `RolePermission` (فقط ناحیه‌ی Admin)، و به داده‌های محرمانه دسترسی ندارد |
| «ادمین اصلی» | وجود نداشت | **یک نفر** (مهراد حسینی، `09339750767`): بدون هیچ ردیف مجوزی به **همه‌ی** کنترلرها/endpointهای Admin و به همه‌ی داده‌های محرمانه |

نام نمایشی نقش ۲ فقط با SQL عوض می‌شود (`Name = «ادمین»`)؛ `Label` همان `main-admin` می‌ماند چون کد روی Id و Label تکیه دارد.

## هویت ادمین اصلی (`Application/Common/Security/SuperAdminIdentity.cs`)

در دیتابیس ذخیره **نمی‌شود** (نه ستون، نه نقش جدا)؛ با پیکربندی سرور سنجیده می‌شود، پس هیچ باگ mass-assignment یا ویرایش از پنل کسی را ادمین اصلی نمی‌کند. شرط‌ها (همه با هم):

1. موبایل کاربر == `SuperAdmin:Mobile` (در `Api/appsettings.json`؛ با env `SuperAdmin__Mobile` قابل override؛ نرمال‌سازی ۰۹…/+۹۸…/ارقام فارسی)،
2. نقشش «ادمین» (RoleId = 2)،
3. حذف/قفل نشده.

پیکربندی خالی ⇒ ادمین اصلی وجود ندارد (fail-closed). اگر موبایل ادمین اصلی از دیتابیس عوض/حذف شود، دسترسی ویژه‌اش خودبه‌خود قطع می‌شود.

مسیر اعتبارسنجی هر درخواست: `UserService.CheckUserWithIdentityAsync` (از رکورد دیتابیس، نه فقط claim توکن) ← `OnTokenValidatedService` نشانه‌ی `HttpContext.Items["Pastil.SuperAdminVerified"]` را می‌گذارد ← policyها (`AdminArea`، `SuperAdminOnly`) و فیلتر Hangfire همین نشانه را می‌خوانند. همان محاسبه در `CurrentUserDto.IsSuperAdmin` برای سرویس‌ها در دسترس است (هرگز از ورودی کلاینت پر نمی‌شود).

## سخت‌سازی ورود

- ادمین اصلی همیشه باید با **OTP + رمز عبور (۲FA)** وارد شود، حتی اگر `TwoFactorEnabled` پروفایلش خاموش باشد (`SuperAdmin:RequireTwoFactor`، پیش‌فرض `true`).
- اگر رمز عبور برایش تعریف نشده باشد **اصلاً وارد نمی‌شود** (رویداد `super_admin_password_not_set` در audit). ⚠️ قبل از دیپلوی: با همین نسخه‌ی فعلی وارد پنل شوید، رمز عبور و ۲FA را برای حساب فعال کنید.
- `UserDetail` برای او کد `TwoFactor` برمی‌گرداند تا پنل فیلد رمز را نشان دهد.
- ورود به پنل (`isAdmin`/`isSiteAdmin`) برای هر کس جز ادمین اصلی فقط با داشتن مجوز ناحیه‌ی Admin (و برای سایت‌پنل `SiteDashboard`) مجاز است؛ «ادمین» بدون مجوز دیگر وارد پنل نمی‌شود.
- اگر قفل شدید و حساب بسته ماند: env `SuperAdmin__RequireTwoFactor=false` موقتاً شرط ۲FA را برمی‌دارد.

## سطح‌های دسترسی ناحیه‌ی Admin (`AdminAreaAuthorizationConvention`)

- **`SuperAdminOnly`** (حتی «ادمین»ِ دارای مجوز هم رد می‌شود): `Role`، `RolePermission`، `Permission`، `PermissionSync`، `Merchant`، `Wallet`، `ServerMonitoring`، `PushDiagnostics`، و داده‌های محرمانه: `UserMemory` (خاطرات پت‌ها)، `PastilMatchMessage`، `PastilMatchMessageAttachment`، `PastilMatchMessageReaction`، و endpointهای گفتگوی PastilAI (`PastilAI/conversations*`). هم‌چنین `BackgroundTask` و داشبورد Hangfire.
- **`AdminArea`** (بقیه): ادمین اصلی همیشه؛ «ادمین» و بقیه‌ی نقش‌ها فقط اگر ردیف `RolePermission` همان controller/action را داشته باشند. کنترلرهایی که قبلاً «همیشه AdminOnly» بودند و حالا تفویض‌شدنی‌اند: `User`، `Code`، `CodeGroup`، `BaseDetail`، `Notice`، `PushBroadcast`، `MissingProduct`، `ProductImageSuggestion` (سه‌تای آخر همچنان لایه‌ی `AdminOnly` = نقش «ادمین» را هم دارند).
- `AdminOnly` (claim نقش ۲) فقط برای مسیرهای بدون controller/action می‌ماند: هاب SignalR اعلان‌ها و آپلود در سرویس File.

## داده‌های محرمانه (فقط ادمین اصلی)

1. **تیکت‌های پشتیبانی** (`TicketService` / `TicketMessageService`): ادمین اصلی همه‌ی تیکت‌ها را می‌بیند/پاسخ می‌دهد/حذف و واگذار می‌کند. هر ادمین دیگر فقط تیکت‌هایی را می‌بیند که **به او واگذار شده** (`AdminId = خودش`)؛ لیست تیکت‌های پروفایل کاربر هم همین‌طور فیلتر می‌شود، تیکت بدون مسئول را نمی‌بیند و «گرفتن تیکت آزاد» (`TicketAdmin/{id}/Take`) فقط برای ادمین اصلی است. ادمین دیگر وضعیت/اهمیت/واگذاری را فقط روی تیکت خودش عوض می‌کند.
2. **خاطرات پت‌ها** در پروفایل کاربر (`Admin/UserMemory`).
3. **چت‌های خصوصی PastilMatch** (پیام، پیوست، واکنش) و **چت/پیوست/واکنش رزروها** (Clinic، Companion، Coach): میانبر «ادمین همه‌چیز را ببیند» در ۱۲ سرویس از `RoleId == Admin` به `CurrentUser.IsSuperAdmin` تغییر کرد (این سرویس‌ها از مسیر EndUser هم قابل دسترسی‌اند، پس فقط بستن کنترلر کافی نبود).
4. **گفتگوهای PastilAI** (`PastilAI/conversations`).

## حفاظت از خود حساب ادمین اصلی (`Admin/UserController`)

- هیچ‌کس جز خودش حسابش را ویرایش نمی‌کند؛ خودش هم از مسیر پنل نقش، موبایل و قفل حسابش را عوض نمی‌کند (موبایل فقط با OTP از `changeMobile`).
- حذف حساب او از پنل برای همه (حتی خودش) رد می‌شود.
- تغییر `RoleId` هر کاربر و ساخت کاربر با نقش غیر مشتری فقط برای ادمین اصلی (جلوگیری از ارتقای خود به پرقدرت‌ترین نقش توسط یک مدیرِ دارای مجوز «کاربران»).
- ثبت یا تغییر موبایل هیچ حساب دیگری به شماره‌ی ادمین اصلی رد می‌شود.
- هشدار پوش مانیتورینگ سرور فقط به دستگاه‌های ادمین اصلی می‌رود؛ درگاه تستی/پارسیان (`MerchantGatewayRules.IsMainAdmin`) هم فقط برای او.

## ترتیب دیپلوی

1. (قبل از دیپلوی) با نسخه‌ی فعلی وارد پنل شوید و برای حساب مهراد رمز عبور + ۲FA فعال کنید.
2. اجرای `backend/scripts/SuperAdminManagerRole.sql` (گام ۱ نام نقش، گام ۲ اختیاری/توصیه‌شده: دادن مجوزهای فعلی Admin به نقش «ادمین» تا مدیرهای فعلی لحظه‌ی دیپلوی قفل نشوند).
3. دیپلوی Api (و Payment اگر هم‌زمان منتشر می‌شود؛ `appsettings.json` را در publish هم داشته باشد یا env `SuperAdmin__Mobile` را بگذارید).
4. با شماره‌ی `09339750767` (OTP + رمز) وارد پنل شوید؛ در «نقش‌ها» مجوزهای نقش «ادمین» را هرس کنید. بعد از هر دیپلوی که کنترلر جدید اضافه کرد `PermissionSync` را بزنید.

## نکته‌ها و تصمیم‌های قابل تغییر

- `Merchant` و `Wallet` (پول/درگاه) را **ادمین‌اصلی-فقط** نگه داشتم چون قبلاً هم تفویض‌نشدنی بودند؛ اگر مدیرها باید به آن‌ها برسند از `SuperAdminOnlyControllers` برداشته شوند.
- فقط چت‌های خصوصی PastilMatch (پیام/پیوست/واکنش) محرمانه حساب شد؛ گزارش/مسدودسازی/پروفایل PastilMatch و کارت بانکی برای مدیرها باز ماند.
- بقیه‌ی میانبرهای `RoleId == Admin` در سرویس‌های غیرمحرمانه و در مسیرهای ProviderPanelAccess / AreaMembership برای نقش «ادمین» دست‌نخورده ماند.
- پنل/وب‌اپ تغییری نکرد: منو و دکمه‌ها از `PermissionMenu` سمت سرور می‌آید؛ برای «ادمین اصلی» همه‌چیز Granted است. نام نقش از دیتابیس نمایش داده می‌شود.
- بعد از تغییر پیکربندی/نقش، نشست‌های جاری تا نوبت بعدی اعتبارسنجی هر درخواست با دیتابیس دوباره سنجیده می‌شوند (هر درخواست `CheckUser` دارد)، پس نیاز به خروج دستی نیست.
