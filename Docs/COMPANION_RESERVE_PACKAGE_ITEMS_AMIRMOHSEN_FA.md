# تأیید/لغو تکی پکیج‌های رزرو — مستند مو‌به‌مو برای اپ نماینده (امیرمحسن)

> بک پیاده شد، **دیپلوی نشده**. قرارداد کامل و قواعد مالی: [COMPANION_RESERVE_PACKAGE_ITEMS_FA.md](COMPANION_RESERVE_PACKAGE_ITEMS_FA.md)
> پاسخ‌ها **همیشه HTTP 200** با `{ isSuccess, messages, data }`؛ موفقیت را از `isSuccess` بخوانید و خطا را عیناً از `messages[0].item1` نشان دهید. camelCase. همه‌ی endpointها `Authorization: Bearer …`.

## ۱) چه چیزی عوض شد
قبلاً نماینده فقط کل رزرو را می‌توانست لغو کند. حالا در جزئیات هر رزرو **هر پکیج جدا** وضعیت دارد و نماینده می‌تواند:
- **تأیید** کند («این پکیج را در این زمان ارائه می‌دهم»)،
- **لغو** کند (با دلیل)؛ سهم پرداختیِ همان پکیج **خودکار به کیف پول کاربر** برمی‌گردد و کاربر پوش می‌گیرد،
- **پکیج جدید به رزرو اضافه** کند،
- (فقط رزرو پرداخت‌نشده) پکیج را از رزرو **حذف** کند.
لغو کل رزرو مثل قبل است و دست نخورده.

وضعیت هر پکیج: `1` در انتظار تأیید · `2` تأییدشده · `3` لغوشده.

## ۲) دریافت وضعیت پکیج‌ها
`GET /api/Companion/CompanionReservePackage/{reserveId}` — یا همان `PackageItems` داخل `GET /api/Companion/CompanionReserve/{id}` (جزئیات رزرو). ساختار:
```json
{
  "isSuccess": true,
  "data": {
    "reserveId": 123,
    "canManage": true,
    "items": [
      { "id": 55, "packageId": 9, "packageName": "حمام کامل", "petCount": 2, "price": 600000,
        "status": 1, "statusReason": null, "statusChangedDate": null, "statusChangedByAdmin": false,
        "refundAmount": 0, "refundDate": null, "addedAfterPayment": false, "createDate": "2026-10-03T10:00:00" }
    ],
    "summary": { "total": 10, "pending": 6, "approved": 0, "cancelled": 4, "refundedTotal": 400000 }
  }
}
```
- `canManage=false` ⇒ همه‌ی دکمه‌ها را مخفی کنید (رزرو لغو/کامل/نهایی شده یا خدمت انجام شده).
- `items[].id == 0` ⇒ رزرو قدیمی که هنوز ردیف ندارد؛ **همه‌ی عملیات با `packageId` انجام می‌شود، نه `id`**، پس مشکلی نیست.
- یک پکیج ممکن است دو بار بیاید (یک بار لغوشده و بعد دوباره اضافه‌شده)؛ لغوشده‌ها فقط تاریخچه‌اند.

## ۳) صفحه‌ی جزئیات رزرو — چه نشان دهید
بخش «پکیج‌های رزرو»: برای هر آیتم نام، قیمت، تعداد پت و **نشان وضعیت** (زرد «در انتظار تأیید»، سبز «تأییدشده»، قرمز «لغوشده»).
- لغوشده: «دلیل: `statusReason`» و اگر `refundAmount > 0` «{مبلغ} تومان به کیف پول کاربر برگشت».
- `addedAfterPayment=true`: برچسب «افزوده‌شده بعد از پرداخت (پیش‌پرداخت ندارد)».
- بالای لیست خلاصه: «در انتظار X · تأییدشده Y · لغوشده Z».
- دکمه‌ها فقط وقتی `canManage=true` و `status != 3`: «تأیید» (فقط برای `status==1`) و «لغو پکیج».
- یک دکمه‌ی «تأیید همه» می‌توانید سمت اپ بسازید که برای هر پکیج `status==1` یک PUT تأیید بزند.

## ۴) تأیید پکیج
`PUT /api/Companion/CompanionReservePackage/{reserveId}/{packageId}`
```json
{ "status": 2 }
```
پاسخ: `data = { item, refundAmount: 0, reserveCancelled: false, items: {…همان ساختار بالا} }`؛ لیست را از `data.items` تازه کنید. کاربر پوش «نماینده پکیج X را تأیید کرد» می‌گیرد.

## ۵) لغو پکیج (با بازگشت مبلغ)
قبل از ارسال، تأییدیه بگیرید: «پکیج «X» لغو شود؟ سهم پرداختی آن به کیف پول کاربر برمی‌گردد.» و **دلیل را اجباری** کنید (برای کاربر نمایش داده می‌شود، تا ۱۰۰۰ کاراکتر):
```json
{ "status": 3, "reason": "در این ساعت امکان ارائه‌ی این خدمت نیست" }
```
پاسخ موفق: `data.refundAmount` مبلغ برگشتی؛ `data.reserveCancelled=true` یعنی این **آخرین پکیج فعال** بود و **کل رزرو لغو شد** (کل باقی‌مانده برگشت). در این حالت پس از toast به فهرست رزروها برگردید یا صفحه را تازه کنید (وضعیت رزرو `isCancel=true`).
نمایش مبلغ برگشتی به کاربر: «{refundAmount} تومان به کیف پول کاربر برگشت».

خطاهای متداول (`isSuccess:false`، متن را عیناً نشان دهید):
| حالت | پیام |
| --- | --- |
| دلیل خالی | لطفاً دلیل لغو را وارد کنید |
| رزرو لغو/کامل/نهایی شده | این رزرو لغو، کامل یا نهایی شده و پکیج‌هایش دیگر قابل تغییر نیست. |
| رزرو پرداخت‌نشده | تأیید یا لغو پکیج فقط برای رزرو پرداخت‌شده ممکن است. |
| پکیج قبلاً لغو شده / انتقال نامجاز | تغییر وضعیت این پکیج مجاز نیست. |
| ثبت کیف پول ناموفق | بازگشت مبلغ به کیف پول کاربر انجام نشد؛ دوباره تلاش کنید. (هیچ تغییری ثبت نشده؛ می‌شود دوباره زد) |
| دسترسی | شما به این رزرو دسترسی ندارید |

چه کسی مجاز است: مالک کلینیک یا کارشناسی که رزرو به او تخصیص دارد (با عضویت فعال). دیگران `AccessDenied`.

## ۶) افزودن / حذف پکیج
- فهرست پکیج‌های قابل افزودن: همان endpoint فعلی پکیج‌های خدمت (`GET /api/Companion/CompanionAssistancePackage?companionAssistanceId=…`)؛ آن‌هایی که هم‌اکنون «فعال» (غیرلغوشده) در رزرو هستند را از لیست انتخاب بردارید.
- افزودن: `POST /api/Companion/CompanionReservePackage/{reserveId}` با `{ "packageId": 12 }` ⇒ `data` همان ساختار لیست. وضعیت «در انتظار تأیید». اگر رزرو **پرداخت‌شده** باشد پیش‌پرداخت جدیدی گرفته نمی‌شود و قیمت پکیج در مبلغ نهایی خدمت حساب می‌شود (به نماینده بگویید: «در مبلغ نهایی ثبت کنید»). اگر **پرداخت‌نشده** باشد قیمت رزرو بازمحاسبه می‌شود. خدمت‌های «تک‌پکیجی» اجازه نمی‌دهند.
- حذف: `DELETE …/{reserveId}/{packageId}` **فقط برای رزرو پرداخت‌نشده** (و باید حداقل یک پکیج بماند). برای پرداخت‌شده «لغو» کنید تا مبلغ برگردد؛ پیام: «برای رزرو پرداخت‌شده پکیج را حذف نکنید؛ آن را لغو کنید…».

## ۷) تعامل با مبلغ نهایی
- بعد از لغو، `packagePrice`/`paymentPrice` رزرو کم می‌شود و سهم کلینیک بازمحاسبه می‌شود؛ مبلغی که نماینده در «ثبت نتیجه/مبلغ نهایی» وارد می‌کند باید فقط پکیج‌های **تأییدشده/فعال** را پوشش دهد. پیشنهاد: در صفحه‌ی ثبت نتیجه لیست پکیج‌های فعال را کنار فیلد مبلغ نشان دهید.
- لغو تکی ممکن است پس از ثبت مبلغ نهایی/کامل‌شدن رزرو انجام نشود (`canManage=false`).

## ۸) سناریوهای تست (بعد از SQL و دیپلوی)
۱. رزرو پرداخت‌شده با ۳ پکیج ⇒ هر سه «در انتظار»؛ `canManage=true`.
۲. تأیید یکی ⇒ سبز؛ پوش به کاربر.
۳. لغو یکی بدون دلیل ⇒ خطا؛ با دلیل ⇒ قرمز + مبلغ برگشتی؛ کیف پول کاربر زیاد می‌شود.
۴. لغو دومی ⇒ مبلغ از باقی‌مانده‌ی جدید حساب می‌شود؛ لغو سومی (آخرین) ⇒ `reserveCancelled=true` و کل باقی‌مانده برمی‌گردد.
۵. لغو پکیج لغوشده ⇒ خطای «مجاز نیست».
۶. افزودن پکیج به رزرو پرداخت‌شده ⇒ «در انتظار»، «افزوده‌شده بعد از پرداخت».
۷. حذف روی رزرو پرداخت‌شده ⇒ خطا؛ روی پرداخت‌نشده ⇒ موفق.
۸. رزروی که اپراتور «کامل» زده ⇒ `canManage=false` و عملیات رد می‌شود.
۹. رزرو قدیمی (`id=0`) ⇒ همه‌چیز با `packageId` کار می‌کند.

## ۹) چک‌لیست اپ نماینده
- [ ] بخش «وضعیت پکیج‌ها» در جزئیات رزرو با نشان وضعیت، دلیل و مبلغ برگشتی
- [ ] دکمه‌های تأیید / لغو (با دلیل اجباری و تأییدیه) / (اختیاری) تأیید همه، فقط با `canManage` و `status != 3`
- [ ] مدیریت `reserveCancelled=true` (آخرین پکیج) و تازه‌کردن صفحه
- [ ] افزودن پکیج (انتخاب از پکیج‌های خدمت) و حذف برای پرداخت‌نشده
- [ ] نمایش پیام‌های فارسی خطا از `messages`
- [ ] رزرو قدیمی (`id=0`): فقط با `packageId`
- [ ] هماهنگی با «ثبت مبلغ نهایی»: فقط پکیج‌های فعال
- [ ] دیپلوی هم‌زمان با بک (تا SQL اجرا نشود endpointها خطا می‌دهند)
