# تحویل‌گیری سفارش فروشگاهی توسط خود کاربر — قرارداد بک‌اند (مرجع وب‌اپ و اپ فروشنده)

> وضعیت: **بک و پنل ادمین پیاده‌سازی و تست شد (۶۷۶ تست سبز)؛ دیپلوی نشده و SQL اجرا نشده.** تأیید خودکار ۷ روزه هم اضافه شد (بند ۳٫۱).
> مستند تیم‌ها: [وب‌اپ (مشتری + بک‌آفیس فروشنده داخل وب‌اپ)](PRODUCT_ORDER_USER_DELIVERY_WEBAPP_FA.md) · [اپ فروشنده](PRODUCT_ORDER_USER_DELIVERY_SELLER_APP_FA.md)

## ۱) تصمیم محصول

«تحویل داده شد» (نهایی‌شدن سفارش) **فقط دست خود کاربر** است. فروشگاه و ادمین دیگر نمی‌توانند سفارش را «تحویل داده شد» کنند. کاربر در «سفارش‌های من» دو گزینه دارد:

| انتخاب کاربر | اثر |
| --- | --- |
| **تحویل گرفتم** | سفارش همان لحظه `ProductOrderStatus_Delivered` و **نهایی** می‌شود؛ امتیاز باشگاه (مثل قبل با «تحویل داده شد») ثبت می‌شود. غیرقابل برگشت. |
| **تحویل نگرفتم** | فقط ثبت می‌شود (`userReceived: false` + توضیح اختیاری). وضعیت سفارش در **«ارسال شده»** می‌ماند تا فروشگاه/ادمین پیگیری کنند. کاربر تا وقتی نهایی نشده می‌تواند پاسخش را عوض کند (مثلاً بعداً «تحویل گرفتم» بزند). |

فروشگاه (اپ فروشنده/بک‌آفیس) و ادمین (پنل) در فهرست و جزئیات سفارش می‌بینند کاربر «تحویل گرفته / تحویل نگرفته / منتظر پاسخ» است.

## ۲) داده

ستون‌های جدید `ProductOrders` (مایگریشن `AddProductOrderUserDelivery`، اسکریپت `backend/scripts/AddProductOrderUserDelivery.sql`، idempotent):

| ستون | معنی |
| --- | --- |
| `UserReceived bit NULL` | `null` = هنوز پاسخ نداده، `true` = تحویل گرفتم، `false` = تحویل نگرفتم |
| `UserReceivedDate datetime2 NULL` | زمان آخرین پاسخ کاربر (ساعت سرور/ایران؛ بدون آفست در JSON) |
| `UserReceiveNote nvarchar(500) NULL` | توضیح کاربر برای «تحویل نگرفتم» |

## ۳) API

### کاربر: ثبت پاسخ
`PUT /api/EndUser/ProductOrderDelivery` — `Authorization: Bearer …`

```json
{ "id": "5f3c…(guid سفارش)", "received": true, "note": null }
{ "id": "5f3c…", "received": false, "note": "بسته نرسیده؛ پیک تماس نگرفت" }
```

- `id` شناسه‌ی سفارش (**رشته** guid، همان `id` در سفارش‌ها؛ نه `orderCode`).
- `note` اختیاری، حداکثر ۵۰۰ نویسه (بیشتر بریده می‌شود)؛ برای `received:true` نادیده گرفته و پاک می‌شود.
- پاسخ **همیشه HTTP 200** با `{ isSuccess, messages, data }`:
  - موفق: `isSuccess: true`.
  - خطاها (`isSuccess:false`، متن فارسی در `messages`):
    | شرایط | پیام |
    | --- | --- |
    | سفارش مال این کاربر نیست/وجود ندارد | «چیزی یافت نشد» |
    | قبلاً «تحویل گرفتم» زده | «تحویل این سفارش قبلاً توسط شما تأیید شده است.» |
    | سفارش پرداخت‌نشده، لغو شده، یا وضعیتش «ارسال شده» نیست | «تحویل‌گیری فقط برای سفارش پرداخت‌شده‌ی لغو‌نشده‌ای که وضعیتش «ارسال شده» است قابل ثبت است.» |
- ایمن در برابر دوبار کلیک/هم‌زمانی: گذار اتمی؛ دومی یا موفق بی‌اثر یا خطای «قبلاً تأیید شده/قابل ثبت نیست» می‌گیرد.

### خواندن (کاربر، فروشنده، ادمین)
فیلدهای جدید در **همان** پاسخ‌های موجود (فهرست و جزئیات سفارش؛ مشتری: `GET /api/EndUser/ProductOrder[/{id}]`، فروشنده: `GET /api/Seller/ProductOrder…`، ادمین: `GET /api/Admin/ProductOrder[/{id}]`):

| فیلد | معنی |
| --- | --- |
| `userReceived` | `null` / `true` / `false` |
| `userReceivedDate` | زمان پاسخ |
| `userReceiveNote` | توضیح «تحویل نگرفتم» |
| `canConfirmDelivery` | `true` ⇒ **الان** می‌شود پاسخ داد: پرداخت‌شده، لغو‌نشده، وضعیت «ارسال شده»، و هنوز «تحویل گرفتم» نزده. دکمه‌های کاربر را فقط با این فیلد نشان دهید (از ساعت/وضعیت دستگاه حدس نزنید). |

### فیلتر فهرست (فروشنده و ادمین، و کاربر)
پارامتر جدید `userDelivery` روی `GET …/ProductOrder`:

| مقدار | معنی |
| ---: | --- |
| `0` | منتظر پاسخ مشتری (ارسال‌شده، پرداخت‌شده، لغو نشده، هنوز پاسخ نداده) |
| `1` | تحویل گرفته |
| `2` | تحویل نگرفته |
| خالی | همه |


### ۳٫۱) تأیید خودکار بعد از ۷ روز

اگر کاربر **هیچ پاسخی** ندهد، ۷ روز بعد از لحظه‌ای که سفارش «ارسال شده» شد، سیستم خودکار «تحویل گرفتم» را ثبت می‌کند (سفارش «تحویل داده شد» و نهایی؛ امتیاز باشگاه ثبت می‌شود).

- **مبدأ ۷ روز:** `SentDate` = لحظه‌ی ورود به «ارسال شده» (با `ChangeStatus`). ثبت دوباره‌ی همان وضعیت ساعت را عوض نمی‌کند؛ اگر سفارش از «ارسال شده» برگردد (مثلاً «در حال پردازش») ساعت پاک می‌شود و با ارسال دوباره از نو شروع می‌شود.
- **«تحویل نگرفتم» هرگز خودکار تأیید نمی‌شود.** (اختلاف است و پیگیری دستی می‌خواهد.) فقط وقتی `userReceived == null` باشد.
- فقط سفارش پرداخت‌شده و لغو‌نشده؛ گذار اتمی (اگر هم‌زمان کاربر پاسخ بدهد، پاسخ کاربر برنده است).
- **هشدار ۲ روز قبل** (روز ۵): یک پوش `PushProductOrderAutoDeliveryWarning` (۸۸) فقط یک‌بار برای هر سفارش: «سفارش {کد} را تحویل گرفته‌اید؟ اگر تا {تاریخ شمسی} در «سفارش‌های من» پاسخ ندهید، خودکار «تحویل گرفته شد» ثبت می‌شود.»
- **بعد از تأیید خودکار** پوش `PushProductOrderAutoDelivered` (۸۹) به کاربر: «۷ روز از ارسال سفارش {کد} گذشت و پاسخی ثبت نشد؛ خودکار «تحویل داده شد» ثبت شد. اگر بسته را دریافت نکرده‌اید، با پشتیبانی تماس بگیرید.» هر دو مقصد `/orders`.
- **job ساعتی** `ProductOrderAutoDelivery` (Hangfire؛ خودش ثبت می‌شود): (۱) سفارش‌های قدیمیِ «ارسال شده» که `SentDate` ندارند را با «همین لحظه» مهر می‌زند (**روز اول دیپلوی هیچ سفارش قدیمی‌ای یک‌جا خودکار تأیید نمی‌شود؛ ۷ روز از دیپلوی شمرده می‌شود**)، (۲) هشدار می‌فرستد، (۳) تأیید خودکار می‌کند (هر اجرا حداکثر ۱۰۰ سفارش).
- **فیلدهای تازه در DTO:** `userReceivedAuto` (`true` = خودکار ثبت شده؛ `userReceived` هم `true` است)، و `autoConfirmDate` (زمان تأیید خودکار؛ فقط وقتی هنوز منتظر پاسخ است و `SentDate` دارد؛ برای شمارش معکوس «تا X روز دیگر خودکار تأیید می‌شود»).
- ستون‌های جدید: `SentDate datetime2 NULL`، `UserReceivedAuto bit NOT NULL DEFAULT 0` (مایگریشن `AddProductOrderAutoDelivery` + seed پوش‌های ۸۸ و ۸۹: `SeedProductOrderAutoDeliveryPushTypes`؛ اسکریپت **`scripts/AddProductOrderAutoDelivery.sql`** که شامل `AddProductOrderUserDelivery` هم هست؛ یک بار آن را اجرا کنید).
- ثابت‌ها: `ProductOrderDeliveryRules.AutoConfirmAfterDays = 7` و `WarnAfterDays = 5` (تغییرشان یک خط است).

### ۳٫۲) نمایش در صفحه‌ی مالی/تسویه‌ی فروشگاه

`GET /api/Admin/FinanceStore?StoreId=` و `GET /api/Seller/FinanceStore` (همان سرویس) حالا برای هر سفارش در `financeProductOrders` این فیلدها را دارند: `userReceived` (`null`/`true`/`false`)، `userReceivedDate`، `userReceivedAuto` (تأیید خودکار ۷ روزه)، `userReceiveNote`.

- شمارنده‌های جدید در ریشه‌ی پاسخ: `notReceivedCount` (سفارش‌هایی که مشتری «تحویل نگرفتم» زده) و `receivedCount` (تحویل گرفته یا تأیید خودکار)، روی همان فهرست فیلترشده.
- فیلتر جدید `UserDelivery` کنار `Permitted`: `0` منتظر پاسخ (ارسال‌شده و بی‌پاسخ)، `1` تحویل گرفته، `2` تحویل نگرفته.
- **پنل ادمین (انجام شد):** ستون «تحویل‌گیری مشتری» و فیلتر در `finance/store-[id]`؛ هشدار قرمز بالای جدول وقتی `notReceivedCount > 0`؛ در صفحه‌ی ثبت تسویه‌ی فروشگاه (`finance/settlement/new`) هشدار «N سفارش را مشتری تحویل نگرفتم زده؛ پیش از تسویه بررسی شوند».
- **تسویه مانع نمی‌شود:** ثبت تسویه همه‌ی سفارش‌های تسویه‌نشده را شامل می‌شود (مثل قبل)؛ این فقط نمایش و هشدار است، نه قفل. اگر خواستید سفارش‌های «تحویل نگرفتم» از تسویه کنار گذاشته شوند، بگویید تا اضافه شود.
### فروشگاه/ادمین: تغییر وضعیت (تغییر رفتار)
`PUT /api/Seller/ProductOrderChangeStatus` و `PUT /api/Admin/ProductOrderChangeStatus`:

- انتخاب «تحویل داده شد» (`ProductOrderStatus_Delivered`، شناسه‌ی ۱۸) → **رد می‌شود** با «وضعیت «تحویل داده شد» فقط با تأیید خود مشتری ثبت می‌شود؛ فروشگاه و ادمین نمی‌توانند آن را تغییر دهند.»
- سفارشی که کاربر «تحویل گرفتم» زده: تغییر وضعیتش رد می‌شود «مشتری تحویل این سفارش را تأیید کرده است و وضعیت آن دیگر قابل تغییر نیست.»
- وضعیت‌های دیگر (درج، در حال پردازش، ارسال‌شده) مثل قبل. سفارش‌های قدیمی که قبلاً با روش قدیمی «تحویل داده شد» شده‌اند دست‌نخورده‌اند و برای اصلاح قابل تغییرند (فقط اگر `userReceived != true`).

## ۴) قواعد و نکته‌ها

- **«تحویل نگرفتم» نهایی نیست.** سفارش در «ارسال شده» می‌ماند و در فهرست فروشگاه/ادمین باید برجسته (قرمز) شود تا پیگیری شود. هیچ بازپرداخت/لغو خودکاری انجام نمی‌شود؛ رسیدگی دستی با ادمین است (می‌توان از `ProductOrderCancelRequest`/تغییر حالت استفاده کرد).
- **سفارش‌هایی که کاربر هرگز پاسخ نمی‌دهد** بعد از ۷ روز خودکار تأیید می‌شوند (بند ۳٫۱) و امتیاز باشگاه ثبت می‌شود. «تحویل نگرفتم» در «ارسال شده» می‌ماند تا فروشگاه/ادمین پیگیری کنند. تسویه‌ی فروشگاه (`Permitted`) به این فیلد وابسته نیست و مثل قبل ادمین‌محور است؛ نمایش `userReceived` در صفحه‌ی مالی/تسویه‌ی فروشگاه در بند ۳٫۲ آمده است.
- **پوش به فروشگاه هنگام «تحویل نگرفتم»:** نوع `PushProductOrderNotReceivedStore` (۹۰) به همه‌ی کاربران فروشگاه(های) آن سفارش می‌رود: «مشتری ({نام}) سفارش {کد} را تحویل نگرفته است. لطفاً با مشتری تماس بگیرید و پیگیری کنید.» مقصد `/sellerProfile/orders`. یک‌بار برای هر سفارش و هر گیرنده (تغییر توضیح مشتری یا ثبت دوباره پوش تازه نمی‌سازد). best-effort است و ثبت پاسخ مشتری را خراب نمی‌کند. برای ادمین پوش نمی‌رود (در پنل با فیلتر `userDelivery=2` دیده می‌شود).
- برای کاربر هنگام تغییر وضعیت به «ارسال شده» پوش/پیامک قبلی (`PushSentOrderUser`) مثل قبل می‌رود؛ پیشنهاد: متن آن را با «بعد از دریافت بسته در «سفارش‌های من» تحویل را تأیید کنید» تکمیل کنید.
- پنل ادمین: ستون «تحویل‌گیری مشتری» و فیلتر در فهرست سفارش‌ها، کارت «تحویل‌گیری مشتری» در جزئیات (با توضیح کاربر)، و حذف گزینه‌ی «تحویل داده شد» از لیست تغییر وضعیت. (انجام شد.)
