# تأیید ادمین برای بسته‌های مشاوره‌ی آنلاین کلینیک و مربی — راهنمای اپ نماینده

**مخاطب:** توسعه‌دهنده‌ی اپ نماینده (صفحه‌ی «بسته‌های مشاوره‌ی آنلاین» کلینیک/مربی)
**تاریخ:** ۱۴۰۵/۰۸/۰۳ (2026-10-25)
**وضعیت بک‌اند:** کد و تست آماده است، ولی **هنوز روی سرور دیپلوی نشده** (مایگریشن `ConsultationPackageApproved` اجرا نشده). تا اعلام دیپلوی، فیلد `approved` در پاسخ‌ها نمی‌آید؛ اپ باید نبودن این فیلد را تحمل کند (بند ۷).
**پیش‌نیاز:** این مستند ادامه‌ی `CONSULTATION_VENUE_PACKAGES_NEMAYANDE_APP_FA.md` است؛ اندپوینت‌ها، کانال‌ها و قواعد اعتبارسنجی همان‌جا توضیح داده شده و تغییری نکرده‌اند.

---

## ۱) چه چیزی عوض شد (خلاصه)
تا امروز هر بسته‌ای که کلینیک یا مربی می‌ساخت، اگر فعال بود و قیمت داشت، **بلافاصله** برای مشتری نمایش داده و فروخته می‌شد.
از این نسخه:

1. هر بسته‌ی **جدید** کلینیک/مربی در وضعیت **«در انتظار تأیید»** ساخته می‌شود.
2. تا وقتی ادمین پاستیل آن را از پنل تأیید نکند، مشتری آن را **نمی‌بیند و نمی‌تواند بخرد**، حتی اگر نماینده آن را «فعال» کرده باشد.
3. اگر نماینده **محتوای** یک بسته‌ی تأییدشده را تغییر دهد، بسته دوباره به «در انتظار تأیید» برمی‌گردد (فهرست دقیق در بند ۳).
4. بسته‌هایی که **قبل از این نسخه** روی سایت بوده‌اند، خودکار «تأییدشده» حساب می‌شوند و از دید مشتری حذف نمی‌شوند.
5. هیچ اندپوینت جدیدی برای اپ نماینده اضافه نشده؛ فقط یک فیلد **فقط‌خواندنی** به پاسخ اضافه شده است: `approved`.

این تغییر فقط مربوط به بسته‌های **کلینیک (`clinicId`) و مربی (`coachId`)** است. بسته‌های نمایندگی قدیمی (Companion، اندپوینت `Companion/ConsultationPackage`) مثل قبل بدون تأیید منتشر می‌شوند و همیشه `approved = true` دارند.

## ۲) فیلد جدید در پاسخ
اندپوینت‌ها همان قبلی‌اند:

| متد | مسیر |
|---|---|
| GET / POST / PUT / DELETE | `/api/Companion/ClinicConsultationPackage?clinicId=` |
| GET / POST / PUT / DELETE | `/api/Companion/CoachConsultationPackage?coachId=` |

در پاسخ **GET** (فهرست) و پاسخ **POST/PUT** (آیتم ذخیره‌شده)، هر آیتم یک فیلد جدید دارد:

| فیلد | نوع | معنی |
|---|---|---|
| `approved` | `bool` | `true` = ادمین تأیید کرده؛ اگر `active` هم `true` باشد برای مشتری نمایش داده می‌شود. `false` = در انتظار تأیید ادمین؛ مشتری نمی‌بیند. |

نمونه‌ی یک آیتم در پاسخ GET:

```json
{
  "id": 412,
  "channelId": 1,
  "durationMinutes": 30,
  "price": 200000,
  "active": true,
  "approved": false,
  "bookable": false,
  "name": "چت ۳۰ دقیقه",
  "description": "پاسخ‌گویی متنی دامپزشک",
  "pictureId": null,
  "sortOrder": 1,
  "picture": null
}
```

**مهم:** `approved` را **در بدنه‌ی POST/PUT نفرستید**. اگر هم بفرستید سرور نادیده‌اش می‌گیرد. نماینده نمی‌تواند بسته را خودش تأیید کند؛ فقط ادمین از پنل می‌تواند.

ساختار پاسخ مثل همیشه `{ isSuccess, code, messages, data }` با HTTP 200 است؛ `isSuccess` را بخوانید.

## ۳) چه ویرایشی تأیید را از بین می‌برد
وقتی نماینده با `PUT` بسته‌ای را ویرایش می‌کند که الان `approved = true` است:

| تغییر در بدنه‌ی PUT | نتیجه |
|---|---|
| `channelId` (کانال) | دوباره «در انتظار تأیید» |
| `durationMinutes` (مدت) | دوباره «در انتظار تأیید» |
| `price` (قیمت) | دوباره «در انتظار تأیید» |
| `name` (نام) | دوباره «در انتظار تأیید» |
| `description` (توضیح) | دوباره «در انتظار تأیید» |
| `pictureId` (تصویر) | دوباره «در انتظار تأیید» |
| `bookable` (قابل رزرو) | دوباره «در انتظار تأیید» |
| `active` (روشن/خاموش کردن) | **تأیید می‌ماند** |
| `sortOrder` (ترتیب نمایش) | **تأیید می‌ماند** |
| ارسال دوباره‌ی همان مقادیر قبلی بدون هیچ تغییر | **تأیید می‌ماند** |

نکته‌ها:
- مقایسه‌ی نام و توضیح بعد از نرمال‌سازی سرور (حذف فاصله‌ی اول و آخر، یکی کردن فاصله‌های پشت‌سرهم در نام، تبدیل «ي/ك» عربی به «ی/ک» فارسی) انجام می‌شود؛ پس اگر کاربر فقط روی «ذخیره» بزند و چیزی عوض نکند، تأیید نمی‌پرد.
- اگر `bookable` را در بدنه نفرستید (null)، تغییری حساب نمی‌شود.
- بسته‌ای که الان در انتظار تأیید است، با هر ویرایشی همچنان در انتظار می‌ماند.
- سرور پاسخ PUT را با `approved` به‌روز برمی‌گرداند؛ **وضعیت را از پاسخ بخوانید** و حدس نزنید.

## ۴) چه چیزی در اپ باید تغییر کند (کار تیم اپ)

### ۴-۱) فهرست بسته‌ها
برای هر کارت بسته، بر اساس دو فیلد `active` و `approved` یکی از این چهار وضعیت را نشان دهید:

| `active` | `approved` | برچسب پیشنهادی | رنگ پیشنهادی | مشتری می‌بیند؟ |
|---|---|---|---|---|
| `true` | `true` | «فعال» | سبز | ✅ بله |
| `true` | `false` | «در انتظار تأیید پاستیل» | زرد/نارنجی | ❌ نه |
| `false` | `true` | «غیرفعال» | خاکستری | ❌ نه |
| `false` | `false` | «غیرفعال · در انتظار تأیید» | خاکستری | ❌ نه |

متن راهنمای پیشنهادی زیر بسته‌ی در انتظار:
> این بسته پس از بررسی و تأیید پشتیبانی پاستیل برای کاربران نمایش داده می‌شود.

### ۴-۲) بعد از ساخت بسته (POST موفق)
پیام موفقیت را عوض کنید. به‌جای «بسته منتشر شد» بنویسید:
> بسته ذخیره شد و پس از تأیید پاستیل برای کاربران نمایش داده می‌شود.

### ۴-۳) قبل از ویرایش بسته‌ی تأییدشده
اگر کاربر در فرم ویرایش یکی از فیلدهای جدول بند ۳ (به‌جز `active` و `sortOrder`) را عوض کرده، **قبل از ارسال PUT** هشدار بدهید:
> با ذخیره‌ی این تغییرات، بسته تا تأیید دوباره‌ی پاستیل از دید کاربران پنهان می‌شود. ادامه می‌دهید؟

دکمه‌ها: «ذخیره و ارسال برای تأیید» / «انصراف».
برای کلید روشن/خاموش (`active`) و جابه‌جایی ترتیب این هشدار لازم نیست.

### ۴-۴) بعد از ویرایش (PUT موفق)
اگر در پاسخ `approved = false` آمد و قبلاً `true` بود، پیام بدهید:
> تغییرات ذخیره شد و بسته برای تأیید دوباره ارسال شد.

### ۴-۵) به‌روز ماندن وضعیت
تأیید در پنل ادمین اتفاق می‌افتد و **هیچ پوش یا نوتیفیکیشنی برای نماینده ارسال نمی‌شود** (در این نسخه). پس:
- هر بار صفحه‌ی بسته‌ها باز می‌شود، `GET` را دوباره بزنید.
- Pull-to-refresh روی همین صفحه داشته باشید.
- وضعیت را در حافظه‌ی محلی کش نکنید.

### ۴-۶) خلاصه/داشبورد مرکز (اختیاری)
اگر جایی تعداد بسته‌های فعال یا وضعیت «مشاوره‌ی آنلاین فعال است» را نشان می‌دهید:
- «فعال برای مشتری» یعنی فقط `active && approved`.
- اگر مرکز هیچ بسته‌ی `active && approved` ندارد، به نماینده بگویید هنوز چیزی برای مشتری نمایش داده نمی‌شود (مثلاً «بسته‌های شما در انتظار تأیید است»).

## ۵) اثر روی سمت مشتری (برای اطلاع و تست)
بسته‌ای که `approved = false` است:
- در `GET /api/Clinic/{id}/ConsultationPackages` و `GET /api/Coach/{id}/ConsultationPackages` **نمی‌آید**.
- در `EndUser/ConsultationPackage?clinicId=|coachId=` و جست‌وجوی سراسری **نمی‌آید**.
- خرید جدید آن با `EndUser/...` خطای «یافت نشد» (`NothingFound`) می‌دهد.
- رزرو ساعت برای آن (بسته‌های `bookable`) پذیرفته نمی‌شود.
- در محاسبه‌ی نشان «مشاوره‌ی آنلاین دارد» در فهرست کلینیک‌ها/مربی‌ها حساب نمی‌شود.

**خریدها و جلسه‌های قبلی دست‌نخورده‌اند.** اگر ادمین تأیید بسته‌ای را لغو کند یا نماینده آن را ویرایش کند، مشاوره‌هایی که مشتری قبلاً خریده همچنان در صف جلسه‌ها (`/api/Companion/ConsultationSession…`) می‌آیند و باید انجام شوند. هیچ تغییری در صف جلسه‌ها لازم نیست.

---

## ۶) سمت ادمین (برای اطلاع؛ کار اپ نیست)
- مسیر پنل: منوی «خریدهای مشاوره» ← تب «کلینیک/مربی مستقل» ← انتخاب مرکز ← دکمه‌ی «تأیید پکیج» / «لغو تأیید» روی هر بسته.
- اندپوینت ادمین: `PUT /api/Admin/ConsultationVenue/{clinic|coach}/{venueId}/Packages/Approve?id=&approved=true|false` (فقط با دسترسی ادمین؛ اپ نماینده نباید صدا بزند).
- ادمین می‌تواند تأیید یک بسته‌ی فعال را هم لغو کند؛ در آن صورت `approved` در GET بعدی اپ `false` می‌شود. نماینده با ویرایش بسته نمی‌تواند آن را دوباره تأیید کند؛ باید منتظر ادمین بماند.

## ۷) سازگاری با نسخه‌ی فعلی سرور (تا قبل از دیپلوی)
تا وقتی این نسخه روی سرور دیپلوی نشده، فیلد `approved` در پاسخ **وجود ندارد**. برای این‌که اپ با هر دو نسخه‌ی سرور کار کند:
- `approved` را **nullable** (یا با پیش‌فرض) تعریف کنید.
- اگر فیلد نیامد (`null` / missing)، آن را **`true`** در نظر بگیرید، چون رفتار سرور قدیمی «انتشار فوری» است.
- هشدار بند ۴-۳ را فقط وقتی نشان دهید که `approved` واقعاً از سرور آمده باشد.

نمونه (Kotlin):
```kotlin
@Serializable
data class ConsultationPackageItem(
    val id: Long,
    val channelId: Int,
    val durationMinutes: Int,
    val price: Double,
    val active: Boolean,
    val approved: Boolean? = null, // null = سرور قدیمی → تأییدشده فرض شود
    val bookable: Boolean = false,
    val name: String,
    val description: String? = null,
    val pictureId: Long? = null,
    val sortOrder: Int = 0,
)

val ConsultationPackageItem.isApproved get() = approved ?: true
val ConsultationPackageItem.isVisibleToCustomer get() = active && isApproved
```

نمونه (Dart/Flutter):
```dart
final bool approved = json['approved'] as bool? ?? true; // نبودن فیلد = سرور قدیمی
bool get visibleToCustomer => active && approved;
```

## ۸) چک‌لیست تست روی دستگاه (بعد از اعلام دیپلوی)
1. یک بسته‌ی جدید فعال با قیمت بسازید → پاسخ POST باید `approved: false` داشته باشد و کارت «در انتظار تأیید پاستیل» نشان دهد.
2. همان مرکز را در اپ مشتری/وب‌اپ باز کنید → بسته نباید دیده شود.
3. از پنل ادمین بسته را تأیید کنید → در اپ نماینده رفرش کنید → «فعال» شود؛ در اپ مشتری دیده شود.
4. فقط کلید فعال/غیرفعال را بزنید → `approved` باید `true` بماند.
5. قیمت را عوض کنید → هشدار بند ۴-۳ بیاید؛ بعد از ذخیره `approved: false` و بسته از دید مشتری پنهان شود.
6. بدون تغییر چیزی «ذخیره» بزنید → `approved` نباید عوض شود.
7. یک بسته‌ی قدیمی (قبل از دیپلوی) را باز کنید → باید `approved: true` داشته باشد.
8. یک مشاوره‌ی خریداری‌شده‌ی قبلی از بسته‌ای که الان در انتظار تأیید است → باید در صف جلسه‌ها بماند و قابل انجام باشد.

- آیا ادمین باید هنگام رد کردن **دلیل** بنویسد که در اپ نمایش داده شود؟ در این نسخه فقط «تأیید / لغو تأیید» وجود دارد و دلیلی ذخیره نمی‌شود.
