# محصولات ثبت‌نشده در کاتالوگ (`MissingProduct`) — راهنمای اپ فروشنده‌ی فلاتر

Base URL: `https://api.pastil.pet` — همهٔ endpointها `Authorization: Bearer {accessToken}` می‌خواهند.
`StoreId` **همیشه از توکن** گرفته می‌شود؛ هیچ‌جا در بدنه/مسیر نفرستید. پاسخ‌ها همان قالب استاندارد
`{ isSuccess, code, messages, data }` هستند و پیام خطا در `messages[0].item1` (فارسی و قابل‌نمایش مستقیم) است.
تقریباً همیشه HTTP 200؛ فقط `isSuccess`/`code` را بخوانید (استثنا: ۴۰۱ و ۴۱۳).

## ایده در یک نگاه

فروشنده محصولی را که در کاتالوگ پاستیل پیدا نمی‌شود ثبت می‌کند، تکمیلش می‌کند و برای بررسی می‌فرستد.
**وقتی ادمین تأیید کند، دو اتفاق خودکار می‌افتد:**

1. محصول در **کاتالوگ اصلی پاستیل** ساخته می‌شود و برای همه نمایش داده می‌شود — یعنی از آن لحظه
   **هر فروشگاه دیگری هم می‌تواند همان محصول را به فروشگاه خودش اضافه کند** (و در همان اسکن هوشمند
   قفسه هم به‌عنوان کاندید پیدا می‌شود). تصاویر فروشنده (تا ۵ تا) به گالری همان محصول منتقل می‌شوند.
2. همان محصول **به فروشگاهِ ثبت‌کننده هم اضافه می‌شود** (با همان قیمت و موجودی‌ای که فروشنده وارد کرده بود) — به شرط این‌که قیمت (`price`) بزرگ‌تر از صفر داده باشد. اگر قیمت نداده باشد، محصول فقط در کاتالوگ ساخته می‌شود و فروشنده باید مثل هر محصول دیگری خودش موجودی/قیمت ثبت کند.

## چرخهٔ وضعیت (`status`)

| `status` | یعنی | ویرایش/حذف | اقدام مجاز |
|---|---|---|---|
| `draft` | پیش‌نویس (ساخته‌شده از اسکن یا دستی‌ویرایش‌شده) | ✅ | ویرایش، آپلود تصویر، **ارسال**، حذف |
| `submitted` | در صف بررسی ادمین | ❌ قفل | فقط نمایش |
| `approved` | تأیید شد؛ `productId` = محصول ساخته‌شده در کاتالوگ | ❌ | نمایش، باز کردن محصول با `productId` |
| `rejected` | رد شد؛ دلیل در `rejectionReason` | ✅ | ویرایش، (ویرایش آن را به `draft` برمی‌گرداند) بعد **ارسال** دوباره، یا حذف |

قاعدهٔ مهم: **هر `PUT` یا آپلود تصویر روی رکورد `rejected`، آن را خودکار `draft` می‌کند و `rejectionReason` را پاک می‌کند.** یعنی بعد از اصلاح باید دوباره `submit` بزنید.
`submit` فقط از `draft` ممکن است.

| فیلد | نوع | توضیح |
|---|---|---|
| `id` | number | |

## ۰. خلاصهٔ تغییرات این نسخه (برای فرانت)

| تغییر | کار لازم در اپ |
|---|---|
| **تا ۵ تصویر** به‌جای ۱ تصویر؛ فیلد جدید `pictures[]` در پاسخ | گالری چندتصویری (بخش ۴) — **الزامی** |
| `POST /{id}/picture` دیگر **جایگزین نمی‌کند، اضافه می‌کند** | اگر دکمهٔ «تعویض تصویر» دارید: اول `DELETE` بعد `POST` — **الزامی** |
| endpoint جدید `DELETE /{id}/picture/{pictureId}` | دکمهٔ حذف روی هر تصویر — **الزامی** |
| `pictureUrl` همچنان هست و = اولین تصویر | هیچ — سازگار با کد فعلی |
| بعد از تأیید، همهٔ تصاویر به گالری محصول کاتالوگ می‌روند | هیچ (سمت سرور) |
| توضیحات/قیمت/تعداد/برند/سایز از قبل بودند و عوض نشدند | هیچ |

بقیهٔ سند بدون تغییر است.

## ۱. ثبت دسته‌ای (از اسکن قفسه)

```http
POST /api/Seller/MissingProduct
Content-Type: application/json
```

```json
{
  "items": [
    { "name": "شانه پلاستیکی سگ", "brand": "پت‌استایل", "packageSize": "بزرگ", "source": "shelf" }
  ]
}
```

```json
{ "isSuccess": true, "code": 0, "messages": [], "data": { "created": 3, "alreadyKnown": 1 } }
```

- **Idempotent و بدون تکرار:** کلید یکتا = (همین فروشگاه + نام نرمال‌شده). نرمال‌سازی: `ي/ك` عربی ← فارسی، ارقام فارسی/عربی ← لاتین، حذف کامل فاصله/نیم‌فاصلهٔ اضافه، حروف کوچک. یعنی «غذای گربه ۴۰۰ گرم» و «غذاي گربه 400گرم» یک نام حساب می‌شوند. اگر همین فروشگاه قبلاً آن نام را (در **هر** وضعیتی) ثبت کرده باشد، رکورد جدید ساخته نمی‌شود و در `alreadyKnown` می‌شمارد. تکراری داخل خودِ همین درخواست هم `alreadyKnown` است. می‌توانید با خیال راحت اسکن یک قفسه را چندبار بفرستید یا درخواست شکست‌خورده را دوباره بزنید.
- حداکثر **۱۰۰ آیتم**؛ بیشتر ← `isSuccess:false, code:1` (کل درخواست رد می‌شود؛ خودتان تکه‌تکه کنید).
- آیتمی که `name` خالی یا بلندتر از ۲۰۰ کاراکتر دارد **نادیده** گرفته می‌شود و بقیه ثبت می‌شوند (نه در `created` می‌آید نه در `alreadyKnown`).
- `brand`/`packageSize` تا ۱۰۰ کاراکتر (بیشتر بریده می‌شود). `source` خالی = `shelf`.
- رکوردهای ساخته‌شده `draft` هستند و **هنوز برای ادمین دیده نمی‌شوند** تا فروشنده `submit` کند.
- طبق قرارداد قبلی: خطای این endpoint **مانع ادامهٔ اسکن نیست**؛ فقط به فروشنده اطلاع دهید.

## ۲. فهرست

```http
GET /api/Seller/MissingProduct?pageSize=200
```

```json
{
  "isSuccess": true, "code": 0, "messages": [],
  "data": { "items": [ { "id": 12, "name": "…", "status": "draft", "…": "…" } ], "total": 17 }
}
```

جدیدترین اول؛ فقط رکوردهای همین فروشگاه. `pageSize` پیش‌فرض ۲۰۰ و سقف ۲۰۰ است؛ صفحه‌بندی ندارد (`total` تعداد کل است).
چون فعلاً Push برای تأیید/رد وجود ندارد، **هر بار که صفحه باز می‌شود (یا pull-to-refresh)** فهرست را دوباره بگیرید تا `approved`/`rejected` شدن را ببینید.

## ۳. ویرایش

```http
PUT /api/Seller/MissingProduct
Content-Type: application/json
```

```json
{ "id": 12, "name": "شانه پلاستیکی سگ", "brand": "پت‌استایل", "packageSize": "بزرگ",
  "description": "جنس ABS", "price": 250000, "quantity": 12 }
```

- **جایگزینی کامل** فیلدهاست: فیلدی که نفرستید/`null` بفرستید پاک می‌شود. همیشه همهٔ فیلدها را با مقدار فعلی فرم بفرستید.
- `name` الزامی (حداکثر ۲۰۰)، `description` حداکثر ۲۰۰۰، `price ≥ 0`، `quantity ≥ 0` یا `null`.
- تغییر نام دوباره نرمال و چک می‌شود؛ اگر با رکورد دیگرِ همین فروشگاه یکی شود: `isSuccess:false, code:1` با «این نام قبلاً برای فروشگاه شما ثبت شده است.»
- فقط `draft`/`rejected` قابل ویرایش‌اند، وگرنه `code:1` «فقط پیش‌نویس یا درخواست ردشده قابل ویرایش است.»
- پاسخ: **رکورد کامل به‌روزشده** در `data` (با `status` جدید).

## ۴. تصاویر (تا ۵ تصویر) — ⚠️ رفتار عوض شده

> **تغییر مهم برای اپ:** این endpoint قبلاً تصویر قبلی را **جایگزین** می‌کرد و هر درخواست فقط یک
> تصویر داشت. حالا **اضافه** می‌کند و هر درخواست تا **۵ تصویر** می‌گیرد. اگر اپ فعلی برای «تعویض
> تصویر» دوباره همین را صدا می‌زند، از این به بعد تصویر دوم اضافه می‌شود نه جایگزین — برای تعویض
> باید اول `DELETE` بزنید بعد `POST`.

### ۴-۱. افزودن یک تصویر

```http
POST /api/Seller/MissingProduct/{id}/picture
Content-Type: multipart/form-data      (فیلد: image — یک فایل)
```

- هر بار **یک** فایل. برای ۵ تصویر، ۵ بار پشت‌سرهم صدا بزنید (ترتیب فراخوانی = ترتیب نمایش).
- فقط `jpg/jpeg/png/webp`، حداکثر ۸MB، و **محتوای واقعی فایل** بررسی می‌شود (نه فقط پسوند). ناموفق: `code:1` «تصویر معتبر نیست؛ فقط jpg، png یا webp تا ۸ مگابایت.»
- تصویر ششم: `code:1` «حداکثر ۵ تصویر برای هر محصول مجاز است؛ یکی را حذف کنید.» — اپ هم خودش قبلش جلویش را بگیرد.
- خطای آپلود سمت سرور فایل: `code:5` «آپلود تصویر ناموفق بود؛ دوباره تلاش کنید.» — دکمهٔ «تلاش دوباره» بگذارید.
- پاسخ: رکورد کامل با `pictures` به‌روزشده. **فهرست را از پاسخ بخوانید، خودتان محلی نسازید.**
- اپ می‌تواند عکس را قبل از ارسال کوچک کند (ضلع بلند ~۲۰۴۸، JPEG ۸۵) تا آپلود سریع‌تر شود.

### ۴-۲. حذف یک تصویر

```http
DELETE /api/Seller/MissingProduct/{id}/picture/{pictureId}
```

- `pictureId` از `pictures[].pictureId` همان رکورد. تصویری که مال این درخواست نباشد: `code:3` «این تصویر برای درخواست پیدا نشد.»
- پاسخ: رکورد کامل با `pictures` به‌روزشده. اگر اولین تصویر حذف شود، تصویر بعدی خودکار کاور (`pictureUrl`) می‌شود.
- فقط `draft`/`rejected`.

### ۴-۳. نکته‌های UI
- گالری با امکان افزودن/حذف، و شمارنده‌ی «n از ۵».
- تصویر اول به‌عنوان کاور نشان داده شود (همان `pictureUrl`).
- بعد از تأیید ادمین، **همهٔ این تصاویر** به گالری محصول کاتالوگ منتقل می‌شوند، نه فقط کاور.

## ۵. ارسال برای بررسی

```http
POST /api/Seller/MissingProduct/{id}/submit
```

- پیش‌شرط سمت سرور: `name` غیرخالی **و حداقل یک تصویر**؛ وگرنه `code:1` «برای ارسال، تصویر محصول لازم است.» (اپ هم قبلش چک کند: `pictures.isEmpty`.)
- موفق ← `status = "submitted"` و رکورد در صف ادمین ظاهر می‌شود. پاسخ: رکورد کامل.
- اگر قبلاً ارسال شده: `code:1` «این درخواست قبلاً ارسال شده است.»
- توصیه: `price`/`quantity` را **قبل از ارسال** پر کنید؛ ادمین موقع تأیید همین دو مقدار را برای ساخت آیتم فروشگاه استفاده می‌کند و بعد از `submitted` دیگر قابل ویرایش نیستند.

## ۶. حذف

```http
DELETE /api/Seller/MissingProduct/{id}
```

فقط `draft`/`rejected`. رکورد فروشندهٔ دیگر یا ناموجود هر دو دقیقاً `isSuccess:false, code:3` «درخواست یافت نشد.» می‌گیرند. بعد از حذف می‌شود همان نام را دوباره ثبت کرد.

---

## کدهای خطا

| `code` | معنی | مثال پیام |
|---:|---|---|
| 0 | موفق | — |
| 1 | ورودی/وضعیت نامعتبر | «اطلاعات ارسال‌شده معتبر نیست.» / «نام محصول لازم است.» / پیام‌های بالا |
| 3 | یافت نشد (یا متعلق به فروشندهٔ دیگر) | «درخواست یافت نشد.» |
| 5 | خطای موقت (آپلود تصویر) | «آپلود تصویر ناموفق بود؛ دوباره تلاش کنید.» |

## جریان پیشنهادی UI

1. پایان اسکن قفسه: کالاهای «در کاتالوگ نیست» (با `confidence ≥ 0.6` و **بدون** `catalogMatchFailed`) ← `POST /MissingProduct` با `name`/`brand`/`packageSize` (`source:"shelf"`). خطا را فقط اطلاع بدهید. اگر endpoint هنوز روی سرور نیست (`404/405/501`) بی‌صدا رد شوید.
2. صفحهٔ «محصولات ثبت‌نشده»: `GET` فهرست، با نشان وضعیت هر ردیف (`draft` خاکستری، `submitted` زرد، `approved` سبز، `rejected` قرمز + متن `rejectionReason`).
3. فرم ویرایش (`draft`/`rejected`): نام، برند، سایز/وزن، توضیحات و مشخصات، قیمت، تعداد ← `PUT`؛
   سپس گالری تصاویر (تا ۵ تا) با `POST …/picture` برای هر تصویر و `DELETE …/picture/{pictureId}`
   برای حذف ← دکمهٔ «ارسال برای بررسی» (تا وقتی `pictures` خالی است غیرفعال باشد).
4. برای `submitted` فرم را قفل کنید؛ برای `approved` دکمهٔ «مشاهده در کاتالوگ» با `productId`.
5. بعد از `approved` (اگر `price` داده بود) محصول خودبه‌خود در محصولات فروشگاه هم هست؛ فهرست محصولات فروشگاه را دوباره بگیرید.

## آنچه هنوز نیست

- اعلان Push برای تأیید/رد (فعلاً با باز کردن صفحه/pull-to-refresh).
- صفحه‌بندی فهرست.
- **«مشخصات» ساختاریافته** (ویژگی/مقدار مثل ProductFeatureValues کاتالوگ). فعلاً مشخصات داخل
  `description` (تا ۲۰۰۰ کاراکتر) نوشته می‌شود و ادمین موقع تأیید، دسته‌بندی و ویژگی‌های رسمی محصول
  را خودش ست می‌کند. اگر فرم ساختاریافته لازم شد بگویید تا طراحی شود.
- **تغییر ترتیب تصاویر** (drag & drop). ترتیب فعلاً = ترتیب آپلود؛ برای جابه‌جایی باید حذف و دوباره
  آپلود کرد.
