# مستند اپ نماینده: پرونده‌ی پت در مشاوره‌ی آنلاین

**مخاطب:** امیرمحسن — اپ نماینده
**Scope:** پاسخ به این سؤال: «خرید مشاوره هیچ شناسه‌ی پتی ندارد، پس نماینده هنگام مشاوره چطور پرونده/سابقه برای پت می‌نویسد؟»

---

## ۱. تأیید مشاهده‌ی شما

درست دیده بودید: **خرید مشاوره (`ConsultationPurchase`) هیچ‌جا `petId` ندارد** — نه در `ONLINE_CONSULTATION_APP_FA.md`، نه در `NOBES_ONLINE_CONSULTATION_CHAT_CALL_VIDEO_FA.md`، نه در هیچ مستند دیگری، چون واقعاً در دیتابیس هم نیست. کاربر هنگام خرید پکیج مشاوره پتش را انتخاب نمی‌کند؛ فقط روش ارتباط (چت/تماس/ویدیو/تلفن) و مدت را می‌خرد.

**مشکلی که همین بررسی نشان داد:** مسیر نوشتن سابقه (`POST /api/Operator/UserPetRecord`، طبق `NOBES_OPERATOR_PET_MEDICAL_RECORDS_FA.md`) قبل از امروز **فقط** روی `CompanionReserve` (رزرو خدمت حضوری/معمولی) چک می‌کرد. یعنی اگر مشتری‌ای فقط از طریق مشاوره‌ی آنلاین با یک کلینیک در ارتباط بوده و هیچ‌وقت رزرو خدمت معمولی نگرفته، نماینده **اصلاً نمی‌توانست** برای پت او سابقه بنویسد — نه فقط این‌که پت مشخص نبود، بلکه اجازه‌اش هم داده نمی‌شد. این را همین امروز درست کردم.

## ۲. چه چیزی در بک‌اند عوض شد

### ۲.۱ مجوز نوشتن سابقه گسترش یافت
`POST /api/Operator/UserPetRecord` (مسیر و بدنه بدون تغییر) حالا علاوه بر رزرو خدمت، **مشاوره‌ی معتبر** را هم می‌پذیرد:

نماینده می‌تواند برای `userPetId` سابقه بنویسد اگر:
1. (قبلاً بود) یک `CompanionReserve` فعال/لغونشده برای همان پت داشته باشد، یا
2. **(جدید)** صاحب همان پت با همین کلینیک یک خرید مشاوره با وضعیت **پرداخت‌شده / در جریان / پایان‌یافته** داشته باشد، **و** درخواست‌دهنده همان نماینده‌ی شروع‌کننده‌ی آن مشاوره یا مالک کلینیک باشد.

یعنی چون خرید مشاوره پت مشخص ندارد، بک‌اند محدودش نمی‌کند به یک پت خاص — **هر پتی که مال همان مشتری باشد** قابل نوشتن است، و خود نماینده حین گفتگو با مشتری تشخیص می‌دهد سابقه مال کدام پت است.

### ۲.۲ لیست پت‌های مشتری به «مشاوره‌های من» اضافه شد
تا امروز `GET /api/Companion/ConsultationSession` هیچ اطلاعاتی از پت‌های مشتری نمی‌داد. حالا هر آیتم فیلد جدید `customerPets` دارد:

```jsonc
{
  "id": 501,
  "purchaseCode": "CNS-...",
  "userId": 88,
  "userFullName": "سارا محمدی",
  "customerPets": [
    { "userPetId": 12, "name": "نودل", "petName": "سگ", "picture": { "url": "..." } },
    { "userPetId": 34, "name": "میشا", "petName": "گربه", "picture": null }
  ],
  ...
}
```
`customerPets` **همه‌ی** پت‌های ثبت‌شده‌ی آن کاربر است (نه فقط پت‌هایی که قبلاً رزرو داشته‌اند)، چون هدف این است که نماینده در همان لحظه‌ی مشاوره پت درست را از یک لیست انتخاب کند، نه این‌که با کیبورد شناسه بزند.

## ۳. فلوی پیشنهادی برای UI

1. نماینده مشاوره را باز می‌کند (`GET /api/Companion/ConsultationSession`).
2. در صفحه‌ی مشاوره، کنار نام مشتری، لیست `customerPets` را نشان بده (چیپ یا دراپ‌داون کوچک — «این مشاوره برای کدام پت است؟»).
3. اگر مشتری فقط یک پت دارد، همان را پیش‌فرض انتخاب‌شده نشان بده؛ اگر چند پت دارد، نماینده حین گفتگو می‌پرسد و انتخاب می‌کند.
4. بعد از تشخیص پت، سابقه را عادی ثبت کن:
   ```http
   POST /api/Operator/UserPetRecord
   { "userPetId": 12, "name": "توضیح سابقه‌ی مشاهده‌شده در مشاوره..." }
   ```
   چیزی درباره‌ی این‌که این سابقه از مشاوره آمده لازم نیست بفرستی؛ سرور خودش مجوز را طبق بند ۲.۱ بررسی می‌کند.
5. اگر `customerPets` خالی بود (مشتری هنوز هیچ پتی ثبت نکرده)، دکمه‌ی «ثبت سابقه» را غیرفعال کن و پیام بده «مشتری هنوز پتی ثبت نکرده است» — سرور هم در این حالت چون `userPetId` معتبری وجود ندارد، `AccessDenied` می‌دهد.

## ۴. چیزهایی که عوض *نشده*

- خرید مشاوره همچنان `petId` ندارد و قرار نیست داشته باشد — این یک تصمیم طراحی عمدی است (کاربر موقع خرید مشاوره لازم نیست پت را انتخاب کند)، نه چیزی که فراموش شده باشد.
- `GET /api/Companion/CompanionReserve/{reserveId}` (منبع پت برای رزرو خدمت معمولی، طبق `NOBES_OPERATOR_PET_MEDICAL_RECORDS_FA.md`) بدون تغییر است؛ آن‌جا همچنان پت از خودِ رزرو می‌آید، نه از این مسیر.
- محدودیت پانسیون که در همان سند قبلی گفته شده بود («فقط CompanionReserve چک می‌شود، نه PansionReserve») هنوز پابرجاست — این تغییر فقط مشاوره را اضافه کرد، پانسیون را نه.

## ۵. سناریوی تست
1. مشتری‌ای که **فقط** یک مشاوره‌ی پرداخت‌شده دارد (هیچ `CompanionReserve`ای ندارد) ← نماینده‌ی همان کلینیک `GET /api/Companion/ConsultationSession` را بزند ← `customerPets` پر باشد.
2. همان نماینده برای یکی از آن پت‌ها `POST /api/Operator/UserPetRecord` بزند ← موفق.
3. نماینده‌ی کلینیک دیگر (بدون مشاوره یا رزرو مشترک با آن مشتری) همان درخواست را بزند ← `AccessDenied`.
4. مشاوره‌ی لغوشده/منقضی/بازپرداخت‌شده (نه Paid/Active/Completed) ← نوشتن سابقه مجاز نیست.
5. مشتری بدون هیچ پتی ← `customerPets` خالی، دکمه‌ی ثبت در UI غیرفعال شود.

## وضعیت بیلد
بک‌اند بدون خطا بیلد شد و همه‌ی ۵۶۲ تست موجود سبز است. **مایگریشن یا تغییر دیتابیس لازم نبود** — فقط منطق مجوز و یک فیلد جدید در پاسخ API.
