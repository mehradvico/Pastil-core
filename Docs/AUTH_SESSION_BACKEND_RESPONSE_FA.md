# پاسخ بک‌اند: نشست، توکن و refresh (ورود با دستگاه دوم)

تاریخ: ۱۴۰۵/۰۷/۱۵ (۲۰۲۶‑۱۰‑۰۷). همه‌ی موردها از روی کد بک‌اند چک شده؛ لاگ و نمونه‌ی واقعی بررسی نشده.

## خلاصه
- بک‌اند **تک‌نشستی** است و ابطال **همان لحظه** اعمال می‌شود؛ نیازی به `sid` جدا نیست.
- یک **باگ واقعی بک‌اند** پیدا و رفع شد: دستگاهی که با ورود دستگاه دیگر بیرون افتاده بود، با اولین refresh خودش «سرقت توکن» حساب می‌شد و **نشست تازه‌ی دستگاه دوم را هم می‌کُشت.**
- **علت چرخیدن آزادانه‌ی لپ‌تاپ در بقیه‌ی صفحه‌ها، وب‌اپ است نه بک‌اند:** روت‌های BFF عمومی (مثل `banner`، `product`، ...) اصلاً توکن را به بک‌اند نمی‌فرستند، پس هرگز ۴۰۱ نمی‌بینند.

## الف) ورود با دستگاه دوم چه می‌کند؟
- `ResetTokenAsync` در هر ورود، **همه‌ی ردیف‌های `UserTokens` هم‌نوع** (غیرپنل با غیرپنل، پنل با پنل) را `Deleted` می‌کند. هر ردیف هم access و هم refresh را نگه می‌دارد (هش)، پس **هر دو** باطل می‌شوند.
- وب‌اپ و موبایل هر دو «غیرپنل» حساب می‌شوند → ورود موبایل، لپ‌تاپ را باطل می‌کند. ادمین پنل جدا و از وب‌اپ مستقل است.
- هر درخواست احرازشده در `OnTokenValidated → CheckUser` هش توکن را در دیتابیس می‌سنجد. توکن `Deleted` **فوراً ۴۰۱** می‌گیرد (تا `exp` منتظر نمی‌ماند). تنها استثنا: توکنی که با refresh تازه rotate شده و جانشین زنده‌اش کمتر از ۱۵ ثانیه پیش ساخته شده (برای درخواست‌های موازی در راه)؛ ورود دستگاه دوم جانشین نمی‌سازد، پس این مهلت شامل آن نمی‌شود.
- پس لازم نیست `CurrentUser` شناسه‌ی نشست جدا بسنجد: خودش همین کار را انجام می‌دهد.

## ب) رد شدن refresh ← ۴۰۱ (انجام شد)
`POST api/Account/refreshtoken`:
| وضعیت | قبل | حالا |
|---|---|---|
| refresh/توکن منقضی، باطل، استفاده‌شده، نشست بسته‌شده، سرقت | HTTP ۲۰۰ + `isSuccess:false` | **HTTP ۴۰۱** + همان بدنه‌ی `BaseResultDto` |
| بدنه‌ی ناقص (`token` یا `refreshToken` خالی) | ۵۰۰ (NullReference) | **HTTP ۴۰۰** |
| خطای موقت سرور | ۵۰۰ | ۵۰۰ |
پنل (`useApi.ts`) هر ۴۰۰/۴۰۱/۴۰۳ را «شکست قطعی نشست» می‌داند و وب‌اپ هر دو شکل را می‌شناسد. **اپ‌های فلاتر را باید بررسی کنند** که refresh با ۴۰۱ را هم «نشست تمام شد» بخوانند (قبلاً ۲۰۰ با `isSuccess:false` بود).

## پ) چرخش refresh و رقابت هم‌زمان
- refresh token **یک‌بارمصرف** است (rotation در تراکنش Serializable) و **reuse detection دارد.**
- مهلت رقابت بی‌ضرر ۱۵ ثانیه است (`TokenRotationPolicy.GracePeriod`): اگر همان refresh token ظرف ۱۵ ثانیه بعد از rotate دوباره بیاید (دو تب/درخواست هم‌زمان از همان دستگاه)، یک توکن تازه‌ی هم‌زنجیره صادر می‌شود (idempotent)، نه باطل کردن نشست.
- **باگی که رفع شد:** ردیف `Deleted` دو علت دارد: ۱) rotate شده با refresh (جانشین دارد)، ۲) باطل‌شده با خروج/ورود دستگاه دیگر (جانشین ندارد). کد قبلی هر دو را «استفاده‌ی مجدد» می‌دانست. پس لپ‌تاپ بعد از ورود موبایل، با refresh خودش «سرقت» تشخیص داده می‌شد و **همه‌ی نشست‌های کاربر (از جمله موبایل) باطل می‌شد** + هشدار امنیتی کاذب. حالا (`RefreshReuseRules`):
  - بدون جانشین → فقط همان درخواست رد می‌شود: «نشست شما پایان یافته است (خروج یا ورود از دستگاه دیگر)؛ دوباره وارد شوید.» (۴۰۱)، نشست دستگاه دوم دست‌نخورده می‌ماند.
  - با جانشین، ظرف مهلت و همان دستگاه → توکن تازه (رقابت بی‌ضرر).
  - با جانشین، بیرون مهلت یا دستگاه متفاوت → سرقت: همه‌ی نشست‌ها باطل (مثل قبل).

## ت) یکدستی ۴۰۱
هر توکن ارائه‌شده (حتی روی endpoint عمومی) اعتبارسنجی می‌شود و توکن منقضی/نامعتبر/باطل ۴۰۱ می‌دهد؛ ۴۰۳ فقط برای «کاربر شناخته‌شده ولی بدون مجوز» (در ناحیه‌ی Admin). مجموعه‌ی اندازه‌گیری شما با کد هم‌خوان است.
**ولی** endpoint عمومی بدون توکن همیشه ۲۰۰ است، و روت‌های BFF عمومی وب‌اپ توکن را نمی‌فرستند (نمونه: `app/server/api/banner/banner.get.js` هیچ `Authorization` ندارد؛ ۱۱۰ روت GET از ۱۹۹ تا هم بدون آن‌اند). پس برای لپ‌تاپِ باطل‌شده، خانه/فروشگاه/کلینیک هیچ‌وقت ۴۰۱ نمی‌بینند و فقط اولین درخواست احرازشده (مثل پروفایل) نشست را آشکار می‌کند. این وب‌اپ است؛ راه‌حل: وب‌اپ در ناوبری، `CurrentUser` را (بدون حافظه‌ی ۳۰ ثانیه‌ای) یک‌بار بعد از هر بازگشت به تب بسنجد، یا روی لپ‌تاپ polling سبک `CurrentUser` داشته باشد.

## ث) طول عمر توکن‌ها (مقادیر فعلی)
| مورد | مقدار |
|---|---|
| access token (کاربر و ادمین) | **۱۰۰ دقیقه** |
| refresh token (وب‌اپ/اپ؛ غیرپنل) | **۵۲۵٬۶۰۰ دقیقه = ۱ سال** (نشست ماندگار؛ ورود غیرپنل همیشه `rememberMe=true`) |
| refresh پنل با «مرا به خاطر بسپار» | ۱۰٬۰۸۰ دقیقه = ۷ روز |
| refresh پنل بدون آن | ۲۰۰ دقیقه |
| `ClockSkew` | ۳۰ ثانیه |
access هیچ‌وقت دیرتر از refresh منقضی نمی‌شود.

## ج) تست پذیرش (طبق سند شما)
۱) لپ‌تاپ وارد شود، سپس موبایل با همان شماره. ۲) روی لپ‌تاپ هر صفحه‌ی **احرازشده** (یا هر درخواست با توکن) ۴۰۱ می‌گیرد؛ refresh لپ‌تاپ **۴۰۱ با پیام «نشست پایان یافته»** می‌دهد و **موبایل سالم می‌ماند** (قبلاً می‌پرید). ۳) چند refresh هم‌زمان با یک refresh token: همه توکن می‌گیرند، نشست باطل نمی‌شود.

## د) برای بررسی لاگ (انجام نشد)
نیاز است زمان و شماره‌ی نمونه‌ی واقعی را بدهید. در لاگ امنیتی دنبال `RefreshTokenTheft` با detail `reuse_outside_grace_all_sessions_revoked` برای همان کاربر بگردید؛ اگر بعد از ورود دستگاه دوم دیده شود، همین باگ بوده. بعد از دیپلوی، حالت جدید با `RefreshToken` و detail `session_already_ended_no_successor` ثبت می‌شود.
