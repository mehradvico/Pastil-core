# تنوع محصول و قیمت/موجودی فروشنده — راهنمای اپ (وضعیت نهایی بک‌اند)

این سند **جایگزین بخش‌های طراحی** در `BACKEND_PRODUCT_VARIETY_MIGRATION_FA.md` است. آن سند فرض می‌کرد فروشنده نوع تنوع را انتخاب می‌کند و مقدار
جدید می‌سازد؛ تصمیم نهایی محصول این نیست. آنچه اینجا آمده **در بک‌اند پیاده و deploy شده** است (روی دیتابیس واقعی هنوز تست دستی کامل نشده؛ بخش ۸).

Base URL: `https://api.pastil.pet` — همه‌ی endpointها `Authorization: Bearer {accessToken}`.
پاسخ‌ها قالب استاندارد `{ isSuccess, code, messages, data }` و تقریباً همیشه HTTP 200؛ پیام خطا در `messages[0].item1` (فارسی، قابل نمایش مستقیم).
`StoreId` **همیشه از توکن** گرفته می‌شود؛ هیچ‌جا نفرستید.

---

## ۱. جریان نهایی محصول

1. **ادمین** نوع(های) تنوع محصول را تعیین می‌کند (مثلاً «رنگ»، «وزن»؛ حداکثر دو تا) و **مقدارها** را به مخزن هر تنوع اضافه می‌کند (قرمز، سبز، ۱ کیلو…).
2. **فروشنده تنوع یا مقدار جدید نمی‌سازد.** فقط از مقدارهای موجودِ همان محصول انتخاب می‌کند و برای هر ترکیبِ انتخاب‌شده **قیمت و موجودی** می‌دهد
   (یک `ProductItem` به‌ازای هر فروشگاه × مقدار ۱ × مقدار ۲).
3. محصول بدون تنوع ⇒ فقط یک سطر با `varietyItemId = null`.
4. **موجودی ۰ = ناموجود** (آیتم ساخته می‌شود؛ قیمت مهم نیست). **«ندارمش» = `active:false`** برای همان سطر.

## ۲. Endpointها

### ۲-۱. ساختار تنوع محصول (جدید)
```http
GET /api/Seller/ProductVariety?productId=5231
```
```json
{ "isSuccess": true, "code": 0, "messages": [],
  "data": {
    "productId": 5231,
    "variety":  { "id": 3, "name": "رنگ", "label": "color",
                  "values": [ { "id": 10, "name": "قرمز", "label": "red" }, { "id": 11, "name": "سبز", "label": "green" } ] },
    "variety2": null
  } }
```
- `variety: null` ⇒ محصول بدون تنوع؛ UI فقط یک ردیف قیمت/موجودی نشان دهد.
- `variety2` فقط وقتی محصول دو تنوع دارد پر است.
- محصول یافت نشد ⇒ `isSuccess:false` با پیام «دیتا استباه است».

### ۲-۲. فرم قیمت‌گذاری (قدیمی + دو پارامتر اختیاری جدید)
```http
GET /api/Seller/ProductItem/id?id=5231&varietyItemIds=10,11&variety2ItemIds=
```
- بدون `varietyItemIds`/`variety2ItemIds` ⇒ **رفتار قبلی**: همه‌ی ترکیب‌های ممکن (حاصل‌ضرب کامل مقدارها).
- با آن‌ها (id جداشده با کاما) ⇒ فقط ترکیب‌های همان مقدارها **به‌علاوه‌ی آیتم‌های موجودِ همین فروشگاه** (که هیچ‌وقت از فرم حذف نمی‌شوند تا فروشنده بتواند غیرفعالشان کند).
- شکل پاسخ عوض نشده: `data.productItems[]` با فیلدهای `varietyItemId`، `varietyItem2Id`، `varietyItem{id,name,…}`، `basePrice`، `quantity`، `active`، `warranty`، `id` (اگر قبلاً ساخته شده).

توصیه‌ی UI: ابتدا `ProductVariety` را بگیرید، مقدارها را با چک‌باکس نشان دهید، سپس فرم را با مقدارهای انتخاب‌شده بخواهید (یا خودتان سطرها را بسازید).

### ۲-۳. ثبت (بدون تغییر در JSON)
```http
POST /api/Seller/ProductItem
```
```json
{ "productId": 5231,
  "productItems": [
    { "varietyItemId": 10, "varietyItem2Id": null, "basePrice": 250000, "quantity": 12, "active": true,  "warranty": "" },
    { "varietyItemId": 11, "varietyItem2Id": null, "basePrice": 250000, "quantity": 0,  "active": true,  "warranty": "" },
    { "varietyItemId": 12, "varietyItem2Id": null, "basePrice": 0,      "quantity": 0,  "active": false, "warranty": "" }
  ] }
```
قواعد جدید سمت سرور:

| وضعیت سطر | نتیجه |
|---|---|
| `basePrice > 0` و `quantity ≥ 0`، آیتم قبلاً نبوده | **آیتم ساخته می‌شود** (با `quantity:0` = ناموجود). قبلاً `quantity > 0` لازم بود. |
| آیتم از قبل هست | قیمت، موجودی و `active` به‌روز می‌شود (موجودی ۰ مجاز). |
| `basePrice = 0` و آیتم قبلاً نبوده | ساخته **نمی‌شود** (سطر خالی؛ بدون خطا). |
| `basePrice` یا `quantity` منفی | کل درخواست رد؛ «دیتا استباه است». |
| `varietyItemId`/`varietyItem2Id` متعلق به تنوع همین محصول نیست، یا محصولِ بدون تنوع مقدار گرفته، یا محصولِ دارای تنوع بدون مقدار آمده | **کل درخواست رد** و هیچ سطری ذخیره نمی‌شود: «مقدار تنوع انتخاب‌شده برای این محصول معتبر نیست.» |

پس اپ نباید سطرِ مقدارِ نامربوط بفرستد (مثلاً مقدار قدیمیِ کش‌شده). اگر این خطا آمد، ساختار را دوباره با ۲-۱ بگیرید.

## ۳. تأثیر روی جریان «درخواست افزودن به کاتالوگ» (`MissingProduct`)
- محصولِ تأییدشده **بدون تنوع** ساخته می‌شود و آیتم فروشگاه با `varietyItemId = null` ثبت می‌شود.
- **تغییر نسبت به قبل:** اگر فروشنده قیمت داده ولی موجودی نداده/۰ بود، آیتم فروشگاه حالا **ساخته می‌شود (ناموجود)**؛ قبلاً بی‌صدا ساخته نمی‌شد (`storeItemCreated:false`).
- اگر ادمین بعد از تأیید برای آن محصول تنوع تعیین کند، آیتمِ بدون‌مقدارِ فروشنده (چون معتبر نیست) کنار می‌رود و فروشنده باید دوباره با مقدارها قیمت بدهد. (اگر فروشنده‌ای از قبل آیتم **با مقدار** داشته باشد، ادمین اصلاً اجازه‌ی تغییر ندارد — بخش ۴.)

## ۴. آنچه ادمین دیگر نمی‌تواند (به اپ مربوط است چون فروشنده ممکن است بعداً خطای مرتبط ببیند)
- **حذف مقدار تنوع** که در آیتم فعالِ فروشنده‌ای یا در سفارش‌ها استفاده شده ⇒ رد.
- **حذف نوع تنوع** که روی محصولی تنظیم شده یا مقدارهایش استفاده شده ⇒ رد.
- **حذف/جایگزینی/جابه‌جایی تنوع یک محصول** یا **افزودن تنوع دوم** وقتی فروشنده‌ای برای آن آیتم با مقدار دارد ⇒ رد («فروشنده‌ای برای این محصول با تنوع فعلی آیتم ثبت کرده است؛ …»). قبلاً این کار آیتم‌های همه‌ی فروشگاه‌ها را بی‌صدا پاک می‌کرد.
- **افزودن مقدار جدید به مخزن یک تنوع** همیشه آزاد است؛ فروشنده بعد از آن می‌تواند برای مقدار جدید آیتم بسازد.
- ویرایش عادی محصول دیگر `VarietyId`/`Variety2Id` را عوض نمی‌کند (فقط با `ProductChangeVariety`).

نتیجه برای اپ: ساختار تنوع محصولی که خودتان روی آن آیتم دارید زیر دست شما عوض نمی‌شود؛ فقط ممکن است **مقدار جدید** اضافه شود.

## ۵. صفحه‌ی محصول مشتری
قرارداد عوض نشده. فقط سخت‌تر شده: آیتمِ بی‌مقدار روی محصولِ دارای تنوع (داده‌ی قدیمی) نمایش داده نمی‌شود و `varietyItem1Id` نامعتبر به‌جای خطای ۵۰۰ به اولین مقدار موجود برمی‌گردد.

## ۶. آنچه از سند قبلی دیگر معتبر نیست
- انتخاب نوع تنوع توسط فروشنده و «قفل» آن (R1/R5)، `PUT api/Seller/ProductVariety`.
- افزودن مقدار توسط فروشنده (`POST api/Seller/VarietyItem`)، `CreatedByStoreId`، کد 409 «تکراری».
- Migration (`NormalizedName`، unique index) — **هیچ تغییر دیتابیسی انجام نشد.**
- سقف بسته‌ها/مخزن مشترک قابل‌ساخت توسط فروشگاه‌ها.

## ۷. دو تصمیم قبلاً باز، حالا انجام شده
1. **ساخت محصول توسط فروشنده (`POST api/Seller/ProductAdmin`):** `varietyId` و `variety2Id` بدنه **نادیده گرفته می‌شوند** (محصول بدون تنوع ساخته می‌شود)؛
   نوع تنوع را فقط ادمین تعیین می‌کند. اگر اپ این فیلدها را می‌فرستد، خطا نمی‌گیرد ولی اثری هم ندارد.
2. **یکتایی نام مقدار (ادمین، `Admin/VarietyItem`):** حالا **داخل همان تنوع** و با نرمال‌سازی املایی بررسی می‌شود
   (فاصله/نیم‌فاصله، ی/ک عربی، ارقام فارسی/لاتین، حروف بزرگ/کوچک، «آبی» = «ابی»). «قرمز» در دو تنوع مختلف مجاز است؛
   ردیف حذف‌شده مانع نیست؛ نامی که هیچ حرف/رقمی ندارد رد می‌شود. مترادف‌ها («قرمز»/«سرخ») همچنان کار ادمین است.
   ردیف‌های تکراریِ قدیمی همچنان قابل ویرایش‌اند (بررسی فقط وقتی نام یا تنوع عوض شود انجام می‌شود). به اپ ربطی ندارد.

## ۷-۱. هنوز باز (فقط تیم اپ)
- **`AiProductMatch`:** `matches[].packages` فقط از آیتم‌های **موجود** ساخته می‌شود؛ برای محصولی که هنوز هیچ فروشنده‌ای آیتم نساخته خالی است.
  گزینه‌ها: (الف) اپ خودش با `GET Seller/ProductVariety` گزینه‌ها را بسازد (الان ممکن است، بدون تغییر بک‌اند)؛ (ب) بک‌اند بسته‌ها را از «تعریف محصول» بسازد
  (شکل JSON همان می‌ماند). کدام؟

## ۸. تست پیشنهادی روی staging (اپ + بک‌اند)
1. محصول بدون تنوع: ثبت با `quantity:0` و قیمت مثبت ⇒ آیتم ساخته می‌شود و «ناموجود» است.
2. محصول با تنوع: `GET ProductVariety`، انتخاب دو مقدار، ثبت؛ مقدار سوم (انتخاب‌نشده) آیتم نمی‌سازد.
3. ثبت با `varietyItemId` متعلق به تنوعِ دیگر ⇒ خطای «معتبر نیست» و هیچ‌چیز ذخیره نمی‌شود.
4. ثبت `active:false` برای ترکیبی که قبلاً ثبت شده ⇒ از صفحه‌ی مشتری کنار می‌رود.
5. ادمین: حذف مقدارِ استفاده‌شده و تغییر تنوع محصولِ دارای آیتم ⇒ رد؛ افزودن مقدار جدید ⇒ موفق و برای فروشنده قابل‌انتخاب.
6. `MissingProduct`: تأیید با قیمت و بدون موجودی ⇒ `storeItemCreated:true`.
