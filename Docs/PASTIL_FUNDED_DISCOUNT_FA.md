# تخفیف محصول: سهم فروشگاه و سهم پاستیل (حسابداری دقیق) — مستند

> این سند **مرجع بک** است (برای وب‌اپ و اپ نماینده سند جدا هست؛ بخش ۷). وضعیت: **بک و پنل ادمین پیاده و تست شد، دیپلوی نشده.** ترتیب: اول SQL `backend/scripts/PastilFundedDiscount.sql` (کاربر اجرا کند)، بعد Api (و Payment)، بعد پنل/وب‌اپ.
> تست‌ها: `Application.Tests/PastilFundedDiscountTests.cs` (روی LocalDB واقعی، شامل اجرای خودِ procedure).

## ۱) مدل

تخفیفِ محصول **دو لایه‌ی مستقل** دارد:

| لایه | چه کسی می‌سازد | سقف | هزینه با |
| --- | --- | --- | --- |
| تخفیف **فروشگاه** | خود فروشگاه (پنل فروشنده) یا ادمین | هر درصدی (۱ تا ۹۹) | **فروشگاه** |
| تخفیف **سهم پاستیل** | **فقط ادمین** (`FundedByPastil=true`) | درصدِ آن ≤ «سهم پاستیل از فروش» (`Store.CommissionPercent`) همان فروشگاه | **پاستیل** |

- لایه‌ها به هم ربطی ندارند؛ **اول** تخفیف فروشگاه روی قیمت پایه، **بعد** تخفیف پاستیل روی «قیمتِ بعد از تخفیف فروشگاه»:
  `قیمت نهایی = پایه × (۱ − فروشگاه٪) × (۱ − پاستیل٪)`
- هر لایه جدا «بیشترین ردیف فعال» را برمی‌دارد (مثل قبل که فقط یک تخفیف می‌آمد). فروشگاه ۱۵٪ + پاستیل ۸٪ ⇒ نه ۱۵ و نه ۲۳، بلکه `۱ − ۰٫۸۵×۰٫۹۲ = ۲۱٫۸٪` (در کالا به‌صورت `discountPercent = ۲۲` گرد نمایش داده می‌شود؛ قیمت دقیق است).
- **کد تخفیف (Rebate) و تخفیف ارسال باشگاه** از قبل کاملاً هزینه‌ی پاستیل‌اند (مبنای کمیسیون فروشگاه `PaymentPrice` فروشگاه است و از Rebate کم نمی‌شود)؛ تغییری نکرد و فقط فروشگاه‌ها نمی‌توانند Rebate بسازند.

## ۲) حسابداری سفارش (دقیقاً چه چیزی ثبت می‌شود)

برای هر فروشگاهِ سفارش: `payment` = مبلغ پرداختیِ مشتری برای آن فروشگاه (همان `ProductOrderStore.PaymentPrice` فعلی، یعنی بعد از هر دو تخفیف و با هزینه‌ی ارسال)، `F` = جمع «تخفیفِ سهم پاستیل» آیتم‌های باقی‌مانده، `c` = `Store.CommissionPercent`:

```
سهم فروشگاه (StoreShare) = (payment + F) × (۱ − c٪)
سهم پاستیل  (SiteShare)  = payment − StoreShare = c٪ × (payment + F) − F
```

- بدون تخفیف پاستیل (`F=0`) **دقیقاً همان فرمول قبلی** است (`StoreShare = payment×(۱−c)`).
- چون تخفیف پاستیل روی قیمتِ بعد از تخفیف فروشگاه اعمال می‌شود و ≤ کمیسیون است، `SiteShare` **هیچ‌وقت منفی نمی‌شود**.
- اگر پاستیل دقیقاً برابر کمیسیون تخفیف بدهد (مثلاً کمیسیون ۸٪، تخفیف پاستیل ۸٪)، `SiteShare = ۰` و فروشگاه همان مبلغی را می‌گیرد که بدون تخفیف پاستیل می‌گرفت («به‌جای کمیسیون تخفیف»).

**مثال:** پایه ۱٬۰۰۰٬۰۰۰ | فروشگاه ۱۵٪ | پاستیل ۸٪ | کمیسیون ۸٪

| | مبلغ |
| --- | --- |
| بعد از تخفیف فروشگاه | ۸۵۰٬۰۰۰ |
| تخفیف پاستیل (۸٪ از ۸۵۰٬۰۰۰) = `F` | ۶۸٬۰۰۰ |
| مشتری می‌دهد | ۷۸۲٬۰۰۰ |
| سهم فروشگاه = (۷۸۲٬۰۰۰ + ۶۸٬۰۰۰) × ۹۲٪ | ۷۸۲٬۰۰۰ |
| سهم پاستیل | **۰** (۶۸٬۰۰۰ کمیسیونش را به مشتری داده) |

با پاستیل ۴٪: مشتری ۸۱۶٬۰۰۰؛ `F=۳۴٬۰۰۰`؛ فروشگاه ۷۸۲٬۰۰۰؛ پاستیل ۳۴٬۰۰۰.

### فیلدهای حسابداری جدید (برای گزارش‌ها)
| محل | فیلد | معنی |
| --- | --- | --- |
| `ProductOrders` | `PastilFundedAmount` | جمع هزینه‌ی تخفیف پاستیل در سفارش (`F` همه‌ی فروشگاه‌ها)؛ کنار `StoreShare`/`SiteShare` |
| `ProductOrderItems` | `PastilDiscountUnit` | تخفیف پاستیلِ هر واحد، **هنگام ثبت سفارش snapshot** می‌شود (تغییر بعدی تخفیف‌ها سفارش‌های قدیمی را عوض نمی‌کند) |
| `ProductItems` | `PastilDiscountPercent`, `PastilDiscountAmount` | درصد/مبلغ (هر واحد) تخفیف پاستیلِ جاری |
| `Discounts` | `FundedByPastil` | ردیف تخفیفِ سهم پاستیل |

- حذف/کاهش تعداد آیتم توسط فروشنده/ادمین: سهم‌ها و `PastilFundedAmount` از روی آیتم‌های باقی‌مانده **دوباره حساب** می‌شود.
- مجموع «هزینه‌ی تخفیف پاستیل» در گزارش مالی فروشگاه: `FinanceStore` → `PastilFundedAmount` هر سفارش و `TotalPastilFundedAmount`. (`StoreShare + SiteShare` همیشه برابر `PaymentPrice` سفارش است.)

## ۳) قواعد اعتبارسنجی (بک)

- فقط ادمین (`Admin/Discount`) می‌تواند `fundedByPastil=true` بسازد/فعال/حذف کند. فروشنده (`Seller/Discount`) هرچه بفرستد، تخفیفِ **خودش** ثبت می‌شود و دست‌زدن به ردیف سهم‌پاستیل با خطای «تخفیفِ سهم پاستیل را فقط ادمین می‌تواند تغییر دهد» رد می‌شود.
- ساخت/فعال‌سازیِ تخفیف پاستیل با درصد بیشتر از کمیسیون فروشگاه: «درصد تخفیف پاستیل (۹٪) نمی‌تواند از سهم پاستیل این فروشگاه (۸٪) بیشتر باشد.» (کمیسیون صفر ⇒ تخفیف پاستیل ممکن نیست.)
- **کاهش کمیسیون فروشگاه** (`Admin/FinanceStore` → `UpdateStoreCommission`) وقتی تخفیف فعالِ پاستیلِ بیشتر از مقدار جدید دارد رد می‌شود: «سهم پاستیل نمی‌تواند از تخفیف فعالِ پاستیل … کمتر شود؛ ابتدا آن تخفیف را کاهش یا غیرفعال کنید.»
- تخفیف خودِ فروشگاه هیچ سقفی ندارد (جز ۱ تا ۹۹ مثل قبل).

## ۵) SQL (کاربر اجرا کند)

`backend/scripts/PastilFundedDiscount.sql` (چندبار اجرا امن، transaction، قفل ۱۵ ثانیه): ۵ ستون جدید + **بازنویسی procedure `UpdateProductItemDiscount`** (`CREATE OR ALTER`) + ثبت migration. **بدون ردیفِ `FundedByPastil=1` قیمت‌ها و رفتار دقیقاً مثل قبل است** (روی LocalDB با ۱۰ سناریو تست شد). متن procedure قبلی انتهای اسکریپت (بخش بازگشت) هست. migration معادل: `20261113120000_PastilFundedDiscount` (procedure را هم می‌سازد؛ Down نسخه‌ی قبلی را برمی‌گرداند).

> **ترتیب مهم:** اگر Api جدید قبل از SQL بالا بیاید، خواندن `Discounts/ProductItems/ProductOrders` خطای ستون ناموجود می‌دهد.
> بعد از اجرای SQL، قیمتِ کالاهای موجود تا اولین ویرایش تخفیف/قیمت (که procedure را صدا می‌زند) همان است؛ نیازی به اجرای دستی نیست چون هیچ ردیف پاستیلی هنوز وجود ندارد.

- فرم «ثبت تخفیف»: سوئیچ **«تخفیف از سهم پاستیل»** + فیلد «شناسه‌ی فروشگاه» (وقتی روشن است). درصد را سرور با کمیسیون فروشگاه می‌سنجد و پیام فارسی برمی‌گرداند.
- ویرایش: نوار توضیح «این تخفیف از سهم پاستیل است…». لیست: نشان سبز **«سهم پاستیل»** کنار درصد.

## ۸) نکته‌ها و محدودیت‌ها

- تخفیف پاستیل و تخفیف فروشگاه روی یک کالا می‌توانند هم‌زمان بیش از یک ردیف داشته باشند؛ از هر لایه فقط بیشترین ردیف اعمال می‌شود. انقضا: وقتی هر دو لایه هست، تاریخ پایانِ **زودتر** ملاک است تا قیمت‌ها به‌موقع دوباره حساب شوند.
- تخفیف دیلی/گروه تخفیف (`DiscountGroup`): دست‌نخورده؛ همان دو لایه را می‌گیرند (گروهِ لایه‌ی فروشگاه اولویت دارد).
- فروشگاهِ بدون کمیسیون (۰٪) ⇒ تخفیف پاستیل برایش ساخته نمی‌شود.
- سفارش‌های قبلی (`PastilDiscountUnit=0`) و محاسباتی که قبلاً انجام شده تغییر نمی‌کنند.
- آمار «بیشترین تخفیف فروشگاه» (`MaxDiscountPercent`) شامل ردیف‌های سهم پاستیل هم می‌شود (برچسب «تا X٪ تخفیف» برای مشتری).
- **هزینه‌ی ارسال:** هیچ‌کدام از دو لایه‌ی تخفیف و `PastilFundedAmount` به ارسال دست نمی‌زنند (تست: `Delivery_never_enters_the_discount_math…`). فقط رفتار قدیمیِ کمیسیون روی `PaymentPrice` (که ارسال را هم دارد: ۹۲٪ فروشگاه/۸٪ پاستیل) دست‌نخورده مانده؛ اگر بخواهید ارسال کلاً از سهم‌ها جدا شود، باید تصمیم بگیرید پول ارسال برای هر نوع ارسال (پیک Miare / خود فروشگاه) به چه کسی برسد.
