# قیمت پکیج به‌ازای «نحوه ارائه» — مستند تیم اپ موبایل

> تاریخ: ۲۹ شهریور ۱۴۰۵ · مخاطب: توسعه‌دهنده‌ی اپ (Flutter) · وب‌اپ همین تغییر را پیاده کرده است

## ۱) خلاصه
هر **پکیج** یک خدمت (`CompanionAssistance`) حالا می‌تواند برای هر «نحوه ارائه» قیمت و بیعانه‌ی جدا داشته باشد:

| `companionAssistanceTypeId` | معنی |
| ---: | --- |
| `37` | آنلاین (چت / تماس داخل برنامه) |
| `38` | حضوری در مرکز (نماینده/کلینیک) |
| `39` | در محل مشتری (اعزام) |

- قبلاً حالت‌ها فقط روی **خدمت** انتخاب می‌شدند (`assistance.codes`) و هر پکیج یک `price` و یک `prePaymentPrice` برای همه‌ی حالت‌ها داشت.
- **حالا نماینده نحوه ارائه را هنگام تعریف «پکیج» انتخاب می‌کند، نه روی خدمت.** ساخت/ویرایش خدمت دیگر انتخاب حالت نمی‌خواهد؛ `companionAssistanceTypeIds` در `POST/PUT` خدمت **اختیاری** است (خالی ⇒ در ویرایش حالت‌های فعلی دست‌نخورده می‌ماند؛ در ساخت خدمت خالی می‌ماند).
- `codes` خدمت (`assistance.codes`، فیلتر `Type` در جست‌وجوی خدمات و اعتبارسنجی رزرو) را **سرور خودش نگه می‌دارد**: اجتماع حالت‌های پکیج‌های **فعال** آن خدمت. هر بار پکیجی ثبت/ویرایش/فعال/غیرفعال/حذف شود همگام می‌شود.
- حالا هر پکیج یک آرایه‌ی `types` دارد: `[{ companionAssistanceTypeId, price, prePaymentPrice }]`.
- **سازگاری با قبل:** پکیجی که `types` ندارد (پکیج‌های قدیمی) همه‌ی حالت‌های خدمت را با `price/prePaymentPrice` خودش ارائه می‌دهد و هیچ رفتاری برایش عوض نشده.

## ۲) شکل داده (پاسخ‌های خواندن پکیج)
`GET /api/EndUser/CompanionAssistancePackage`، `GET /api/Companion/CompanionAssistancePackage` و `GET .../{id}` حالا این فیلد را دارند (در پکیج‌های تو در توی **جزئیات رزرو** `types` پر نمی‌شود؛ قیمت رزرو را از `packagePrice/prePaymentPrice` خودِ رزرو بخوانید):

```json
{
  "id": 731,
  "name": "ویزیت و معاینه",
  "price": 120000,
  "prePaymentPrice": 120000,
  "petSize": null,
  "active": true,
  "types": [
    { "id": 9001, "companionAssistanceTypeId": 37, "companionAssistanceTypeName": "آنلاین",  "price": 120000, "prePaymentPrice": 120000 },
    { "id": 9002, "companionAssistanceTypeId": 38, "companionAssistanceTypeName": "در مرکز",  "price": 200000, "prePaymentPrice": 40000 },
    { "id": 9003, "companionAssistanceTypeId": 39, "companionAssistanceTypeName": "در محل",   "price": 350000, "prePaymentPrice": 70000 }
  ]
}
```

- `price` / `prePaymentPrice` سطح بالا وقتی `types` وجود دارد = مقدار **ارزان‌ترین حالت** است (برای «قیمت از …» و مرتب‌سازی). قیمت واقعی هر حالت فقط در `types` است.
- پکیج قدیمی: `types` خالی یا `null` است.

## ۳) قاعده‌ی محاسبه‌ی قیمت در اپ (همان چیزی که سرور اعمال می‌کند)
```dart
// mode = companionAssistanceTypeId انتخابی کاربر (۳۷/۳۸/۳۹)؛ اگر هنوز انتخاب نشده mode == null
Quote resolve(Package p, int? mode) {
  if (p.types.isEmpty || mode == null) {
    return Quote(offered: true, price: p.price, pre: p.prePaymentPrice);   // پکیج قدیمی یا قبل از انتخاب حالت
  }
  final row = p.types.firstWhereOrNull((t) => t.companionAssistanceTypeId == mode);
  if (row == null) return Quote(offered: false);                            // این پکیج در این حالت ارائه نمی‌شود
  return Quote(offered: true, price: row.price, pre: row.prePaymentPrice);
}
```
- مبلغ قابل پرداخت هر پکیج = `pre > 0 ? pre : price` (همان منطق قبلی وب‌اپ)، ضرب در **تعداد پت‌های رزرو**.
- در لیست پکیج‌های صفحه‌ی رزرو، پکیجی که `offered == false` است را **پنهان** کنید.
- وقتی کاربر «نحوه ارائه» را عوض می‌کند: قیمت پکیج‌های انتخاب‌شده را دوباره حساب کنید و پکیجی را که در حالت جدید ارائه نمی‌شود از انتخاب/سبد **حذف** کنید.
- قیمت نهایی را همیشه از پاسخ رزرو (`packagePrice`، `prePaymentPrice`، `paymentPrice`) بخوانید؛ محاسبه‌ی اپ فقط برای نمایش پیش از ثبت است.

## ۴) رزرو (کاربر)
`POST /api/EndUser/CompanionReserve` و سبد گروهی `POST /api/EndUser/CompanionReserveBatch` (فیلدها بدون تغییر):
`companionAssistanceId`، `companionAssistanceTypeId`، `companionAssistancePackagesIds[]`، `userPetIds[]`، `companionAssistancePackageOnlineSelectionId` (اختیاری، فقط آنلاین) و ...

سرور:
1. `companionAssistanceTypeId` باید جزو حالت‌های **خدمت** باشد.
2. برای هر پکیج انتخابی قیمت را از ردیف همان حالت می‌خواند:
   `packagePrice = Σ price(حالت) × تعداد پت`، `prePaymentPrice = Σ prePaymentPrice(حالت) × تعداد پت`، `paymentPrice = prePaymentPrice`.
3. اگر پکیج `types` دارد ولی ردیفی برای حالت انتخابی ندارد ⇒ رزرو رد می‌شود: `isSuccess=false` با پیام «نوع ارائه انتخاب‌شده متعلق به این خدمت نیست.»
4. تغییر تعداد پت در رزرو (`PUT`) قیمت را با همان حالتِ ثبت‌شده‌ی رزرو دوباره حساب می‌کند.

### قیمت روش آنلاین (`CompanionAssistancePackageOnlineSelection`)
- پکیج **جدید** (دارای `types`): `selection.price` **دیگر به قیمت اضافه نمی‌شود**؛ قیمت آنلاین همان قیمت حالت `37` پکیج است. `selection.price` را به کاربر به‌صورت «مبلغ اضافه» نشان ندهید (برای پکیج‌های جدید `0` است).
- پکیج **قدیمی** (بدون `types`): مثل قبل `selection.price` روی قیمت پکیج جمع می‌شود.

## ۵) نماینده: ثبت و ویرایش پکیج
`POST /api/Companion/CompanionAssistancePackage` (جدید) و `PUT` (ویرایش):

```json
{
  "id": 0,
  "companionAssistanceId": 512,
  "name": "ویزیت و معاینه",
  "discription": "توضیح پکیج",
  "petSize": null,
  "pictureId": null,
  "types": [
    { "companionAssistanceTypeId": 38, "price": 200000, "prePaymentPrice": 40000 },
    { "companionAssistanceTypeId": 39, "price": 350000, "prePaymentPrice": 70000 },
    { "companionAssistanceTypeId": 37, "price": 120000, "prePaymentPrice": 120000 }
  ]
}
```

- `types` **غیرخالی** در `PUT` ⇒ کل فهرست حالت‌های پکیج **جایگزین** می‌شود (همه‌ی حالت‌های فعال را بفرستید؛ حالتِ نفرستاده حذف می‌شود).
- `types` خالی/`null` ⇒ «بدون تغییر». اپ قدیمی که فقط `price/prePaymentPrice` می‌فرستد مثل قبل کار می‌کند.
- وقتی `types` می‌فرستید، `price/prePaymentPrice` سطح بالا نادیده گرفته و از ارزان‌ترین حالت ساخته می‌شود.
- فرم پیشنهادی: همیشه **هر سه حالت** (۳۷ آنلاین، ۳۸ در مرکز، ۳۹ در محل) را به‌صورت کارت با تیک + «قیمت نهایی» + «بیعانه» نشان دهید؛ حداقل یک حالت باید فعال باشد. برای پکیج جدید هیچ حالتی از قبل تیک ندارد. پکیج قدیمی (بدون `types`) هنگام ویرایش: حالت‌هایی که خدمت از قبل داشت تیک می‌خورند و قیمت قدیمی پکیج در آن‌ها پر می‌شود تا نماینده فقط اصلاح کند.
- در فرم ساخت/ویرایش **خدمت** انتخاب نحوه ارائه را حذف کنید (یا اگر نگه می‌دارید، الزامی نباشد). در `PUT` خدمت `companionAssistanceTypeIds: []` بفرستید تا حالت‌های فعلی دست نخورد.
- هر ثبت/ویرایش پکیج `active=false` می‌شود و **دوباره تأیید ادمین** می‌خواهد (مثل قبل).

### اعتبارسنجی سرور (پیام `isSuccess=false` / «داده نامعتبر» یا «مقدار تکراری»)
| قاعده | نتیجه |
| --- | --- |
| هر `companionAssistanceTypeId` یکی از `37/38/39` باشد و در `types` تکراری نباشد (دیگر لازم نیست قبلاً روی خدمت انتخاب شده باشد) | وگرنه «داده نامعتبر» |
| `price > 0` و `0 ≤ prePaymentPrice ≤ price` (برای هر حالت) | وگرنه «داده نامعتبر» |
| مسیر قدیمی (بدون `types`): `price ≥ 0` و `0 ≤ prePaymentPrice ≤ price` | وگرنه «داده نامعتبر» (قبلاً هیچ کنترلی نبود) |
| تکراری‌بودن = **هم‌نام + هم‌سایز پت** در همان خدمت | «مقدار تکراری» (قبلاً هر پکیج هم‌قیمت رد می‌شد؛ حالا دو پکیج هم‌قیمت مجاز است) |

- چون حالت‌ها روی پکیج‌اند، اضافه‌کردن یک حالت جدید = ویرایش همان پکیج و تیک زدن آن حالت (بعد از تأیید ادمین، حالت به `codes` خدمت اضافه می‌شود).
- توجه: `codes` خدمت فقط از پکیج‌های **فعال** ساخته می‌شود. تا وقتی پکیجِ تازه‌ثبت‌شده/ویرایش‌شده توسط ادمین تأیید نشده، حالتش در `codes` خدمت (و در فیلتر «نحوه ارائه») ظاهر نمی‌شود؛ رزرو هم بدون پکیج فعال ممکن نیست.

## ۶) نکات سازگاری برای اپ
- فیلد جدید فقط **افزودنی** است؛ نسخه‌های قدیمی اپ خراب نمی‌شوند (`types` را نادیده می‌گیرند و قیمت پایه را می‌بینند)، اما در پکیج‌های جدید قیمت پایه = ارزان‌ترین حالت است؛ برای نمایش درست حالت‌محور باید اپ به‌روز شود.
- در جست‌وجوی سراسری (`SearchCompanionAssistancePackageDto`) فقط `price/prePaymentPrice` پایه برمی‌گردد (= «از …»).
- پنل ادمین/وب‌اپ همین قرارداد را استفاده می‌کنند.

## ۷) چک‌لیست تست اپ
0. ساخت خدمت **بدون** انتخاب نحوه ارائه ← موفق؛ سپس ثبت پکیج با حالت‌ها ← پس از تأیید ادمین `codes` خدمت شامل همان حالت‌ها می‌شود.
1. ثبت پکیج با سه حالت و قیمت‌های متفاوت ← در پاسخ `types` سه ردیف و `price` = ارزان‌ترین.
2. ویرایش و حذف یک حالت (`PUT` با دو ردیف) ← ردیف حذف‌شده دیگر در `types` نیست.
3. رزرو در هر سه حالت ← `packagePrice/prePaymentPrice` با ردیف همان حالت برابر (× تعداد پت).
4. رزرو با پکیجی که حالت انتخابی را ندارد ← خطا و پنهان‌بودن پکیج در لیست.
5. عوض‌کردن حالت وسط رزرو/سبد ← قیمت دوباره حساب می‌شود و پکیج نامربوط حذف می‌شود.
6. پکیج قدیمی (بدون `types`) ← قیمت همان قبلی در هر سه حالت؛ روش آنلاین هنوز «مبلغ اضافه» دارد.
7. ثبت دو پکیج هم‌قیمت با نام متفاوت ← موفق؛ هم‌نام و هم‌سایز ← «مقدار تکراری».
8. قیمت منفی یا بیعانه بیشتر از قیمت ← «داده نامعتبر».

## ۸) استقرار (برای هماهنگی)
- مایگریشن `AddCompanionPackageTypes` (جدول `CompanionAssistancePackageTypes`) روی دیتابیس اعمال شده است؛ Api جدید باید deploy شود تا فیلد `types` در پاسخ‌ها ظاهر شود.
- تا Api جدید deploy نشود، `types` در پاسخ نیست؛ اپ باید در این حالت مثل پکیج قدیمی رفتار کند (`types` نبود ⇒ قیمت پایه).
