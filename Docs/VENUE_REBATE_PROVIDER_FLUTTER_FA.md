# راهنمای Flutter اپ نماینده: کد تخفیف پنج مرکز

تاریخ: ۱۴۰۵/۰۸/۲۷ (۲۰۲۶-۱۱-۱۸)  
پروژهٔ اپ: `provider_panel`  
مبنای این سند: `Api/Areas/Companion/Controllers/RebateController.cs` و `Application/Services/Order/RebateSrv/RebateService.cs`.

## رفتار مورد انتظار

مالک مربی، کلینیک، آرایشگاه، پانسیون یا مدرسه بتواند برای **همان مرکز** کد تخفیف بسازد، کدهای آن را ببیند، فعال/غیرفعال یا حذف کند. کد روی رزرو خدمات همان مرکز اعمال می‌شود و برای مرکز دیگر معتبر نیست. کد ساخته‌شده از API نماینده همیشه با نسبت تأمین تخفیف **۰٪ پاستیل / ۱۰۰٪ مرکز** است؛ اپ امکان تعیین این نسبت ندارد. حذف کد نرم است و کد حذف‌شده دیگر در فهرست یا خریدهای آینده قابل استفاده نیست.

**وضعیت تحویل:** در مخزن `provider_panel` برای این قابلیت تغییری اعمال نشده است. تیم Flutter باید صفحه و Repository مدیریت کد را پیاده کند و ورودی آن را در بخش هر پنج مرکز قرار دهد. این سند قرارداد دقیقِ سمت سرور و رفتار مورد انتظار اپ است.

## شناسه و نوع مرکز

| مرکز | `targetType` در URL | `targetId` |
| --- | --- | --- |
| مربی | `Coach` | شناسهٔ مربی (`CoachProfile.id`) |
| کلینیک | `Clinic` | شناسهٔ کلینیک |
| آرایشگاه | `Groomer` | شناسهٔ آرایشگاه |
| پانسیون | `Pansion` | شناسهٔ پانسیون |
| مدرسه | `School` | شناسهٔ مدرسه، **نه شناسهٔ دوره** |

نوع را دقیقاً با همین املای انگلیسی در مسیر بفرستید. مرکز را از دادهٔ حساب فعلی اپ انتخاب کنید؛ به شناسهٔ دستکاری‌شدهٔ کلاینت برای مجوز تکیه نکنید. سرور مالکیت را از توکن کاربر دوباره بررسی می‌کند. ساخت، فعال/غیرفعال‌سازی و حذف برای مرکز فعال و تأییدشده مجاز است؛ فهرست کدهای مرکزِ تحت مالکیت برای مرکز هنوز تأییدنشده نیز قابل خواندن است. مالکیت مربی/کلینیک/آرایشگاه با `OwnerId` و پانسیون/مدرسه با سرویس مالکیت همان مرکز بررسی می‌شود.

## ارتباط با API

همهٔ مسیرها زیر `https://api.pastil.pet` و نیازمند توکن همان حساب نماینده‌اند. از `DioClient.instance.dio` موجود استفاده کنید تا سرآیند احراز هویت و مدیریت خطای مشترک اپ اعمال شود.

| کار | درخواست | ورودی |
| --- | --- | --- |
| فهرست | `GET /api/Companion/Rebate/{targetType}/{targetId}` | `pageIndex`، `pageSize`؛ اختیاری `q` |
| ساخت | `POST /api/Companion/Rebate/{targetType}/{targetId}` | JSON جدول پایین |
| فعال/غیرفعال | `PUT /api/Companion/Rebate/{targetType}/{targetId}/{rebateId}/Active?active=true\|false` | بدنه لازم نیست |
| حذف نرم | `DELETE /api/Companion/Rebate/{targetType}/{targetId}/{rebateId}` | بدنه لازم نیست |

`GET` یک شیء صفحه‌بندی‌شده برمی‌گرداند، نه آرایهٔ مستقیم:

```json
{
  "pageIndex": 1,
  "pageSize": 20,
  "totalCount": 1,
  "list": [{
    "id": 123,
    "name": "تخفیف پاییز",
    "codeValue": "autumn10",
    "priceValue": 10,
    "isPriceRebate": false,
    "minCartPrice": 0,
    "startDatetime": "2026-11-18T00:00:00",
    "endDatetime": "2026-12-18T00:00:00",
    "active": true,
    "useCount": 100,
    "usedCount": 4,
    "maxUsePerUser": 1,
    "targetType": 12,
    "targetId": 45,
    "siteFundedPercent": 0,
    "providerFundedPercent": 100
  }]
}
```

مقادیر مثال فقط برای نشان‌دادن شکل پاسخ‌اند. در JSON، `targetType` معمولاً مقدار عددی enum است؛ برای نمایش نوع مرکز به رشتهٔ مسیری که صفحه را با آن باز کرده‌اید تکیه کنید. برای فهرست بیش از ۱۰۰ کد، صفحه‌ها را بر اساس `totalCount` بارگذاری کنید و فهرست را به صفحهٔ اول محدود نکنید.

### بدنهٔ ساخت

```json
{
  "name": "تخفیف پاییز",
  "codeValue": "autumn10",
  "priceValue": 10,
  "isPriceRebate": false,
  "minCartPrice": 0,
  "useCount": 100,
  "maxUsePerUser": 1,
  "startDatetime": "2026-11-18T00:00:00",
  "endDatetime": "2026-12-18T00:00:00",
  "active": true
}
```

| فیلد | قاعده |
| --- | --- |
| `name` | عنوان غیرخالی برای نمایش به نماینده |
| `codeValue` | کد یکتا در کل سامانه؛ سرور فاصله‌ها را حذف، حروف را کوچک و تکراری‌بودن را کنترل می‌کند |
| `isPriceRebate` | `false`: درصدی؛ `true`: مبلغ ثابت |
| `priceValue` | برای درصدی عدد ۱ تا ۹۹؛ برای مبلغ ثابت عدد مثبت، با واحد **تومان** |
| `minCartPrice` | حداقل مبلغ رزرو، تومان؛ برای مبلغ ثابت باید دست‌کم `priceValue + 1000` باشد |
| `useCount` | سقف کل استفاده، حداقل ۱ |
| `maxUsePerUser` | سقف استفادهٔ هر مشتری، از ۱ تا `useCount` |
| `startDatetime` / `endDatetime` | تاریخ میلادی ISO؛ شروع زودتر از تاریخ امروز سرور نباشد و پایان قبل از شروع نباشد. سرور بخش ساعت را به ابتدای روز تبدیل می‌کند |
| `active` | برای کد قابل استفاده `true` |

`typeId`، `targetType`، `targetId`، `productId`، `clubRewardId` و `id` را در بدنه نفرستید: سرور نوع کد و مرکز را از مسیر تعیین می‌کند. `userId` در API نماینده عمداً خالی می‌شود، پس کد نماینده برای همهٔ مشتریان واجد شرایط همان مرکز است.

`siteFundedPercent` و `providerFundedPercent` را نیز در درخواست نماینده نفرستید. سرور هر دو را به‌ترتیب روی `0` و `100` می‌گذارد، حتی اگر کلاینت مقدار دیگری بفرستد. این دو عدد، نسبت تأمین **مبلغ تخفیف** هستند و با درصد کمیسیون پاستیل در رزرو تفاوت دارند. کدهای قدیمی ممکن است در پاسخ فهرست برای هر دو فیلد `null` داشته باشند؛ نسبت مؤثر آن‌ها هم `0/100` است.

اگر کدی توسط ادمین با سهم پاستیل بیشتر از صفر ساخته شده باشد، نماینده می‌تواند آن را در فهرست مرکز ببیند ولی API نماینده تغییر وضعیت یا حذف آن را با ۴۰۴ رد می‌کند. برای این ردیف‌ها کنترل تغییر وضعیت/حذف را در اپ غیرفعال یا پنهان کنید.

در پاسخ ساخت و تغییر وضعیت/حذف، HTTP 200 به‌تنهایی نشانهٔ موفقیت نیست؛ `isSuccess` را بررسی کنید. خطای اعتبارسنجی معمولاً HTTP 200 با `isSuccess: false` و `messages` است. مالک نبودن یا تعلق نداشتن کد به مرکز HTTP 404، و نبود احراز هویت HTTP 401 می‌دهد. پیام خطای سرور را با `ApiFailure.fromResponse` / `ApiFailure.fromDio` به کاربر نشان دهید. پس از عملیات موفق، فهرست را دوباره از سرور بگیرید.

## حسابداری و کاربرد کد

فقط کدی که `TargetType` آن یکی از پنج مرکز و `TargetId` آن برابر مرکز رزرو باشد، از سهم همان مرکز تأمین می‌شود؛ مگر کدی که ادمین با نسبت دیگری ساخته باشد. در زمان **پرداخت موفق**، سهم‌ها در خود رزرو ذخیره می‌شوند و گزارش مالی/تسویه از آن‌ها استفاده می‌کند. اپ نماینده نباید سهم‌ها را مستقلاً دوباره محاسبه یا به سرور ارسال کند.

```text
G = مبلغ اصلی رزرو
D = مبلغ تخفیف اعمال‌شده
C = کمیسیون پاستیل از G (برای رزرو چندخدمتی، جمع کمیسیون هر خدمت)
پرداخت مشتری = G - D
سهم پاستیل = C
سهم مرکز = G - C - D
```

مثال کد نماینده: رزرو ۱٬۰۰۰٬۰۰۰ تومان، کمیسیون ۲۰٪ و کد ۱۰۰٬۰۰۰ تومانی: پرداخت مشتری ۹۰۰٬۰۰۰، سهم پاستیل ۲۰۰٬۰۰۰ و سهم مرکز ۷۰۰٬۰۰۰ تومان است. اگر `D > G - C` باشد، سرور هنگام اعمال کد آن را رد می‌کند تا سهم مرکز منفی نشود. بنابراین ممکن است کد درصدی بسیار بزرگ برای بعضی خدمات ساخته شود، ولی روی رزروی که سهم مرکز آن کافی نیست قابل اعمال نباشد؛ این محدودیت را در توضیح فرم به نماینده نشان دهید. کد عمومی و کدهای باشگاه از قواعد حسابداری قبلی پیروی می‌کنند. کد ساخته‌شده توسط ادمین می‌تواند نسبت دیگری داشته باشد؛ جزئیات فرمول در `VENUE_FUNDED_REBATES_FA.md` است.

## رفتار صفحهٔ Flutter

1. عنوان صفحه نام همان مرکز باشد. بارگذاری، حالت خالی، خطای اتصال و تلاش دوباره را جدا نشان دهید.
2. فرم ساخت شامل عنوان، کد یا تولید کد، نوع تخفیف، مقدار، حداقل رزرو، سقف کل/هر کاربر، تاریخ شروع/پایان باشد. در فرم روشن بنویسید «تخفیف از سهم همین مرکز کم می‌شود». مقدار مبلغی و حداقل رزرو به تومان هستند.
3. در هر ردیف، عنوان، کد قابل کپی، درصد یا مبلغ، تعداد استفاده، وضعیت فعال، تاریخ اعتبار و نسبت مؤثر تأمین تخفیف نمایش داده شود. برای دو فیلد `null` نسبت ۰٪ پاستیل / ۱۰۰٪ مرکز نشان دهید. تغییر وضعیت و حذف با همان `targetType` و `targetId` صفحه انجام شود؛ پیش از حذف تأیید کاربر گرفته شود.
4. دکمهٔ ثبت و عملیات هر ردیف هنگام درخواست تکراری غیرفعال شود. پس از موفقیت فهرست تازه شود. خطاهای اعتبارسنجی و ۴۰۴ را با متن قابل فهم نشان دهید.
5. برای فهرست‌های بزرگ صفحه‌بندی اضافه کنید؛ وضعیت «فعال» به‌تنهایی به معنی معتبر بودن امروز نیست و تاریخ، سقف استفاده و حداقل رزرو هم هنگام استفاده توسط سرور بررسی می‌شوند.

## چک‌لیست تحویل اپ‌نویس

- ورود به صفحهٔ کدها از هر پنج نوع مرکز با شناسهٔ درست؛ مدرسه با `school.id`، نه `course.id`.
- ساخت کد درصدی و مبلغ ثابت با تاریخ و محدودیت استفادهٔ معتبر؛ نمایش پیام کد تکراری یا فرم نامعتبر.
- فهرست، بارگذاری صفحه‌های بعدی، فعال/غیرفعال، حذف با تأیید و تازه‌سازی پس از هر عملیات.
- جلوگیری از عملیات تکراری در زمان انتظار؛ نمایش خطای ۴۰۱، ۴۰۴، قطع اتصال و `isSuccess: false`.
- نمایش توضیح هزینهٔ تخفیف برای نماینده؛ عدم محاسبهٔ تسویه در کلاینت.
- بررسی دستی اینکه کد مرکز A روی رزرو مرکز B رد می‌شود و کد ساخته‌شده از اپ، سهم پاستیل را کم نمی‌کند.

طبق دستور پروژه برای این تغییر بیلد و دیتابیس لوکال انجام نشده است. این API و کد فعلی باید پس از استقرار با حساب‌های واقعی مالک هر سه مرکز بررسی شوند.
