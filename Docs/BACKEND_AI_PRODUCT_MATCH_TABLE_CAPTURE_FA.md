# تحلیل تصویری جدول نرم‌افزار انبار (سپیدار/دامپزشکیار) — پاسخ بک‌اند به `BACKEND_WINDOW_CAPTURE_SPEC.md`

این سند برای تیم **Pastil Bridge** (پنل ویندوز) است. بک‌اند دقیقاً طبق مستندی که فرستادید پیاده و در همین
مخزن (`Pastil-core`) commit شده. این سند خلاصه‌ی چیزی‌ست که باید سمت Bridge پیاده/چک بشه؛ هرجا چیزی با
مستند اصلی‌تون فرق داره یا هنوز تصمیم من است نه توافق مشترک، صریح علامت زده شده.

Endpoint دست‌نخورده مونده، فقط ورودی جدید قبول می‌کنه:

```http
POST /api/Seller/AiProductMatch/analyze
Authorization: Bearer {accessToken}
Content-Type: multipart/form-data
```

---

## ۱. چه چیزی عوض شده در ورودی

`sourceType=veterinary` و `sourceType=sepidar` از این به بعد **دو حالت** دارن:

| فیلد | حالت متنی (قبلی، بدون تغییر) | حالت جدید (اسکرین‌شات) |
|---|---|---|
| `sourceType` | `veterinary` یا `sepidar` | همون |
| `rowsJson` | پر | **خالی** |
| `images` | خالی | پر — تا ۴۰ فایل PNG، با همون الگوی تکرار فیلد `images` که برای `shelf` هست |
| `currency` | اختیاری، `IRT` | همون |

⚠️ **باید دقیقاً یکی از `rowsJson` یا `images` پر باشد، نه هر دو.** اگه هر دو با هم پر بفرستید، بک‌اند رد
می‌کنه (`isSuccess:false`, `code:1`) — این یک قانون جدیده، قبلاً چون `images` اصلاً برای این دو `sourceType`
معنی نداشت این تداخل ممکن نبود.

### محدودیت‌ها

- تعداد: حداکثر **۴۰ تصویر** (نه ۸ مثل `shelf`).
- حجم هر تصویر: همون سقف قبلی (**۸ مگابایت**) — برای اسکرین‌شات یک پنجره خیلی زیاده، جای نگرانی نیست.
- حجم کل درخواست: سقف سرور از ۶۴ به **۱۲۸ مگابایت** بالا رفت تا ۴۰ فایل جا بشه.
  ⚠️ اگه بین اپ و سرور یک reverse proxy/CDN باشه (که معمولاً هست)، سقف اون‌جا رو هم باید جدا چک کنید —
  من فقط سمت کد ASP.NET Core رو می‌بینم، نه لایه‌ی جلوترش.

## ۲. پاسخ — همون Contract قبلی، بدون تغییر شکل

هیچ فیلدی توی `items[]` اضافه/حذف/rename نشده (همون‌طور که در سند شما هم خواسته شده بود). فقط رفتار
چند فیلد برای این حالت فرق داره:

```json
{
  "isSuccess": true,
  "code": 0,
  "messages": [],
  "data": {
    "items": [
      {
        "rowId": "table-1-3",
        "detectedName": "کنسرو گربه شایر مرغ و بوقلمون 400 گرم",
        "externalCode": "SPD-7788",
        "price": 1950000,
        "quantity": 12,
        "productId": 4821,
        "productItemId": null,
        "productName": "کنسرو گربه شایر مرغ و بوقلمون",
        "confidence": 0.91,
        "sourcePictureId": null,
        "issues": [],
        "matches": [ ... همون ساختار قبلی ... ]
      }
    ]
  }
}
```

نکات مخصوص همین حالت:

- **`price`/`quantity` واقعی برمی‌گردن، نه `null`** — این دقیقاً همون چیزیه که خواسته بودید (بر خلاف
  `shelf` که همیشه `null`ان). اگه سلولی ناخوانا/بریده/دو-عددی بود، همون فیلد `null` می‌مونه و یک `issue`
  متنی به همون ردیف اضافه می‌شه (مثلاً «قیمت این ردیف واضح نبود») — نه یک عدد حدسی.
- **`price` همیشه قیمت فروش است، نه خرید** — اگه جدول دو ستون قیمت داشته باشه، مدل صراحتاً به انتخاب
  ستون «فروش» دستور داده شده؛ اگه نتونه تشخیص بده کدوم ستونه، `null` می‌مونه (باز هم حدس نمی‌زنه).
- **`externalCode`** از روی ستون کد/بارکد جدول (اگه بود) پر می‌شه — دقیقاً مثل `rowsJson`، فقط جهت
  نمایش، کلید تطبیق کاتالوگ نیست.
- **`rowId` با پیشوند `table-` می‌آد** (مثل `table-2-5`)، نه `shelf-`/`row-`. این فقط داخلی‌ست، هیچ
  معنایی براش نذارید جز اینکه در همین پاسخ منحصربه‌فرده — دقیقاً مثل قبل.
- ⚠️ **`sourcePictureId` برای این حالت همیشه `null` است**، حتی وقتی عکس واقعاً آپلود و ذخیره شده. چون
  چند اسکرین‌شات با هم در یک فراخوانی مدل پردازش می‌شن (بخش ۴)، نمی‌شه با قطعیت گفت هر ردیف از کدوم
  عکس اومده. اگه این برای بازبینی بعدی لازمتون بود بگید، باید طراحی جداگانه بشه.
- **ادغام ردیف‌های هم‌پوشان بین اسکرین‌شات‌های پشت‌سرهم** (که با اسکرول گرفته می‌شن) خودکار انجام
  می‌شه — اول بر اساس `externalCode` دقیقاً یکسان، بعد نام نرمال‌شده. یعنی تعداد `items[]` ممکنه از
  تعداد ردیف‌های واقعی جدول کمتر باشه اگه صفحات هم‌پوشانی داشتن؛ طبیعیه.

کدهای خطا (`code`) همون جدول `FLUTTER_AI_PRODUCT_MATCH_INTEGRATION_FA.md` بخش ۲.۳ هست، با یک اصلاح:
اگه استخراج از **همهٔ** اسکرین‌شات‌ها به‌خاطر خطای Provider/تمام‌شدن بودجهٔ زمانی شکست بخوره، حالا `code:5`
برمی‌گرده (قبلاً اشتباهاً `code:3` بود؛ همون چیزی که در تست واقعی دیدید). `code:3` فقط وقتیه که مدل تصویر
رو دیده و هیچ ردیفی پیدا نکرده. همچنین آیتم‌هایی که تطبیق کاتالوگشون کامل نشد `catalogMatchFailed:true` دارن.

## ۴. زمان پاسخ — به‌روزرسانی: حالا واقعاً async/Job شد

قبلاً اینجا نوشته بودم sync می‌مونه با batching. بعد از تست واقعی روی سرور شما، دیدیم حتی با batching
(۴ عکس در هر فراخوانی) بعضی وقت‌ها به سقف Timeout می‌خوریم — چون هر provider (خصوصاً وقتی شبکه/سرویس
کند باشه) می‌تونه چند ده ثانیه طول بکشه، و یک درخواست HTTP همزمان که تا انتها منتظر می‌مونه همیشه یک ریسک
واقعیه. **پس دو endpoint جدید اضافه شد** — دقیقاً همون راه‌حلی که این سند از اول به‌عنوان گزینه‌ی دوم مطرح
کرده بود.

⚠️ **`POST /analyze` قبلی هنوز دقیقاً همون‌طور که بود کار می‌کنه** — چیزی ازش برداشته نشده، اپ فلاتر
فروشنده (برای قفسه) هنوز داره همینو صدا می‌زنه و لازم نیست کاری باهاش بکنید. این دو endpoint جدید فقط
یک **مسیر جایگزین اختیاری** برای `veterinary`/`sepidar`+`images` هستن — پیشنهاد می‌کنم Bridge برای همین
حالت خاص (که طولانی می‌تونه بشه) بره سراغشون، نه برای `shelf`.

### ۴.۱ شروع تحلیل (بلافاصله برمی‌گرده)

```http
POST /api/Seller/AiProductMatch/analyze/start
Authorization: Bearer {accessToken}
Content-Type: multipart/form-data
```

دقیقاً همون فیلدهای `sourceType`/`images`/`rowsJson`/`currency` که `analyze` می‌گیره. پاسخ فوری:

```json
{ "isSuccess": true, "code": 0, "messages": [], "data": { "jobId": "3f9a1c...", "totalBatches": 10 } }
```

- `totalBatches`: تعداد دسته‌های ۴تایی که قراره پردازش بشه (برای عکس قفسه هم اگه از این مسیر استفاده کنید، برابر تعداد عکسه). این عدد رو برای مخرج progress bar استفاده کنید.
- خطاهای اعتبارسنجی (سایز/تعداد/سورس‌تایپ اشتباه، `code`های ۱/۶) همینجا هم فوری برمی‌گردن، دقیقاً مثل `analyze` قدیم — یعنی برای خطای ورودی نیازی به Polling نیست.

### ۴.۲ Polling وضعیت/پیشرفت

```http
GET /api/Seller/AiProductMatch/analyze/status/{jobId}
Authorization: Bearer {accessToken}
```

```json
{
  "isSuccess": true,
  "code": 0,
  "messages": [],
  "data": {
    "status": "processing",
    "totalBatches": 10,
    "completedBatches": 4,
    "result": null
  }
}
```

- `status`: `"processing"` | `"completed"` | `"failed"`.
- `completedBatches/totalBatches`: همون دو عددی که برای progress bar لازم دارید (مثلاً `4/10` → ۴۰٪).
- `result`: تا وقتی `status != "completed"` همیشه `null`ه. وقتی `"completed"` شد، **دقیقاً همون شکل `data` که `POST /analyze` برمی‌گردوند** اینجا میاد (`items[]` با همون فیلدها) — پارس نتیجه رو عوض نمی‌کنید، فقط از کجا می‌خونیدش عوض می‌شه.
- اگه `status == "failed"` بود، همون منطق کدهای خطای بخش ۲.۳ `FLUTTER_AI_PRODUCT_MATCH_INTEGRATION_FA.md` رو به کاربر نشون بدید.
- پیشنهاد: هر ۱.۵ تا ۲ ثانیه یک‌بار poll کنید، نه تندتر — این فقط یک شمارنده‌ی in-memory سبکه ولی دلیلی نداره فشار بی‌مورد بیاریم.

⚠️ **این Jobها فقط در حافظه‌ی سرور نگه داشته می‌شن، نه دیتابیس** — اگه سرور بین شروع و پایان یک Job ری‌استارت بشه (نادر، ولی ممکنه)، `jobId` دیگه پیدا نمی‌شه و `analyze/status` جواب می‌ده:
```json
{ "isSuccess": false, "code": 1, "messages": [...] , "data": null }
```
در این حالت باید فرض کنید Job از دست رفته و از کاربر بخواید دوباره شروع کنه (یا خودکار دوباره `analyze/start` بزنید). همچنین اگه یک Job بیش از ۱۵ دقیقه تموم نشه (خیلی بعیده)، از حافظه پاک می‌شه و همین وضعیت پیش میاد.

### پیشنهاد UI

1. کاربر عکس‌ها رو انتخاب می‌کنه → `POST /analyze/start` → `jobId`+`totalBatches` می‌گیرید.
2. یک progress bar نشون بدید که با `completedBatches/totalBatches` از هر poll آپدیت می‌شه (نه indeterminate spinner ساده — چون الان عدد واقعی دارید).
3. هر ۱.۵-۲ ثانیه `GET /analyze/status/{jobId}` بزنید تا `status == "completed"` یا `"failed"` بشه.
4. دیگه هیچ نگرانی Timeout سمت کلاینت نیست، چون هر درخواست (چه start چه هر poll) خودش خیلی سریع برمی‌گرده — فقط کل فرایند ممکنه چند ده ثانیه طول بکشه، نه یک درخواست HTTP.

## خلاصه‌ی کار برای Bridge

1. برای `veterinary`/`sepidar`: وقتی جدول متنی خوانده نشد، به‌جای/علاوه‌بر `rowsJson`، `images` بفرستید
   (تا ۴۰ فایل) — نه هر دو با هم.
2. برای همین حالت (تصویر جدول)، به‌جای `POST /analyze`، از `POST /analyze/start` + `GET /analyze/status/{jobId}` استفاده کنید (بخش ۴) — شکل `result` نهایی همون `AiProductMatchAnalyzeResultDto` قبلیه، فقط از جای دیگه‌ای می‌خونیدش.
3. یک progress bar واقعی (نه spinner) بر اساس `completedBatches/totalBatches` نشون بدید.
4. پارس نتیجه‌ی نهایی عوض نمی‌شه، فقط این‌بار `price`/`quantity` واقعی‌ان و `sourcePictureId` همیشه `null`ه.
5. مسیر `shelf` (قفسه) رو دست نزنید — همون `POST /analyze` سینک قبلی کافیه، چون تعدادش کمه (تا ۸ عکس) و معمولاً به مشکل Timeout نمی‌خوره.
